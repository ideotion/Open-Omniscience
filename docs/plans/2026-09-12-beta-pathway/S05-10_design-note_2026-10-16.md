# S05-10 — design note: what a source is keyed on, measured first (row J, S1)

Written 2026-10-16 before any schema line, as the brief's S1 asks. Every number below is from the
production seeder's own capture (`seed_default_sources`, `seed_sources` replaced by a recorder — never a
rebuild of its inputs), 6,670 entries, 6,195 distinct domains, **475 shadowed** (the ratchet's
`_BOOT_SHADOWED_ENTRIES_BUDGET`, so the capture is the same population). The script is
`scripts/measure_feed_key.py`.

## What the measurement found

| Question | Answer |
|---|---|
| Shadowed entries with a feed / without | 221 / 254 |
| Feeds carried by more than one **domain** (registered today as separate rows, 95 entries beyond the first) | 52 (smh.com.au + theherald.com.au, telex.hu + g7.hu, aljazeera.net + chinese.aljazeera.net) |
| Feed-less shadowed entries whose domain survivor HAS a feed | 235 of the 254 (210 are `sources_spectrum.yml`, the lean-tagged catalogue; 58 carry the survivor's own name) |
| `lean-*` tags on shadowed entries / of those on a feed-less sibling of a feed row | 192 / 186 |

Two consequences the ruling's sentence («key a source on its FEED») does not say:

1. **A unique key on the feed alone cannot be installed on a real store.** 52 feeds are already
   carried by several separate rows, one per domain. A `UNIQUE(rss_url)` would fail the migration, and "fixing" it by merging
   the pairs deletes rows an operator may have tags, qualification verdicts and articles on (R100: local data
   never gives way). **Decision: the key is COMPOSITE — normalised (domain, feed).** `domain` stays part of
   the identity; the feed is what is added.
2. **A feed-less entry is not a source, it is a description of one.** The 235 are the same outlet as the
   survivor, from a catalogue that carries a different tag set and no feed. Giving each its own row would put
   a second, uncollectable copy of Stuff, Malaysiakini and de Volkskrant in the sources list and double-count
   them everywhere a source is counted. **Decision: a feed-less entry whose domain has a feed row merges its
   TAGS into that row and creates none; it becomes a row (keyed on its domain alone) only when the domain has
   no feed row at all.** That recovers 186 of the 192 lean tags without a duplicate outlet.

## The key

`feed_key` = `f:` plus the feed URL normalised (scheme dropped, host lower-cased, a trailing slash on the path
dropped, fragment dropped, query kept — a query is part of what a feed is), or `''` for a source with no feed.
`UNIQUE (domain, feed_key)` replaces `UNIQUE (domain)` and the `idx_source_domain` unique index; a plain
index on `domain` stays (every domain lookup in the tree uses it). `rss_url` stays as the human-readable
value and is never the key itself.

## What it does to the catalogue

216 of the 475 shadowed entries become new rows (the language services), 235 merge their tags into the row
that already exists, 24 stay unregistered (same domain and same feed, or a feed-less duplicate of a
feed-less domain). **The shadow budget falls from 475 to 24.** Rows after a fresh seed: 6,411 (was 6,195
domain rows, plus the 216).

## The reaches (the data-safety review's checklist)

The brief names four; the sweep found more. Every one is a place that reads "a domain" as "a source":

- **Domain lookups returning ONE row** (`filter_by(domain=…).first()`, ~25 sites: `source_manager`,
  `ingestion`, `stats/ingest`, `series_corpus`, `wiki/corpus`, `law/corpus`, `hazards/ingest`, `pdf_import`,
  `import_job`, `csv_io`, `source_management`, `integrity/profile`, `qualification_integrity`, …). Once a
  domain can hold several rows, an unordered `.first()` is a coin toss — and with the composite index it is
  not even rowid order any more. **Decision: one helper, `source_for_domain`, ordered by `id`.** The row
  that exists today always has the lowest id, so every lookup keeps answering as it does now on an
  unmigrated store; a guard test finds an unconverted site.
- **Intentionally many** (`Source.domain.in_(…)`: newsletters, local-import domains, the overlay, wikipedia):
  these keep working and now correctly cover every feed of the domain.
- **The four named reaches:** the alias-aware dedup (`cited_sources`), the restore-merge joins (five
  `m.domain = i.domain`, plus the qualification-landed tallies), the overlay (`load_overlay`), the citations
  tally (`source_citation_tally`); plus `is_disqualified_domain`.
- **The restore** of an older backup: a domain-keyed `sources` member has no `feed_key`; the join becomes
  `(domain, feed_key)` with `feed_key` computed by the ONE normaliser registered as a SQLite function on the
  merge connection, never re-implemented in SQL. An old backup carrying two feeds of one domain yields two
  rows; a domain-keyed backup never duplicates an existing feed-keyed row.

## The three calls the brief says to ask about — RULED R145 (coordinator, 2026-10-16)

1. **No feed.** A feed-less source is keyed by its normalised domain alone (`feed_key = ''`); every feed key
   carries the prefix `f:`. The two namespaces cannot meet, whatever a feed URL looks like; pinned by
   `tests/test_feed_key.py::test_a_feed_key_and_a_domain_only_key_can_never_collide`.
2. **Qualification.** The migration itself changes no source's verdict. Every existing domain-level verdict
   (qualified or disqualified) is copied onto every sibling feed key, so a measured verdict never gives way
   (R100); from then on new overlay verdicts are feed-level. The hard disqualify list stays domain-level. The
   measured sibling counts go in the PR that registers siblings (J3).
3. **Backup format.** No bump. Both directions are safe: the restore-merge matches on `(domain, feed_key)` with
   the key recomputed from the incoming `rss_url`, so a domain-keyed member maps onto feed keys; and an older
   build given a feed-keyed backup refuses it with a named error, because the store is stamped at the revision
   that introduced the key and `prepare_staged_corpus` refuses a revision its build does not know («unknown to
   this build»). Pinned by `tests/test_source_composite_key.py::test_an_older_build_refuses_a_feed_keyed_backup_by_a_named_error`.
4. **Q301 = c.** R135's session-generated backup counts as the real restore for J, as for B.

Amendment on the tag merge (J3): a merged tag never overwrites a different existing value on the feed row; the row
keeps its value and the conflict is listed in the migration report with both sources, each conflict counted. The
24 entries that stay unregistered are named in the report with a reason each.

## Order of work

S2a the normaliser, the helper and the converted lookups (behaviour-identical on today's schema, so each
step is provable alone) → S2b the migration + the composite key, with before/after row counts and a
duplicate-key scan → S2c the seeder (the tag merge, the budget 475 → 23) → S3 the four reaches, one test and

## J3 as built (measured on the production capture, `scripts/measure_feed_key.py --list`)

`src/ingest/seed_plan.py::plan_registration` decides every entry's fate purely; the seeder carries it out.

| Fate | Count |
|---|---|
| rows (a fresh install registers) | 6,411 (was 6,195: the 216 language services and sibling feeds) |
| merged: a feed-less entry whose domain has a feed row, or the SAME feed named by a second catalogue | 240 (235 feed-less + 5 same-feed; the five are the spectrum catalogue's CNN, The Atlantic, CBC, Tagesschau and Dawn) |

**Deviation from R145's wording, flagged for the coordinator:** R145 left the five same-feed entries unregistered (24).
They are the spectrum catalogue describing a source the curated catalogue already registers, and dropping them loses
`lean-center-left` on CNN -- the named example of what the shadowing cost. They merge their tags like a feed-less entry;
the unregistered count is 19 and the budget is pinned there.

**The 19, named (reason `feedless_duplicate`):** curated: ihsmarkit.com (IHS Markit Oil & Gas); ieeexplore.ieee.org
(RA-L); psycnet.apa.org (Journal of Educational Psychology); journals.elsevier.com x2 (Intelligence and Education,
Journal of Psychometrics); muse.jhu.edu x9 (the Project MUSE journal and subject entries); asia.si.edu; perseus.tufts.edu;
sourcebooks.fordham.edu. markets: argusmedia.com. legal: uspto.gov, epo.org (the ruled 2026-07-17 collapse of a host's
second portal). Each is a second feed-less description of a host that already has a feed-less row; with no feed there is
nothing to collect that the first row does not already collect.

**Tag merge rules (built):** a merged tag never overwrites a different existing value (`lean-*` is exclusive: a second,
different lean is a counted conflict listed with both sides); a tag is merged ONCE per row (kept in the row's baseline),
so a tag the operator removed is not put back by the next boot; a row with no readable baseline is skipped and counted.

**Siblings and verdicts:** a new sibling row inherits the outlet's oldest measured `qualified`/`disqualified` verdict as an
`inherited` attempt plus an admission-audit row (the overlay's own pair); a curated-catalogue stamp is NOT handed on (it states
provenance, not a verdict). The shipped overlay already covers every feed of a domain (`Source.domain.in_`), so a fresh
install needs nothing more.

**Add / import / filter:** `create_source` and the discovery adder match on `(domain, feed)`; the YAML and CSV imports treat a
record as an EDIT of the row it matches (identical feed; the domain's only row; the oldest for a feed-less record) and a new
feed as a sibling -- matching on the domain alone made a round trip of a thirty-feed outlet overwrite the first row thirty
times. The article `source` filter names every source of that name.

**The three lean tags the merge does not carry (189 of 192), each with its reason.** None is lost: each is on a row of its
own, because the spectrum catalogue names a DIFFERENT feed than the curated entry, so the entry is a sibling row and keeps
its own tag. What it does not do is put the lean on the curated feed row of the same outlet (the outlet's lean then reads on
one of its two feeds). Telegraph (`lean-center-right`, `telegraph.co.uk/rss.xml`), Daily Mail (`lean-right`,
`dailymail.co.uk/articles.rss`) and Sky News (`lean-center`, `feeds.skynews.com/feeds/rss/world.xml`).
