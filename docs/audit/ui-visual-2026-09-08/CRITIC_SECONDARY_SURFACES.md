## Coverage gaps

**Three of the eight assigned surfaces have zero walk/verify data: custody, integrity, help.** The JSON I was handed contains complete walk+verify pairs for law, indices, library, settings, and analyze, but nothing at all for custody, integrity, or help — not even a `notReached` stub. That is the largest single gap in this round, not a set of small ones, and I closed it directly (see below) rather than just flagging it.

Within the five surfaces that *were* covered, recurring gap patterns worth naming as classes (not just per-surface footnotes):

- **Long/adversarial text input was never tried anywhere.** No agent across law/indices/library/settings/analyze injected an unusually long string, an emoji-heavy string, or a string with embedded HTML/markdown into any of the many text inputs (Law's add-by-URL, Settings' 3618-row source names, Integrity's `anno-value`/`anno-target`, Analyze's search). Given `mdToHtml` in Help hand-rolls its own markdown renderer with regex-based inline parsing (I read it directly — see below), and Integrity/Law both accept free-text into fields that presumably render later, this is a live blind spot, not a theoretical one.
- **Deep-linking / hash-routing was never exercised as its own class.** Analyze's own complexity note documents `?corpus=`/`?analyze=` deep links and a persisted multi-tab workspace; invariant #23 documents a `?corpus=` boot deep-link on Home; none of the five reports drove a raw hash/query-param load to verify these paths. My own Help investigation (below) found a serious defect living exactly in this class — the app's global `popstate` handler — which no other surface's agents were positioned to catch because none tested hash navigation directly.
- **Non-English locale testing is uneven and skips the richest surface.** Library, Indices, Settings (partially, via `#dr-faces`), and Custody/Integrity (mine) got RTL/Arabic passes; **Analyze — the single surface the app's own honesty rules are built around — was never tested in any non-English locale.** Given Library's independent i18n failures (untranslated stat labels, a mid-sentence English/Arabic splice) and my own finding of the same splice pattern in Help's doc-nav chrome, Analyze's 13-subtab, caveat-dense UI is the most likely place for the identical defect class to also live, and it is unverified.
- **Double-click/rapid-repeat interaction testing only happened on Library and Settings.** Analyze independently reported a real 429 from rapid clicking, which is exactly the condition idempotency testing is meant to catch, but no agent formally double-clicked any of Analyze's 9-per-subtab export/action buttons to check for duplicate POSTs.
- **No download/export flow was verified end-to-end anywhere in the batch**, including my own pass (Integrity's "Export signed bundle" produced no visible feedback and no download event — ambiguous, flagged below, unresolved).
- **Keyboard-only task completion** (not just focus-ring/tab-order, but actually filling and submitting a form via keyboard alone) was checked nowhere; only individual-widget keyboard contracts were verified.
- Law's own agent flagged an incomplete Tab-order trace (started mid-page, not from top) as a known gap — this is Law-specific but the same caution should generalize: several other surfaces' "Tab 25/30 times" traces also started from a `.focus()` call or after a prior click, not from a hard page reload with a fresh, blurred `document.body`.

## Contradictions

1. **The shared contrast harness was live-patched mid-audit, and three separate walk agents (Law LAW-6, Indices idx-11, Settings F8) independently rediscovered — and reported as an active defect — the exact same "excludes the element's own background" bug, only to have their own verify passes find the harness already fixed** (`oohelp.py`'s own source comment cites "2026-09-08... two audit agents caught this independently"). This means the harness itself is not a stable instrument across this session's timeline — the same measurement genuinely changed answers between a walk pass and its verify pass, purely because of when each ran, not what changed in the app. The next round needs to either pin/version the harness for the duration of a run or treat any contrast_failures() count as timestamp-qualified.
2. **Indices idx-01's own headline claim ("index AND commodity chart rendering entirely unverified") is directly contradicted by its own verify pass**, which found a sibling "Commodities" tab on the same instance with three real, populated series correctly exercising invariant #16's bar/line rules. The walk agent conflated a dead, UI-unused API catalog (`/api/markets/board?category=commodity`) with the actual, reachable commodity feature living one click away. This is a caution about scope-checking sibling surfaces before declaring an invariant "unverified" on a fixture.
3. **Law LAW-1's diagnosis ("the official ↗ link is dead") was refuted by its own verify pass**, which discovered the true mechanism: a native `confirm()` dialog (`_externalLinkGuard`) that Playwright silently auto-dismisses unless a `page.on('dialog', ...)` handler is registered — invisible to any screenshot. The walk agent's own evidence file (`guard-dialogs-after-link-click.json`) only checked for `<dialog>` elements, never a native `confirm()`, which is exactly why it looked dead rather than gated. This is the same trap (native dialogs are invisible to screenshots and eaten by default automation) that I had to route around explicitly for Custody's OTS confirm() below.
4. **Library L-3's numeric specifics were partly wrong even though the underlying defect is real**: the claimant's "active tab is worse than inactive" sub-claim (3.73 vs 3.85) was refuted (verify measured 3.94, i.e. better), and the total failure count was undercounted by more than 2x because the claimant's repro path didn't match what was actually on-screen when measured. The defect (paper theme fails AA on subtab/top-bar chrome) stands; the specific numbers attached to it do not.

## Three gaps I closed myself

All driven live on port 8017 against Chromium via the shared `oohelp.py` harness; screenshots and raw JSON probes under `/home/user/oo-ui/wf-a2/critic/`.

**Custody** (`custody-probe*.json`, `custody-*.png`) — the surface is well-built and I could not break it. Clicking "Anchor root" with OpenTimestamps off correctly performs a **local-only** anchor with zero network requests (`/api/custody/anchor` → 127.0.0.1, 200) and an honest disclosure ("Anchored via local — Recorded in the local anchor book... NOT independent third-party proof"). Turning the `#cust-ots` checkbox on and clicking "Save custody settings" correctly fires a genuine `confirm()` naming the recurring privacy cost verbatim ("From now on, every article this app ingests will submit a hash to public Bitcoin calendar servers — revealing your IP and the timing... This repeats on every future ingest, not just once") — a live, working confirmation of CLAUDE.md's invariant #14f, dated the same day as this audit. Per safety rule 1 I registered a `page.on('dialog', ...)` handler that dismisses every such dialog rather than accepting it. `axe()` returned only the app-wide `page-has-heading-one`; zero contrast failures, zero console/uncaught errors, zero overflow.

**Integrity** (`integrity-probe*.json`, `integrity-*.png`) — also well-built and honest: "Scan for coordination" (loopback-only) correctly returns "No coordinated near-duplicate clusters found" rather than fabricating a result; "Profile" on a made-up source correctly returns "Source 'example.com' not found." rather than guessing. One real, confirmed defect: **axe reports `select-name` (critical) on `#anno-kind`**, the annotation-type `<select>` (ownership/leaning/coordination-tag/transparency-fact/correction/note) — it has no accessible name, so a screen-reader user hears only "combobox" with no indication of what it selects. RTL Arabic pass showed clean, fully-translated chrome (a positive contrast with Library's i18n gaps). "Export signed bundle" clicked with zero stored annotations produced no visible feedback and no download event — plausibly a correct no-op (nothing to export) but genuinely ambiguous; flagged, not resolved.

**Help** (`help-probe*.json`, `help-*.png`) — the most valuable find of the three, and a real, live-only, cross-file defect that static code review would be very unlikely to catch in one file:

- The manual's own client-side markdown renderer (`mdToHtml`, `src/static/app-settings.js`) emits headings as bare `<h2>…</h2>`/`<h3>…</h3>` **with no `id` attribute at all**, while the manual's hand-written Table of Contents links to those same sections by anchor (`#30-home`, `#31-search`, `#39-settings`, `#30a-activity--the-task-manager`, …) — axe independently flags 15 of these as `link-in-text-block` and named exactly these hrefs.
- Because those target elements don't exist, and because clicking a same-document `<a href="#x">` fires a `popstate` event in this Chromium build, the app's global `popstate` handler (`app-shell.js`) blindly re-runs `showTab(location.hash.slice(1), false)`. `showTab`'s own fallback rule — `if (!document.getElementById("tab-" + name)) name = "home"` — then fires, because there is obviously no `tab-30-home` element.
- **Net effect, reproduced and instrumented three ways (framenavigated events, `document.querySelector('.tab-page.active').id`, and a monkey-patched `history.replaceState` with captured stack trace pointing at `app-shell.js:167`, the popstate listener):** clicking almost any entry in the User Manual's own Table of Contents doesn't fail to scroll — **it silently ejects the user from Help and dumps them on Home**, rewriting the URL to `#home` in the process. This is not a Help-only bug in mechanism; the same `showTab`-on-`popstate` pattern would misfire for any surface that renders internal `#`-anchors that don't correspond to top-level tabs.
- Separately, **mobile (375×812) is genuinely broken**, unlike every other surface tested this round: `documentScrollsHorizontally: true`, doc width 781px vs 375px viewport, the entire prose column renders at a fixed ~744px with visible mid-sentence text truncation (screenshot `help-10-mobile.png` shows "ethically...", "one searchable, c[orpus]" cut off at the right edge), and the whole left nav/brand column renders off-screen to the left (`escapes-viewport-left` up to 250px) rather than collapsing into the hamburger pattern every other surface uses correctly.
- RTL Arabic pass: the doc-nav chrome (button captions like "The complete guide: install, every tool, workflows, reference, and per-feature deep-dives.", "Governance & acceptable use", "Threat model, local-first posture, and the security audit.") stays hard-coded English inside an otherwise-Arabic shell — the same untranslated-chrome-next-to-translated-chrome pattern Library's L-1 already documented on a different surface.
- axe also flags `scrollable-region-focusable` (serious, n=3) on the manual's own `<pre>` code blocks (install one-liner, API route listing) — no `tabindex`, unreachable by keyboard.
