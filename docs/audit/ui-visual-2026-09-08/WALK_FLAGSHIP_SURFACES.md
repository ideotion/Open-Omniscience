## 2. Findings by severity (post-verification)

### P0 — user-visible breakage / data-integrity / consent

**[P0] Search's rate limit + auto-retry design self-locks the entire surface, and a fresh page load during lockout shows nothing at all**
*Surface: Search · CONFIRMED (partially — two secondary symptoms refuted, see below) · port 8012, ink/en/1440×900*
`GET /api/articles` is `@limiter.limit("100/hour")` per IP (`src/api/main.py:1349-1350`) with no `Retry-After` header, while the client's `api()` helper (`app-core.js` ~1859-1909) retries a 429 up to **4 times** — 5 requests per click. Once ordinary exploratory querying (the exact behavior the surface's boolean-query/filter grammar invites) exhausts the budget, every further Search click fires all 5, all 429, and the results table + count line vanish with only a transient toast. Verify went further: **a brand-new page load or refresh while already locked out renders a completely blank results area with zero toast and zero error at all**, because the toast only fires on a user *click*, not on the boot-time auto-search. Verify measured the lockout still active after 5+ minutes idle, consistent with the hourly window.
*Two originally-claimed downstream symptoms were REFUTED on redrive:* the Analyze window's "Nothing extracted yet" tile is an unrelated content-fixture fact (that query genuinely has no deducible entities, confirmed by calling the extractor directly), and the "Synthesize results" dialog does **not** hang forever — polled every second for 15s, it correctly resolves to an honest "Could not load articles. Too many requests." message inside the dialog, exactly the degrade-loudly pattern the project asks for.
*Evidence:* `/home/user/oo-ui/wf-a1/search/search-16-locked-after-retries.png`, `search-17-locked-after-toast-timeout.png`; `/home/user/oo-ui/wf-a1/verify-search/20-pre-click-state.png` (blank fresh load), `part3-final.json` (`pre_click: {meta:"", rows:0}` before any click); `src/api/main.py:1349-1350`; `app-core.js` `_API_MAX_RETRIES=4`.
*Why it matters:* this is the single densest, most iterative surface in the app, purpose-built for exactly the query-refinement pattern that burns the budget fastest, and its failure mode degrades from "confusing toast" to "silently, permanently blank" the longer a session runs.
*Suggestion:* stop retrying a 429 client-side (it only accelerates exhaustion of a budget that is already exhausted); surface the real remaining-quota/reset time from the server; never render an empty state indistinguishable from "still loading."

**[P0] The Observatory's ranked-table drill-through into Analysis is broken for every galaxy tried — and for some, it is silently *wrong*, not just empty**
*Surface: Observatory · CONFIRMED, and escalated by verify · port 8013, ink/en/1440×900*
Clicking a ranked-table row (e.g. "Elections & democracy," the corpus's #1 galaxy by mentions: Sources 7, Mentions 263) opens the Analysis window with the galaxy's curated cluster **name** used as a literal full-text search query. Root cause (verify, from source): `openAnalysisFor(g.name,…)` treats a keyword-cluster label as searchable text, and it almost never appears verbatim in article bodies — `/api/articles?query=Elections+%26+democracy` returns `total=0`. Two of two galaxies tried in the walk (Ecology & biodiversity; Elections & democracy) landed on "No keywords yet / Nothing extracted yet / No sources yet." Verify confirmed this is systemic from source (not a 2-sample coincidence) and found a **worse variant**: for "Public finance," the literal-text query coincidentally matches 19 unrelated articles, so the drill-through opens a populated-looking, plausible, but **completely wrong** article set instead of the galaxy's true 150-mention/6-source membership — with nothing in the UI to signal the mismatch.
*Evidence:* `/home/user/oo-ui/wf-a1/observatory/observatory-after-table-row-click.png`, `observatory-after-table-row-click-elections.png`; verify's direct API probes and `/home/user/oo-ui/wf-a1/verify-observatory/c1-01-after-click-elections.png`.
*Why it matters:* the ranked table exists specifically so a user can go from a number to its evidence; the drill-through is that mechanism, and it fails at the exact place the surface's honesty-forward design promises to hold up — worse, the wrong-but-plausible variant is undetectable without independently re-deriving the true galaxy membership.
*Suggestion:* pass the galaxy's real member-keyword set (or its underlying article-id list, which the Observatory API already has) into the Analysis window instead of re-deriving it from the display name as free text.

**[P1] A keyboard user can silently activate hidden state-changing controls on Home's flip cards (Dismiss / Add to draft / Open corpus), with zero visible feedback**
*Surface: Home · CONFIRMED and escalated by verify · port 8011, ink/en/1440×900*
The card-back (`.card-face.card-back`, `rotateY(180deg)`, `backface-visibility:hidden`) carries no `inert`/`tabindex=-1` gating while the card is un-flipped, so Tab reaches its buttons in normal order and they render a real, computed focus ring the user cannot see (the whole face is rotated away). Verify went beyond the original claim by tabbing straight to an invisible "Dismiss" button and pressing **Enter**: it genuinely fired the handler and injected a live, functional "Why dismiss? (optional)" reason-chip form into the DOM, with **zero visible change on screen**.
*Evidence:* `/home/user/oo-ui/wf-a1/home/home-30-focus-addtodraft-card-unflipped.png` (front visible, no focus ring); `/home/user/oo-ui/wf-a1/verify-home/v-blind-01-after-enter-on-dismiss.png` (post-Enter, no visible change, live form in DOM); `keyboard-tab-order-2.json`; `src/static/app-home.js` ~1375-1392 (no inert gating).

**[P1] Two of the four core Search behaviors — non-Latin-script matching and boolean NOT — are silently wrong, in opposite directions**
*Surface: Search · CONFIRMED (mechanism corrected by verify) · port 8012*
- An Arabic query returns 216 results including plainly non-matching English articles, while the surface's own Export (same query, same filters) correctly returns 28. **Verify traced the real mechanism**: this is not tokenizer failure as originally claimed, but the *disclosed*, on-by-default cross-language equivalence expansion feature (R1, `expand=True`, `src/api/main.py:1492`) — a working, intentional feature whose disclosure banner (`_crossLangNotice()`) is wired into the Analyze window's Articles tab but **never into the plain Search tab** (`doSearch()`), so a Search-tab user sees a silently broadened result set with no indication it happened and no way to turn it off (unlike Analyze's Advanced panel, which has an expand toggle).
- Literal CJK substrings verified present in the corpus's own zh-language article bodies (开源, 一家, 合作社, 软件) return **0 results** even with expansion on — confirmed the search index does not tokenize CJK body text at all, only reachable via English title words.
- A standalone `NOT opinion` query — the exact syntax the search box's own placeholder teaches — returns all 453 articles instead of 452 (excluding the 1 "opinion" match). Root cause in source (`src/database/fts.py`): a purely-negative query returns `None` from the renderer with a comment saying callers "may treat None as no match," but the caller instead falls through to "no text constraint," silently ignoring the exclusion.
*Evidence:* `/home/user/oo-ui/wf-a1/search/search-06-query-ar.png`, `search-05-query-zh.png`; verify's direct `_query_articles(expand=True/False)` calls; `/home/user/oo-ui/wf-a1/verify-search/part1-final.json` (`opinion`→1, `NOT opinion`→453).
*Why it matters:* one silent under-match, one silent over-match, one silent no-op — three different, undetectable failure modes in the app's own advertised query language, on its flagship search surface, none with a warning.

The real `#net-consent` dialog was captured on a **second** click and is correctly built (local interface IPs, ISP-caveat, app-scoped clarification). *Evidence:* `/home/user/oo-ui/wf-a1/critic/c1-08-toggle-state-over-time.json`, `c1-13-multi-trial-fresh-load.json`, `c1-11-after-second-click.png`, `c1-12-consent-after-second-click.json`.
*Why it matters:* in an always-boots-offline fixture this mis-click never lets a consent-free online transition through (it only fires the harmless double-offline branch), but a user's first, correctly-intentioned attempt to go online silently does nothing — worth a clean-machine timing re-check before triage (the 4–8.5s figure is likely inflated by this session's own CPU contention).

## 3. Cross-surface patterns (highest-leverage fixes)

1. **One shared-shell accessibility gap, six report lines.** Every one of the six surfaces tested reports axe's `page-has-heading-one` (no `<h1>` anywhere in the app), and three (Insights, Observatory, Timemap) additionally report `#subtab-strip`/`#oo-tip` not contained by a landmark region. This is a single fix in the shared shell/tooltip components, not six per-surface bugs — worth exactly one PR.

2. **A retry-storm rate limiter is the app's own biggest self-inflicted failure mode.** Search's P0 lockout, Insights' P2 toast cascade, and Observatory's (refuted-as-caused-by-the-measure-dropdown, but real-in-general) 429 traffic all trace back to the same `100/hour` limiter on `/api/articles` combined with a client that retries 4× per call with no `Retry-After` honored. Fixing the retry policy once (stop retrying 429s; surface real reset time) removes a P0 and shrinks a P2 in one change.

3. **Drill-throughs from a data view into a second surface (Analysis / Settings) are the app's weakest transition, and fail two different ways.** Observatory's ranked-table → Analysis passes a curated cluster *name* as literal search text (P0, sometimes silently wrong); Timemap's "Explore sources" lands in generic, unfiltered Settings→Advanced plumbing with no active-tab indicator (P1, unverified by a second pass). By contrast, Home's own "Open corpus" deep-link (positive, below) does this correctly — it passes real article IDs, not a label — and is the pattern the other two should copy.

4. **The contrast-scanning harness (`oohelp.py`) had a real, now-already-fixed bug, and it cost real audit time three times over.** Home's walk found the harness *missed* a true failure (Home's Back-button, 1.04:1); Feed/Insights/Search's walks independently found the harness *inventing* false failures on filled buttons (both directions are the same root cause: excluding a scored element's own background from its composited backdrop). By the time each surface's *verify* pass ran, the harness had already been patched mid-session — so three independent verify passes spent real effort re-diagnosing a bug that had already stopped reproducing. Net effect on the app: **zero outstanding contrast defects from this thread** (see §7); the process lesson is not to assume a shared, live tool is static mid-audit.

5. **Native `<input>` elements lack any visible focus ring while every button/custom control has a strong, consistent one.** Confirmed concretely only on Search (query box, source/language filters, all date inputs — `outline:none 0px` vs. buttons' `solid 2px`), but every surface's keyboard walk shows the *same* button-ring convention working everywhere, making this specifically an `<input>` gap likely to recur wherever plain text/date fields appear (untested elsewhere).

6. **Locale-switch coverage for dynamically-rendered blocks is incomplete, and this is a recurring bug class, not a one-off.** Home's stats strip freezes in English after a live language switch; source confirms `app-boot.js`'s `oo:langchange` listener has an explicit allowlist of what it re-renders, and this block isn't on it — the same class of bug the maintainer already fixed once for the briefing lead title. A full audit of the `oo:langchange` listener's coverage list against every dynamically-rendered block, app-wide, would likely find more instances than the one surfaced here.

7. **The offline-education coachmark (`#net-coach`) ignores its own "seen" flag and overlaps live content at common widths.** Confirmed independently on Feed (899/901/375px, plus over the Analysis window post-drill) and Observatory (375px, over caveat text through scroll) — one shared component, two independent live reproductions.

8. **The local-reader-first / external-link-preview invariant (#6/#7) is correctly and consistently wired.** Verified structurally on both Feed and Search: `open` always targets `/api/articles/{id}/view`, and `source ↗` never navigates directly — both route through `openLinkPreview()` first, with the outbound anchor's full URL as its own visible text. This is a genuine cross-surface positive worth protecting.

## 5. Visual impression of the product as a whole

Read together rather than as eight separate reports, Open Omniscience is unmistakably **one product with one disciplined design language**, not a patchwork: the same dark "ink" panel system, the same restrained accent-blue, the same amber caveat colour reserved exclusively for honesty-required disclosures, the same subtab grammar, and the same small accent-dot-on-hover tooltip convention recur, correctly, on every surface an agent opened — Home's flip cards, Feed's reader, Insights' chart interactions, Search's export panels, Observatory's polar chart, and Timemap's choropleth all clearly come from the same hand and the same rules. Visually the app looks whole and considered at every screenshot; functionally, the seams show up specifically at the transitions between one honestly-built piece and the next.

## 6. Complexity & automation notes harvested from the walk

- **Search** is the densest surface by raw control count (135 buttons + 5 inputs), but ~100 of those are one repeating per-row unit; the real complexity burden is in the **13 unique secondary action buttons** (Export ×2, Methods appendix, Synthesize, Summarize/Translate-all, Run extractor, Export signed evidence, 5 time presets) sitting undifferentiated in two rows with no grouping — the only way to tell a safe read action from a local-compute job is to hover every one of them once. The boolean query language is taught by placeholder text alone, with no inline builder or script-safety indication — directly relevant given the CJK/Arabic findings above.
- **Insights** is the densest surface by subtab count (9), several carrying real statistical sophistication (a circular-shift permutation test with Benjamini-Hochberg correction on Lunar; PMI association scoring on the mind-map) presented with full, honest methodology — genuinely no dishonesty, but a first-time user reads a purpose paragraph, a caveat, and sometimes a methodology note before reaching each panel's actual content.
- **Home** stacks a 9-lens subtab bar over two-sided cards with two independent nested disclosure levels (why vs. math) plus a dismiss-reason sub-panel whose two visually-similar paths (chips vs. free-text+button) have *opposite* commitment models — a distinction discoverable in this session only by watching network traffic, with no visible cue.
- **Feed**'s 101-control count is the most misleading of the six: it decomposes into one small, learnable interaction vocabulary repeated per card, and the real complexity risk is invisible plumbing (the per-order-mode resume bookmark) rather than visible UI weight.
- **Observatory** packs five simultaneous encoding channels (angle/radius/size/colour/meaningless-hash-position) plus a 77-row table behind only two form controls — efficient, but only survives because four paragraphs of essential (not decorative) caveat text precede it; skipping that text produces real misreadings (e.g. mistaking wedge-position for meaning).
- **Timemap** was reported as having a genuinely learnable single interaction vocabulary across its four lenses, undercut by the broken drill-through noted above.
- **Automation/methodology notes for future runs:** (a) the shared contrast harness was live-patched mid-audit — confirm current behavior before trusting a cached description of it; (b) `window`-scoped debug variables declared with `let` never attach to `window` — re-fetch the endpoint directly instead of trying to read live state off the page; (c) a synthetic `.click()` can fail to reproduce a real scroll/focus side-effect that an actual Playwright mouse click does reproduce — prefer real mouse events when a finding depends on browser-native behavior; (d) heap-usage figures (`performance.memory`) are noisy enough between runs (18MB vs. 190MB for an identical repro) that they should be treated as directional, not exact.
