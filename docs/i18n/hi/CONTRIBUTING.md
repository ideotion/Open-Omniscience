# योगदान

मदद के लिए धन्यवाद। मार्गदर्शक सिद्धांत है **ईमानदारी**: कोई फ़ीचर वही करे जिसका वह दावा करता
है, वरना वह शिप नहीं होता। कोई गढ़े हुए आउटपुट नहीं, कोई नकली विश्वास-स्कोर नहीं, कोई चुपचाप
गिरावट नहीं — देखें [DESIGN.md](DESIGN.md) §3।

## सेटअप

```bash
python3.13 -m venv .venv && . .venv/bin/activate
pip install -e ".[analysis,dev]"
pytest -q          # full suite, a few minutes
```

निर्भरताओं के लिए `pyproject.toml` ही सत्य का एकमात्र स्रोत रहता है (हम न्यूनतम सीमाओं के भीतर
नवीनतम संस्करण इंस्टॉल करते हैं ताकि CI अपस्ट्रीम की टूट जल्दी पकड़ ले)। **पुनरुत्पादनीय /
रिलीज़ इंस्टॉल** के लिए उससे बना एक हैश-पिन किया हुआ लॉक है:

```bash
pip install -r requirements.lock          # exact, hash-verified core + analysis pins
# regenerate after a dependency change:
pip-compile --generate-hashes --extra analysis -o requirements.lock pyproject.toml
```

**यह `./install.sh` में जुड़ा हुआ है, केवल हाथ से चलाया जाने वाला कमांड नहीं।** ऑनलाइन इंस्टॉल
पथ (`pip_install()`) `requirements.lock` का अपने-आप उपयोग करता है जब भी वह मौजूद हो, आपके
चल रहे Python के लिए बनाया गया हो, और आपके माँगे हर घटक (`OO_COMPONENTS`) को कवर करता हो —
यह लॉक के अपने `pip-compile ... --extra=...` हेडर से जाँचा जाता है, कभी हाथ से नहीं रखा जाता। जब
इनमें से कोई शर्त पूरी न हो (लॉक आपके Python के लिए पुराना हो, या ऐसा घटक माँगा गया हो जिसके साथ
लॉक नहीं बना, या कोई पिन इस प्लेटफ़ॉर्म पर हल न हो) तो यह सामान्य, न्यूनतम-सीमा आधारित
`pip install -e ".[...]"` रिज़ॉल्व पर लौट आता है, एक स्पष्ट संदेश के साथ कि ऑडिट किया गया पथ
क्यों इस्तेमाल नहीं हुआ — `OO_USE_LOCK=0` बिना शर्त लॉक से बाहर कर देता है। **जैसा शिप हुआ है,
लॉक केवल `--extra analysis` को कवर करता है**, जबकि `install.sh` का अपना डिफ़ॉल्ट घटक-समूह
`analysis,compression,columnar` है — इसलिए डिफ़ॉल्ट, बिना निगरानी वाला `./install.sh` आज
न्यूनतम-सीमा आधारित रिज़ॉल्व पर लौटता है (compression/columnar लॉक के कवरेज में नहीं हैं)।
ऑडिट किए गए पथ को अभी की स्थिति में आज़माने के लिए `OO_COMPONENTS=analysis ./install.sh` चलाएँ,
या डिफ़ॉल्ट इंस्टॉल पथ को भी लॉक-आधारित बनाने के लिए `pip-compile --extra analysis --extra
compression --extra columnar ...` से लॉक का कवरेज बढ़ाएँ।

**ऑफ़लाइन/एयर-गैप्ड बंडल** (`scripts/build_offline_bundle.sh`, जिसे Qubes/Tails लक्ष्य के लिए
`install.sh` का `--no-index` ऑफ़लाइन पथ उपयोग करता है) **अभी लॉक से नहीं जुड़ा है** — यह हर बार
बनने पर `pyproject.toml` की न्यूनतम सीमाओं से नए सिरे से रिज़ॉल्व होता है। यह एक ज्ञात, खुला अंतर
है, भूल नहीं: ऑफ़लाइन बंडल को भी लॉक-आधारित बनाना
(`pip download --require-hashes -r requirements.lock`, और जिन extras को लॉक कवर नहीं करता उनके
लिए `$SPEC`-आधारित रिज़ॉल्व को फ़ॉलबैक के रूप में रखना) आगे के काम के रूप में दर्ज है।

## कार्यप्रवाह

- **Python 3.13**, एक ही `pyproject.toml` (कोई requirements.txt नहीं)।
- **ruff** से लिंट/फ़ॉर्मैट; **mypy** से टाइप-जाँच: `make lint && make typecheck`।
- हर बदलाव हरे पर ख़त्म होता है: `make check` (ruff + pytest)। नए व्यवहार के लिए एक व्यवहारिक
  परीक्षण जोड़ें; ठीक करें या क्वारंटीन करें — इम्पोर्ट पथ में आधा-अधूरा काम करने वाला कोड न छोड़ें।
- छोटे, ईमानदार चरणों में कमिट करें, ऐसे संदेशों के साथ जो *क्या और क्यों* बताएँ।
- स्कीमा बदलाव Alembic से होकर जाते हैं (`alembic revision --autogenerate`); मॉडल/माइग्रेशन
  विचलन पकड़ने के लिए CI `alembic check` चलाता है।

## शिप्ड लेजर: प्रति पंक्ति एक फ़ाइल

`docs/ledger/shipped.csv` में जोड़ें (append) नहीं। GitHub की मर्ज-जाँच फ़ाइल के `merge=union`
नियम को अनदेखा करती है, इसलिए हर PR द्वारा जोड़ी गई पंक्ति हर मर्ज के बाद हर खुले PR में टकराव
पैदा करती थी। इसके बजाय एक नई फ़ाइल जोड़ें:

    python scripts/ledger_shipped.py new --date 2026-09-30 --area tests --item "..." \
        --status "shipped (draft)" --refs "PR #1240" --key-paths "src/a.py; tests/b.py" --summary "..."

यह `docs/ledger/shipped.d/<date>-<slug>.csv` लिखता है (लेजर का हेडर और एक पंक्ति)। कोई दूसरा PR
उस फ़ाइल से नहीं टकरा सकता जिसे वह छूता ही नहीं। `python scripts/ledger_shipped.py check` हर
खंड (fragment) की जाँच करता है; रिलीज़ नोट्स और रिपो-इनवेरिएंट परीक्षण पहले `shipped.csv` पढ़ते हैं
और उसके बाद खंड। `ledger_shipped.py fold` खंडों को बाइनरी में `shipped.csv` में जोड़ता है और
उन्हें हटा देता है; यह अनुरक्षक या रिलीज़ के लिए है, फ़ीचर PR के लिए कभी नहीं। `refs` असली PR
संख्या होनी चाहिए, `PR pending` नहीं (इस पर एक परीक्षण विफल होता है)।

## सबक़ और शिप्ड-लॉग प्रविष्टियाँ: हर एक की एक फ़ाइल

यही परिपाटी दोनों बड़े संग्रहों पर लागू होती है। एक सबक़ एक फ़ाइल है,
`docs/ledger/lessons.d/<date>-<slug>.md` (`python scripts/lessons.py --new SLUG`); एक शब्दशः
शिप्ड-लॉग प्रविष्टि एक फ़ाइल है, `docs/ledger/shipped_log.d/<date>-<slug>.md`
(`python scripts/ledger_fold.py new-log SLUG`)। `LESSONS.md` या `SHIPPED_LOG.md` में कभी न जोड़ें
और `_LESSONS_LINE_CEILING` को कभी संपादित न करें: ऐसा करने वाला हर PR बाक़ी हर PR से टकराया। एक
खंड `## <date> — title` से शुरू होता है, एक newline पर ख़त्म होता है, और LF पंक्ति-अंत के साथ UTF-8
होता है; एक सबक़ (शिप्ड-लॉग प्रविष्टि नहीं) में दूसरा शीर्षक नहीं होता और वह 200 पंक्तियों से कम
रहता है (यह एक प्रविष्टि का आकार सीमित करता है); `python scripts/ledger_fold.py check` (और
`tests/test_ledger_fragments.py`) इसे सत्यापित करता है, `#NNNN` और `PR pending` प्लेसहोल्डर
अस्वीकार करता है, और `lessons.py <words>` खंडों में भी खोजता है।
`ledger_fold.py fold` रिलीज़ के समय खंडों को संग्रहों में मिलाता है और फ़ीचर PR के लिए कभी नहीं है।

## लोकेल फ़ाइलें और मर्ज टकराव

12 `src/static/locales/*.json` फ़ाइलें **क्रमबद्ध** रखी जाती हैं (पहले `_meta`, फिर कोड-पॉइंट क्रम में कुंजियाँ), ताकि स्ट्रिंग जोड़ने वाले दो PR अलग-अलग जगह डालें और साफ़-साफ़ मर्ज हों। स्ट्रिंग जोड़ने के बाद `python scripts/locales_merge.py` चलाएँ; यह फ़ाइलों को क्रमबद्ध करता है और जाँचता है (`--check` केवल सत्यापित करता है; `tests/test_locales_merge.py` अक्रमबद्ध या दोहराई गई कुंजियों पर विफल होता है)।

यदि `git merge origin/main` लोकेल फ़ाइलों में टकराव-चिह्न छोड़ दे, तो वही स्क्रिप्ट चलाएँ: यह हर हंक के दोनों पक्ष रखती है, क्रमबद्ध करती है, और यदि दोनों पक्षों ने एक ही कुंजी को अलग पाठ दिया हो तो उस कुंजी का नाम लेकर रुक जाती है (एक वास्तविक विरोधाभास जिस पर निर्णय करना है)। `docs/ledger/shipped.csv` `.gitattributes` में `merge=union` है, जिसका लोकल `git merge` पालन करता है पर GitHub का वेब मर्ज और update-branch बटन नहीं करते: main को लोकल रूप से मर्ज करें, फिर दोहराई गई `(date, area, item)` पंक्तियों की जाँच करें।

## संस्करण नीति

> **हम जानबूझकर परिपक्वता को कम आँकते हैं। प्रचार से ऊपर ईमानदारी।** उपयोगकर्ता का सुखद रूप से
> चकित होना गुमराह होने से बेहतर है। संस्करण संख्या *परिपक्वता* के बारे में एक वादा है, और हम उस
> वादे को संयमित रखते हैं।

### सत्य का एकमात्र स्रोत

संस्करण **एक जगह रहता है: `pyproject.toml` (`[project] version`)**। बाक़ी सब उसी से निकलता है:

- चलता हुआ ऐप इसे इंस्टॉल किए गए पैकेज मेटाडेटा से पढ़ता है
  (`importlib.metadata.version("open-omniscience")`) — इसलिए `/api/health`, API का `version=`,
  और UI सभी अपने-आप *असली* इंस्टॉल किया गया संस्करण बताते हैं।
- कोई और कोड संस्करण का शाब्दिक मान हार्डकोड नहीं करता। परीक्षण पैकेज मेटाडेटा के विरुद्ध जाँच
  करते हैं, किसी स्ट्रिंग के विरुद्ध नहीं (देखें `tests/test_api_search.py`)।
- रिपो-रूट का `README.md` अपने हेडर में संस्करण एक बार बताता है, और एक CI गार्ड जाँचता है कि वह
  पैकेज से मेल खाता है (`tests/test_repo_invariants.py::test_readme_version_matches_package`)।

**संस्करण बढ़ाने के लिए केवल `pyproject.toml` बदलें**, README हेडर को मेल खाने के लिए अपडेट करें
(गार्ड इसे लागू करता है), फिर `pip install -e .` चलाएँ ताकि मेटाडेटा ताज़ा हो जाए।

**`vX.Y.Z` टैग केवल उस कमिट पर लगाएँ जिसका `pyproject.toml` पहले से `X.Y.Z` पढ़ता हो।** रिलीज़
वर्कफ़्लो (`.github/workflows/release.yml`) कुछ भी बनाने से पहले किसी भी अन्य टैग को अस्वीकार कर
देता है, इसलिए संस्करण-वृद्धि से पहले काटा गया टैग बिना wheel, sdist या checksums के रिलीज़ प्रकाशित
करता है। पहला `v0.4.0` 2026-09-28 को इसी तरह काटा गया था; संस्करण बाद में सेट किया गया और टैग उस
पर ले जाया गया (`docs/product/RELEASE_0.4_GATE.md` पंक्ति G)। **टैग ले जाने के लिए git चाहिए:**
GitHub की वेबसाइट न टैग हटा सकती है न ले जा सकती है, और वहाँ प्रकाशित रिलीज़ वर्कफ़्लो शुरू किए
बिना मौजूदा टैग का दोबारा उपयोग करती है। यदि आपके पास push कर सकने वाला लोकल क्लोन नहीं है, तो
`main` पर एक Codespace खोलें और चलाएँ
`git fetch origin && git tag -f vX.Y.Z origin/main && git push -f origin vX.Y.Z`। यदि वर्कफ़्लो को
जनित नोट्स लिखने हैं तो पहले GitHub रिलीज़ हटाएँ: यह मौजूदा रिलीज़ के नोट्स रखता है और केवल फ़ाइलें
और checksums जोड़ता है।

### परिपक्वता की सीढ़ी (हम कहाँ हैं, कहाँ जा रहे हैं)

सॉफ़्टवेयर नया है और अभी परखा जा रहा है, इसलिए यह **`1.0` से नीचे** रहता है:

```
0.0.x  pre-alpha    the first, un-public pre-alpha iterations (0.0.4 .. 0.0.9).
0.x    alpha        ← we are here (0.5.0). Public, working, honestly-labelled — open
                     to feedback, but not yet consolidated (each cycle is still an
                     "honest about every limit, not finished" release, per the README
                     header — see it for the current cycle's exact status).
0.x    beta         once things consolidate (a deliberate, later maintainer call —
                     not implied by any particular `0.x` number crossing over from alpha).
1.0    release      an official, stable release.
```

हम ऐसी संस्करण संख्या पर **नहीं** कूदेंगे जो मौजूद से अधिक परिपक्वता का संकेत दे (उदाहरण के लिए,
`0.2` का अर्थ "20% पूरा" या "बीटा के क़रीब" नहीं है — यह अब तक के अल्फ़ा चक्रों की ईमानदार गिनती
है)। हर चक्र एक छोटा, वास्तविक पुनरावर्तन है — इससे अधिक का दावा नहीं किया जाता।

### चक्र ↔ संस्करण मानचित्रण

ऊपर के सेवानिवृत्त संख्यांकित शाखा-नामों में से किसी पर नहीं।

### यह क्यों मायने रखता है (मूल्यों से जुड़ाव)

को बढ़ा-चढ़ाकर बताए, वह इसका जड़ से खंडन करेगा। संयमित संस्करण-निर्धारण वही अनुशासन है जो बाक़ी
कोडबेस में है: **केवल वही दावा करो जो वास्तविक है, और उसे सिद्ध करो।**
