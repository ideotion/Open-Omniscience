# Участие в разработке

Спасибо за помощь. Руководящий принцип — **честность**: функция должна делать то, что заявлено,
иначе она не выпускается. Никаких сфабрикованных результатов, никаких поддельных оценок
уверенности, никакой скрытой деградации — см. [DESIGN.md](DESIGN.md) §3.

## Настройка

```bash
python3.13 -m venv .venv && . .venv/bin/activate
pip install -e ".[analysis,dev]"
pytest -q          # full suite, a few minutes
```

`pyproject.toml` остаётся единственным источником истины для зависимостей (мы устанавливаем
последние версии в пределах минимальных границ, чтобы CI рано замечал поломки в upstream). Для
**воспроизводимой установки / установки релиза** существует закреплённый по хешам lock-файл,
построенный на его основе:

```bash
pip install -r requirements.lock          # exact, hash-verified core + analysis pins
# regenerate after a dependency change:
pip-compile --generate-hashes --extra analysis -o requirements.lock pyproject.toml
```

**Это встроено в `./install.sh`, а не просто команда, которую нужно запускать вручную.** Путь
онлайн-установки (`pip_install()`) автоматически использует `requirements.lock`, если он
присутствует, был сгенерирован для используемой вами версии Python и покрывает все запрошенные
компоненты (`OO_COMPONENTS`) — это проверяется по собственному заголовку lock-файла
`pip-compile ... --extra=...`, а не поддерживается вручную. Если какое-либо из этих условий не
выполняется (lock-файл устарел для вашего Python, запрошен компонент, с которым lock-файл не
генерировался, или закреплённая версия не разрешается на этой платформе), установка
возвращается к обычному разрешению по минимальным границам `pip install -e ".[...]"` с заметным
сообщением о том, почему проверенный путь не был использован, — `OO_USE_LOCK=0` безусловно
отключает lock-файл. **В поставляемом виде lock-файл покрывает только `--extra analysis`**,
тогда как набор компонентов по умолчанию в самом `install.sh` — `analysis,compression,columnar`,
поэтому стандартный автоматический запуск `./install.sh` сегодня возвращается к разрешению по
минимальным границам (compression/columnar не входят в покрытие lock-файла). Запустите
`OO_COMPONENTS=analysis ./install.sh`, чтобы пройти проверенный путь в нынешнем виде, или
расширьте покрытие lock-файла с помощью `pip-compile --extra analysis --extra compression --extra
columnar ...`, чтобы и путь установки по умолчанию опирался на lock-файл.

**Офлайн-пакет для изолированных систем** (`scripts/build_offline_bundle.sh`, используемый
офлайн-путём `--no-index` в `install.sh` для целевых систем Qubes/Tails) **пока не связан с
lock-файлом** — при каждой сборке он заново разрешает зависимости по минимальным границам из
`pyproject.toml`. Это известный открытый пробел, а не недосмотр: перевод офлайн-пакета на
lock-файл (`pip download --require-hashes -r requirements.lock`, с сохранением разрешения на
основе `$SPEC` как запасного варианта для дополнений, которые lock-файл не покрывает)
отслеживается как последующая работа.

## Рабочий процесс

- **Python 3.13**, единственный `pyproject.toml` (без requirements.txt).
- Линтинг/форматирование — **ruff**; проверка типов — **mypy**: `make lint && make typecheck`.
- Каждое изменение завершается зелёным: `make check` (ruff + pytest). Добавляйте поведенческий
  тест для нового поведения; исправляйте или помещайте в карантин — не оставляйте наполовину
  работающий код на пути импорта.
- Делайте коммиты небольшими честными шагами, с сообщениями, которые объясняют, *что и зачем*.
- Изменения схемы проходят через Alembic (`alembic revision --autogenerate`); CI запускает
  `alembic check`, чтобы выявлять расхождения между моделью и миграциями.

## Журнал выпущенного: один файл на строку

Не дописывайте строки в `docs/ledger/shipped.csv`. Проверка слияния GitHub игнорирует правило
`merge=union` для этого файла, поэтому строка, добавляемая каждым PR, приводила к конфликту у
каждого открытого PR после каждого слияния. Вместо этого добавьте ОДИН новый файл:

    python scripts/ledger_shipped.py new --date 2026-09-30 --area tests --item "..." \
        --status "shipped (draft)" --refs "PR #1240" --key-paths "src/a.py; tests/b.py" --summary "..."

Команда записывает `docs/ledger/shipped.d/<date>-<slug>.csv` (заголовок журнала плюс одна
строка). Ни один другой PR не может конфликтовать с файлом, которого он не касается.
`python scripts/ledger_shipped.py check` проверяет каждый фрагмент; примечания к релизу и тесты
инвариантов репозитория читают сначала `shipped.csv`, а затем фрагменты.
`ledger_shipped.py fold` дописывает фрагменты в `shipped.csv` в двоичном режиме и удаляет их; эта
команда предназначена для сопровождающего или для релиза, но никогда для PR с новой функцией.
`refs` должно содержать реальный номер PR, а не `PR pending` (иначе тест проваливается).

## Уроки и записи журнала выпущенного: по одному файлу

То же соглашение распространяется на два больших архива. Урок — это ОДИН файл,
`docs/ledger/lessons.d/<date>-<slug>.md` (`python scripts/lessons.py --new SLUG`); дословная
запись журнала выпущенного — ОДИН файл, `docs/ledger/shipped_log.d/<date>-<slug>.md`
(`python scripts/ledger_fold.py new-log SLUG`). Никогда не дописывайте в `LESSONS.md` или
`SHIPPED_LOG.md` и никогда не изменяйте `_LESSONS_LINE_CEILING`: каждый PR, делавший это,
конфликтовал со всеми остальными. Фрагмент начинается с `## <date> — title`, заканчивается
переводом строки и записан в UTF-8 с окончаниями строк LF; урок (в отличие от записи журнала
выпущенного) не содержит второго заголовка и остаётся короче 200 строк (это ограничивает размер
одной записи); `python scripts/ledger_fold.py check` (и `tests/test_ledger_fragments.py`)
проверяет его, отклоняет заполнители `#NNNN` и `PR pending`, а `lessons.py <words>` ищет также и
по фрагментам. `ledger_fold.py fold` объединяет их с архивами при релизе и никогда не
предназначен для PR с новой функцией.

## Файлы локализации и конфликты слияния

12 файлов `src/static/locales/*.json` хранятся **отсортированными** (сначала `_meta`, затем ключи в порядке кодовых точек), поэтому два PR, добавляющие строки, вставляют их в разные места и сливаются без конфликтов. После добавления строк запустите `python scripts/locales_merge.py`; он сортирует файлы и проверяет их (`--check` только проверяет; `tests/test_locales_merge.py` проваливается на неотсортированных или повторяющихся ключах).

Если `git merge origin/main` оставляет маркеры конфликтов в файлах локализации, запустите тот же скрипт: он сохраняет обе стороны каждого фрагмента, сортирует и останавливается, называя ключ, если обе стороны дали одному ключу разный текст (настоящее противоречие, которое нужно разрешить). Для `docs/ledger/shipped.csv` в `.gitattributes` задано `merge=union`, что учитывает локальный `git merge`, но не учитывают веб-слияние GitHub и кнопка обновления ветки: выполните слияние main локально, а затем проверьте, нет ли повторяющихся строк `(date, area, item)`.

## Стандарты

- Происхождение везде: хранимые данные содержат источник + отметку времени + хеш.
- Любое число, показанное пользователю, должно получаться реальным методом с указанной
  неопределённостью (`src/analysis`), а не быть константой.
- Сбор данных проходит через единый этичный загрузчик (robots с закрытием при сбое, с
  ограничением частоты).
- Сфабрикованному/мёртвому коду место в `quarantine/` (с документацией), а не в `src/`.

## Политика версионирования

> **Мы намеренно преуменьшаем зрелость. Честность важнее шумихи.** Лучше, чтобы пользователь
> был приятно удивлён, чем введён в заблуждение. Номер версии — это обещание о *зрелости*, и мы
> держим это обещание консервативным.

### Единственный источник истины

Версия хранится в **одном месте: `pyproject.toml` (`[project] version`)**. Всё остальное
выводится из неё:

- Работающее приложение читает её из метаданных установленного пакета
  (`importlib.metadata.version("open-omniscience")`), поэтому `/api/health`, параметр API
  `version=` и интерфейс автоматически сообщают *реальную* установленную версию.
- Никакой другой код не содержит жёстко заданной строки версии. Тесты сверяются с метаданными
  пакета, а не со строкой (см. `tests/test_api_search.py`).
- `README.md` в корне репозитория указывает версию один раз, в своём заголовке, а проверка CI
  убеждается, что она совпадает с пакетом
  (`tests/test_repo_invariants.py::test_readme_version_matches_package`).

**Чтобы повысить версию, измените только `pyproject.toml`**, обновите заголовок README
соответственно (проверка это обеспечивает), а затем выполните `pip install -e .`, чтобы
обновились метаданные.

**Ставьте тег `vX.Y.Z` только на коммит, в котором `pyproject.toml` уже содержит `X.Y.Z`.**
Workflow релиза (`.github/workflows/release.yml`) отклоняет любой другой тег до начала сборки,
поэтому тег, поставленный раньше повышения версии, публикует релиз без wheel, sdist и
контрольных сумм. Первый `v0.4.0` был поставлен именно так 2026-09-28; версия была выставлена
позже, и тег перенесли на неё (`docs/product/RELEASE_0.4_GATE.md`, строка G). **Для переноса тега
нужен git:** веб-сайт GitHub не может ни удалить, ни перенести тег, а релиз, опубликованный там,
повторно использует существующий тег, не запуская workflow. Если нет локального клона с правом
push, откройте Codespace на `main` и выполните
`git fetch origin && git tag -f vX.Y.Z origin/main && git push -f origin vX.Y.Z`. Сначала удалите
релиз на GitHub, если workflow должен записать сгенерированные примечания: он сохраняет
примечания существующего релиза и лишь добавляет файлы и контрольные суммы.

### Лестница зрелости (где мы сейчас и куда движемся)

Программа молода и всё ещё проходит проверку, поэтому она остаётся **ниже `1.0`**:

```
0.0.x  pre-alpha    the first, un-public pre-alpha iterations (0.0.4 .. 0.0.9).
0.x    alpha        ← we are here (0.5.0). Public, working, honestly-labelled — open
                     to feedback, but not yet consolidated (each cycle is still an
                     "honest about every limit, not finished" release, per the README
                     header — see it for the current cycle's exact status).
0.x    beta         once things consolidate (a deliberate, later maintainer call —
                     not implied by any particular `0.x` number crossing over from alpha).
1.0    release      an official, stable release.
```

Мы **не** будем перескакивать на номер версии, подразумевающий большую зрелость, чем есть на
самом деле (например, `0.2` не означает «готово на 20%» или «почти бета» — это честный счёт
пройденных альфа-циклов). Каждый цикл — небольшая реальная итерация, и ничего сверх этого не
заявляется.

### Соответствие циклов и версий

Циклы разработки (и их ветки) называются по версии, которую они выпускают, с опущенными для
краткости ведущими нулями:

| Имя ветки / цикла | Версия пакета |
|---|---|
| `0.04` | `0.0.4` |
| `0.05` | `0.0.5` |
| `0.06` | `0.0.6` |
| `0.07` | `0.0.7` |
| `0.08` | `0.0.8` |
| `0.09` | `0.0.9` |
| `0.1`  | `0.1.0` |  (ветка цикла `0.09` была переименована `0.09 → 0.1` при переходе к альфе)
| `0.2`  | `0.2.0` |  (ветка цикла `0.1` была переименована `0.1 → 0.2` при переходе к 0.2)
| `main` | `0.2.0` → `0.3.0` → `0.4.0` → `0.5.0` |  (ветка цикла `0.2` была переименована `0.2 → main` 2026-07-15 — ветка по умолчанию теперь навсегда `main`, а имя ветки и версия независимы; тег `v0.2.0` был поставлен после проверки масштабирования на реальном корпусе, `v0.3.0` завершил цикл «измерено и проверено», `v0.4.0` завершил цикл живых источников, а `main` теперь содержит `0.5.0` — релиз «стол следователя», с тегом `v0.5.0`)

Так, «интеллектуальный слой `0.06`» означает «работу, которая выходит в `0.0.6`». Встречая в
документации сокращённое обозначение цикла вроде `0.05`, читайте его как `0.0.5`. PR вливаются в
`main`, ветку текущего цикла, — а не в какие-либо из выведенных из употребления нумерованных
веток, перечисленных выше.

**Начиная с первой альфы (`0.1.0`), соответствие таково: цикл `0.N` ⇒ `v0.N.0`** — цикл `0.2`
завершился `v0.2.0`, цикл `0.3` — `v0.3.0`, цикл `0.4` — `v0.4.0`, цикл `0.5` — `v0.5.0`
(единственное исключение — объединённый цикл `0.09`, который выпустил `0.1.0`). Цикл называется
по релизу, который его завершает, — файлы критериев релиза говорят об этом своими словами
(`RELEASE_0.4_GATE.md` — это «проверяемый перечень для завершения цикла `0.4`»), — а номер
версии может быть *выставлен* в середине цикла, до тега (например, `0.4.0` был выставлен
2026-09-28, чтобы на него перенести тег; `0.5.0` был выставлен в PR повышения версии, а тег
указывает на его коммит слияния), поэтому дата заголовка в журнале изменений и дата его тега
могут различаться.

### Почему это важно (связь с ценностями)

Этот проект существует, чтобы помогать людям честно видеть информацию. Инструмент, который
преувеличивал бы собственную зрелость, противоречил бы этому в самой основе. Консервативное
версионирование — та же дисциплина, что и во всей остальной кодовой базе: **заявлять только
то, что реально, и доказывать это.**
