# المساهمة

شكرًا لمساعدتك. المبدأ الموجِّه هو **الصدق**: يجب أن تفعل الميزة ما تدّعيه، وإلا فلن تُشحن.
لا مخرجات مختلَقة، ولا درجات ثقة زائفة، ولا تدهور صامت — انظر [DESIGN.md](DESIGN.md) §3.

## الإعداد

```bash
python3.13 -m venv .venv && . .venv/bin/activate
pip install -e ".[analysis,dev]"
pytest -q          # full suite, a few minutes
```

يبقى `pyproject.toml` المصدر الوحيد للحقيقة فيما يخص التبعيات (نثبّت أحدث إصدار ضمن الحدود
الدنيا كي يكتشف التكامل المستمر أعطال المنبع مبكرًا). ومن أجل **تثبيت قابل لإعادة الإنتاج /
تثبيت إصدار** يوجد ملف قفل مثبّت بالتجزئات مشتق منه:

```bash
pip install -r requirements.lock          # exact, hash-verified core + analysis pins
# regenerate after a dependency change:
pip-compile --generate-hashes --extra analysis -o requirements.lock pyproject.toml
```

**هذا موصول في `./install.sh`، وليس مجرد أمر تشغّله يدويًا.** يستخدم مسار التثبيت عبر الإنترنت
(`pip_install()`) الملف `requirements.lock` تلقائيًا متى كان موجودًا، ووُلِّد لإصدار Python
الذي تشغّله، ويغطي كل مكوّن طلبته (`OO_COMPONENTS`) — ويُتحقَّق من ذلك مقابل ترويسة
`pip-compile ... --extra=...` الخاصة بالقفل نفسه، ولا تُصان يدويًا أبدًا. وحين لا يتحقق أيٌّ من
ذلك (القفل قديم بالنسبة إلى Python لديك، أو يطلب مكوّنًا لم يُولَّد القفل به، أو يتعذّر حلّ
تثبيت ما على هذه المنصة) يرجع إلى الحلّ العادي المبني على الحدود الدنيا `pip install -e
".[...]"`، مع رسالة صريحة تقول لماذا لم يُستخدم المسار المُدقَّق — و`OO_USE_LOCK=0` يلغي
استخدام القفل دون شرط. **كما هو مشحون، لا يغطي القفل إلا `--extra analysis`**، بينما مجموعة
المكوّنات الافتراضية في `install.sh` هي `analysis,compression,columnar` — لذا فإن تشغيل
`./install.sh` افتراضيًا ودون إشراف يرجع اليوم إلى الحلّ المبني على الحدود الدنيا (compression/columnar
ليسا ضمن تغطية القفل). شغّل `OO_COMPONENTS=analysis ./install.sh` لتجربة المسار المُدقَّق كما هو
الآن، أو وسّع تغطية القفل بـ `pip-compile --extra analysis --extra compression --extra
columnar ...` ليصبح مسار التثبيت الافتراضي قائمًا على القفل أيضًا.

**الحزمة غير المتصلة/المعزولة عن الشبكة** (`scripts/build_offline_bundle.sh`، التي يستهلكها
مسار `install.sh` غير المتصل `--no-index` لهدف Qubes/Tails) **ليست موصولة بالقفل بعد** — فهي
لا تزال تُحَلّ من جديد من الحدود الدنيا في `pyproject.toml` في كل مرة تُبنى فيها. هذه فجوة
معروفة ومفتوحة، لا سهو: جعل الحزمة غير المتصلة قائمة على القفل أيضًا
(`pip download --require-hashes -r requirements.lock`، مع إبقاء الحلّ القائم على `$SPEC`
احتياطًا لأي إضافات لا يغطيها القفل) مُدرَج كعمل لاحق.

## سير العمل

- **Python 3.13**، وملف `pyproject.toml` واحد (لا requirements.txt).
- التدقيق/التنسيق بـ **ruff**؛ وفحص الأنواع بـ **mypy**: `make lint && make typecheck`.
- كل تغيير ينتهي أخضر: `make check` (ruff + pytest). أضف اختبارًا سلوكيًا لكل سلوك جديد؛
  أصلِح أو اعزِل — لا تترك شيفرة نصف عاملة في مسار الاستيراد.
- التزم (commit) بزيادات صغيرة وصادقة برسائل تقول *ماذا ولماذا*.
- تغييرات المخطط تمر عبر Alembic (`alembic revision --autogenerate`)؛ ويشغّل التكامل المستمر
  `alembic check` لاكتشاف انحراف النموذج/الترحيل.

## سجل الشحن: ملف واحد لكل صف

لا تُلحِق بـ `docs/ledger/shipped.csv`. فحص الدمج في GitHub يتجاهل قاعدة `merge=union` الخاصة
بالملف، لذا كان الصف الذي يُلحقه كل طلب سحب يجعل كل طلب سحب مفتوح يتعارض بعد كل دمج.
أضف ملفًا جديدًا واحدًا بدلًا من ذلك:

    python scripts/ledger_shipped.py new --date 2026-09-30 --area tests --item "..." \
        --status "shipped (draft)" --refs "PR #1240" --key-paths "src/a.py; tests/b.py" --summary "..."

يكتب `docs/ledger/shipped.d/<date>-<slug>.csv` (ترويسة السجل مع صف واحد). لا يمكن لأي طلب سحب
آخر أن يتعارض مع ملف لا يلمسه. يتحقق `python scripts/ledger_shipped.py check` من كل جزء؛ وتقرأ
ملاحظات الإصدار واختبارات ثوابت المستودع `shipped.csv` أولًا ثم الأجزاء بعده. يُلحِق
`ledger_shipped.py fold` الأجزاء بـ `shipped.csv` بالصيغة الثنائية ويحذفها؛ وهو للمشرف أو
للإصدار، لا لطلب سحب ميزة أبدًا. يجب أن يكون `refs` رقم طلب السحب الحقيقي، لا `PR pending`
(يفشل اختبار عند وجوده).

## الدروس ومدخلات سجل الشحن: ملف لكل منها

الاصطلاح نفسه يشمل الأرشيفين الكبيرين. الدرس ملف واحد،
`docs/ledger/lessons.d/<date>-<slug>.md` (`python scripts/lessons.py --new SLUG`)؛ ومُدخل سجل
الشحن الحرفي ملف واحد، `docs/ledger/shipped_log.d/<date>-<slug>.md`
(`python scripts/ledger_fold.py new-log SLUG`). لا تُلحِق أبدًا بـ `LESSONS.md` أو `SHIPPED_LOG.md`
ولا تعدّل أبدًا `_LESSONS_LINE_CEILING`: كل طلب سحب فعل ذلك تعارض مع كل طلب آخر. يبدأ الجزء
بـ `## <date> — title`، وينتهي بسطر جديد، ويكون بترميز UTF-8 بنهايات أسطر LF؛ والدرس (لا مُدخل
سجل الشحن) لا يحوي عنوانًا ثانيًا ويبقى دون 200 سطر (وهذا يحدّ حجم المُدخل الواحد)؛ يتحقق منه
`python scripts/ledger_fold.py check` (و`tests/test_ledger_fragments.py`)، ويرفض العناصر النائبة
`#NNNN` و`PR pending`، ويبحث `lessons.py <words>` في الأجزاء أيضًا.
يدمج `ledger_fold.py fold` الأجزاء في الأرشيفين عند الإصدار، وليس لطلب سحب ميزة أبدًا.

## ملفات اللغات وتعارضات الدمج

تُبقى ملفات `src/static/locales/*.json` الاثنا عشر **مرتّبة** (`_meta` أولًا، ثم المفاتيح بترتيب نقاط الترميز)، بحيث إن طلبَي سحب يضيفان نصوصًا يُدرجانها في مواضع مختلفة فيندمجان بسلاسة. بعد إضافة نصوص، شغّل `python scripts/locales_merge.py`؛ فهو يرتّب الملفات ويفحصها (`--check` يتحقق فقط؛ ويفشل `tests/test_locales_merge.py` عند وجود مفاتيح غير مرتّبة أو مكرّرة).

إن ترك `git merge origin/main` علامات تعارض في ملفات اللغات، فشغّل السكربت نفسه: يُبقي الجانبين من كل قطعة، ويرتّب، ويتوقف مسمّيًا المفتاح إن أعطى الجانبان للمفتاح نفسه نصًا مختلفًا (تناقض حقيقي يجب الحسم فيه). الملف `docs/ledger/shipped.csv` هو `merge=union` في `.gitattributes`، وهو ما يحترمه `git merge` المحلي لكن لا يحترمه الدمج عبر موقع GitHub ولا زر تحديث الفرع: ادمج main محليًا، ثم افحص وجود صفوف `(date, area, item)` مكرّرة.

## سياسة الإصدارات

> **نحن نقلّل عمدًا من تقدير النضج. الصدق قبل الضجيج.** من الأفضل أن يُفاجأ المستخدم
> مفاجأة سارّة على أن يُضلَّل. رقم الإصدار وعدٌ بشأن *النضج*، ونحن نُبقي هذا الوعد متحفّظًا.

### المصدر الوحيد للحقيقة

يعيش الإصدار في **مكان واحد: `pyproject.toml` (`[project] version`)**. وكل ما عداه مشتق منه:

- يقرؤه التطبيق العامل من بيانات وصف الحزمة المثبّتة
  (`importlib.metadata.version("open-omniscience")`) — لذا فإن `/api/health`، و`version=` في
  الواجهة البرمجية، وواجهة المستخدم كلها تُبلغ تلقائيًا عن الإصدار المثبّت *الحقيقي*.
- لا شيفرة أخرى تكتب رقم إصدار حرفيًا. تتحقق الاختبارات مقابل بيانات وصف الحزمة، لا مقابل
  سلسلة نصية (انظر `tests/test_api_search.py`).
- يذكر `README.md` في جذر المستودع الإصدار مرة واحدة، في ترويسته، ويتحقق حارس في التكامل
  المستمر من مطابقته للحزمة (`tests/test_repo_invariants.py::test_readme_version_matches_package`).

**لرفع الإصدار، غيّر `pyproject.toml` فقط**، وحدّث ترويسة README لتطابقه (الحارس يفرض ذلك)،
ثم شغّل `pip install -e .` لتتجدّد بيانات الوصف.

**ضع الوسم `vX.Y.Z` فقط على التزام يقرأ فيه `pyproject.toml` أصلًا `X.Y.Z`.** يرفض سير عمل
الإصدار (`.github/workflows/release.yml`) أي وسم آخر قبل أن يبني أي شيء، لذا فإن وسمًا يُقطع قبل
رفع إصداره ينشر إصدارًا بلا wheel ولا sdist ولا مجاميع تحقق. قُطع أول `v0.4.0` بهذه الطريقة في
2026-09-28؛ وضُبط الإصدار بعد ذلك ونُقل الوسم إليه (`docs/product/RELEASE_0.4_GATE.md` الصف G).
**نقل الوسم يتطلب git:** لا يستطيع موقع GitHub حذف وسم ولا نقله، والإصدار المنشور هناك يعيد
استخدام الوسم الموجود دون تشغيل سير العمل. وإن لم تكن لديك نسخة محلية قادرة على الدفع، فافتح
Codespace على `main` وشغّل
`git fetch origin && git tag -f vX.Y.Z origin/main && git push -f origin vX.Y.Z`. احذف إصدار GitHub
أولًا إن كان على سير العمل أن يكتب الملاحظات المولّدة: فهو يُبقي ملاحظات الإصدار الموجود ولا
يضيف إلا الملفات ومجاميع التحقق.

### سُلّم النضج (أين نحن، وإلى أين نتجه)

البرنامج حديث ولا يزال قيد الإثبات، لذا يبقى **دون `1.0`**:

```
0.0.x  pre-alpha    the first, un-public pre-alpha iterations (0.0.4 .. 0.0.9).
0.x    alpha        ← we are here (0.5.0). Public, working, honestly-labelled — open
                     to feedback, but not yet consolidated (each cycle is still an
                     "honest about every limit, not finished" release, per the README
                     header — see it for the current cycle's exact status).
0.x    beta         once things consolidate (a deliberate, later maintainer call —
                     not implied by any particular `0.x` number crossing over from alpha).
1.0    release      an official, stable release.
```

**لن** نقفز إلى رقم إصدار يوحي بنضج أكبر مما هو موجود (مثلًا،
`0.2` لا يعني "20% مُنجَز" ولا "قريب من بيتا" — إنه العدّ الصادق لدورات ألفا حتى الآن). كل
دورة تكرار صغير وحقيقي — ولا يُدّعى أكثر من ذلك.

### تقابل الدورة ↔ الإصدار

تُسمّى دورات التطوير (وفروعها) باسم الإصدار الذي تنتجه، مع حذف الأصفار البادئة للإيجاز:

| اسم الفرع / الدورة | إصدار الحزمة |
|---|---|
| `0.04` | `0.0.4` |
| `0.05` | `0.0.5` |
| `0.06` | `0.0.6` |
| `0.07` | `0.0.7` |
| `0.08` | `0.0.8` |
| `0.09` | `0.0.9` |
| `0.1`  | `0.1.0` |  (أُعيدت تسمية فرع دورة `0.09` (`0.09 → 0.1`) عند الانتقال إلى ألفا)
| `0.2`  | `0.2.0` |  (أُعيدت تسمية فرع دورة `0.1` (`0.1 → 0.2`) عند الانتقال إلى 0.2)
| `main` | `0.2.0` → `0.3.0` → `0.4.0` → `0.5.0` |  (أُعيدت تسمية فرع دورة `0.2` (`0.2 → main`) في 2026-07-15 — الفرع الافتراضي الآن `main` بشكل دائم، واسم الفرع ورقم الإصدار مستقلان؛ وُسم `v0.2.0` بعد التحقق من التوسّع على مجموعة نصية حية، وأغلق `v0.3.0` دورة القياس والتحقق، وأغلق `v0.4.0` دورة المصادر الحية، و`main` يقرأ الآن `0.5.0`، إصدار مكتب المحقّق، الموسوم `v0.5.0`)

لذا فإن "طبقة الذكاء في `0.06`" تعني "العمل الذي يُشحن في `0.0.6`". حين تقرأ اختصار دورة مثل
`0.05` في الوثائق، اقرأه `0.0.5`. تُدمج طلبات السحب في `main`، فرع الدورة الحالية — لا في أيٍّ من
أسماء الفروع المرقّمة المتقاعدة أعلاه.

**منذ أول ألفا (`0.1.0`)، التقابل هو دورة `0.N` ⇒ `v0.N.0`** — أُغلقت دورة `0.2` بـ `v0.2.0`،
ودورة `0.3` بـ `v0.3.0`، ودورة `0.4` بـ `v0.4.0`، ودورة `0.5` بـ `v0.5.0`
(الاستثناء الوحيد هو دورة `0.09` المدمجة، التي أنتجت `0.1.0`). تُسمّى الدورة باسم الإصدار الذي
يغلقها — وتقول ملفات بوابة الإصدار ذلك بكلماتها
(`RELEASE_0.4_GATE.md` هو "the checkable inventory for closing the `0.4` cycle") — وقد *يُضبط*
رقم الإصدار في منتصف الدورة قبل الوسم (مثلًا ضُبط `0.4.0` في 2026-09-28، كي يُنقل الوسم إليه؛
وضُبط `0.5.0` في طلب سحب الانتقال، والوسم يسمّي التزام دمجه)، ولهذا قد يختلف تاريخ عنوان سجل
التغييرات عن تاريخ وسمه.
