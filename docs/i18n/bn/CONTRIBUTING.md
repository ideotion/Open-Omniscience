# অবদান রাখা

সাহায্যের জন্য ধন্যবাদ। পথনির্দেশক নীতি হলো **সততা**: একটি ফিচার যা দাবি করে তা-ই করতে হবে,
নইলে তা শিপ হয় না। কোনো বানানো আউটপুট নয়, কোনো নকল আস্থা-স্কোর নয়, কোনো নীরব অবনতি নয় — দেখুন
[DESIGN.md](DESIGN.md) §3।

## সেটআপ

```bash
python3.13 -m venv .venv && . .venv/bin/activate
pip install -e ".[analysis,dev]"
pytest -q          # full suite, a few minutes
```

নির্ভরতার ক্ষেত্রে `pyproject.toml`-ই সত্যের একমাত্র উৎস থাকে (আমরা ন্যূনতম সীমার মধ্যে সর্বশেষ
সংস্করণ ইনস্টল করি, যাতে CI আপস্ট্রিমের ভাঙন আগেভাগে ধরে)। **পুনরুৎপাদনযোগ্য / রিলিজ ইনস্টলের**
জন্য এটি থেকে তৈরি একটি হ্যাশ-পিন করা লক আছে:

```bash
pip install -r requirements.lock          # exact, hash-verified core + analysis pins
# regenerate after a dependency change:
pip-compile --generate-hashes --extra analysis -o requirements.lock pyproject.toml
```

**এটি `./install.sh`-এ সংযুক্ত, শুধু হাতে চালানোর একটি কমান্ড নয়।** অনলাইন ইনস্টল পথ
(`pip_install()`) স্বয়ংক্রিয়ভাবে `requirements.lock` ব্যবহার করে যখনই সেটি উপস্থিত থাকে, আপনি যে
Python চালাচ্ছেন তার জন্য তৈরি হয়ে থাকে, এবং আপনার চাওয়া প্রতিটি উপাদান (`OO_COMPONENTS`) কভার
করে — লকের নিজস্ব `pip-compile ... --extra=...` হেডারের সঙ্গে মিলিয়ে যাচাই করা হয়, কখনো হাতে
রক্ষণাবেক্ষণ করা হয় না। এর কোনোটি সত্য না হলে (লকটি আপনার Python-এর জন্য পুরোনো, বা এমন উপাদান
চাওয়া হয়েছে যা দিয়ে লক তৈরি হয়নি, বা কোনো পিন এই প্ল্যাটফর্মে সমাধান হয় না) এটি সাধারণ,
ন্যূনতম-সীমাভিত্তিক `pip install -e ".[...]"` সমাধানে ফিরে যায়, একটি স্পষ্ট বার্তাসহ যে নিরীক্ষিত
পথ কেন ব্যবহৃত হয়নি — `OO_USE_LOCK=0` নিঃশর্তভাবে লক থেকে বেরিয়ে আসে। **যেমন শিপ করা হয়েছে, লক
কেবল `--extra analysis` কভার করে**, অথচ `install.sh`-এর নিজস্ব ডিফল্ট উপাদান-সমষ্টি হলো
`analysis,compression,columnar` — তাই একটি ডিফল্ট, তত্ত্বাবধানহীন `./install.sh` চালানো আজ
ন্যূনতম-সীমাভিত্তিক সমাধানে ফিরে যায় (compression/columnar লকের কভারেজে নেই)। নিরীক্ষিত পথটি
বর্তমান অবস্থায় চালিয়ে দেখতে `OO_COMPONENTS=analysis ./install.sh` চালান, অথবা ডিফল্ট ইনস্টল
পথকেও লকভিত্তিক করতে `pip-compile --extra analysis --extra compression --extra columnar ...` দিয়ে
লকের কভারেজ বাড়ান।

**অফলাইন/এয়ার-গ্যাপড বান্ডল** (`scripts/build_offline_bundle.sh`, যা Qubes/Tails লক্ষ্যের জন্য
`install.sh`-এর `--no-index` অফলাইন পথ ব্যবহার করে) **এখনো লকের সঙ্গে সংযুক্ত নয়** — প্রতিবার
তৈরির সময় এটি `pyproject.toml`-এর ন্যূনতম সীমা থেকে নতুন করে সমাধান হয়। এটি একটি জানা, খোলা
ফাঁক, অবহেলা নয়: অফলাইন বান্ডলকেও লকভিত্তিক করা
(`pip download --require-hashes -r requirements.lock`, লক যেসব extras কভার করে না সেগুলোর জন্য
`$SPEC`-ভিত্তিক সমাধান বিকল্প হিসেবে রেখে) পরবর্তী কাজ হিসেবে তালিকাভুক্ত।

## কর্মপ্রবাহ

- **Python 3.13**, একটিমাত্র `pyproject.toml` (কোনো requirements.txt নয়)।
- **ruff** দিয়ে লিন্ট/ফরম্যাট; **mypy** দিয়ে টাইপ-যাচাই: `make lint && make typecheck`।
- প্রতিটি পরিবর্তন সবুজে শেষ হয়: `make check` (ruff + pytest)। নতুন আচরণের জন্য একটি আচরণগত
  পরীক্ষা যোগ করুন; ঠিক করুন বা কোয়ারান্টাইন করুন — ইমপোর্ট পথে আধা-কার্যকর কোড রেখে যাবেন না।
- ছোট, সৎ ধাপে কমিট করুন, এমন বার্তাসহ যা *কী ও কেন* বলে।
- স্কিমা পরিবর্তন Alembic-এর মধ্য দিয়ে যায় (`alembic revision --autogenerate`); মডেল/মাইগ্রেশনের
  বিচ্যুতি ধরতে CI `alembic check` চালায়।

## শিপড লেজার: প্রতি সারিতে একটি ফাইল

`docs/ledger/shipped.csv`-এ যোগ (append) করবেন না। GitHub-এর মার্জ-যাচাই ফাইলটির `merge=union`
নিয়ম উপেক্ষা করে, তাই প্রতিটি PR-এর যোগ করা সারি প্রতিটি মার্জের পরে প্রতিটি খোলা PR-এ সংঘাত
সৃষ্টি করত। এর বদলে একটি নতুন ফাইল যোগ করুন:

    python scripts/ledger_shipped.py new --date 2026-09-30 --area tests --item "..." \
        --status "shipped (draft)" --refs "PR #1240" --key-paths "src/a.py; tests/b.py" --summary "..."

এটি `docs/ledger/shipped.d/<date>-<slug>.csv` লেখে (লেজারের হেডার এবং একটি সারি)। কোনো PR যে
ফাইল ছোঁয় না, অন্য কোনো PR তার সঙ্গে সংঘাতে যেতে পারে না। `python scripts/ledger_shipped.py check`
প্রতিটি খণ্ড (fragment) যাচাই করে; রিলিজ নোট ও রিপো-ইনভ্যারিয়েন্ট পরীক্ষাগুলো আগে `shipped.csv`
পড়ে এবং তারপর খণ্ডগুলো। `ledger_shipped.py fold` খণ্ডগুলো বাইনারিতে `shipped.csv`-এ যোগ করে এবং
সেগুলো মুছে দেয়; এটি রক্ষণাবেক্ষণকারী বা রিলিজের জন্য, কখনো ফিচার PR-এর জন্য নয়। `refs` অবশ্যই
আসল PR নম্বর হতে হবে, `PR pending` নয় (এতে একটি পরীক্ষা ব্যর্থ হয়)।

## শিক্ষা ও শিপড-লগ এন্ট্রি: প্রতিটির জন্য একটি ফাইল

একই রীতি দুটি বড় আর্কাইভেও প্রযোজ্য। একটি শিক্ষা একটি ফাইল,
`docs/ledger/lessons.d/<date>-<slug>.md` (`python scripts/lessons.py --new SLUG`); একটি হুবহু
শিপড-লগ এন্ট্রি একটি ফাইল, `docs/ledger/shipped_log.d/<date>-<slug>.md`
(`python scripts/ledger_fold.py new-log SLUG`)। কখনো `LESSONS.md` বা `SHIPPED_LOG.md`-এ যোগ করবেন
না এবং কখনো `_LESSONS_LINE_CEILING` সম্পাদনা করবেন না: যে PR-ই তা করেছে, সেটি অন্য প্রতিটির সঙ্গে
সংঘাতে গেছে। একটি খণ্ড `## <date> — title` দিয়ে শুরু হয়, একটি newline দিয়ে শেষ হয় এবং LF লাইন-
সমাপ্তিসহ UTF-8 হয়; একটি শিক্ষায় (শিপড-লগ এন্ট্রিতে নয়) দ্বিতীয় কোনো শিরোনাম থাকে না এবং তা ২০০
লাইনের কম থাকে (এটি একটি এন্ট্রির আকার সীমিত করে); `python scripts/ledger_fold.py check` (এবং
`tests/test_ledger_fragments.py`) এটি যাচাই করে, `#NNNN` ও `PR pending` স্থানধারক প্রত্যাখ্যান করে,
এবং `lessons.py <words>` খণ্ডগুলোতেও অনুসন্ধান করে।
`ledger_fold.py fold` রিলিজের সময় খণ্ডগুলো আর্কাইভে মিশিয়ে দেয় এবং কখনো ফিচার PR-এর জন্য নয়।

## লোকেল ফাইল ও মার্জ সংঘাত

১২টি `src/static/locales/*.json` ফাইল **সাজানো** রাখা হয় (প্রথমে `_meta`, তারপর কোড-পয়েন্ট ক্রমে কী), যাতে স্ট্রিং যোগ করা দুটি PR ভিন্ন ভিন্ন জায়গায় ঢোকায় এবং পরিচ্ছন্নভাবে মার্জ হয়। স্ট্রিং যোগ করার পরে `python scripts/locales_merge.py` চালান; এটি ফাইলগুলো সাজায় ও যাচাই করে (`--check` কেবল যাচাই করে; `tests/test_locales_merge.py` অসাজানো বা পুনরাবৃত্ত কী থাকলে ব্যর্থ হয়)।

যদি `git merge origin/main` লোকেল ফাইলে সংঘাত-চিহ্ন রেখে যায়, একই স্ক্রিপ্ট চালান: এটি প্রতিটি হাঙ্কের দুই পক্ষই রাখে, সাজায়, এবং দুই পক্ষ একই কী-কে ভিন্ন পাঠ্য দিলে সেই কী-এর নাম বলে থেমে যায় (সিদ্ধান্ত নেওয়ার মতো একটি প্রকৃত বৈপরীত্য)। `.gitattributes`-এ `docs/ledger/shipped.csv` হলো `merge=union`, যা লোকাল `git merge` মানে কিন্তু GitHub-এর ওয়েব মার্জ ও update-branch বোতাম মানে না: main লোকালি মার্জ করুন, তারপর পুনরাবৃত্ত `(date, area, item)` সারি আছে কি না যাচাই করুন।

## সংস্করণ নীতি

> **আমরা ইচ্ছাকৃতভাবে পরিপক্বতাকে কম করে বলি। প্রচারের চেয়ে সততা।** একজন ব্যবহারকারী বিভ্রান্ত
> হওয়ার চেয়ে আনন্দিতভাবে বিস্মিত হওয়া ভালো। সংস্করণ নম্বর হলো *পরিপক্বতা* সম্পর্কে একটি
> প্রতিশ্রুতি, এবং আমরা সেই প্রতিশ্রুতি সংযত রাখি।

### সত্যের একমাত্র উৎস

সংস্করণ থাকে **একটি জায়গায়: `pyproject.toml` (`[project] version`)**। বাকি সবকিছু এটি থেকেই আসে:

- চলমান অ্যাপ এটি ইনস্টল করা প্যাকেজ মেটাডেটা থেকে পড়ে
  (`importlib.metadata.version("open-omniscience")`) — তাই `/api/health`, API-এর `version=`, এবং
  UI সবাই স্বয়ংক্রিয়ভাবে *আসল* ইনস্টল করা সংস্করণ জানায়।
- অন্য কোনো কোড সংস্করণের আক্ষরিক মান হার্ডকোড করে না। পরীক্ষাগুলো প্যাকেজ মেটাডেটার বিপরীতে যাচাই
  করে, কোনো স্ট্রিংয়ের বিপরীতে নয় (দেখুন `tests/test_api_search.py`)।
- রিপো-রুটের `README.md` তার হেডারে একবার সংস্করণ উল্লেখ করে, এবং একটি CI প্রহরী যাচাই করে যে তা
  প্যাকেজের সঙ্গে মেলে (`tests/test_repo_invariants.py::test_readme_version_matches_package`)।

**সংস্করণ বাড়াতে কেবল `pyproject.toml` বদলান**, মিল রাখতে README হেডার হালনাগাদ করুন (প্রহরী এটি
প্রয়োগ করে), তারপর `pip install -e .` চালান যাতে মেটাডেটা নতুন হয়।

**`vX.Y.Z` ট্যাগ কেবল সেই কমিটে দিন যার `pyproject.toml` আগে থেকেই `X.Y.Z` পড়ে।** রিলিজ
ওয়ার্কফ্লো (`.github/workflows/release.yml`) কিছু তৈরির আগেই অন্য যেকোনো ট্যাগ প্রত্যাখ্যান করে,
তাই সংস্করণ বাড়ানোর আগে কাটা ট্যাগ wheel, sdist বা checksum ছাড়াই একটি রিলিজ প্রকাশ করে। প্রথম
`v0.4.0` এভাবেই 2026-09-28-এ কাটা হয়েছিল; সংস্করণ পরে নির্ধারণ করা হয় এবং ট্যাগটি সেখানে সরানো
হয় (`docs/product/RELEASE_0.4_GATE.md` সারি G)। **ট্যাগ সরাতে git লাগে:** GitHub-এর ওয়েবসাইট
ট্যাগ মুছতেও পারে না, সরাতেও পারে না, এবং সেখানে প্রকাশিত রিলিজ ওয়ার্কফ্লো শুরু না করেই বিদ্যমান
ট্যাগ আবার ব্যবহার করে। push করতে পারে এমন লোকাল ক্লোন না থাকলে, `main`-এ একটি Codespace খুলুন
এবং চালান
`git fetch origin && git tag -f vX.Y.Z origin/main && git push -f origin vX.Y.Z`। ওয়ার্কফ্লোকে
তৈরি করা নোট লিখতে দিতে চাইলে আগে GitHub রিলিজটি মুছুন: এটি বিদ্যমান রিলিজের নোট রেখে দেয় এবং
কেবল ফাইল ও checksum যোগ করে।

### পরিপক্বতার সিঁড়ি (আমরা কোথায় আছি, কোথায় যাচ্ছি)

সফটওয়্যারটি নতুন এবং এখনো প্রমাণিত হচ্ছে, তাই এটি **`1.0`-এর নিচে** থাকে:

```
0.0.x  pre-alpha    the first, un-public pre-alpha iterations (0.0.4 .. 0.0.9).
0.x    alpha        ← we are here (0.5.0). Public, working, honestly-labelled — open
                     to feedback, but not yet consolidated (each cycle is still an
                     "honest about every limit, not finished" release, per the README
                     header — see it for the current cycle's exact status).
0.x    beta         once things consolidate (a deliberate, later maintainer call —
                     not implied by any particular `0.x` number crossing over from alpha).
1.0    release      an official, stable release.
```

আমরা এমন কোনো সংস্করণ নম্বরে লাফ দেব **না** যা বিদ্যমানের চেয়ে বেশি পরিপক্বতা বোঝায় (যেমন,
`0.2` মানে "২০% সম্পন্ন" বা "বিটার কাছাকাছি" নয় — এটি এ পর্যন্ত আলফা চক্রের সৎ গণনা)। প্রতিটি চক্র
একটি ছোট, বাস্তব পুনরাবৃত্তি — এর বেশি কিছু দাবি করা হয় না।

### চক্র ↔ সংস্করণ মানচিত্রণ

উন্নয়ন-চক্র (এবং তাদের শাখা) যে সংস্করণ তৈরি করে তার নামে নামকরণ করা হয়, সংক্ষিপ্ততার জন্য
সামনের শূন্যগুলো বাদ দিয়ে:

| শাখা / চক্রের নাম | প্যাকেজ সংস্করণ |
|---|---|
| `0.04` | `0.0.4` |
| `0.05` | `0.0.5` |
| `0.06` | `0.0.6` |
| `0.07` | `0.0.7` |
| `0.08` | `0.0.8` |
| `0.09` | `0.0.9` |
| `0.1`  | `0.1.0` |  (আলফায় উত্তরণের সময় `0.09` চক্র-শাখার নাম বদলানো হয়, `0.09 → 0.1`)
| `0.2`  | `0.2.0` |  (0.2-এ উত্তরণের সময় `0.1` চক্র-শাখার নাম বদলানো হয়, `0.1 → 0.2`)
| `main` | `0.2.0` → `0.3.0` → `0.4.0` → `0.5.0` |  (2026-07-15-এ `0.2` চক্র-শাখার নাম বদলানো হয়, `0.2 → main` — ডিফল্ট শাখা এখন স্থায়ীভাবে `main` এবং শাখার নাম ও সংস্করণ স্বাধীন; লাইভ-কর্পাস স্কেল যাচাইয়ের পরে `v0.2.0` ট্যাগ করা হয়, `v0.3.0` মাপা-ও-যাচাইকৃত চক্র বন্ধ করে, `v0.4.0` জীবন্ত-উৎস চক্র বন্ধ করে, এবং `main` এখন `0.5.0` পড়ে, তদন্তকারীর-ডেস্ক রিলিজ, যার ট্যাগ `v0.5.0`)

তাই "`0.06` ইন্টেলিজেন্স স্তর" মানে "যে কাজ `0.0.6`-এ শিপ হয়"। নথিতে `0.05`-এর মতো চক্র-সংক্ষেপ
পড়লে তা `0.0.5` হিসেবে পড়ুন। PR আসে `main`-এ, বর্তমান চক্র-শাখায় — ওপরের অবসরপ্রাপ্ত সংখ্যাযুক্ত
শাখা-নামগুলোর কোনোটিতে নয়।

**প্রথম আলফা (`0.1.0`) থেকে, মানচিত্রণ হলো `0.N` চক্র ⇒ `v0.N.0`** — `0.2` চক্র `v0.2.0` দিয়ে
বন্ধ হয়েছে, `0.3` চক্র `v0.3.0` দিয়ে, `0.4` চক্র `v0.4.0` দিয়ে, `0.5` চক্র `v0.5.0` দিয়ে
(একমাত্র ব্যতিক্রম একীভূত `0.09` চক্র, যা `0.1.0` তৈরি করেছিল)। একটি চক্রের নাম রাখা হয় যে রিলিজ
তা বন্ধ করে তার নামে — রিলিজ-গেট ফাইলগুলো নিজেদের ভাষায় তা বলে
(`RELEASE_0.4_GATE.md` হলো "the checkable inventory for closing the `0.4` cycle") — এবং ট্যাগের আগে
চক্রের মাঝখানে একটি সংস্করণ নম্বর *নির্ধারণ* করা যেতে পারে (যেমন `0.4.0` নির্ধারিত হয়
2026-09-28-এ, যাতে ট্যাগটি সেখানে সরানো যায়; `0.5.0` নির্ধারিত হয় ফ্লিপ PR-এ, এবং ট্যাগটি তার
মার্জ কমিটকে নির্দেশ করে), এ কারণেই একটি changelog শিরোনামের তারিখ ও তার ট্যাগের তারিখ ভিন্ন হতে
পারে।
