## 2026-11-07 — pricing a key file's key derivation prices every caller that constructs the object that loads it: count the constructions before swapping a 0.3 ms derivation for an 80 ms one (custody Ed25519 wrap, R449, PR #1786)

**What was found.** The evidence key (PR #1749) is read once per export, so moving it from PKCS8's PBKDF2 (2048 rounds, 0.33 ms a load) to the repository's own scrypt wrap (N = 2^15, about 79 ms and 32 MiB) cost nothing anyone could feel. The custody Ed25519 key is not like that: it is loaded by `HybridSigner.__init__`, and a `HybridSigner` is built by everything that opens a `CustodyLog` and by `/api/custody/settings`. Measured here (median of 8 constructions under a held passphrase): 79 ms with the scrypt wrap, where the PKCS8 key loaded in 0.33 ms. The callers that pay it: the four routes of `src/api/custody.py` that open a log through `_log()`, `_settings_status` (the network consent popup reads `/api/custody/settings?late=0` every time it opens, and its own comment in `src/static/app-core.js` says that route once took 5.7 s and the popup read "..." for that long), one `CustodyLog` per ingest batch (`_CustodyBatch.log` in `src/ingest/pipeline.py`) and, where no batch is passed, one per article. On a build with the ML-DSA library the construction already paid one scrypt for that key, so the Ed25519 wrap makes it two (about 160 ms). The independent read named the burst: `src/custody/log.py` documents a 50-way parallel case, and fifty constructions at once held fifty derivations at the same time. Measured here (4 cores): 1.16 s wall and a peak of +1,298 MiB for fifty.

**The rule.** Whoever moves a key file onto a priced derivation (and they should: a copy of a file that tests a guess at the database passphrase for 0.3 ms is the cheap way in, see the evidence-key lesson of 2026-11-07) lists the callers that construct the loading object, per request and per batch, with a measured figure each, in the same change. That list decides between three answers, none of which is "do nothing and hope": accept the cost (a per-batch or per-export caller), cache the opened key in the process (a design decision with its own exposure: what is held, keyed by what, dropped when), or load lazily on first use (a signer that is only asked for its identity needs the public key, not the secret). This change accepts the per-call cost and says so, and bounds the burst: at most one derivation per core at a time (`_KDF_SLOTS` in `src/custody/signing.py`; the bound comes from the machine, not from a number chosen), which takes the same fifty from +1,298 MiB to +129 MiB in 1.35 s, because a derivation is CPU-bound and the wall time was never in the parallelism. It does not cache the opened key: a cache keyed on anything derived from the passphrase is a second place the passphrase's consequences live in memory (and `tests/test_passphrase_hashing_guard.py` exists for a reason), and nobody has ruled on that.

**One module, not a second copy.** The atomic-create and replace-in-place protocol of PR #1749 (a private file under `keys/.pending/`, `os.link` into place, replace only if the file is still the one that was read, sweep the aliases of a replaced plaintext key) now lives in `src/custody/keyfile.py` and is used by `src/reporting/evidence.py` and `src/custody/signing.py`. The protocol is the part that took four independent reads to get right, and two copies of it is how the next fix reaches one of them. What moved with it: the tests that patch the protocol's `os` calls patch `keyfile.os` through `tests.os_scope.scope_os`, because a patch has to land on the module that makes the call, not on the one that imports the function.

**Findings of the independent read that were fixed here, and why they are worth keeping.** A key file that is a symbolic link was "wrapped" by swapping the link for a regular file while the plaintext stayed at its target, with `key_protection` saying the wrap was done (the identity check used `stat`, which follows the link; it is `lstat` now, and a path with a hard link outside `keys/.pending` is refused the same way, `KeyFileLinked`). A creation loser trusted the winner's file without judging it: a winner that held no passphrase left a plaintext file the loser reported as wrapped (the loser now takes the same path as any file found there). A damaged PEM reached the caller as a bare `ValueError` (named now, in both signers). Losing a wrap race logged a warning in each loser (debug now; a warning stays for every other refusal). And a test that cannot tell whether `seen` is threaded through is not a test: the custody twin changes the file after the read and before the copy begins.

**What a status read must do after losing a race.** The signer reports `key_protection` from the FILE, so when its own re-wrap stands down because another caller wrapped the file first, it reads the file again before saying anything: left at the form it first read, it would call a wrapped file plaintext until the next construction. A test that loses the race on purpose pins it.

**What was and was not established.** Measured: 79.2 ms (min 76.9, max 82.5) per construction with the wrap, 0.33 ms for the PKCS8 load. Not measured: how often the custody routes are called in a real session, so the cost is a per-call figure, not a per-session one; a real FAT/exFAT volume and a Windows hard link (stand-ins only, as in the first PR). **Stated limits.** The custody ML-DSA keys are still written with `write_bytes` then `chmod`, two first callers can each make one, and one written in the clear before the passphrase existed stays in the clear until it is wrapped (named in `docs/SECURITY.md`); a build from before this change cannot read a key wrapped by it (no downgrade path, as for the evidence key); a backup restored from an install with another passphrase brings its custody key under that passphrase, and the custody routes refuse with the cause until the file is moved aside, as they already did for the PKCS8 form.
