## 2026-10-13 — qualify a bundled engine by measuring its behaviour, pin both behaviours in the tests, and give the next release its own lane

**(1) Select a test's expectation by measuring the engine, not by a version string.** `sqlcipher3` is a wheel that carries its own SQLCipher, and two tests encoded one engine's report (an empty `MemoryError` after a damaged page; a page whose damage makes the table check answer "unchecked"). `_poison_style()` builds a tiny damaged store, reads the leaf, asks the next statement and returns "memory" or "corrupt"; anything else fails loudly, so a third behaviour is a red test and not a silent pass. A version string would have passed 0.6.5 into whichever branch it guessed.

**(2) A test fixture that asks the engine for a thing it no longer has takes 21 tests with it.** The module fixture `pytest.fail`-ed because 4.19 has no page that makes the table check answer "unchecked", so 21 tests never ran and the logic they cover (unchecked, never latch) had no coverage on the new engine. When the engine cannot make the answer, make it by faulting the one seam the function reads through (the module's `_open`, only for the damaged copy and only the `articles` check), and keep the real-engine path for the engine that can.

**(3) A behaviour change measured with the production defaults off is not the behaviour.** On 4.19 a damaged last overflow page, invisible to the read on both engines, makes the NEXT statement raise a real corruption error, so the observer latches the file and files one class-only incident; but the suite runs with re-reads off, and with them on (the process default) the automatic re-read reads the HEALTHY table the paying statement named, clean, releases the latch and ends the incident superseded as `clean`. The first version of this entry called it an accepted latch; an independent read ran it with the defaults and found the record says nothing about the statement only surfacing the damage. Pin the outcome with the production switch on, and write what the record does, not what the first assertion saw.

**(4) A ceiling is only half of a pin; the other half is a lane that sees the next release.** The ceiling stopped the wholesale red, and the `sqlcipher-engines` job (floor blocking, newest as an observation leg, driver forced with `--no-deps` because the ceiling would refuse it) makes the next release one visible red leg. Fixtures written once by each engine (`tests/fixtures/sqlcipher/`) prove a store made by either opens under the other, which a single-engine process cannot otherwise show. The lock, the smoke pin and the pyproject ceiling move in one PR, and the lock's hash block is regenerated from PyPI's JSON, never typed.
