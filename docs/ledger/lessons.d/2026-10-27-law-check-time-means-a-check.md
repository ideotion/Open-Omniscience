## 2026-10-27 — A time stamped "checked" must be set only by an attempt that checked; give it back when no request was made, and then make sure the selection does not feed on the document you gave it back to (R293, OSM's C1 read of the law tracker)

**What was found.** `track_document` stamped `LawDocument.last_checked_at = now` BEFORE it fetched, and its `except FetchError` branch committed that stamp with `last_status = "fetch error: ..."`. Two outcomes of `fetcher.fetch` are not a failed check because no request was made: the kill switch's refusal (`FetchFailed("network kill switch is active ...")`) and `CrawlDelayDeferred` (a deferral the ruling S04-13 S2, Q1013 = a, says "is not a failure of the source"). Measured with the real `make_fetcher()` and the switch engaged: a document last checked 3 days ago and "unchanged" came out `last_checked_at` = now with the status overwritten, and `auto_track_due` reported `due: 0` as soon as the switch cleared, with the fetcher never reached: the 24 h gate read the refusal as a check. The same stamp is read as "last checked" by the law status line, the Living sources freshness (the newest and the OLDEST check, invariant #32), the coverage ages and the ingest report's "never checked". In ordinary use this is not only the direct API: pressing Stop mid-pass trips the switch while `auto_track_due` still has a batch to go, and every remaining document was stamped the same way. The deferral had the same effect through `except FetchError` (it inherits from it): `status: "error"`, stamped, counted as an error.

**Rules.**
1. **A "last checked" time means a check happened. Keep the previous value in a local and give it back in the branches where no request was made.** `last_checked_at` and `last_status` are two facts: the time of the last real check, and how the latest ATTEMPT ended. They may disagree, and that is the honest state (the body of the PR says why). The status still names the kill switch (invariant #14e's corollary, `tests/test_law_lane_offline.py`); only the time stays put. A real failed request keeps stamping (the back-off), and a robots disallow is a real answer about the document, so both are tested as controls that must still stamp (restoring on every failure is a mutant). Other outcomes that made no request to the document also keep stamping, on purpose, because they are deterministic answers and the stamp is their back-off: a cached `RobotsUnavailable` or `RobotsDisallowed`, `BlockedTarget` and a malformed URL. So the rule is narrower than its headline: it restores for the two outcomes that are about OUR state (the switch, the host's own pacing), not for every outcome without a request.
2. **Decide "the switch refused it" by the switch, or by the fetcher's own refusal sentence matched WHOLE at the start of the text; never by a substring of a text that carries a URL or a server's words.** The socket-level guard raises `AirplaneModeError(OSError)`, which lands in the generic `except Exception`, and a switch engaged mid-flight surfaces there; `kill_switch_active()` sees both branches. The first version of this rule reused OSM's `classify_fetch_failure` for the text half, and its `"kill switch" in d` is a substring test that runs BEFORE the HTTP status checks: a real 503 for `https://gazette.test/acts/Internet Kill Switch Act`, a redirect target, or a server's status line that happens to say it is classified `offline`, restored (so never backed off), and counted under `skipped_offline`: the same bug as before the fix, for a document whose address says so, found by the independent read of the rebase and measured on three such texts. The law tracker now tests `startswith("network kill switch is active")` (the sentence `src/ingest/__init__.py` raises at four sites); a control per kind of text, and the sentence placed INSIDE a real failure's text, pin it (a substring mutant of the new test is caught only by the last one: a control whose text does not contain the whole sentence cannot tell the exact test from the loose one). Limits: the switch cleared again between the failure and the check would leave the stamp (the cautious direction), and a real failure that coincides with a Stop is not stamped either (it is retried sooner).
3. **Giving a time back changes the order a selection walks, so look at what the selection does next.** `auto_track_due` takes the least-recently-checked documents first (it used to cut them with `limit(batch)`; the order is now pinned by a test, on main nothing pinned it). A deferred document keeps its old time and so stays at the head; a host with a long `Crawl-delay` (above `OO_CRAWL_DELAY_MAX_WAIT`, 180 s) would fill every pass and the hosts behind it would never be reached. MEASURED with the restore alone: three documents of one slow host, the oldest, in a batch of two, and the fast host's document got no baseline. Before the fix the stamp had hidden this by pushing the deferred documents back a day, for the wrong reason. The walk now spends the batch on documents that were ASKED (a deferral does not count), and asks a host that defers once per pass (its other documents are passed over, not asked again). Walking by id and URL moved two reads out in front of the per-document guard, and the measured cost of that was the lane: `urlsplit` raises on an unbalanced bracket (the add-a-document API checks only the `http(s)://` prefix), a never-checked row sorts first, and so one such document stopped automatic law tracking on every pass, where on main it was one error with a 24 h back-off. Compute anything that can raise INSIDE the per-item guard, and give each read that moved a test. Two slow hosts are needed to test it, because one half of the rule alone is enough for one slow host: the test has two, and a mutant that drops either half fails it.
4. **A new tally key is additive and present only when it happened** (the convention of OSM's `skipped_offline`, whose tests pin the old shape of a pass without one). `deferred` appears in both trackers' tallies only when a document was deferred, so a caller that reads the old keys, and a test that pins the old shape, sees no change; a deferral is not in `errors`, and it is not in `documents` either: that key means documents ATTEMPTED (a refused or failed document counts, as it does on main, so a Stop mid-pass still shows N; the Activity Ledger prints it as "N document(s) read" and the toast as "Tracked N"), so counting a deferral there would let a pass where every law was deferred read as a quiet success, and would let `documents` exceed `batch`. The status text of a deferral stays main's ("fetch error: Crawl-delay ..."): `_verdict_of` badges that as an error and a `deferred: ...` text as "other", so a new text needs its verdict and its label (x12 locales) first. The toast in `app-gov-law.js` does not show the key (a new chrome string is x12 locales, and OSM's C1 changes that same toast); the number is in the response.
5. **Not checked, stated.** Whether a law host can trigger the deferral today (a gazette declaring a `Crawl-delay` above 180 s) is not measured: the catch is real, the reach is not. The walk loads every due document's id and URL (not the rows), then reads one row per document asked. **A second place the same lie came from, fixed in the fetcher:** `EthicalFetcher._fetch_locked` runs the pacing check at the top of EVERY attempt, so a first request that failed with a 503, 429 or timeout, followed by a retry on a host whose Crawl-delay exceeds `OO_CRAWL_DELAY_MAX_WAIT`, raised the deferral AFTER a request was made. The tracker then restored the time for a real failed request, and the collector filed it in its deferral bucket (`pipeline.py`): measured with a real fetcher and a stub session, one request made, status `deferred`, not stamped; with a 10 s delay the same failure makes three requests and stamps. A deferral on the FIRST attempt is the only true one, so a retry that defers now raises the failure in hand (the host's next-allowed-at was persisted before the raise, so the next pass still waits). A rule that sorts outcomes by exception type is only as good as the code that picks the type: check where the type is raised, not only where it is caught. **Also found, not introduced here:** a document whose processing raises AFTER a good fetch is rolled back by `auto_track_due` (the stamp goes with it) and so is re-fetched on every pass; the same rule 3 shape (a selection that feeds on a document it did not back off).
