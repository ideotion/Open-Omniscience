## 2026-10-16 — count the expensive thing before arguing about who pays it: encrypted opens, and a reuse whose lifetime is one function call

**What was found.** A debug bundle showed one collector thread spending 41 CPU-seconds a minute with a sampled frame on `connect.py:313` (`SELECT 1 FROM sqlite_master`), the first read of an encrypted file, where SQLCipher derives its key (PBKDF2-HMAC-SHA512 x 256,000: 163 ms of thread CPU, median of 20 on one pinned core, 158-208 ms). Nothing in the app counted opens, so the claim "this thread keeps re-opening connections" could be neither confirmed nor refuted. Instrumenting every keyed open of one real collect pass (the real pipeline and pool, an encrypted store, two CPUs, 96 articles) found where they come from: `_maybe_record_custody` built a new `CustodyLog()` for EVERY stored article, which is a new keyed connection to `custody_log.db` plus a signer (166.7 ms of CPU per article: 163 derivation, 1.2 Ed25519 key load, 1.2 the record, 0.1 settings). That was 94 of the 118 opens of the pass: with custody off the same pass used 36-46% less CPU on two cores (33.0 s against 51.7 s; 33.9 s against 62.3 s in a second configuration), and the 94 key derivations alone are 15.7 s. In the runs without the fix the pool made 21-25 opens a pass whatever the worker count, the fetch delay, or a write gate held 80% of the time: no storm. (The probe is `probe.py` in the project files, `keyword-export/reopen-2026-10-16/`; it wraps `_try_open_encrypted` from outside and is not in the repo. The 173 ms that `connect.py` and the ledger carry for one unlock is an earlier measurement of the same order, not re-measured here.)

**The rules.**
1. **When a sampled frame names a cost, count the cost, do not argue from the frame.** A sampler (vitals' `busiest` frames) shows where a thread STOOD at one instant and lands where threads release the GIL, which is native code; the thread's CPU is its total. Neither says how often the call happened. `src/database/open_stats.py` counts attempts to open an existing encrypted file, with the opening thread's CPU and wall time, by file and thread family, in the pass summary line (`encrypted_opens`) and the run report, the two places the bundle already carries (the same as `extraction_lock`). A statistic added for a field question goes where the bundle already looks; a new bundle member is a new thing to ship and to scrub.
2. **Do not claim the fix explains the field number.** The same arithmetic on the field bundles (487 new articles in 39 minutes = 12.5 a minute) puts custody at about 2 CPU-seconds a minute for the whole process, not 41 for one thread. The per-flush fix is real in the benchmark (118 opens to 32, 51.7 s of CPU to 34.3 s at flush size 8) and the 41 stays unexplained until the counter has field numbers. Say both, in that order.
3. **A reuse whose lifetime is one function call needs a small invalidation rule, not an epoch.** The per-thread cached connection that was proposed holds a keyed connection and the signing key for the thread's life, so it needs an epoch for a passphrase change, a lock and a restore, and one more connection per collector. `_CustodyBatch` lives for one `with` block in `_flush_batched`: opened when the first entry is written, closed when the block ends however it ends, dropped after a failed write (a connection in an unknown state: a failed INSERT leaves a transaction and a write lock open until the connection is closed, tested with a real failing INSERT and a second writer) so the next entry opens a fresh one, which is what every entry did before. Nothing is module state or an attribute of another object. BUT a log fixes three things when it is opened: its anchoring mode, its PQC flag and the key. The independent read found that withdrawing OpenTimestamps consent mid-flush would still have stamped the rest of the flush (each entry sent to the public calendars, invariant #14f), where the old per-entry open re-read the settings every time; a crypto-erase cannot reach the connection either. Each entry therefore compares the custody settings it was just read with, and whether the process still has a passphrase, with what the log was opened under, and a log opened under others is dropped first. "Nothing is cached" was the claim that hid this: say what the held thing fixed at open, and re-check exactly that. The gain scales with articles per flush; the single-article paths (the redo after a failed batched commit, the unbatched store) are unchanged.
4. **Read everything the entry carries BEFORE touching the shared resource.** In CUST-1 the article's expired columns could not be reloaded because the pool was exhausted. That is not the log's failure: with a per-flush log, dropping it for that failure would cost the batch a healthy log (and opening one first would open it for nothing). `_maybe_record_custody` builds the entry, and only then opens or uses the log; only a failure after that point drops the batch's log. A source-level test pins the order.
5. **A diagnostic that prints a name prints a closed vocabulary, and the vocabulary is tested against the names the world really uses.** Thread names are built from requests (`oo-osm-{key}`, `oo-dump-{key}`), and a restore or merge opens files whose names a person chose. The block carries the app's own database file names (else `(other)`) and the FAMILY of the thread name (`oo-<word>` of at most 16 letters, or a fixed name from a list, else `(other)`), never a path, a thread's full name, the key, or an exception's words. An AST scan of every `Thread(...)`/`ThreadPoolExecutor(...)` call in `src` fails any `oo-` name that does not start with a literal word (an f-string, a `+`, `.format` or `%` straight after `oo-` would put a variable's letters into the family). The first version listed `anyio` for the framework's worker threads and the test used a made-up `anyio-worker-3`, so it passed while every open from a sync FastAPI endpoint was counted as `(other)`: anyio and starlette really name them `AnyIO worker thread`; the test now reads the names off live threads. Rows are capped (32 kept, the first seen, 11 printed, the rest in an `(others)` row) and the totals stay exact: a cap shrinks what is printed, never what is counted. The size claims (a row at most 209 bytes, a block at most 3.2 KB, 30 reports at most 97 KB) are computed in a test from the real `snapshot()` over the longest strings and the largest numbers, because the first "measured 2.1 KB" came from short invented names.
6. **An unmeasured figure is absent with its count, never a zero.** When the per-thread CPU clock cannot be read the open still counts, `cpu_unmeasured` says how many, and `cpu_s` is left out when none could be measured.
