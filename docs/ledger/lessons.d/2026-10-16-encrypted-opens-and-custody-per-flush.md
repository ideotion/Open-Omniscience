## 2026-10-16 — count the expensive thing before arguing about who pays it: encrypted opens, and a reuse whose lifetime is one function call

**What was found.** A debug bundle showed one collector thread spending 41 CPU-seconds a minute with a sampled frame on `connect.py:313` (`SELECT 1 FROM sqlite_master`), the first read of an encrypted file, where SQLCipher derives its key (PBKDF2-HMAC-SHA512 x 256,000: 163 ms of thread CPU, median of 20 on one pinned core, 158-208 ms). Nothing in the app counted opens, so the claim "this thread keeps re-opening connections" could be neither confirmed nor refuted. Instrumenting every keyed open of one real collect pass (the real pipeline and pool, an encrypted store, two CPUs, 96 articles) found where they come from: `_maybe_record_custody` built a new `CustodyLog()` for EVERY stored article, which is a new keyed connection to `custody_log.db` plus a signer (166.7 ms of CPU per article: 163 derivation, 1.2 Ed25519 key load, 1.2 the record, 0.1 settings). That was 94 of 96 opens in a 118-open pass, 36-46% of the pass's CPU on two cores. The pool was flat at 21-25 opens a pass whatever the worker count, the fetch delay, or a write gate held 80% of the time: no storm.

**The rules.**
1. **When a sampled frame names a cost, count the cost, do not argue from the frame.** A sampler (vitals' `busiest` frames) shows where a thread STOOD at one instant and lands where threads release the GIL, which is native code; the thread's CPU is its total. Neither says how often the call happened. `src/database/open_stats.py` counts attempts to open an existing encrypted file, with the opening thread's CPU and wall time, by file and thread family, in the pass summary line (`encrypted_opens`) and the run report, the two places the bundle already carries (the same as `extraction_lock`). A statistic added for a field question goes where the bundle already looks; a new bundle member is a new thing to ship and to scrub.
2. **Do not claim the fix explains the field number.** The same arithmetic on the field bundles (487 new articles in 39 minutes = 12.5 a minute) puts custody at about 2 CPU-seconds a minute for the whole process, not 41 for one thread. The per-flush fix is real in the benchmark (118 opens to 32, 51.7 s of CPU to 34.3 s at flush size 8) and the 41 stays unexplained until the counter has field numbers. Say both, in that order.
3. **A reuse whose lifetime is one function call needs no invalidation rules.** The per-thread cached connection that was proposed holds a keyed connection and the signing key for the thread's life, so it needs an epoch for a passphrase change, a lock and a restore, and one more connection per collector. `_CustodyBatch` lives for one `with` block in `_flush_batched`: opened when the first entry is written, closed when the block ends however it ends, dropped after a failed write (a connection in an unknown state) so the next entry opens a fresh one, which is what every entry did before. Nothing is module state or an attribute of another object, so there is nothing to go stale, and the key object lives one flush longer, not one thread's life. The gain scales with articles per flush; the single-article paths (the redo after a failed batched commit, the unbatched store) are unchanged.
4. **Read everything the entry carries BEFORE touching the shared resource.** In CUST-1 the article's expired columns could not be reloaded because the pool was exhausted. That is not the log's failure: with a per-flush log, dropping it for that failure would cost the batch a healthy log (and opening one first would open it for nothing). `_maybe_record_custody` builds the entry, and only then opens or uses the log; only a failure after that point drops the batch's log. A source-level test pins the order.
5. **A diagnostic that prints a name prints a closed vocabulary.** Thread names are built from requests (`oo-osm-{key}`, `oo-dump-{key}`), and a restore or merge opens files whose names a person chose. The block carries the app's own database file names (else `(other)`) and the FAMILY of the thread name (`oo-collect` for `oo-collect_22`, a fixed word from a list, else `(other)`), never a path, a thread's full name, the key, or an exception's words. A test scans `src` for a thread named straight from a variable (`name=f"oo-{...`) because that would put the variable's letters into the family. Rows are capped (32 kept, 11 printed, the rest in an `(others)` row) and the totals stay exact: a cap shrinks what is printed, never what is counted.
6. **An unmeasured figure is absent with its count, never a zero.** When the per-thread CPU clock cannot be read the open still counts, `cpu_unmeasured` says how many, and `cpu_s` is left out when none could be measured.
