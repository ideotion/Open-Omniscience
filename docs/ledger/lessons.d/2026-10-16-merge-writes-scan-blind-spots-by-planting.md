## 2026-10-16 — a scan that reads statements is blind to the writes that are not statements: plant the shapes, measure the misses, then close or write down each one

**(1) What was measured.** `tests/test_merge_writes_name_main.py` reads `merge.py`'s SQL and fails on a write that names no schema. About 75 planted shapes were run through it before changing anything; 31 were not flagged (three of those are correct passes: `VACUUM main`, `VACUUM INTO`, `iterdump`), and the rest were not random: they were the ways to write that are not a `DELETE`/`INSERT`/`UPDATE` head, which is all the classifier knew. (a) **PRAGMAs.** `PRAGMA wal_checkpoint` with no schema checkpoints EVERY attached database: measured with stdlib sqlite3, a bare `PRAGMA wal_checkpoint(TRUNCATE)` emptied the attached file's `-wal` (4,152 bytes to 0) while `PRAGMA main.wal_checkpoint` left it; a bare `PRAGMA journal_mode=wal` switched the attached file to WAL as well. `PRAGMA inc.user_version = 3`, `PRAGMA inc.incremental_vacuum` and `PRAGMA writable_schema = 1` write the backup or its catalogue. The classifier had one pragma rule (`optimize`). (b) **`VACUUM inc`** and a raw **`ATTACH`** (creates a file when the path is missing). (c) **Reaching `execute` without naming it:** `getattr(con, name)(built_sql)`, `operator.methodcaller`, `__getattribute__`, `vars`, `eval`, `sqlite3.Connection.execute(con, sql)` (the statement is the SECOND argument, so the scan read the connection as the SQL), `con.backup/deserialize/blobopen(name="inc")`. (d) **An ORM session**, which writes through unqualified table names.

**(2) Why a literal-only check hid them.** A planted case with a LITERAL statement (`getattr(con, n)("DELETE FROM t")`) is caught by the "any string that starts like a write" pass, so it looks covered. Only a BUILT statement (`f"{v} FROM t"`, no literal head) shows the miss. **When you plant a shape to test a reader, build the statement so the second line of defence cannot catch it, or the case proves the wrong clause.**

**(3) What closed and what is written down.** PRAGMA, VACUUM, ATTACH, the reflection names, a dynamic `getattr`, the class-receiver form, the three sqlite3 methods and an ORM import are now problems (an allowlist entry with a reason excuses one); the functions in other modules that receive the merge connection are pinned by name with a reason each (six today, all read once). Five shapes stay outside and are listed in the test module's docstring, with the reason each is too costly or too common to flag (ORM method names like `add`, a non-sqlite object with its own method name, side-effect SQL functions that Python's sqlite3 does not ship, a connection under another name, lexical over-reports). **A miss that is not closed is counted in the boundary list, never silently dropped.**

**(4) How each clause is pinned.** Every new clause was removed in turn and the file re-run: 39 mutations, 4 survived the first planting (the unparseable-PRAGMA branch and three ORM names that had only their module form planted), and each got the case that kills it; the final run had no survivor. The same discipline holds for the cross-module reader (seven mutations, one survivor, killed).

**(5) The settings write-slot gap this PR (#1413) also closes.** `tests/test_kv_store_write_hold.py::test_a_hold_that_starts_right_after_a_write_passed_the_check_waits_for_that_write` starts a restore's hold in the instant between a write's hold check and its count (a hook that runs right after the first `with _hold` exits). It fails when `_inflight.add(token)` leaves that locked section, after it or into the `with _lock:` block (both measured), which no earlier test did; this closes the "known and not pinned" remainder of the 2026-10-16 write-slot lesson.
