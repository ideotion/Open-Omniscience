## 2026-10-13 — an audit's reading of one slow number is a hypothesis until the parts are timed by name; the instrument goes beside the code's shape, never around it (init_db per-step timing, PR #1372)

**(1) The audit's reading of the 4.1 and 4.2 s `init_db` ("about 30 self-heal probes on a cold cache") stayed a hypothesis for one reason: the record held one number for 37 steps.** Timed by name on a synthetic store (1,200 articles, plain and SQLCipher, warm page cache, no unclean end), no `ensure_*` probe on an already stamped store was above 8.5 ms (most 0.3 to 1.8 ms), and a cold process on it (503 to 1,241 ms; the same call again 44 to 114 ms) spent its time in alembic's first use (`align_stamp_to_head`, 149 to 771 ms), `create_all` (the process's first connection, which carries the key derivation on the encrypted store) and `heal_bulk_build`; the first run on a never-stamped copy (579 to 1,602 ms) added the one-time stamp (`stamp_if_unstamped`, 308 to 927 ms) and a few one-time backfills (the largest 196.5 ms). A fix aimed at the reading, batching the 30 probes into one, would have saved about 30 ms. **Before changing a path, make the field able to say which part it was: time the parts by name where a zip can carry them, then decide.** The field's 4 s followed an unclean end on a cold cache and this machine cannot reproduce that, so the measurement did not refute the hypothesis either; the decider (PR 2) waits for a record that names a step.

**(2) Name the steps, do not wrap them.** The first design ran every step through a runner (`steps.run(ensure_x, engine)`). Six tests read `init_db`'s source (`inspect.getsource` of `session.py`), and `tests/test_scale_bench.py::_called_ensure_names` reads the `ast.Call` callee names; a runner moves each name into an argument and breaks all of them for a change that touches nothing they protect. A `_init_step("name")` line before each literal call, and a decorator on the function, changed no pin. **When code is pinned by tests that read its source, put the instrument beside the shape (a line before, a decorator over), never around it; and let an AST test fail for a step added later without its name, because an unnamed step is silently charged to its neighbour.** (Same family as lesson 7 of the write-gate-holds entry of the same day.)

**(3) Time between two names belongs to the earlier name, so every import inside the function is a step of its own, and one cost can still land on the wrong step.** SQLAlchemy configures its mappers on the first ORM use of a process (about 95 to 250 ms here, taken as `heal_bulk_build`'s first call minus its second), so on the cold call it sits in whichever step reaches the ORM first (`heal_bulk_build`), which a reader would take for a slow step. The record's `METHOD` text says so, and the P0.4 verdict prints it beside the steps. **A record that attributes time to names must say which costs travel; read the cold call apart from the warm ones.** And a call COUNTER is not a cold-call marker: the launcher's `init_db` against a still-locked encrypted store raised at `create_all` and was `process_call` 1, so the unlock's call, the one the field's slow readings were about, was call 2. The independent read caught it; the record now carries `earlier_complete_calls` (0 = no earlier call got through) and the first-call record is the first to COMPLETE. **Define "first" by the event that matters (the store opened), not by the count of attempts.**

**(4) Two conditions that look alike in a total are not, and a range quoted from several files is only as good as its scoping.** The probe's first run on each fresh copy of the test store stamped it (`stamp_if_unstamped` 308 to 927 ms, the stamp itself), while the cold processes after it ran on an already stamped store (`align_stamp_to_head` 149 to 771 ms, alembic's first use in the process). The first write-up gave one range for "a cold process" from the later files only and "no `ensure_*` above 66 ms" while a first-run file had one at 196.5 ms; the independent read recomputed every figure from the folder and found four ranges that two of the files contradicted. **Write each range with the condition it came from, recompute it from every file it cites before it goes into a ledger, and read field records by `earlier_complete_calls` and `machine_uptime_s` (how long the machine had been up; it is not a page-cache reading), never from one.**

**(5) A rule about secrets needs a test that plants one.** The step names are code constants and a raising step is kept by its class alone, but the guarantee is the test: a marker in a raising step's message is searched for in the in-memory records, the unlock record, the sentinel, the P0.4 verdict and every file under the data dir, and the same test asserts the exception itself is untouched. And a record that rides a zip in three places is sized by a test (2.4 KB each, pinned at 4,000 bytes) before it ships, because the 4 MB budget is only as good as its largest unmeasured member.
