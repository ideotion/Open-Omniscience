## 2026-10-28 — the release gate judged refs by its own copy of the predicate, so it passed what the fragment check refuses

**What was found (the limit #1643's own lesson stated, closed under R307).** `scripts/release_notes.py:refuse_placeholders`, the gate that stops a release body from citing a row whose `refs` is still a to-do, decided with `"pending" in refs.lower()`. `ledger_shipped.py check` decides with `REFS_PLACEHOLDER` (`\bpending\b`, `#NNNN`, `#PRNUMBER\b`, case-insensitive). The two disagreed in both directions: a cited row whose refs said `#NNNN` or `#PRNUMBER` went through the release gate and into a release body as a permanent citation (the fragment check would have refused it, but a hand-written row in `shipped.csv` never meets that check), and a refs value saying "depending on #1637" was refused at tag time by a rule the fragment check never applied, which is where a lane would first meet the surprise. Nothing was lost on the real ledger: over the real ledger (1,677 rows when first measured, 1,682 at this PR's head: the file plus every fragment) the two predicates differ on none.

**The rule.** A gate that re-derives a predicate another tool owns is a second copy that agrees until the day the first one learns a token; the release gate is the worst place to find that out, because it runs once per tag. `release_notes.refs_carry_placeholder` now reads `ledger_shipped.REFS_PLACEHOLDER` through one cached loader (`_ledger_shipped`, which the fragment reader already needed), and the refusal message names all three tokens. The deliberate narrowing is stated in the PR body and in the test docstring ("depending on #1637" is accepted): `pending` is a word, so a `pending` glued to word characters (`PR_pending`, refused by the old test, accepted now) is not seen by either tool, which is `#1643`'s choice and not widened here.

**What it measured.** Against the old script 7 of the 13 new tests are red and 6 pass on both (the three `PR pending` spellings and the three negative twins that the old predicate also got right): 4 on the predicate (`#NNNN` and `#PRNUMBER`, two spellings each), 1 on the narrowing ("depending on #1637" is no longer refused), 1 on the message (it must name all three tokens) and 1 on the source-following test (which cannot even import the loader on the old script). Five mutants of the new script were run: the old substring predicate (6 red: the four `#` forms, the narrowing twin and the source-following test), a private copy of the three-token regex (only the source-following test red, so that one test is what makes "one predicate" hold), the cache removed (the same test, which therefore pins one cached, live attribute lookup and not merely "follows the source"), the predicate always False (11 red), and a message that names only `#PRNUMBER` (it survived the first version of the tests, found by the Opus read of the PR, and is now killed by `test_the_refusal_names_all_three_tokens_it_judges_by`). Not measured: any other reader of a ledger `refs` cell; `grep` found `refs_carry_placeholder` at two call sites (the gate and its real-ledger test) and `sweep_pr_number.py` already uses the same predicate (#1648).

**Owner.** `scripts/release_notes.py` is in no lane's file-ownership list; it is Plan's by R307 and R313(2) (the lane that found the defect takes the unlisted file), and this lesson is the index entry that says so for the next session that touches it.
