## 2026-10-17 — a build that fits its memory limit is not a rollup that can answer (rollup build, PR #1422)

**Found.** The sharded build was sized to finish inside DuckDB's 1,004 MB limit, and the first write-up said the model "errs high" and holds "under the limit to about 21 M mentions". A first set of streamed builds on seeded corpora (8 mentions per keyword, 2 threads) seemed to say otherwise (peaks 601 to 604 MiB at 12 M, 771 at 16 M, 928 at 20 M against the model's 645, 716 and 881), but those peaks, and the "resident size varies by 300 MiB between runs" that went with them, were read by a SECOND CURSOR POLLING `duckdb_memory()` every 20 ms during the build (see 5). What survives the correction: serving queries run on the resident rollup needed more memory than the build left (at 12 M the all-history top-terms query ran out of memory, at 16 M the 30-day one and the all-history counts did on the polled runs, at 20 M every query did), and the serve swallows that error and falls back to the live scan, so a build could spend minutes and most of its memory to answer nothing.

**Rules this gives.**
1. A build that finishes under a memory limit proves the build, not the use: run the queries the structure exists to serve, at the same limit, before saying the size "fits". A resident structure needs headroom for its readers (the 30-day top-terms query needed about 190 MiB over the resident rollup at 12 M).
2. A size claim from a model is labelled inferred until a streamed run at that size exists, and the model's error band is written beside it with its sign: a model that is high at one size and low at another is not "conservative".
3. Do not refit a three-parameter model to six points to chase a 5% miss; keep the margin that already absorbs it (the 70% fit target) and state the measured band.
4. An error that a caller swallows and answers around (here, live fallback) hides a wasted build; a measured canary after the build is the only thing that says the structure can serve.
5. **The instrument is part of the experiment.** A concurrent cursor polling the engine's memory view coincided with resident readings 80 to 310 MiB above the same build run alone (16 M: 766 and 536 MiB with it, 456.1 to 456.4 in 7 of 7 runs without it), and the "variance between runs" it produced was written into the PR, the queue and this file as a property of DuckDB. Before calling a spread real, repeat the measurement with the observer removed, and say how each figure was taken (polled by a second cursor, synchronous at batch boundaries = a lower bound, process high-water mark). The mechanism (an open snapshot on the second cursor keeping old versions alive) is plausible and was not isolated. A serve canary (R157) is still the right guard, because it measures the build that exists; it is not a response to variance, which was not real.
6. **Match an engine's wall by class and name it, or it is a failure the system retries.** At the edge DuckDB raised a `FatalException` (a checkpoint could not allocate) instead of `OutOfMemoryException`; only the second is classified as the limit, so the first ended the build as a plain failure with no kept stop (R160 classifies it by class name plus one fixed phrase, with the engine's text going nowhere).
7. **Look for the engine's own statement before building around its behaviour.** The rollup sat 456 MiB resident when 73 MiB holds the same rows: an in-memory table is kept uncompressed until a `CHECKPOINT`, and nothing asked for one (R164, `columnar.compact`). It also freed the room the wider windows needed, so the all-history top terms stopped falling back at 12 M and 16 M.
