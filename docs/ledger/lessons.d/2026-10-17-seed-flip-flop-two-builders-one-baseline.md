## 2026-10-17 — two seeds that build one entry two ways and share one baseline correct each other on every boot, and "an empty value is a gap" turns the first erasure into a permanent one

The default seed read `legal_sources.yml` raw; the legal seed read it through `registration_source_rows` (another `source_type`, a gazette feed). Both ran `sync_catalogue_corrections`, which takes a row's corrections from the first entry per domain it is handed and rewrites the row's single `catalog_baseline`, so each seed read the other's baseline write as an upstream change and applied it: 56 and 55 "corrections" on every boot, and for seven news hosts the legal catalogue's FEED-LESS entry wrote an empty `rss_url` over the real one on the first boot. Nothing brought it back because an empty live value is, by design, a gap (`reconcile_source_metadata` fills country, language and tags only), so the sync skipped it for ever. **Two rules.** (1) A correction may come only from the catalogue that made the row (its `via:` tag against the entry's `_provenance`); any two writers of one baseline need one builder for the one entry. Either fix alone is not enough, measured: the provenance rule alone left 40 applied, the shared builder alone left 16/15. (2) A guard that reads emptiness as "not mine" needs the matching repair when something else empties the value: the fingerprint of the erasure was the baseline (no operator action writes it), which is what separates an erased feed from one an operator cleared. A fresh-store seed run twice is the test that finds this, and it must use the shipped catalogues, not a synthetic pair, because the cause was in how two real files were loaded. The same read found the name-pairing fallback reaching across two seed calls (each call sees only part of the catalogue, so every other catalogue's row is a "leftover"): gate any cross-row heuristic on the catalogue too.
