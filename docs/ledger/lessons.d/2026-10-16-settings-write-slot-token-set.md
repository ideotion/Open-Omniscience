## 2026-10-16 — the leak that real signals produce is in the release's lock, not in the two statements that looked wrong; release before you take the lock

**(1) What looked wrong, and was not.** `kv_store._write_slot` counted a settings save as in flight with `_inflight += 1` and then `counted = True`. Reading that, an interrupt between the two statements seemed to leave a count for ever (every later `hold_writes` waits out its budget and raises `KvWriteBusy` until the process restarts), and swapping them seemed to risk a decrement of a write that was never counted. It was rewritten as a SET of per-write tokens (one `add` counts, `discard` releases and does nothing for a token never added). An independent read then MEASURED it with real SIGALRM-driven KeyboardInterrupts on CPython 3.13: about 164,000 interrupted writes never hit the two-statement window, because those bytecodes contain no point where CPython delivers a signal (delivery is at RESUME, at backward jumps and after calls). **A window that exists in the source is not a window that exists at run time; measure with real signals before claiming a fix, and write the claim after the measurement, not before.**

**(2) The window that did leak.** The release was `with _hold: _inflight.discard(token); _hold.notify_all()`, and `Condition.__enter__` is Python code in 3.13: a KeyboardInterrupt delivered there arrives AFTER the write finished and BEFORE the decrement. That leaked about 5 % of interrupted writes in the old code and in the first token-set version alike (2,274 of 41,613 and 2,189 of 40,924). The fix is to release with one lock-free C call and take the lock only to wake a waiting hold: `_inflight.remove(token)` (a `KeyError` means it was never counted, so nothing to wake), then `with _hold: _hold.notify_all()`. Measured: 0 leaks in about 129,000 interrupted writes. A missed wake only makes a waiting hold use its whole budget and then start; it never refuses wrongly.

**(3) What stays best effort, and is said so.** An interrupt can also leave `_hold`'s own lock taken (the `with` hazard of `Condition.__enter__` and `__exit__`; 4,629 of 40,924 interrupted writes in the probe, pre-existing), which blocks every later settings save and every restore hold at `with _hold:` until the process restarts. The lock is therefore taken only when the write was actually counted (there is a hold to wake), which keeps the exposure as small as it can be. "Safe at any bytecode boundary" cannot be reached with a `with Condition` block, so the code comment says KeyboardInterrupt on the main thread is best effort here. Its reach is small: only a main-thread caller (a CLI script) can receive it, and the served app's main thread is uvicorn's, which handles SIGINT itself.

**(4) How it is pinned.** `tests/test_kv_store_write_hold.py::test_an_interrupt_as_the_release_takes_the_lock_does_not_leave_the_write_counted` makes the lock's second entry raise KeyboardInterrupt and asserts the write is not left counted and a hold then starts; moving the release back inside `with _hold` fails it. `test_an_interrupt_inside_the_slot_neither_leaks_a_count_nor_releases_another_writes` pins the set's contract (an interrupted add, after or before the token is in, with another write's token counted); a plain integer fails it by a TypeError, not by an ordering. **Known and not pinned:** moving the `add` out of the `with _hold:` block that checks the hold survives every test in the two files; no test holds the slot between the hold check and the count. Readers of the count (`while _inflight:` in `hold_writes`, two tests that polled it as an integer) read it as a truthy set.
