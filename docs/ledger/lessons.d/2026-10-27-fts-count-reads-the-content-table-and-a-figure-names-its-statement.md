## 2026-10-27 — `count(*)` on an external-content FTS5 table scans the content table, a bare `count(*)` cannot be stopped by a progress-handler deadline, and a recorded figure is a claim about one statement

**What was found.** The cold encrypted measurement of `fts_status` at 1,000,000 articles (the app's own SQLCipher engine, 5 cold runs) put 99% of the call in a statement nobody had changed since D4: `SELECT count(*) FROM article_fts`, 9.6 to 11.9 s cold and 5.5 to 6.0 s warm, 3 to 5 s from its own 15 s deadline. The statement the work had just added (the index's ends) cost 76 to 100 ms. For an external-content table FTS5 answers a `count(*)` by reading every row of the content table, columns included, so it costs what `SELECT count(*) FROM articles NOT INDEXED` costs (9.5 to 10.5 s cold) and follows the article TEXT, while a count over a covering index follows the NUMBER of articles and took 0.24 to 0.33 s cold. The swap changed no value on a healthy store and `fts_status` went from 9.7 to 12.0 s to 0.29 to 0.49 s cold (median 11.4 s to 0.37 s). Separately, the docstrings, two test comments, a PR body and a ledger entry had all said that a count of articles "is the 74 s cold scan the boot refuses": a figure with no statement recorded beside it, repeated for weeks as the reason for a design. One measurement at the real size on the current schema did not reproduce it. And the first version of the swap, `count(*) FROM articles`, was wrong in a way no test of the answer could show: SQLite runs a bare `count(*)` as ONE opcode, `statement_deadline` is a progress handler that SQLite consults once per 20,000 opcodes, and that statement is nine opcodes in all with the whole walk inside one of them, so the 15 s block around it bounded nothing (handler consulted 0 times, against 30 for `count(1)` over the same covering index, at 200,000 articles; a 0.5 s deadline around it over 6,000,000 rows returned after 0.74 s). An independent read of the PR found it, and the claims ("a slow count is reported as timed_out") had been written, measured and tested around the statement that could not do it.

**The rules.**

1. **Time a diagnostic whole, statement by statement, on a store of the real size before saying what its cost is, and before saying which part is yours.** The new statement was 0.1 s; the cost sat in a line older than the work. A timing that covers only what you added cannot find that.
2. **To count the documents of an external-content FTS5 table, ask the content table; to count the index, ask its `_docsize` shadow table.** `count(*)` on the virtual table is a content-table scan (it reads the text), so it is neither cheap nor a measure of the index. A cheap count needs a covering index, and WHICH index is the planner's choice (it varies with the order the schema's indexes were created in; here it picked one four times the size of the smallest candidate): pin "a covering-index scan" by capturing the statement the code actually issued at the cursor and running `EXPLAIN QUERY PLAN` on that text, and pin the exact text for what a plan cannot see. The plan check turns red for `count(content)`, `NOT INDEXED` or a `WHERE` on an unindexed column; `count(id)`, `count(created_at)` and a `WHERE` on an indexed column keep a covering plan (all four read off the app's schema), so only the exact text catches those.
3. **A deadline built on a progress handler bounds only what loops.** A bare `count(*)` (and the same inside a scalar subquery) is one opcode: no handler fires while it runs. Use `count(1)`, which has the same covering-index plan and loops (cold cost the same; warm 16 to 24 ms per 1,000,000 rows against 1 ms), and test the bound itself with the REAL deadline at a tiny value over enough rows (30,000 articles, a millionth of a second: `count(1)` is asked after 20,000 opcodes and stops, `count(*)` returns whole), asserting the typed timeout. The first version of that test re-ran the statement under `set_progress_handler(cb, 1)`, a handler asked at EVERY opcode, and asserted it was consulted: a bare `count(*)` is nine opcodes and is consulted nine times, so the test passed against the very statement it was written to catch (found by a second read; the interval and the row count are what tell the two apart, and a mutant respelling the statement to `count(*)` is the check). A test that only checks the statement sits inside the `statement_deadline` block pins nesting, not a bound, and a test of the call site's value does not pin the value itself: the wrong deadline, one that never fires and a floor of zero survived until each was pinned.
4. **A recorded figure belongs to a statement, a schema, a store size, a disk and a temperature.** "74 s cold" had none of them, so it could be neither reproduced nor retired, and it was cited as the reason a design was refused. When a figure is the reason for a refusal, record those five things with it; when a measurement withdraws the premise, drop the premise in the same change (grep the docstrings, the tests' `reason=` strings and the ledger pointers, including the same day's fragments: annotate them, do not rewrite them) and say the old figure was not reproduced rather than silently replacing it. The refusal itself (here: the boot compares no counts) is a decision and stays one until it is ruled on; losing its premise does not reverse it. And re-measure the FINAL statement: a figure taken on the first spelling of a fix is a claim about a statement that no longer ships.
5. **A test that pins a decision as an absence is rewritten, not deleted, when the decision changes.** "No statement counts the articles" became "exactly one does, it is the plain count, its plan is a covering index, and nothing counts the table it replaced". Key the fakes on one constant, so the next change of spelling is one line.
6. **When a statement behind a reported number is swapped, run the old and the new on the shapes where they could differ and compare them to what the function reports, and name where "the same number" stops.** Full, shrunken after deletes with a reused id, emptied, partial; assert the figure is non-zero so equality is not a tautology. It stops at a store whose index disagrees with its table: the new count reads one index, so an index missing entries reads short and a damaged table page no longer surfaces there. The verdict that must not depend on the number (here `partial (inferred)`) gets its own test with the number answered and with it timed out.
7. **A cold figure is an evicted file AND a fresh process, five times, with the disk class named, and a store rebuilt from a seeded generator is the same data, not the same file.** Here a cold run was 11,382 ms and the same call warm was 5,801 ms before, and 373 ms against 24 ms after: the warm figure hides the codec and the disk, and "a virtual disk reading 1.3 GB/s, the codec dominates" is a limit to state without ranking it against a laptop's, which is unmeasured.
