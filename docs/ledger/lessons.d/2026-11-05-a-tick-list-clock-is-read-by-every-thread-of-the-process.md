## 2026-11-05 — a fake clock that hands out a list of ticks is read by every thread of the process: give the ticks to the test's own thread only (C10, `test_boot_sequence.py`, PR #1726)

**What was found.** The first CI run on the final head of the sharding PR failed one test in one Core-only shard: `tests/test_boot_sequence.py::test_a_slow_step_is_a_warning_naming_what_waited_behind_it` asserted a warning for `warm-cache` and the log said `boot step article-indexes took 300 s`. The test replaces `time.monotonic` with a clock that returns eight scripted readings (seven 0.0, then `SLOW_STEP_S`); `bs.time` is the `time` module, so the replacement is process-wide. Exactly two readings had been taken by someone else before the index step ended, so the 300 s tick landed one step early. The someone is `oo-write-gate-watchdog` (`src/database/writer.py`, `_watchdog_loop`), an ambient daemon thread armed by the first write-gate acquisition in the process: every 15 s it wakes and reads `time.monotonic()` twice (the head of the loop and the next wait). Two reads is its signature; the window it has to hit is the few milliseconds of the run, about one run in thousands. The same test passed on the same shard and position in the run before, and passed 579 of 579 when the shard's first 42 files were replayed locally in order, with the thread list at the test showing the watchdog alive and the storage-events flusher blocked in a wait with no clock; it is a race, not an order, and an unsharded run has the same odds.

**The rule.** A scripted clock replaced on a shared module belongs to one thread: `_own_clock` in `tests/test_boot_sequence.py` returns the scripted readings to the thread that installed it and the real clock to every other thread, so an ambient thread (the write-gate watchdog, the storage-events flusher, any timer) costs the test no reading. Serialising the test against those threads was not an option: they are meant to run. A test that reads the log for WHICH step was slow is only as strong as its count of clock reads.

**What the guard was shown to do.** `test_a_clock_read_by_another_thread_does_not_move_the_slow_step` starts a thread inside the index step that reads the clock twice and requires the warning to name `warm-cache` and no warning to name `article-indexes`. With the thread filter removed it fails (23 of 24 pass), which is the original failure reproduced on demand.

**Stated limits.** Other tests replace `time.monotonic` of the whole process with a tick list or a counter and have the same exposure: `tests/test_diagnostics_runs.py:664`, `tests/test_trending_live_budget.py:81` and `:141`, `tests/test_discovery_read_write_split.py:205`. None of them failed, so none was changed; the same `_own_clock` shape fits them if one does. A constant fake clock is only wrong for a stray reader, never consumed.
