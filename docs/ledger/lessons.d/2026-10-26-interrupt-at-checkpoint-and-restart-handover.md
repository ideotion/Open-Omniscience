## 2026-10-26 — a stop is not a failure to be counted and carried on from, and a record that hands over a count must hand over what the count is about (rollup checkpoint, R172 handover, panic wipe)

**Found by reading the paths the earlier fixes left.** `columnar._checkpoint` is the one place the rollup's `CHECKPOINT` runs: the build's checkpoint before each shard (R169) and the final `compact` (R164). It classified the engine's answer by class name: the allocation wall and a fatal were stops, anything else "failed" and the build carried on. `InterruptException` fell in "anything else". At the aggregate and the bulk insert the same exception already propagated (`_NEVER_RETRIED`), because the slow path would only reach it hours later; at the checkpoint it was counted in `shard_checkpoint_failures` and the next shard was aggregated, so a stop asked for while a checkpoint ran was answered by the rest of the build. Nothing in the app calls `interrupt()` on the build's connection today (the canary's timer is the only caller), so no operator has met it; the shape is what is wrong: two statements of one build disagreeing about what a stop is.

**Rules.**
1. A classifier that sorts an engine's errors into "the wall", "the instance is unusable" and "carry on" needs a fourth, named class for "someone asked this to stop", and it is NOT carried on from. Where one function is the only place a statement runs, put the class there (as the R169 note says of `_checkpoint`), not in each caller. `_INTERRUPTED` sits beside `_NEVER_RETRIED`; the interrupt propagates for the caller's generic path (`_build_and_swap` records a failed build) and `compact` documents that it is no outcome.
2. A kept record that hands a restart ONE of the fields of a run must hand over the others it implies, or say they are unknown. The R172 record carried `consecutive_failures` across a restart, so `status()` printed `consecutive_failures: 3` beside `last_outcome: null` until the process built something: the count said "failed three times" and the outcome said "never ended". The record exists only for a failed build, so the outcome is `failed`; it is marked `last_outcome_restored` because it is an earlier process's, and the mark goes when this process's own build replaces it (absent means this process's, as `failures` absent means zero).
3. A caller that drops a corpus must drop what was counted about it, in every path that drops one. A restore swap and a VACUUM called `served_cache.invalidate()`; the panic wipe, which removes the file, did not, so the served counts and (since the A-002 hooks) the status scans carried beside them outlived the corpus (0.5.1 item 38). The wipe now calls it beside `kv_invalidate()`.
4. The item that turned out to be done is stated as done: a checkpoint that fails and carries on IS logged, by class, through `_checkpoint`'s `log_failure` (the tally names only the first). The test now pins the per-shard path, which had only the final compact's.

**Limits, stated.** The interrupt is a defensive change in the sense that no code path raises it at the checkpoint today; its test builds the exception. The restored `last_outcome` is always `failed` because the kept record is only written for a failed build: if a later change keeps a record for another outcome, the handover must say which.
