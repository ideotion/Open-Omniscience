## 2026-10-28 — A merge made of several autocommitted statements voids its validity stamp BEFORE the first write and restores it after the last; a write on the failure path cannot cover a kill (R306, the keyword-tail double count)

**What was found.** `columnar.refresh_keyword_daily`'s incremental path is an UPDATE of the days the tail shares with the store, an INSERT of the days it adds, the `keyword_meta` upsert and, last, the `last_mention_id` watermark. DuckDB autocommits each, so a stop between the UPDATE and the watermark left the tail's counts added while the watermark still pointed before them. `built_epoch` still equalled the corpus epoch, so the next refresh was incremental and added the same tail again. Measured with a proxy raising on the INSERT after the UPDATE: the next refresh reported `incremental` and 4 of the 24 terms differed from a full rebuild. #1565 had closed the stale-library case only; the others (a DuckDB error, `MemoryError`, a SQLAlchemy error inside the meta upsert, a process kill) were open.

**Rules.**
1. **Where the unit of work cannot be one transaction, write "this store is not vouched for" before the first write and "it is" after the last.** A stamp that says valid is the claim; the window between the first write and the last is exactly when it is false, so it must not read valid then. `-1` is no corpus epoch, so the existing equality gate already refuses it; the reader also refuses it by NAME (`VOIDED_BUILT_EPOCH`, one constant for both writers and the reader), so a corpus epoch that ever equalled the marker would still be refused.
2. **Do not void on the failure path.** A handler that writes `-1` after catching the error covers errors only; a kill, a power loss or an interrupt that skips the handler leaves the stamp valid over a half-merge, and the handler's own write can fail for the same cause as the merge (a closed store, no memory). The stamp written before the first statement survives all of them, and the restore after the last is the only write that can be lost, which fails safe: one needless full rebuild.
3. **`_set_meta` is a DELETE then an INSERT, so a stop between them leaves the key ABSENT, not old.** An absent watermark reads as 0 (re-merge the whole corpus), an absent `built_epoch` reads as no prior build (full rebuild). The second is the safe one, which is one more reason the stamp is what gates the path.
4. **A stop before the first write voids nothing.** A hook raising at `"aggregate"` or the tail aggregate failing changed no row; voiding there would turn every refused refresh into a full rebuild. The test pins both sides (voided after a partial merge, kept before the first write).
5. **Induced faults are labelled by cause and the property is asserted after the stop.** The tests raise at one named statement of the real refresh through a pass-through proxy (the INSERT as a statement error and as `MemoryError`, a SQLAlchemy `OperationalError` in the meta upsert, `KeyboardInterrupt` standing in for a kill at the watermark write). What raised in the field is inferred; what is asserted is that the partial merge IS in the store (the premise) and the next refresh is `full` and equal to a fresh build. Red before: 6 of 8; the 2 controls (an uninterrupted merge, a failure before the first write) pass on both. A failure of the voiding write itself must stop the merge before its first statement (fail closed), and a test pins that.
