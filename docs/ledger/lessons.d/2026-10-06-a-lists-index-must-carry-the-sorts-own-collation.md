## 2026-10-06 — A LIST'S INDEX MUST CARRY THE SORT'S OWN COLLATION, A COLLATED INDEX IS DECLARED WITH `collate()`, AND A BIG BUILD IS A STEP, NOT PART OF OPENING THE DATABASE (R128, the article list's two indexes)

(1) **An index serves a sort only with the sort's own collation.** The list orders `title COLLATE NOCASE`; a plain `(title)` index is scanned for the column but the ORDER BY still sorts (`USE TEMP B-TREE FOR ORDER BY`,
pinned by a test), while `(title COLLATE NOCASE)` gives `SCAN articles USING COVERING INDEX` with no sort step: 807 ms to 3 ms cold on a 40,000-article, 2 GB store, and `(language, published_at)` (the equality first, the order
second) turns the language filter's `idx_article_language` + row reads + temp sort into one covering range: 1,284 ms to 3 ms. Results are identical with and without them (ties and NULL dates included).
(2) **Declare a collated index on the model with `collate(column, "NOCASE")`, not `text("col COLLATE NOCASE")`.** Measured on the stamp alignment (`_schema_diffs_vs_head`): with `collate()` it reads no difference with the live index
present or absent; with the `text()` form the live index reads as a permanent `remove_index`. This contradicts the "mirroring does not fix it" note on `idx_keyword_normterm_nocase` in `maintenance.py` for the `collate()` form (not tried on
that table). A declared plain index that is absent reads `add_index` (schema-behind, stamp kept, harmless, ends at the next start). Inside the class body the column is a `MappedColumn` typed `Mapped[...]`: mypy needs a `cast` for `collate`.
(3) **`PRAGMA optimize` does not analyse an index that was just built**: it is driven by what the connection's own queries used, so right after a build it is a no-op (measured: `sqlite_stat1` stayed empty). `ANALYZE main.<index>` under
`PRAGMA analysis_limit` (a sample) is what gives the planner figures; without them an equality on the first key column is assumed to match about ten rows, which is wrong for a language.
(4) **A `CREATE INDEX` over a corpus-sized table does not belong inside `init_db`**: it reads every row and holds the write lock, minutes of nothing on screen in the call that opens the database. `maintenance.DEFERRED_INDEXES`
leaves such entries out of `init_db`'s pass (`ensure_hot_indexes(engine, include_deferred=False)`; every other caller keeps the whole map) and a boot-sequence step builds them as a task-manager `BackgroundJob`: one statement each under
`write_lock()` (writers queue in Python instead of erroring on the 30 s busy timeout), the free space measured first and a shortfall a FAILED row with the numbers. A step that is a job needs `BackgroundJob.join()` (added), because the
sequence must have the result before the next step. **Adding a step to the sequence runs it for real in every test that runs the real sequence**: four existing tests (`test_boot_sequence.py`, `test_database_verify.py`,
`test_import_lifecycle_stages.py`, `test_bulk_build_window.py`'s source-order pin) had to be changed, which is the cost of an unpatched side effect on a path the suite drives.

**A CREATE INDEX IN THIS APP SORTS IN RAM, SO ITS COST IS MEMORY, NOT A TEMP VOLUME, AND IT MUST NOT BE MOVED TO A FILE (the R128 deep reads, 2026-10-06)**: every connection sets `temp_store=MEMORY` and the bundled
SQLCipher is compiled `SQLITE_TEMP_STORE=2` anyway (L2862), so the sorter of `CREATE INDEX` never writes a temporary file: it holds every key (+73.3 MiB resident for 600,000 articles with 76 Latin characters, 128 bytes an article; 272 bytes for 76 Devanagari characters: about the title's UTF-8 bytes plus 50,
so `RAM_BYTES_PER_ARTICLE` is 300 and a Latin corpus is over-asked on purpose). A free-space check that measures `tempfile.gettempdir()` therefore refuses on a volume the build never touches. **The obvious fix for the memory, `temp_store=FILE` as `backup/merge.py` does, is WRONG on
an encrypted store (measured the same day, 300,000 rows, `cache_size` 1 MiB, the spill file read through `/proc/<pid>/fd` while the statement ran): the sorter's temporary file holds the titles IN THE CLEAR (the marker string
was found in every file observed, on SQLCipher as on plain SQLite), and so did a `SELECT DISTINCT` (138,330 marker hits in an 11 MB temporary file) and an `ORDER BY` sorter: what SQLCipher keys is the main and attached databases (VACUUM's `vacuum_db` among them),
never a temporary or ephemeral b-tree; statement journals were encrypted in the observations made. VACUUM's temporary database stayed encrypted too (no marker in 11 observations), and that was true and beside the point: it was
the WRONG SIZE. At the app's 16,384-byte page size a VACUUM with `temp_store=FILE` wrote a CORRUPT store (`quick_check`: "Rowid 0 out of order"), because the internal `vacuum_db` is keyed at SQLCipher's default 4,096-byte cipher
page while its b-tree pages are 16,384, so every page that spills and is read back decodes as garbage and VACUUM writes it into the store (the deep delta read reproduced it through the real `maintenance.vacuum_database`; 4,096-byte
pages, and any store small enough never to spill, are fine, which is what the first test used; the only knob, `cipher_default_page_size`, is process-global). `maintenance.vacuum_database` keeps its pooled connection, and VACUUM's RAM cost is now gated (the PAGES IN USE times 1.25 plus the memory guard's floor against what is available, refused before the write lock; the pages in use are `page_count` minus `freelist_count` read on a connection, because the file's size on disk misses the log and counts the free pages; the
longer route is open in the open queue). **A test of an encrypted-store change runs `PRAGMA quick_check` afterwards, on a store created at the app's page size and large enough to spill: "the copy stays encrypted" is not "the copy is right".** So the cost is gated as what it is: the build is declined when the machine's AVAILABLE memory is below the estimate plus the memory
guard's floor (`memguard.avail_floor_mb`), through the guard's own reader; an unreadable figure does not refuse. The gate does not catch an estimate that is too small (one opaque statement), so a record of the attempt
is written before the first statement and cleared when the build ends however it ends: two unfinished starts in a row (a kill, a power cut) stop it until the app is updated (the record carries the version), and an
orderly quit gives its attempt back. **PRE-EXISTING, not fixed here (filed in the open queue):** `backup/merge.py` sets `temp_store=FILE` on the working copy of an encrypted store; any `DISTINCT`, `GROUP BY`, `IN` subquery, `ORDER BY` or temporary table of the merge
spills plaintext rows to the temporary directory (statement journals do not). Check the statements before relying on it. **And a refusal that only fills a job's `error` is invisible**: neither task-manager renderer draws `error`
for a kind that is not a download, so the keyed detail frame (`Framed`, which survives into the error state) is what reaches the screen in twelve languages; a test of the API field never saw the missing line. **Two
more from the same fold:** a snapshot that deep-copies a dict the worker is still changing can raise `dictionary changed size`, so the state keeps a COPY of what the worker reports; and a test that assigns
`boot_sequence._STATE[...]` leaks it, because `_reset` does not restore it (use `monkeypatch.setitem`).
