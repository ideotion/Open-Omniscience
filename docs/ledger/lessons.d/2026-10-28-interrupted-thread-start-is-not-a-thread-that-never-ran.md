## 2026-10-28 — an interrupted `Thread.start()` is not a thread that never ran: `ident is None` and `except BaseException` give a live thread's record back

**What was found (R393; the read of #1645, then a sweep).** Four handlers gave a record back when `Thread.start()` raised, on the premise that a raise means the thread never ran: `BackgroundScheduler.start()` (restored `_thread`/`_started_at`), `_watch_for_resume` (retracted the pending-resume claim), `BackgroundJob.start()` (marked the job "error") and `DamageRegistry._single_flight` (dropped the key). Two of them also read `t.ident is None` as the proof. That is true only for an `Exception`: CPython 3.13's `Thread.start()` catches nothing but `Exception` around creating the OS thread (`can't start new thread` is a `RuntimeError`), then waits `self._started.wait()` for the thread to report in, and an interrupt (a `BaseException`) during that wait escapes with the thread created and about to run. MEASURED on 3.13.17 with a `KeyboardInterrupt` injected into `_started.wait`: right after `start()` raised, `t.ident` was None and `is_alive()` False; 0.1 s later the thread had run and was alive. So `ident is None` does not mean the thread never ran. Measured consequences, each with a live worker and the record given back: `BackgroundJob` read 'error' and a second `start()` was ACCEPTED (two workers of one kind, peak 2; every job kind in the app); `DamageRegistry` dropped the key and a second call started a second thread (peak 2) instead of counting itself in `_pending`; the scheduler's first form put its previous record back beside a live loop, so `is_running()` was False, `stop()` could not stop it and the next `start()` ran a second loop.

**The rule.** A handler that gives a record back because a thread did not start is `except Exception`, never `except BaseException` and never an `ident is None` test: an `Exception` out of `start()` is CPython's own 'no thread was created' path, and an interrupt leaves the record to the live thread (whose own `finally` releases it). The trade-off, chosen: an interrupt that lands BEFORE the OS thread is created now leaves the record (a stale 'pending' claim, a 'running' job with no worker) instead of clearing it. That is the cheaper error: an interrupt reaches only the main thread (uvicorn owns SIGINT) and the callers are API and worker threads, so it is rare, and the stale value is cleared by the next start or cancel, where giving back a live thread's record starts a second one.

**Swept and not defects (R393 verdicts).** `scheduler/storage_guard.py:2148` (`stop()` skips the bounded `join` when `ident is None`: harmless, the supervisor exits on its own event); `BackgroundScheduler._start_detached` (already `except Exception`; pinned); `analytics/rollup_serve.py:1532`, `analytics/map_serve.py:193`, `api/served_cache.py:288`, `api/unlock.py:503`, `scheduler/memguard.py:409`, `briefing/service.py:142` (all act on an `Exception` or `RuntimeError` only). `ident` as a key or owner id, not as proof of a start: `monitoring/holder_state.py`, `monitoring/session_hwm.py`, `database/pool_watch.py`, `config/kv_store.py:238`.
