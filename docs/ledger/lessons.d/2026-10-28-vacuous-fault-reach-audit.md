## 2026-10-28 — A stub that raises in a test proves nothing unless the test reaches it: a measured audit of 1,255 tests, three that never did (parent sweep R385, after R376 and #1615)

**The question.** Three times this cycle a test injected a fault the code under test never met (the vacuum preflight helper, the country-migration fallback, a briefing "pin does not outlive" test), and each was green with the code mutated. Is that a corner or a class?

**A static scan cannot tell.** Flagging every test that installs a raising stub with no recorded call or asserted message flags 570 of 990: most are fault tests that prove the fault through the RESULT ("the pass still ends", "the field is absent, never zero"), and that is a sound proof. Whether a result proves the fault was reached depends on what else could have produced it; no name-level scanner decides that. Do not build a ratchet on that count.

**A dynamic audit can.** Method: copy each test file, insert `_oo_reach_(<stub name>)` before every `raise <exc>` inside a function that a test passes as an argument (module-level or nested), run the file under a one-line plugin that appends `PYTEST_CURRENT_TEST<TAB>name` to a file, restore the file, and list the tests none of whose installed stubs raised. 360 files, 1,158 tests; the same for the 109 `(_ for _ in ()).throw(...)` lambdas (97 tests, single-line calls only). Result: 240 + 7 tests whose stubs never raised, and almost all of them are correct, because the right count of raises is ZERO: `AssertionError("must not call")` guards (`_never`, `forbidden`, `refuse`, `must_not_*`), default routes that raise only for an unexpected path (`handler`, `getter`, `fake_getaddrinfo`), and name collisions (a local `link` or `fetch_segment` that is not the module's stub). **Read each by hand: the tool narrows the haystack, it does not decide.**

**The real ones (3), each proved with a source mutant that stayed green under the old test and went red under the new one.**
1. `test_a_raising_tick_sink_never_breaks_a_merge` (`tests/test_merge_step_watch.py`). `_step_watch` calls its sink at most once per `_STEP_WATCH_INTERVAL_S` (2 s) and the 200-row statement takes milliseconds, so the sink was never called. Mutant: stop swallowing the sink's exception: OLD green, NEW red. Fixed by setting the interval to 0 and asserting the sink was asked.
2. `test_the_tick_reports_elapsed_seconds_and_never_a_fraction` (same file). `SELECT 1` is a handful of VDBE operations and the progress handler fires every 1,000, so `seen` and `decorated` stayed `[]` and every assertion in the two `for` loops ran over nothing; the raising `detail` was never asked either. Mutants: un-swallow `detail`, ignore `detail`: OLD green, NEW red. Fixed with a recursive-CTE statement long enough to tick, an assertion that each list is non-empty, and the exact decorated label.
3. `test_models_endpoint_and_put_report_active` (`tests/test_llm_active_model.py`). It overrode `get_llm_client`, which `/api/llm/models` does not use (it depends on `get_ollama_client`), so the injected "Ollama is down" transport was never asked and the route read whatever Ollama the machine really had (loopback refusal in CI). Mutant: report `available: True` when down: OLD green, NEW red. Fixed by overriding the dependency the route uses and asserting the stub was asked.

**The guard, and why it is only this shape.** `tests/test_loops_over_callback_lists_assert_non_empty.py` fails on the one vacuous shape that IS statically decidable: a collection created empty in the test, mutated only inside a nested `def` or `lambda`, iterated by a `for` whose body asserts, with no assertion mentioning it as a whole (a mention that only walks it inside a generator does not count). It flagged the old `test_merge_step_watch.py` on exactly its two loops, and two more tests whose callbacks ARE reached today (`test_import_phase_progress.py`, `test_open_stats.py`): now asserted non-empty, a hardening, not a fix. 20 pinned cases, 7 scanner mutants killed.

**Rule.** (1) A fault stub is proved reached by a recorded call or by a result the fault alone can produce; a stub behind a throttle, an interval, a dependency the route does not use, or a statement too short to tick is not reached by being installed. (2) Before trusting a green fault test, ask what gate stands between the stub and the code, and open it in the test (`monkeypatch.setattr(m, "_STEP_WATCH_INTERVAL_S", 0.0)`). (3) A `for` over a callback-filled list is green whatever the code does until the test asserts the list is non-empty.

**Not covered, stated.** `Mock(side_effect=Exc)` and multi-line `.throw(` calls were not instrumented (2 and an unknown number of sites); stubs a test reaches through a name the audit did not see passed as an argument (a `monkeypatch.setattr(obj, "f", stub)` is an argument and is covered; a stub in a dict or a class attribute is not); parametrized tests were folded to one test. The audit scripts (instrumenter, plugin, driver) are in the lane's scratchpad, not in the repo: a tool that rewrites test files in place is a mechanism, so it is a proposal, not part of this change.
