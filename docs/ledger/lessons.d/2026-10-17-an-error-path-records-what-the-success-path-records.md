## 2026-10-17 — an error path records what the success path records, or the failures cannot be told apart

**What was found.** Every one of the 30 recent runs in each of the two field bundles of 2026-10-16 had ended in a pool timeout, and every record carried the same four things (started, finished, the error's class, the hygiene block). The success path records sources processed and articles stored from the pass's return value; a pass that raises never returns, so those figures were lost at the one moment they mattered, and "ingest starved" could be read only for the pass in flight.

**The rules.**
1. **When a function reports its counts by returning them, give the failure path a second way to report them.** `run_scrape_once` now notes its three counters in a module slot as it ends, whichever way it ends, and the scheduler copies them into the record of a run that raised (`pass_counts`). The slot is reset before every run, so a record can never carry another run's counts (tested with two runs in a row).
2. **A pool that is told to stop does not stop: read what it finished before you report what it did.** The obvious version reports the results the pass thread had READ when the first worker's failure surfaced through `fut.result()`. The executor's exit waits for every queued source and does not cancel them, so a pass that failed at its first worker with 19 more queued reported 0 sources and 0 articles while 19 had run and stored 38 (found by an independent read of the first version and reproduced). `run_scrape_once` now reads the unread finished futures before it hands the counts to the pass monitor and to the failing record, so the pass summary line and the run record agree; a future that raised processed nothing and is in no count, and does not replace the error that ended the pass. The test has 20 sources, 4 workers and the first two calls raising: 18 ran and stored 36. Read each future ONCE: the drain skips the futures the loop already read, and a second test makes a third worker raise only after the loop has read two results (19 processed, 38 articles; a drain that read every finished future again says 21 and 42, the mutant that proved it). The drain reads each remaining future by ``result()`` inside a ``try`` and not by asking ``exception()`` first, because the sink sweep (tests/test_sink_sweep_records.py) treats any ``.exception()`` call as a traceback writer, and a lexical rule is cheaper to satisfy than to relax.
3. **Say which counts they are, in a word the reader can filter on, and make that word the reason where they are unknown.** `pass_returned` (the pass returned and the failure came later, in the pass tail), `pass_raised` (the pass raised: every source whose worker returned by the time it ended) or `not_reported` (the failure came before anything was counted: three nulls, never zeros).
4. **Do not repeat on the success path what the record already holds, and reset the slot after the lock that makes it one run's.** A run that returned has its counts in `result`; a second copy would spend the margin the errored rows need. The member adds 117 bytes to an errored row when the counts are unknown and at most 136 when they are known (measured on the real record, 10-digit counts), at most 4.1 KB for the 30 rows of a debug bundle against 25.5 KB measured for those rows today. A run that loses the run-lock race returns before it resets the slot, so it cannot wipe the counts of the pass that holds the lock (tested with a second `_do_run` arriving mid-pass).
