## 2026-10-28 — a line you cannot read is not a line you may erase: a queue file that is read, filtered and rewritten must carry what it could not parse

**What was found (R386 class, the WAL lane's scan).** A file used as a queue is appended to by many writers, read back as records, and later rewritten from the records read. Three small decisions each look harmless alone: the reader skips a line it cannot parse; the writer appends without checking that the file ends in a newline; the rewrite writes back only what the reader returned. Together they lose data silently: a write cut short leaves a tail with no newline, the next append lands on it and both records are unreadable, nobody is told, and the first rewrite deletes the evidence. `custody_pending.jsonl` had all three, and a write cut short is exactly what a full disk produces, the failure the queue exists for.

**The rule.** For a file that is rewritten from what was read: (1) the append closes a file that ends mid-line before it writes; (2) the reader reads bytes, so a line that is not text is one unreadable line rather than an error that stops the queue; (3) every line the reader could not use is reported (line number and byte length, never its text: a queue line can hold a url or another secret) and is carried through the rewrite, set aside byte for byte or left in place when the set-aside cannot be written, never dropped. A test of such a file needs the cut-short tail, not only a clean file: write the tail, append, read, rewrite, and assert each step.

**What it costs to forget.** A record that the code answered "queued: True" for and that no later read can find, and a rewrite that destroys the only copy of the unreadable text. Not observed in the field; measured with a probe.

**Limits.** The rule is applied to `src/custody/pending.py` only; other files in `src` read lines with `except ValueError: continue` (not searched). A report keyed by line number and length is a per-process dedup, not a record that survives a restart.
