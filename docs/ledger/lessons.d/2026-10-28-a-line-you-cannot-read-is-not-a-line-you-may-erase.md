## 2026-10-28 — a line you cannot read is not a line you may erase: a queue file that is read, filtered and rewritten must carry what it could not parse

**What was found (R386 class, the WAL lane's scan).** A file used as a queue is appended to by many writers, read back as records, and later rewritten from the records read. Three small decisions each look harmless alone: the reader skips a line it cannot parse; the writer appends without checking that the file ends in a newline; the rewrite writes back only what the reader returned. Together they lose data silently: a write cut short leaves a tail with no newline, the next append lands on it and both records are unreadable, nobody is told, and the first rewrite deletes the evidence. `custody_pending.jsonl` had all three, and a write cut short is exactly what a full disk produces, the failure the queue exists for. An independent read of the first fix found the same shapes one level down, in the fix itself: the new side file was appended to with no tail check, and a read error at the rewrite's final re-read still read as an empty queue, which the rewrite then wrote over every record still owed.

**The rule.** For a file that is rewritten from what was read: (1) the append closes a file that ends mid-line before it writes, for every file the code appends to, including a file the fix adds; (2) the reader reads bytes and catches the whole family of parse failures (a decode error, a JSON error, nesting too deep for the parser), so a line that is not text is one unreadable line rather than an error that stops the queue, and a line that parses but is not a record (a value of the wrong type, a boolean where an integer is owed) is unreadable too; (3) every line the reader could not use is reported (line number and byte length, never its text: a queue line can hold a url or another secret) and is carried through the rewrite, set aside byte for byte or left in place when the set-aside cannot be written, never dropped; (4) a file that cannot be READ is not an empty file: only "not there" is an empty queue, any other read error leaves the file exactly as it is and says so, because a rewrite from an "empty" read is a deletion; (5) a reader that must not see a half-written append takes the same lock the appender holds. A test of such a file needs the cut-short tail, not only a clean file: write the tail, append, read, rewrite, and assert each step. A test of "the text never reaches a log" asserts the arguments of every record (numbers and file names only), not the absence of one marker: a marker past the first bytes of the line lets a log of the line's prefix pass.

**What it costs to forget.** A record that the code answered "queued: True" for and that no later read can find, a rewrite that destroys the only copy of the unreadable text, and a transient read error that deletes the whole queue. Not observed in the field; measured with a probe.

**Limits.** The rule is applied to `src/custody/pending.py` only; other files in `src` read lines with `except ValueError: continue` (not searched). A report keyed by line number and length is a per-process dedup, not a record that survives a restart.
