## 2026-10-26 — A byte ceiling on a log that a writer keeps filling is a time bound: name its two terms, and make the red-without the delay that stretches the time

**What was found.** ``tests/test_wal_starvation_soak.py`` failed once on CI (round 2 of 3: 9,261,792 B of WAL at the end of the scan against a ceiling of 6 x 1,048,576 = 6,291,456 B) on a docs-only change, with the code under it unchanged since the 18 Oct base. The property the test is about held in every round: a checkpoint completed while the producer was mid-scan, there were 10 in-scan releases each round and a success each round. Only the byte ceiling failed. The writer thread appends a 256 KiB row every ~20 ms (about 12.5 MB/s, no fsync per commit), and the size read at the end of the scan is the bytes written since the last ``wal_checkpoint(TRUNCATE)`` finished. A TRUNCATE costs three to four fsyncs. So the "6 MiB" bound was never a size: it held only while a truncating checkpoint finished within about half a second of the end of the scan, which is to say while fsync was fast. With 4 to 13 % margin on a fast disk, one slow stretch on a shared runner turns latency into bytes.

**Reproduction (this container, strace-injected, no disk touched).** Re-running the test and loading the CPUs did not reproduce it (peak WAL 0 to 796 KiB idle, 0 to 535 KiB with 4 CPU burners, 0 to 796 KiB with 8). Delaying every fsync/fdatasync did: 100 ms gave 1.6 to 2.9 MiB with 3 to 4 attempts a round; 300 ms gave 6,394,272 / 6,666,192 / 6,666,192 B with 1 attempt a round, over the old ceiling in every round. What was NOT shown: the runner's real fsync latency (nothing logs it), so "a slow stretch" is the mechanism that reproduces the signature, not a measured fact about that run.

**The rules.**
1. **Reproduce a CI-only failure with the mechanism, not by running it again.** Idle repeats (6 iterations of 3 rounds) and CPU-load probes found nothing; a one-line strace injection (``strace -f --seccomp-bpf -e trace=fsync,fdatasync -e inject=fsync,fdatasync:delay_enter=300ms``) reproduced the signature (few attempts, the log growing round after round, releases and the success unchanged) on the first run. When a test fails only on a shared runner, ask which resource the test silently assumes is fast and slow that one down on the real test file.
2. **A bound that mixes bytes and time has to say both terms.** The round's allowance is 6 x the checkpoint ceiling (the headroom the design promises: the log may grow to a few ceilings during a window) PLUS the writer's measured rate x the longest checkpoint attempt of that round (the bytes that arrive while the one attempt that is in flight cannot finish). Each term is a named number in the test (``_allowed_wal_bytes`` returns ``headroom``, ``in_flight`` and ``total``) and a failure prints all three. A fast disk keeps almost the old bound (the in-flight term is the rate times a short attempt); a slow one gets the extra time it took, and no more.
3. **The red-without is the delay, on the real test, not a rewrite.** The new bound fails when the log is never truncated at all (the "never truncated" pin: about 11 MB against about 6.9 MB) and passes a real round whose checkpointer is slowed by 0.6 s per attempt; and under the injected 300 ms fsync the old assertion fails and the new one passes on the same file. Two things stay in place as the anti-vacuity half: in-scan releases >= 4, a success every round, attempts > 0. A relative bound that nothing else checks would pass a round that never checkpointed.
4. **A test that fails only late in a long run is a fixed number pretending to be a property.** The run is 75 minutes in one process, the failure was one round of three, and the test file had no diff: the signal for "this assertion is measuring the machine" is that the failure moves with load and not with the code. Fold the fix into the next change of that lane rather than a PR of its own, but do not retry the job: show the cause.
