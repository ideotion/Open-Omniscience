## 2026-10-26 — a carried count must be tied to the file it counted, and the same flaw repeats wherever the first fix was not copied (Library figures, 0.5.1 item 37)

**Found by asking where else the A-002 flaw lived.** The status memo of `/api/insights/status` was keyed on the engine object, and the read of it found that a restore swaps the file under the ONE module-level engine, so the key said "same database" about a different corpus. `/api/database/figures` carries its finished whole-table `keyword_mentions` count the same way (ten times its own duration) and was keyed on the bind alone: the second copy of a pattern that had been fixed only where it was found. Cost of the flaw: after a restore, a VACUUM or a panic wipe, the Library tile showed the old file's count (and the ratio computed from it) as `counted` for up to ten times the scan's duration, about nine minutes on the field corpus.

**Rules.**
1. When a defect is fixed in one carried-state memo, grep the module tree for the OTHER memos of the same shape (`_..._MEMO` beside a `bind`, `db.get_bind() is`) before closing it. Here that was a ten-line search; the first fix did not run it.
2. The key of a carried value is: engine object (a second engine), corpus epoch (two corpora a re-index, prune, fold or restore-merge told apart), and a generation `served_cache.invalidate()` bumps through `on_invalidate`. The epoch is 0 on any file never bumped, so in practice the generation is what covers a swap; do not drop it because the epoch looks like the real key.
3. Read the generation BEFORE the first read of the database in the computation, store only if it is unchanged, and mark a payload computed across a change `__discard__` so the asker is answered but the cache is not filled with a number about a file that is gone. This holds for a recorded failure as much as for a count: a "failed, retry in 900 s" about the old file is not the new one's.
4. Every path that replaces or removes the corpus calls `served_cache.invalidate()`: the restore swap and VACUUM already did, the panic wipe since #1496. The memo hook makes that one call enough.

**Limits, stated.** A recompute already running when the swap happens can still read the old file for the rest of its statement; what is guaranteed is that its number is neither carried nor cached. The failure window of the figures (900 s) still rides the cache entry's own TTL, so the cheap figures do not refresh during it; the status endpoint keeps its failure in a separate record for that reason, and the figures were left as they were because that is a freshness choice, not an identity one.
