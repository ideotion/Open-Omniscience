## 2026-10-16 — A "TRANSACTION" THAT HOLDS DDL IS ONLY ONE IF THE DRIVER SAYS SO; AND A TOKENIZER IS READ FROM THE TABLE, NOT FROM A MARKER

(1) **pysqlite does not open a transaction before DDL.** The first version of the tokenizer swap ran `DROP TABLE`, `CREATE VIRTUAL TABLE` and the rebuild inside the caller's `with engine.begin()` and assumed a failure in the rebuild would roll the drop back. A test that made the rebuild raise showed the old index GONE: the drop had committed by itself, so a death mid-rebuild would have left an empty index on a stopped app. A `SAVEPOINT` taken first makes the three statements one unit whatever the driver does (it starts the transaction when none is open, nests when one is). **Rule: a guarantee that a multi-statement change is atomic is proved by making the last statement fail and reading the first statement's effect back; the test is the only thing that saw it.**

(2) **The tokenizer an index has is a fact of its own table.** FTS5 fixes it at CREATE and stores it in the table's definition in `sqlite_master`; reading it from there means there is no marker that can disagree with the table (a restore, a copy or a half run cannot desynchronise it), and `fts_status` and the migration both ask the same question.

(3) **A rebuild this size is paid where the operator has already stopped the app.** 981 to 1,645 s per 130 GB is not a boot cost; R39 put it in the country migration's window, so the migration prints the figure first, labelled as scaled from a recorded measurement, and a store that only needs the index gets an index-only run without a second safety copy.
