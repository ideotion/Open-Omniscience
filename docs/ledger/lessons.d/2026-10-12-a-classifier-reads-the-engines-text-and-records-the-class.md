## 2026-10-12 — A CLASSIFIER READS THE ENGINE'S TEXT AND RECORDS THE CLASS, NEVER THE LINE (E3 folds 12 and 13, the coordinator's check of fold 11)

`damage.corruption_of` is the one place the damaged-database work reads a driver's own words: it takes the first line of the driver's error to tell a damaged page ("database disk image is malformed") from a damaged schema ("malformed database schema (name) - ...") from a driver that gave a code and no usual line. It also RECORDED that line (cut at 160 characters), in the incident record `data/database-damage.json`, which rides the diagnostics bundle, and as the reason of the verdict a per-table check files. SQLite words some corruption errors with the name of the schema object and a fragment of its definition, and the record is the one thing in the bundle that no code of ours wrote.

The rule: **classify on the raw line, record the class.** The record now carries one of three FIXED labels (`CORRUPT_IMAGE`, `CORRUPT_SCHEMA`, `CORRUPT_OTHER`, chosen by what the line starts with) and the exception's class name (`driver_class`); no part of the driver's line goes on, scrubbed or not. A scrub is the right tool where the text must be kept (a failure reason the operator needs word for word); where the class answers the question the record exists for, the class is the whole record, and there is nothing left to scrub or to forget to scrub in a new form.

The test that holds it feeds a driver error carrying a marker in each place SQLite puts text (the page, the schema object's name, the fragment after it, a second line, a source line, a code with unusual text) and asserts that the marker is in none of: the dict `corruption_of` returns, the JSON file the registry wrote, and the reason of `verify.classify_error`; and that each class gets its own label (a mutant that collapses the labels, one that returns the raw line from either branch, and one that drops `driver_class` are all killed). A guard that only passed the ordinary "database disk image is malformed" would pass against an implementation that records the whole line, because for that text the label and the line are the same string: the markers are the test.

**Fold 13 swept the rest of the chain for the same shape, and the rule held at every site.** (a) A record's `write_error` (the text of the `OSError` a drive raised) named the PATH it failed on: a home folder with a person's name in it; it is now `failure_label(exc)`, the class and, for an `OSError`, the errno NAME (`OSError ENOSPC`), and the diagnostics member's catch-all says the same instead of `str(exc)[:160]`. (b) `salvage._failure_text` recorded the driver's scrubbed first line, because an earlier check had asked for the scrub; the later ruling overrides it, so it classifies on the raw error and records the class plus a fixed label (the damage label, or SQLite's own constant name such as `SQLITE_IOERR_READ`, validated against a pattern). A scrub is the answer where the text must be kept; the class is the answer where it need not, and removing the scrub removed its whole family of tests (every form of the key, a cut before a scrub). (c) Twenty-nine `exc_info=True` logs the damage chain had added (damage, repair, verify, salvage, the article-list indexes, the start-up hooks) now log `type(exc).__name__`; the traceback of a database error ends in the engine's own words and a record's `exc_info` rides the bundle. A source-level test (`test_no_logging_call_of_the_damage_chain_asks_for_a_traceback`) holds the five modules to it, because the sites are many and the next one is written by someone who has not read this. (d) **The coordinator's check of fold 12 found two more of the same shape in main, in code the damage work never touched, because a sweep by `exc_info` does not see a text kept in a field.** The pool's invalidation ring (`pool_watch._on_invalidate`) stored `str(orig)[:160]` and logged it, and the ring is the `write-gate.json` member of the bundle; the full-text probe (`fts_status`) put `str(exc)[:200]` in an `error` that the integrity report copies. A length cut is not a scrub: 160 characters hold a whole `malformed database schema (name) - ...` line. Both are class-only now (the pool record keeps the exception's class and a `code`, SQLite's constant name or an errno name, and has no `message` at all; the probe uses `damage.failure_text`, which `salvage` and `repair` share), and the sweep that finds the next one is a grep for the two shapes, `exc_info` and a slice or `str()` of an exception stored in a dict, over every module whose record rides a bundle; the record's consumers are the second place to look (`write-gate.json`, the integrity member, the damage member). (e) **A cause chain is a sink, and "the runner scrubs it" was a belief until a test asked.** The first reading was that `raise X from exc` in the salvage and repair paths could stay, because the job runner writes a failed job through `secret_scrub`. The coordinator's ruling made that conditional on a test that pins it, and the test failed: `log_failure` writes the whole traceback, cause and context included, taken clean of the passphrases and of nothing else, so the driver error's own line rode the log through the chain (the published `error` is `str(X)` only and was never the leak). The 21 `raise` sites that chained a driver, SQLAlchemy or OS error in `salvage.py` and `repair.py` are `from None` now, because their own exception already says the class and a fixed label; the guard reads every `raise ... from <name>` of the five modules, including the ones whose `from` is on the closing line of a multi-line statement (the first version of the guard matched single lines and missed three; a grep for the `from exc` still in the file is what showed it), and a wrong-key refusal pins the traceback it prints. A scrub that takes out the secrets you know is not a scrub of words you do not. (f) What was examined and left, by the coordinator's ruling: the lines of `PRAGMA quick_check` / `cipher_integrity_check` that a verification entry keeps in its detail (the engine's report of pages and structure, with page numbers, table and index names and row ids, not an exception's text or a statement), and the 535 other `exc_info` calls and the `str(exc)[:N]` records of `src`, which become their own repo-wide sweep with a guard after the carrier opens.
