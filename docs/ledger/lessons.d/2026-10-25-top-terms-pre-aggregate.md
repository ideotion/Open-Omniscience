## 2026-10-25 — a join in front of a text GROUP BY carries one text row per fact row: sum on the integer key first

The all-history most-mentioned query joined every `keyword_daily` row (one per keyword and day) to `keyword_meta` and grouped the joined rows by four text columns (term, normalized term, kind, language). The engine therefore held a text row per keyword and DAY before it could merge them. On generated corpora at the 1,004 MB tier (DuckDB 1.5.6, memory limit 957.5 MiB, 8 mentions per keyword, one run per size) that query failed with the engine's memory error at 20, 24 and 28 M mentions, with the rollup resident at 99 to 135 MiB. Summing per `keyword_id` first (an integer key, two sums) in an inner query, joining the metadata to that and keeping the text grouping above it answered at all three sizes with the same ranked mention values, polled peaks 652 / 795 / 915 MiB (standalone bench, 2026-10-17); the built serve path reproduced the 20 and 24 M cells (670 / 796 MiB, same ranked values) and its 28 M cell was lost to container recycles, so it is a 0.5.1 item. The extrapolated stop is near 29 to 30 M mentions and is inferred, not measured.

What it cost: the serve answered an EMPTY list (counted as a "top-terms" fallback; it did not go live, see 2026-10-26-serve-oom-goes-live) at every corpus size the rollup build itself had just been made to reach, so the build fix was not felt where the corpus was largest.

Rules it gives:
1. A query that joins a wide text table to a many-row fact table and then groups by the text columns should group by the fact table's integer key first; the text grouping above the join keeps keywords that share their text columns adding, so the result is the same rows.
2. The check that it is the same query is an equality test against the old query text on a corpus with duplicate text tuples (here: two ids sharing all four columns, and one id differing only in language), with a precondition that no two rows tie, so the test compares values, not the engine's tie order. The check that the change does what it claims is a plan test: the join feeds the text grouping one row per keyword, not one per keyword and day (red on the old query: 87 rows against 9).
3. A shape that is exact only if a key is unique (grouping by the text tuple alone) is not exact unless the schema guarantees it. The schema here does not (no unique constraint on the four columns), so that shape was measured and not built; `check_tuple_uniqueness.py` in the lane folder counts the duplicates on a real store, read-only.

Read and left alone (post-#1427 audit, so a later reader can see it was looked at): of the five `_bulk_insert` callers, the build's two (stage insert, meta insert) turn the engine's memory wall into a `duckdb-limit` stop; the other three (the `keyword_agg` read model, the `_new_meta` top-up, the refresh stage in `refresh_keyword_daily`) run on the persisted store, which has no wall hold, and an out-of-memory error there propagates to the generic handler as it did before #1427. The only change is the exception class name in the log (`_PlainEngineWall`, not the engine's own). No behaviour differs, so nothing was built.
