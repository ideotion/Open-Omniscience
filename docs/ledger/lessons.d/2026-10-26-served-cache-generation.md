## 2026-10-26 — a hook that forgets what was carried is not a fence: the store must refuse what was computed across the change (served_cache generation, R233)

**Found by an independent read of the figures fix (#1500).** `served_cache.invalidate()` cleared the cache and then ran the hooks that make a module forget what it carried beside it; #1485 and #1500 added a generation on each module, read before the compute and checked when the module remembers its own scan. The reader asked what stood between the compute's last check and `_store`, and nothing did: a swap that lands there leaves the old file's numbers cached under a bind that is the same engine object (the one module-level engine survives a restore), and with no write since, every later poll re-stamps the entry `verified_current`. The window is microseconds on the keys that check; on `db:stats` and `library:overview`, whose counts take tens of seconds and have no check at all, the compute spans the swap.

**Rules.**
1. The fence belongs where the value is stored, not in each producer: `invalidate()` bumps a generation under the cache's own lock (the whole cache, or one key); `refresh` and the inline cold path read it BEFORE the compute reads anything; `_store` compares it under the same lock and refuses. A producer-side check can only narrow the window; a check under the store's lock closes it, and it covers every key family at once, including the ones nobody thought to guard.
2. Read the generation before the first read of the database and never after: read after, a swap during the compute is already folded into the number that is compared, and the test that places the swap inside the compute is the one that goes red.
3. A refused store still answers the asker (the number is the best there is), caches nothing, and leaves the next poll to compute over the file that is there. A keyed invalidate bumps only that key, so another key's long count is not discarded for it.
4. A test for this places the swap AFTER the compute's last statement (a wrapper that invalidates once the real compute has returned): a swap inside the compute is caught by the per-module checks and proves nothing about the store.

**Limits, stated.** A compute still reads the old file for the rest of its statement; what is guaranteed is that its number is not cached. The generation counters live in memory only, as the cache does.
