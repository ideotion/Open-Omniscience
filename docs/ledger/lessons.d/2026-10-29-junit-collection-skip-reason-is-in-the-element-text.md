## 2026-10-29 — a pytest junit report keeps a skip's reason beside an ABSOLUTE PATH, and at collection time only in the element TEXT; a summary built from it prints classes and counts, never a reason (PR #PRNUMBER)

**What was found.** The skip block of `pytest -rsfE` is hundreds of lines and the only job-log reader a session has returns the last ~13 KB, so the skips of a job could be read only by re-running the suite locally. The remedy is to read the machine report instead, and the report is not safe to print. Measured on pytest 9.1.1 with `--junitxml`: a test-level skip is `<skipped type="pytest.skip" message="REASON">/abs/path/tests/test_x.py:7: REASON</skipped>`: the reason is twice, the second time after an absolute path. A skip at COLLECTION time (a module-level `pytest.importorskip`) is a `<testcase classname="" name="tests.test_x">` whose `<skipped message="collection skipped">` carries the reason and the path ONLY in the element text, as the repr of a tuple: `('/abs/path/tests/test_x.py', 2, "Skipped: could not import 'duckdb': No module named 'duckdb'")`. An expected failure is `<skipped type="pytest.xfail">` and is not a skip. A reader that takes `message` for the reason finds `collection skipped` for every module-level skip, and a reader that prints the element text prints the runner's directory layout (`/home/runner/work/...`) into a log and a step summary.

**The rule.** An observation step over a pytest report prints FIXED WORDS, INTEGERS and identifiers that a strict pattern matched before use, and nothing else: here the class `import MODULE` (the one reason with a machine-readable shape, `could not import 'MODULE'`, read from `message`, or from the element text when the message is `collection skipped`) or `other`, and the test module (`tests.test_x`, from `classname`, or from `name` for a collection skip, cut at the first `test_*` part). Everything outside those two shapes becomes a fixed word (`other`, `(unnamed)`, `(not a test module)`). `tests/test_ci_skip_summary.py` plants a path, a token-shaped secret, a line break and a `::error::` workflow command in every field and reads every output line against a list of fixed line shapes, and it summarizes the report a REAL pytest writes, so a pytest release that moves the shape fails there and not silently in CI. The parser is `defusedxml` (an entity-expansion document is refused and only the exception's class name is printed), the step is `if: always()` and `continue-on-error: true`, and the script exits 0 whatever it finds: a count that moves is a question for a reader, not a verdict (R350).

**The ordering trap beside it.** `tests/test_ci_installed_versions_step.py` finds "the last pytest step" by the substring `pytest` in a step's `run` and requires the installed-versions step straight after it, so a step that reads the report and names the runner in its command would become that step. The summary step goes AFTER the versions step and its command is `python scripts/ci_skip_summary.py "$RUNNER_TEMP/junit.xml" | tee -a "$GITHUB_STEP_SUMMARY"`; `tests/test_ci_pytest_flags_and_preflight.py` pins that exact text. Under GitHub's default `bash -e {0}` (no pipefail) a pipeline ends with the status of `tee`, so the summary step cannot turn the job red by its own pipe either.

**Where it applies.** Any script that turns a pytest report, a coverage file or a log into text for a CI log or a step summary; any new whole-suite `pytest` line in `ci.yml` or `release.yml` (it needs `-rsfE`, and the scan in `tests/test_ci_pytest_flags_and_preflight.py` names it if it is bare). The portability job's Windows leg runs under PowerShell, which does not expand `$RUNNER_TEMP`, so it writes no report.
