## 2026-11-01 — a scheduler loop thread that cannot start turned a FINISHED exclusive operation into a 500

**What was found (WAL's measured probe, `wal-lane/probe-refused-loop-start-2026-11-01.md`, main 6ac8ae7; injected failure, not seen in the field).** With `Thread.start()` refusing the `oo-scheduler` thread: `POST /api/system/encrypt-db` answered 500 (`RuntimeError: can't start new thread`) although the store WAS encrypted and the plaintext `pre-encrypt-…db` snapshot was on disk, so the response that reports both was lost; `GET /api/diagnostics/all` answered 500 after building the whole bundle (17.5 s) and dropped it. Cause (read, then reproduced with a fake scheduler whose `start()` raises): `exclusive_window`'s `finally` calls `resume_after_exclusive_operation`, which called `_start_or_stand_down` inside a `try ... finally` with no `except`, and `Scheduler.start()` re-raises a refused thread. The function's own contract ("a courtesy call never raises into the operation's own finally", written beside the watcher branch) was kept for the watcher and not for the start. Every operation that runs in the window shares the exit (restore volumes `volume_job.py`, `import_queue.py`, `stream_backup.py`, `repair.py`), so one guard fixes them all; they were not probed one by one.

**The fix.** One `except Exception` around the CALL of `_start_or_stand_down` in `resume_after_exclusive_operation`: a WARNING that names the exception's CLASS only (never its words: the operation may have held a passphrase), then it falls through to the existing pending-resume watcher, which says so where the operator looks if it cannot start either. NOT inside `_start_or_stand_down`, whose retry loop must stay free of a handler (R163, `tests/test_gates_survive_an_interrupt.py`: CPython 3.13 puts a loop's back-edge outside the exception table). An interrupt (`BaseException`) is not caught and the `finally` still releases the hold.

**The rule.** A courtesy call made from a `finally` that finishes someone else's operation must not let its own failure replace that operation's result; when the courtesy has a fallback (here the watcher), the failure goes to the fallback, not up. Same family as R386 (an exception dropped without a record): here it is recorded, by class.

**Pinned by** `tests/test_resume_refused_loop_start.py` (5): red on main (3 of 5), a refused start does not raise out of the window and a watcher resumes collection, the words stay out of the log, a watcher that cannot start either says so, an interrupt is not swallowed and the hold is released, a start that works is unchanged. Mutant-proven: words in the log, `BaseException`, return instead of falling through to the watcher each turn a test red.
