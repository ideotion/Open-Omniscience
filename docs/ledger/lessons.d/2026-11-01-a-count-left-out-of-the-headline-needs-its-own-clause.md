## 2026-11-01 — a count that is left out of the headline figures must be printed in a clause of its own, or a pass where everything is left out reads as an empty success (PR #PRNUMBER)

**What was found.** R293 made a host's own `Crawl-delay` deferral a bucket of its own in the law tracker's tally (`deferred`), and kept it out of `documents` ("attempted") and `errors`, on purpose: nothing failed and no request was made. Two documents whose host defers, driven through `track_watched`: `{'documents': 0, 'errors': 0, 'deferred': 2}`. The tally was right. Three readers of the same documents disagreed with it. (1) The Law table badged both rows `fetch error`, because the tracker stored the deferral as `fetch error: Crawl-delay ...` (kept on purpose until a verdict and its label were ruled) and `_verdict_of` classifies the stored text. (2) The coverage report's verdict mix called both `error`, because it calls the same function. (3) The "Track changes now" toast printed `Tracked ${documents} law(s): ... ${errors} errors.` and never read `deferred`: a pass where every host deferred said «Tracked 0 law(s): 0 baselines, 0 changed, 0 flagged, 0 errors.» and nothing about why nothing was fetched, which is the all-zero success the airplane-mode fix (R292, `skipped_offline`) had just removed from the same line. Nothing was lost and the politeness behaviour was right; the three surfaces simply did not say the same thing, and a ruling (Q1013 = a: a deferral is not a failure) was contradicted by the badge. Found by driving the tally, the table row and the coverage report on the same two documents (`export-lane/deferred-law-verdict-2026-11-01/deferred_probe.py`).

**The rule.** (1) When a bucket is deliberately left out of the headline counts, EVERY message built from the headline counts gets a clause for the bucket, shown only when the key is present (the convention of `skipped_offline`), because without it a pass whose members all fell in the bucket prints as an empty success. A grep for the key's name in the UI is the audit: a key the server sends and no client file reads is a count nobody is shown. (2) A stored status that is a verdict in waiting is a decision with a cost, not a neutral choice: the cost here was a badge that contradicted a ruling. When the reason for waiting is «the label is not ruled yet», the pending state belongs in the test that pins it (`test_a_crawl_delay_deferral_is_not_a_check_and_not_an_error` said so in a comment), so the flip is one assertion. (3) A row stored before a new classification is NOT reclassified by guessing at its free text («Crawl-delay» inside a `fetch error:` message): the next check rewrites it, and the transitional state is pinned in a test (`test_a_row_stored_before_the_verdict_existed_still_reads_as_an_error_until_its_next_check`). The tracker keeps a deferred document's old check time, so it heads the due order and is asked again on the next pass; no migration. (4) A classifier over free text judges the prefix it owns FIRST (`deferred` before the `robots` substring test), so no word inside the stored reason can turn it into a verdict about the document.

**Where it applies.** Every UI line built from a tally that has a bucket outside its headline, and every verdict mapper that reads a status a tracker wrote as free text. NOT checked here: whether the Wikipedia track-now, the feed ingest or the collector's pass summary have such a bucket; the grep in rule (1) is how to find out.
