## 2026-11-01 — a count that is left out of the headline figures must be printed in a clause of its own, or a pass where everything is left out reads as an empty success (PR #1684)

**What was found.** R293 made a host's own `Crawl-delay` deferral a bucket of its own in the law tracker's tally (`deferred`), and kept it out of `documents` ("attempted") and `errors`, on purpose: nothing failed and the document itself was not requested (robots.txt may have been read first). Two documents whose host defers, driven through `track_watched`: `{'documents': 0, 'errors': 0, 'deferred': 2}`. The tally was right. Three readers of the same documents disagreed with it. (1) The Law table badged both rows `fetch error`, because the tracker stored the deferral as `fetch error: Crawl-delay ...` (kept on purpose until a verdict and its label were ruled) and `_verdict_of` classifies the stored text. (2) The coverage report's verdict mix called both `error`, because it calls the same function. (3) The "Track changes now" toast printed `Tracked ${documents} law(s): ... ${errors} errors.` and never read `deferred`: a pass where every host deferred said «Tracked 0 law(s): 0 baselines, 0 changed, 0 flagged, 0 errors.» and nothing about why nothing was fetched, which is the all-zero success the airplane-mode fix (R292, `skipped_offline`) had just removed from the same line. Nothing was lost and the politeness behaviour was right; the three surfaces simply did not say the same thing, and a ruling (Q1013 = a: a deferral is not a failure) was contradicted by the badge. Found by driving the tally, the table row and the coverage report on the same two documents (`export-lane/deferred-law-verdict-2026-11-01/deferred_probe.py`).

**The rule.** (1) When a bucket is deliberately left out of the headline counts, EVERY message built from the headline counts gets a clause for the bucket, shown only when the key is present (the convention of `skipped_offline`), because without it a pass whose members all fell in the bucket prints as an empty success. A grep for the key's name in the UI is the audit: a key the server sends and no client file reads is a count nobody is shown. (2) A stored status that is a verdict in waiting is a decision with a cost, not a neutral choice: the cost here was a badge that contradicted a ruling. When the reason for waiting is «the label is not ruled yet», the pending state belongs in the test that pins it (`test_a_crawl_delay_deferral_is_not_a_check_and_not_an_error` said so in a comment), so the flip is one assertion. (3) A row stored before a new classification is read by the EXACT shape its single producer wrote, never by a word searched anywhere in free text, and never by waiting for the next check to rewrite it. The first draft of this change waited (the old rows read as errors «until their next check») and the Opus read of #1684 showed why that does not hold: `auto_track_due` asks ONE document per host per pass (the other due documents of a host that deferred are passed over, `track.py` `deferred_hosts`) and never asks an unwatched one, so a host's sibling rows would have shown the old wording for up to (N-1) x its Crawl-delay and an unwatched row for ever. The old shape, `fetch error: Crawl-delay <n> s: not before <time>`, comes from one raise site (`src/ingest/__init__.py`; a retry that defers re-raises the failure in hand instead), so `_verdict_of` matches that exact start of text (`_PRE_R406_DEFERRAL`), a message that only MENTIONS a Crawl-delay stays an error, and a test drives the real fetcher to get the message so a reworded raise cannot leave the pattern matching nothing (`test_the_message_the_fetcher_really_raises_is_read_as_a_deferral_in_both_stored_shapes`). A claim that a later pass will fix old rows needs the code path that does it; check it with a probe of two passes over several documents of one host. (4) A classifier over free text judges the prefix it owns FIRST (`deferred` before the `robots` substring test), so no word inside the stored reason can turn it into a verdict about the document.

**Where it applies.** Every UI line built from a tally that has a bucket outside its headline, and every verdict mapper that reads a status a tracker wrote as free text. KNOWN sibling, not fixed here (a different file and owner): the Activity Ledger's `lane:law` entry (`src/monitoring/activity_ledger.py`) is built from the same `auto_track_due` tally and prints «Tracked laws: N document(s) read, N change(s) found» with no deferred or errors clause, so a pass where everything deferred reads «0 read, 0 found». NOT checked here: whether the Wikipedia track-now, the feed ingest or the collector's pass summary have such a bucket; the grep in rule (1) is how to find out.
