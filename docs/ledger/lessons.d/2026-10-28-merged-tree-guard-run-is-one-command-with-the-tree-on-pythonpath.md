## 2026-10-28 — The merged-tree guard run is one command (`guards_for_diff.py --onto REF`), and a guard run must put the tree it runs in first on `PYTHONPATH`

**What was found (the coordinator's pick of items 1 and 2, 2026-10-28 12:50 UTC; the "tests/-wide guards on the merged tree" lesson; PR #1635).** CI green-lights a head, and by the time the go is given `main` has moved: #1626's head was built on `23f8798e1` and merged when `main` was `ebd627386`, eleven files later. Merging `main` into the branch to test the real result restarts a CI cycle of about 75 minutes (R190 forbids it while CI runs), so the question "does the tree that will exist after the merge pass what guards the tree?" was answered by hand, in a scratch worktree: merge, work out which guard files apply, run them (20 files, 697 tests, 164 s that day). Picking by hand is where a guard is forgotten, and the pick has a rule already: `scripts/guards_for_diff.py` (groups 1 to 4 of `docs/maintenance/PRE_PUSH_GUARDS.md`). It judged only the branch's own tree and said "merge it first" when the base was ahead. `--onto REF` runs the same rule on the merged tree: a scratch `git worktree` of REF, the branch's committed HEAD merged into it (a commit of the worktree alone, on a detached HEAD, with its own identity and no hook, signing, signature check or rerere of the user's; the rest of their git configuration and the repository's `merge=union` rule still apply), the plan built there, the steps run there, the worktree removed. `--keep` leaves it for a red; a conflict is a named stop that lists the files; uncommitted changes and a change under `src/` are named in a NOTE.

**MEASURED, the part that was not in the plan: the run itself was not independent of where the install points.** On ONE tree (`54ab02a13`, the merge of #1626), the eight restore and WAL files that start child processes (`test_restore_collector_exit`, `test_restore_bumps_epoch`, `test_restore_carries_live_settings`, `test_restore_fixture_matrix`, `test_forensics_wal_at_boot`, `test_failed_open_wal_facts`, `test_r183_leases`, `test_main_module_alias`) gave 111 passed and 4 failed in a scratch worktree, and `test_restore_collector_exit.py` alone gave 49 passed and 4 failed **in the checkout itself**. With the worktree's path first on `PYTHONPATH`, all 115 passed (160.7 s against 157.9 s). The four are the same four tests. The cause: the child process imports `src` from `sys.path`, which is its working directory only for a `-c` or `-m` child started in it, and otherwise from the editable install's finder; this sandbox's `__editable___open_omniscience_0_5_0_finder.py` maps `src` to `/tmp/claude-0/work/tickb`, a stale worktree (`cd /tmp && python -c "import src; print(src.__file__)"` printed `/tmp/claude-0/work/tickb/src/__init__.py`). So a child ran **another tree's `src`**, whichever checkout the install was last made in. The earlier lesson (08:58 UTC, "scratch git worktree runs can red-herring: the children import the primary checkout's `src`") was right about the mechanism and measured it on a machine whose install pointed at the primary checkout; here the primary checkout is red too. Both are the same fact: **the child imports the installed tree, not the tree under test.** CI does not see it because its install points at the checkout.

**The rule.** `run()` gives every step `PYTHONPATH` led by the tree it runs in (`tree_env`), in the plain mode as well as with `--onto`, and says so on its first line. A test that starts a child inherits it; a child started with `-I`, or with `PYTHONPATH` removed (`scripts/analysis/run_stage_a.py:377` pops it), still imports the installed package. Tests that set their own `PYTHONPATH` (about twenty do, to `ROOT` of their own file, which is the tree under test) are unaffected. The advice "run the merged-tree check in the primary checkout, not a worktree" is therefore not about the import (that is closed) but about what a worktree is not: the checkout the app runs from. The project's acceptance is unchanged and the tool repeats it: a scratch-worktree run is the merged-tree check **only for a branch that touches no `src/`**; for one that does, the NOTE says to merge REF into the branch and run the plain `--run`.

**Also found while doing it.** `TREE_WIDE` (the pattern that finds the tests which judge every file) did not match a test that walks the TEST files, `glob("test_*.py")`: `test_artifact_file_members.py`, `test_import_conclusion.py` and `test_source_slicing_discipline.py` were picked by no rule, and those are exactly the guards a test file that `main` has added can break. One alternative added; the tree-wide pick went from 91 to 94 files. The pick is a heuristic and the page says so.

**What the Opus read of the first head found (all folded).** `git worktree prune` in the user's repository on every exit dropped the entry of every worktree whose folder was missing, not only the scratch one (an unmounted disk): removed, the entry is now removed by the path recorded at creation. SIGTERM or SIGHUP in the middle of a step (a closed terminal) left the worktree, its folder and its entry with no message, because Python dies at once: the handlers raise `SystemExit` while a scratch worktree exists, `subprocess.run` kills the step, the `finally` runs, the handlers are put back; a SIGKILL still cannot be caught and the page says so. `git worktree add` ran the user's `post-checkout` hook, which turned a failing one into exit 2 with only "failed: 1": it now gets the same scratch settings as the merge, and those gained `merge.verifySignatures=false` and `rerere.enabled=false` (a conflict would otherwise be recorded in the repository's shared rr-cache). `merge=union` on `docs/ledger/shipped.csv` merges an edit on both sides silently here where GitHub reports a conflict (rule (5a) of CLAUDE.md): a NOTE names such a file when both sides changed it. `git status` followed `status.showUntrackedFiles=no`, which hid an untracked test from the uncommitted-work NOTE. `--keep` printed the `kept:` line only on a clean end. The claims were softened to what the code does: the children import the tree's `src` only when they inherit the environment, and "nothing of the user's" became the list of what is neutralised and the statement that the rest of the git configuration applies. The tests gained a machine-independent identity check (`user.useConfigOnly`), a `post-checkout` and a `reference-transaction` hook, a second worktree whose folder is missing, a locked worktree, a real process sent SIGTERM and SIGHUP, and an autouse fixture that fails any test that leaves a directory in its scratch temp folder (twelve such folders had been left in the real `/tmp` by the mutant runs, because most `--onto` tests did not look).

**What it does not prove.** It runs the guards the script picks, not the suite. It runs the committed HEAD. It is a worktree run, accepted for a branch with no `src/` change only. A green run is not CI: the runner image, the Python patch level and the installed versions are the machine's own (`scripts/diff_installed_versions.py` is how to compare them). It needs a full checkout's disk while it exists. The merge commit is unreachable once the worktree is gone and is collected by git's own gc.
