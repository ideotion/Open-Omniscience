## 2026-10-06 — A FILE SWAP IS NOT SAFE UNTIL EVERY HANDLE ON THE OLD FILE IS REFUSED, THE LOG IS PART OF A FILE'S IDENTITY IN WAL MODE, AND A SIDECAR IS INPUT (the deep read of E3, B1-B3, S1-S7)

(1) **`dispose_engine()` closes idle connections only; a checked-out one stays on the OLD inode, and in WAL mode SQLite never notices the name moved.** SQLite's «the database file has been moved» check runs
for rollback-journal databases only. Measured by the read: a form loads, waits on the write gate for the whole repair, then saves; the save commits with no error into the file that is now `<stem>.damaged-*`
(removed 30 days later) while the library reads as if it never happened. The fix is not to close harder but to REFUSE: `library_generation` stamps each connection of the corpus engine at connect time, and the swap bumps a
counter; a statement on a connection made before it raises BEFORE it runs and the connection is invalidated, so a save that waited fails loudly and is made again. (The next entry is what the second read made of this: the bump goes BEFORE the replace, inside an exclusive lock every open shares, and a COMMIT and a checkout are guarded too.) The restore's swap
(`backup/merge.py`) had the same mechanism and calls the same helper now. A test of this needs a CHECKED-OUT connection across the switch, which a test that disposes the engine
and opens a new connection never has: the test that reproduces the loss (no guard) sits beside the one that proves the guard, so the pair cannot pass for the wrong reason.
(2) **In WAL mode a commit leaves the main file's size, modification time and inode alone, so an identity made of those three «matches» a file that has been saved to.** The sidecar's `source` identity now includes the log's size,
the swap empties the log into the file first (a TRUNCATE checkpoint, the restore's own order, on the data-version connection: see the next entry, (4)) and refuses while a connection still pins it, and a resumed swap compares the identity AGAIN after that fold,
because between the decision and the write gate a save can land. The extra `busy_timeout` a checkpoint wants must be given back before the connection returns to the pool: a connection that goes back with 0 hands the next writer
«database is locked» instead of a wait (the hygiene checkpoint does the same restore for the same reason).
(3) **A sidecar a function acts on is an untrusted input.** `find_resumable` unlinked whatever file a sidecar named as `finished`, and treated `source: null` as matching a file that was not there: an edited sidecar made `plan()`
(which runs at every start, damaged or not) delete the live library. Each name is now checked against the pattern a repair gives, `finished` must be the sidecar's own name without `.json`, the identity must be whole, and a
sidecar that fails removes only itself. The deletion of scratch matches the whole name, not a glob (`*` matches `notes`).
(4) **A cut BETWEEN the replace and the bookkeeping is a state, not an absence.** The next start found the sidecar, found no finished copy, wrote the sidecar off in memory and went on: the kept file (the size of the whole
library) was never recorded, never mentioned and never removed, the follow-up steps never ran and the attempt marker stayed at 1. `plan()` now names the state (`finish`) and `_finish` writes what the swap would have. The general
shape: for every ordered pair of steps ask what the NEXT start sees if the process died between them and give that state a name that acts.
(5) **A record a dead process left `running` must not count as running.** A repair a crash ended held every later removal until ten newer repairs pushed the record out; the registry now marks them `interrupted` at the next start
and asks only about this process's own. **A switch that turns one thing off must not turn off a different thing that reads the same flag:** `OO_DAMAGE_GUARD=0` turns the PAUSE off (`latched()` answers False), and the removal's
«unless the library is damaged again» read `latched()`, so the switch turned the wait off too; the holds now read the registry's own state.
(6) **A notice that promises what the code does not do is a defect of the code.** «Repaired at its next start» was said for damage found while the app ran, and the next start planned no check; the plan now treats an earlier
process's incident that no finished check follows as a reason to check. The sweep's «removes it on {date}» was said with the sweep switched off; the notice now says it is off.
(7) **`synchronous=OFF` on a copy means the copy must be made durable before it is named.** `fsync` of the copy and of the folder before and after the replace; a platform that cannot open a folder has nothing to call.
(8) **When the newest pages of a table without AUTOINCREMENT are lost, the next row gets a lost id and inherits the children kept for it.** The salvage keeps orphans on purpose (one lost page of a parent must not lose every
row that refers to it), but the ones whose parent id is above the highest id left are exactly the ones a new row will claim: those, and repeatedly the grandchildren whose child went, are removed from the copy and reported
per table, naming any table that holds a measured verdict; orphans of a gap are kept. They stay in the damaged copy the repair keeps.
(9) **A scrub runs on the WHOLE text and the cut comes after it.** `salvage._failure_text` took the driver's first line and then scrubbed it: a passphrase with a line break that the driver echoed was cut in two first, neither half matched the needle, and the first half stayed in the repair record (the coordinator's check of E3). Scrub `str(driver)`, then take the first line; the test holds a two-line passphrase and a driver text that echoes it.
