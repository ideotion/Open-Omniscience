## 2026-10-13 — a commit width is a bound on a count and a bound on time only on the machine it was measured on; a watchdog that warns once per hold reports when it noticed the hold, not how long it lasted

**(1) 200 articles are seconds on one machine and minutes on another.** The drain's `commit_batch=200` (R21) was right for a restore that owns the machine and wrong for a drain running beside a person: one batch is one hold of the single-writer gate, from the first article's first read to the commit, and every writer that arrives waits for all of it. Measured on a synthetic store (600 articles, a second writer asking every 0.1 s) it held the gate 7.9 s, and the arriving writer waited exactly that; the same width is about 36 s at the field's 333 articles a minute and 60 to 175 s on the machine that crashed. **A width that is a count protects the writer only on the machine it was tuned on. Bound the hold by seconds, ask the caller's policy after every unit of work (`should_flush(staged, held_s)`), and keep the count as the ceiling, never the floor.** A policy that can only make a commit earlier cannot cost correctness (the batch path keeps its rollback-then-redo fallback), and the cost is commits: about 0.1 s each here, so width 10 cost 17 to 39 % more apply time while width 50 cost nothing measurable.

**(2) The caller owns the policy, the pass owns the loop.** The question "is anyone waiting behind this batch" belongs to the code that knows what else runs (the drain), and the gate's accessor (`waiters()`) is one line; passing a callable meant the shared analytics store gained one parameter and no knowledge of the gate. A policy the loop can drop (class name logged, never its text) is also one that cannot abort a re-index.

**(3) A watchdog that warns once per hold at the first sample past a threshold records the time of detection.** Under a 15 s sample and a 60 s threshold a hold is logged between 60 and 75 s however long it lasts: a 20 s hold under a 3 s threshold and a 1 s tick logged `held 3.0s`, and the gate's `max_hold_s` said 20.0002. The crash logs of 30 Sep read "60.3 to 73.3 s" for seventeen holds and nobody could size any of them; the gate keeps the process's longest hold only. **Whatever warns on entering a state must also say the length on leaving it, once, from the thread that held it, after its lock is dropped, carrying the name and the seconds and nothing else.** The 2,415 s longest wait of that crash is still unexplained for want of that line.

**(4) Two harness traps, both cost a run.** (a) A script that starts a process pool (`reindex_parallel`) re-executes its top level in every child when the platform's start method is not fork: five nested `RESULT` lines and a 125 s run where 35 s was true. A measurement harness needs `if __name__ == "__main__":`. (b) A `git worktree add` (a disk-heavy checkout) during a timing run moved a commit total from 1.9 s to 7.0 s; the run was discarded and repeated with nothing else touching the disk. **A timing that must be trusted runs alone.**

**(5) A figure published as "the hold" must start when the hold starts and end when it ends, in the failing case too.** The first build timed a batch from before its first article asked for the gate to the end of a commit that LANDED. An independent read found the two ways that goes wrong: another writer's hold that the batch queued behind (25 s of a vacuum, say) was published as the drain's own worst hold, which is exactly the attribution the 2,415 s question needs; and a commit that raised after a long hold was not timed at all, so the figure was lowest in the case it exists for. The clock now starts after `hold_write_window` returns, is read in a `finally` around the commit and after the rollback of a failed article, and a run that timed no batch publishes `None` (never `0.0`, which reads as "instant"). **A max against zero hides a skip: test the published value of a run that has nothing to be the maximum OF.**
