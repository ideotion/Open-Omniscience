## 2026-10-28 — A PR number goes into a ledger fragment by finding its cell and swapping the bytes there, and "added by this branch" is `--diff-filter=A --no-renames`

**What was found (the coordinator's relay of 2026-10-28 15:44 UTC, Plan's answer to the "never predict the PR counter" lesson; PR #1639).** A fragment's PR number exists only after the PR is opened, so the fragments carry `PR pending` / `#NNNN` on the first push and the real number goes in right after (a branch push without a PR starts no CI, and a push to the PR's ref cancels the run in flight, so sweeping within a minute of opening the PR costs one effective CI run, not two). Rewriting three tokens by hand across a handful of files is where the wrong number or a missed file comes from. `scripts/sweep_pr_number.py NUMBER` does it, and two facts decided its shape.

**1. A tool that parses a fragment, edits it and writes it back rewrites bytes it was not asked to touch.** 40 of the 527 `shipped.d` fragments on `main` (7.6%, counted 2026-10-28) do not come back byte-identical through `csv.reader` then `csv.writer`: they were written with every cell quoted, or with a cell that holds a newline, or by hand. A sweep that re-serialised them would put a diff in cells nobody changed, in files whose other PRs have already reviewed them. The sweep therefore reads the record the way `csv` does (a quote opens only at the start of a field, `""` is a literal quote, a newline inside quotes is data) to find the **span** of the `refs` cell, swaps the placeholder inside that span, and then parses the old and the new text and refuses unless every other cell is equal and `refs` is exactly the old value with the tokens swapped. The check is not decoration: a mutant that substituted over the whole text was refused by the cell comparison, and one that did so with that comparison removed was caught by the byte comparison in `tests/test_sweep_pr_number.py` of the untouched cells.

**2. `git diff --diff-filter=A` is not "the files this branch added" while rename detection is on.** A new fragment that is textually close to one the branch deleted is reported as `R`, and the `A` filter skips it, so the new fragment would keep its placeholder and the sweep would say nothing was wrong. The fixture needed only a dozen similar lines to reproduce it. `--no-renames` makes the new name an addition, and `merge-base BASE HEAD` (not `BASE`) is the other side of the diff so that a fragment `main` REMOVED since the branch was cut (a release fold) is not counted as the branch's: against `BASE` itself it shows as an addition, and the sweep would give it this PR's number. A fragment already on the base is another PR's and is never touched, whatever it says; a branch stacked on another unmerged branch passes that branch as `--base`.

**The rule.** Swap a value inside a file by locating it and replacing it in place, then prove by parsing both versions that nothing else moved; and when the question is "what did this branch add", ask git with renames off. The sweep refuses (touching nothing) on a number that is not a positive integer, a base that does not resolve or shares no history, a branch that added no fragment, a symlink or a path through one, a file name or text that is not UTF-8, an unclosed fence, a csv the `csv` module cannot read or that is not the ledger's header plus one row, and any placeholder left after the rewrite; a second run says there is nothing to sweep and exits 0.

**3. "No placeholder remains" is only as good as the test that says so, and that test must be the guard's own.** The first version looked for survivors one line at a time, where `ledger_fold.py check` runs `_PLACEHOLDER` over the whole prose and its `\s+` matches a newline, so `PR` at the end of a line and `pending` at the start of the next was neither rewritten nor refused: the sweep reported "nothing to sweep", exit 0, and the ledger check then failed on the same file. In a csv it checked `PR pending` only, where the one guard `shipped.d` has refuses any `pending` in `refs`, so `PR: pending` and `PRs pending` passed the sweep and failed that test. A leftover check that is narrower than the check that will judge the result reports a clean result that the next step rejects; make it the same predicate (here `_PLACEHOLDER.finditer(_prose(text))` and the `pending` rule), and name in the message every way a token can survive (no rule for it, a line break, a code span, a quote). An Opus read found it, and the 12 mutants it found alive were each a behaviour the first 31 tests did not pin: diffing against `BASE` instead of the merge-base, the csv survivor check, CRLF and `""` in a csv, subdirectories, `-z`, `--relative`, a failed file listed as replaced.
