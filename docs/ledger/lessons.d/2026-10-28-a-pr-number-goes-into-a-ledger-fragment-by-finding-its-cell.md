## 2026-10-28 — A PR number goes into a ledger fragment by finding its cell and swapping the bytes there, and "added by this branch" is `--diff-filter=A --no-renames`

**What was found (the coordinator's relay of 2026-10-28 15:44 UTC, Plan's answer to the "never predict the PR counter" lesson; PR #NNNN).** A fragment's PR number exists only after the PR is opened, so the fragments carry `PR pending` / `#NNNN` on the first push and the real number goes in right after (a branch push without a PR starts no CI, and a push to the PR's ref cancels the run in flight, so sweeping within a minute of opening the PR costs one effective CI run, not two). Rewriting three tokens by hand across a handful of files is where the wrong number or a missed file comes from. `scripts/sweep_pr_number.py NUMBER` does it, and two facts decided its shape.

**1. A tool that parses a fragment, edits it and writes it back rewrites bytes it was not asked to touch.** 40 of the 527 `shipped.d` fragments on `main` (7.6%, counted 2026-10-28) do not come back byte-identical through `csv.reader` then `csv.writer`: they were written with every cell quoted, or with a cell that holds a newline, or by hand. A sweep that re-serialised them would put a diff in cells nobody changed, in files whose other PRs have already reviewed them. The sweep therefore reads the record the way `csv` does (a quote opens only at the start of a field, `""` is a literal quote, a newline inside quotes is data) to find the **span** of the `refs` cell, swaps the placeholder inside that span, and then parses the old and the new text and refuses unless every other cell is equal and `refs` is exactly the old value with the tokens swapped. The check is not decoration: a mutant that substituted over the whole text was refused by the cell comparison, and one that did so with that comparison removed was caught by the byte comparison in `tests/test_sweep_pr_number.py` of the untouched cells.

**2. `git diff --diff-filter=A` is not "the files this branch added" while rename detection is on.** A new fragment that is textually close to one the branch deleted is reported as `R`, and the `A` filter skips it, so the new fragment would keep its placeholder and the sweep would say nothing was wrong. The fixture needed only a dozen similar lines to reproduce it. `--no-renames` makes the new name an addition, and `merge-base BASE HEAD` (not `BASE`) is the other side of the diff so that what `main` gained since the branch was cut is not the branch's. A fragment already on the base is another PR's and is never touched, whatever it says; a branch stacked on another unmerged branch passes that branch as `--base`.

**The rule.** Swap a value inside a file by locating it and replacing it in place, then prove by parsing both versions that nothing else moved; and when the question is "what did this branch add", ask git with renames off. The sweep refuses (touching nothing) on a number that is not a positive integer, a base that does not resolve, a branch that added no fragment, a symlink, text that is not UTF-8, a csv that is not the ledger's header plus one row, and a placeholder it does not know how to rewrite (one `ledger_fold._PLACEHOLDER` learns later is named, not skipped); a second run says there is nothing to sweep and exits 0.
