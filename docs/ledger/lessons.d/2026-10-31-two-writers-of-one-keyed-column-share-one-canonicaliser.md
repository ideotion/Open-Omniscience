## 2026-10-31 — two writers of one column that a merge matches by exact string must share one canonicaliser, a column type that converts codes is not one, and the canonicaliser must not guess at words

**What was found (R399 / R189, the WAL lane's measurement of 2026-10-29 on the real path; PR #1679).** A restore matches `law_documents` rows by `m.jurisdiction = i.jurisdiction AND m.url = i.url`: exact text. The column has two writers. The catalogue's loader runs the field through `law_jurisdiction` (`FRA`/`fra`/`FR` -> `fr`, `GBR`/`gb`/`uk` -> `uk`, `EUU` -> `eu`); `POST /api/law/documents` lowercased the jurisdiction the operator typed and stored it (and stored `country` exactly as typed). The column type (`CountryCode`) converts at the bind, but only what it can place and only toward the store's form: an alpha-2 store "is written exactly as it always was" (so `FRA` was stored as `fra`), and an alpha-3 store cannot place `uk`, the app's own code for the UK, so it stores `uk` while a backup from another install typed `gbr` holds `GBR`. Result, both measured: **H** (a store that predates the country marker: typed `FRA`, restore of a backup holding `fr` -> two rows) and **J** (every store, so every new install: typed `uk`, restore of a backup typed `gbr` -> two rows, and the duplicate scan lists `uk` as "unresolved" instead of counting the pair). The fix: a typed CODE (two or three ASCII letters) goes through `law_jurisdiction` on the route and through `config_country` for the document's own `country`, as the loader does; anything else is a word and is stored as typed. The merge needed no change.

**The rule.** When a table is joined, deduped or merged on a column's exact text, every writer of that column goes through the one function that produces the keyed spelling. Two clues that a second writer exists and has not been looked at: a helper whose docstring says it is "the form the rows hold" and that has callers only on the reading and catalogue side, and a route that does its own `.strip().lower()` on a field the catalogue treats as a code. A column type that converts between two forms of the same code is not a canonicaliser: it passes a spelling it cannot place through unchanged, and in an alpha-2 store it does nothing at all. **And convert codes, not words.** The first form of this fix sent every typed string through the helper, which also resolves country NAMES, and the independent read found two regressions from it: (1) the country-name index guesses (`georgia` became the country `ge`, so a US-state jurisdiction was filed under it; `congo` became `cd`, the DR Congo, not the Republic; `england` became `uk` while `scotland` stayed as typed), and the wire layer deliberately never converts a name; (2) the duplicate check, which widens a typed CODE to its spellings but adds only aliases of three letters or fewer, could no longer find a row stored as `france` from the converted `fr`, so "watch again" (the UI posts the jurisdiction exactly as the listing returned it) filed a second, watched `fr` row beside the unwatched `france` row and its history. Leaving words as typed makes the lookup for them byte-identical to what it was. The duplicate check beside the write (`country_query_forms`) is the other half and stays: rows stored before the fix keep their old spelling (a cleanup is the country migration's job, not this route's), and a re-add must still find them. Measured: for every ISO alpha-2 and alpha-3 code and for `eu`, `euu`, `int`, `uk`, `xk`, the lookup set after the fix equals the set before it, so no re-add that was a duplicate has become a second row; and the table of inputs the tests use includes words. **And a writer fix cannot reach what the old writer already wrote.** It stops the divergence growing; a backup is a byte copy of the old spelling, so it is matched against the new writer's output, and for the aliases the writer now converts the mismatch moves from "two installs that typed differently" to "an old backup against a new install" (measured, below). When the keyed artifacts outlive the writer, the durable fix is to canonicalise the COMPARISON on both sides, not only the writers.

**Stated limits.** **The old artifacts outlive the writer.** The route now stores `uk` for a jurisdiction typed `gb` or `gbr` (the UK is the case that matters: the interface shows `GBR`), and `eu`, `an`, `ae`, `cd` for `euu`, `ant`, `uae`, `drc`. A backup made by the earlier route holds the spelling it stored (`gb`, `GBR`), and the merge converts the incoming value toward the store's form but compares exact text, so restoring it over a store whose document was pasted after this change, with the same alias typed on both sides, adds a second row where it used to find one. Measured through the real `merge_corpus` (`wal-lane/probe-law-cross-version-restore-merge-2026-11-01.py`) and over every pair of two- and three-letter spellings of one jurisdiction (`probe-law-cross-version-restore-2026-11-01.py`): with the earlier route's backup restored into a store written by this route, 6 pairs (alpha-2 store) and 8 pairs (alpha-3 store, so every new install) go from one row to two, and 506 and 8 pairs go from two rows to one. It is transitional (it needs a backup made before the upgrade and the same document pasted in both places), and it is the price of changing the string stored for these aliases. Making the merge compare canonical forms on both sides would remove it, H and J for every writer; that is a restore-path change and is proposed separately (`wal-lane/proposal-restore-compares-canonical-jurisdiction-2026-11-01.md`). Rows already stored in another spelling stay as they are (J's rows stay invisible to the duplicate scan until a cleanup). A jurisdiction typed as a WORD on one install and as a code on another (`france` and `fr`) is still two rows to a restore, exactly as before this change: a word is never guessed into a code. The same free-text entry on other country-bearing columns (`sources.country` and the routes that write it) was not measured and is not changed here. `law_revisions` and their summaries follow the document's id, so they follow whether the document row dedupes. A `country` typed as a code is stored as the catalogue stores it (`uk` becomes the ISO `gb`, the document's COUNTRY, where the jurisdiction `uk` is the app's own code); a `country` typed as a name is stored as typed.

**Two test lessons.** (a) The proof is the real merge, not the stored string alone: the same URL typed two ways on two installs, every combination of source and target store form (2 x 2) over five spelling pairs, merged with `merge_corpus` and asserted to leave the target's row untouched (`new == 0, duplicate == 1`). The stored-string table would still pass if the merge learned to compare differently; the matrix passes only if the two installs end up with one string. Each store is a scratch file with the route served on a session bound to it, and the form is the file's marker plus a patched `store_form()` for the route's bind, so nothing touches the suite's shared store. (b) **A table of inputs written for the shape the fix handles proves only that shape.** The first table held codes only, so it, the end-to-end matrix and eight mutants all passed over a fix that broke the words the name index places; the read supplied the inputs the field also accepts (words, an unwatched row, a second URL under the same jurisdiction). When a fix puts a conversion in front of a free-text field, the table of inputs starts with the strings that are NOT what the conversion was written for. The mutants were run on a harness that writes no bytecode, restores the file byte for byte with its original mtime, and requires a passing baseline before any verdict.

**Pinned by** `tests/test_law_add_document_one_spelling.py` (the stored spelling for every code and word in both store forms, the country column, the duplicate check across spellings and for rows stored before the fix, an unwatched row reactivated, another URL a new document, and the restore matrix); fourteen mutants of the route (the jurisdiction and country calls reverted, the `uk` mapping dropped, the lowercase, the strip, the lookup narrowed or mangled, names converted, the code shape widened to four letters or narrowed to two, the reactivation, the URL condition of the lookup) are each killed.
