## 2026-10-26 — an HTML escaper inside a single-quoted attribute argument is undone by the browser before the parser sees it

**Found (JS sink audit, F6).** `data-on-click="f('${esc(x)}')"` was classified safe by the sink walker and by both reading workers, because `esc()` writes an apostrophe as `&#39;`. The browser decodes entities in an attribute BEFORE `oo-on.js` reads it, so the parser sees the apostrophe again, the string argument closes, and the rest of the value parses as further allowed calls: `x'); appShutdown(); ooSetValue('a','b` inside `ooSetValue('agenda-tag', '...')` parsed to four calls (Chromium, real parser). Each piece was correct alone (an HTML escaper; an argument grammar); the defect is their composition, which a per-sink escape check cannot see.

**Rule.** An argument written into a `data-on-*` attribute is `${esc(JSON.stringify(x))}`: the JSON form is a double-quoted string the grammar reads whole whatever the value holds, and `esc()` then only protects the HTML layer. A raw `'${expr}'` is allowed only for a value the code itself chooses (a literal table, an enum key, a DOM id prefix), listed with its reason in `tests/test_oo_on_argument_ratchet.py`; a stale entry also fails. The ratchet is paired with a test that replays hostile values through the REAL parser, with the old form kept as a control that must still inject, so the test cannot pass because the parser stopped being able to see the defect.

**Limits.** Whether any of the 28 converted values can hold an apostrophe was not traced (candidates: ring ids and countries in app-insights, user-calendar keys in app-agenda). Not browser-verified after the change.
