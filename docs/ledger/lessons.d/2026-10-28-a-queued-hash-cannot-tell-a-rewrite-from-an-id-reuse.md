## 2026-10-28 — A queued hash cannot tell an in-place rewrite from an id reused by another article, and queuing URLs puts them in plaintext (the withdrawn #1630, the item_hash follow-on of #1623)

**What was found.** #1623's stated limit was that no production caller puts a hash on a queued custody record, so the drain compares the stored row's CURRENT hash. The follow-on (queue `item_hash`, plus url/canonical_url/source_id, from `_maybe_record_custody`) passed its tests and the Opus read found two reasons it should not ship. (1) On main with #1623: article A at id N has its custody write fail; A is deleted; id N is reused by B, whose own write succeeds. Without the change the drain sees B's hash at `article:N` and settles the entry as present (`already_present: 1`, one entry). With it, the queued record carries A's hash, so the drain writes a second entry under `article:N` binding A's hash (`recorded: 1`, two entries, marked `earlier_ingest_other_hash`). A row whose hash differs from the queued one is the same observation whether the article was rewritten in place or the id belongs to another article; an id alone has no identity over time. (2) `data/custody_pending.jsonl` is plaintext in the data folder; queuing url and canonical_url puts query strings there, where the repo's convention (`activity_ledger.py`) keeps URLs out. Queuing the hash alone avoids (2) but the drain reads the row only when `item_hash` is absent, so the late entry would lose url, canonical_url and source_id.

**What it cost.** A PR, a full read, and a merged-tree probe; no code shipped (the PR was closed unmerged).

**Rules.**
1. **Before adding a field to a queued record, ask what the consumer does with it when the world has moved.** A value captured at one time and consumed at another is only evidence of the world at capture; the drain's job is to bind to what is stored NOW, and the record's hash disagreeing with the row is ambiguous (rewrite vs reuse), so the safe default is the one that never trusts the queued copy.
2. **A plaintext file in the data folder carries no URL**, however small the field looks; queue an identifier and read the rest from the encrypted store.
3. **A read that finds nothing wrong is not the end**: the probe on the merged main (the reuse trace above, one test) is what turned a plausible follow-on into a withdrawn one. Run the world-has-moved trace for any change to a deferred-write path.
