## 2026-10-29 — a start that fails must leave no job that says it is running: set the state, start the thread, and undo the state if the start raises

**What was found (R393 class, the WAL lane's [G] sweep).** A job manager's `start()` follows one order: check nothing is running, set its state to `running` (some also save it), build the thread, call `thread.start()`. Nothing around the last call. `Thread.start()` raises `RuntimeError("can't start new thread")` exactly when the machine is short of the resource the job needs most, and then the manager holds a job that is running and never will be. Three things follow from that one order and all were present: the Task Manager lists the job as running with controls that act on nothing; a saved `running` is read back after a restart as a run that was interrupted (or paused); and the next start, which first joins the previous thread to reuse the manager, joins a thread that was never started and raises `RuntimeError("cannot join thread before it is started")`, so the manager refuses every later job until the process restarts (the volume-backup manager and the import queue; the folder backup and the search re-index only showed a false state).

**The rule.** The undo belongs next to the `start()` call, not in the worker (which never ran): `except Exception:` put back what the start set, and re-raise. Put back means the state the job was in before when that state is a meaningful one (the import queue's earlier run, which also keeps `items_committed` honest), and an `error` that names the exception's class when it is not (the volume manager, whose earlier summary the start had already cleared). Never the exception's text where the start's arguments carry a secret. `Exception` and not `BaseException`, as R393 settled: an interrupt that lands inside `start()` leaves the OS thread created, so undoing would let a second start run a second worker. A test of such a start injects the failure into the module under test (its `threading` replaced by one whose `Thread` refuses), never into `threading.Thread` itself, and asserts the three things above: the job is not running, what was saved says so, and the next start runs.

**Where it is pinned.** `tests/test_failed_thread_start_leaves_no_phantom_job.py` (14 tests, 10 red on main, 4 interrupt pins that pass on both). The unread remainder of the class is listed in the shipped-log entry for 2026-10-29.
