## 2026-10-31 — a pause that guards the write-ahead log has to be asked by every bulk writer, and it can only wait where the writer holds no transaction, no lease and no record of an attempt

**What was found (R400, B1; the WAL lane's read of three field zips, 2026-10-31; PR #1673).** The storage guard paused collection passes, the housekeeping lane, `stoplist_recompute`, the heavy reads and the maintenance writes while its log latch held, and named the reader that pinned the log. Two bulk writers never asked: the re-index resume drain (`api/backup_v2.py::_reindex_resume_worker`, whose `should_stop` was `ctx.stopping or _yield_to_import()`) and the article-index build (`database/article_indexes.py::build_missing`). With a reader holding the log's checkpoint mark they went on appending (8.8 MB/s and 3.1 MB/s measured while the guard was engaged), the log reached 80.6 and 219.8 GB, a commit on it took 260 to 441 s, collectors queued for the gate holding a pooled connection each, and the next unlock spent 105 to 1,776 s recovering the log. A guard that names the pin but is not asked by the writer that deepens it is a report, not a bound. The class repeats: every writer added after a "gate every entry point" ruling is the one that is missing, so the question to put to a new bulk writer is "what does this do while the latch holds?".

**The rule, and the four places it can go wrong.** (1) **Wait, do not stop.** A stop leaves the backlog until the next boot or the end of an import run; the pause ends by itself when its cause does (`StorageGuard.wait_if_engaged(should_stop=..., on_wait=...)`, the log AND the drive latch, never the operator's "Resume anyway", which forces collection on). The wait also ends on the writer's own stop and on an import claiming the machine. (2) **Wait only where nothing is held, and "nothing" includes a lease.** The first poll of a call to `reindex_imported_articles` comes before the call has committed anything, and its session holds a checkout: a waiter there would be the very reader that pins the log. The first form of this change waited at the call's second and later polls (after a window's commit, so no transaction): the Opus read found it still parked INSIDE `corpus_lease("reindex-resume")`, which a restore's swap waits on (`wait_for_quiescence`), so a restore that had spent hours would be refused for a holder that does nothing for as long as the latch lasts (and the pause was counted in the call's wall time and rate). So a running call is not waited in: from its second poll on, a latch that holds makes `should_stop` answer True, the batch stays unstamped with its cursor exactly where it stopped, and the worker waits at the top of its loop (no session, no lease) and runs the same batch again from the cursor. The index build waits before each statement on no connection at all. (3) **A pause is not a crash.** The index build records an attempt before its first statement so that a build that brings the process down is not repeated at every start (two unfinished starts decline the third). A build that waits for hours with that record in place, and is then killed by a power cut, would count the wait as a crash. The first wait therefore comes before the free-space and memory readings and before the record (the readings are taken right before the build, not hours before it), and the wait between the two statements gives this start's attempt back (`_give_back`, which leaves an earlier unfinished start counted) and takes it again after. (4) **A give-back is undone by whatever takes the attempt again, so the taker has to ask whether the app is quitting.** A quit in order (`article_indexes.stop()`, from the shutdown hook) gives the attempt back; the readers that pinned the log end with the app, so the latch releases before the process exits, the wait ends, and the retake wrote the record again just before the second statement, which a process killed there (or two such quits) counted as a crash. `stop()` now says so (`_QUITTING`) and `_arm` writes nothing once it has run, and re-reads the flag after writing so a `stop()` that lands in the gap is seen; a build start clears the flag (a test client's shutdown calls `stop()` too, and the flag must not outlive it).

**Stated limits.** The re-index an import runs inside its own run (an operator-started, exclusive operation) does not wait; only the background drain that finishes an interrupted one does. The first window of a call runs even if the latch engages in that instant (one window; a window made only of deleted ids commits nothing, so "a call commits at least one window" would overstate it); a build that the boot thread starts AFTER a quit in order (`main._stop_database_check` releases the boot thread with `verify.stop()` before it calls `article_indexes.stop()`) clears the flag and records its attempt as it always did, so two such quits during the start-up check can still block the build until an update: older than this change, found by its delta read, and refusing a build after a quit needs a reset hook for the suite's test clients, so it is a follow-on and not part of this PR; the drain's closing whole-corpus counter sweep in its `finally` is another writer with its own slices, not covered; boot's later steps wait behind a paused index build, as they do behind a slow one (`boot_sequence`: no timeout, the slow step is the fault and has to be seen); the free-space and memory readings of the build are not repeated after the wait between its two statements; a call that is asked to return re-reads the batch's ids when it is run again (once per pause, not per window).

**Two test lessons from the same change.** (a) `assert snapshot().get("preflight") is None` was written to prove the readings come after the wait, and passed with the wait moved after them, because the snapshot is only updated at later points: a value that cannot change while the code under test runs proves nothing. The assertion that failed under the mutant was a recorder on `preflight` itself. (b) **The mutation harness itself lied once.** The first harness restored the mutated file by copying a backup over it, which gives the file a new modification time; Python trusts a `.pyc` whose recorded source mtime (whole seconds) and size match the source, so a mutant of the SAME SIZE as the original (a swapped clause order, `queued.append` moved above `enqueue`) compiled in the same second as the copy left a `.pyc` that was still valid for the RESTORED original: the next run of the unmutated tree failed with the mutant's behaviour. Found because a baseline run on the "clean" tree failed three tests; every earlier verdict in that harness had no baseline. The harness now writes no bytecode, restores the file byte for byte with its original mtime, removes the module's `.pyc`, and refuses to give any verdict unless the unmutated tree passes the same tests first. All mutants of this change were re-run on it (the first 18 on the first head, all killed as before; the full set on the final head). Every check is mutant-proven by at least one new test, the tests wait for the writer to have REACHED its pause (observed on the job row it publishes) rather than for a time, and the lease is asserted with the REAL `corpus_lease` and the call a swap makes (`wait_for_quiescence`), not with a fake that records names.
