## 2026-10-26 — A GET that does work is a request a web page of another site can make: refuse it in the route (Host, fetch metadata, Origin), write where the corpus lives, take one at a time, and free the claim on every exit

**What was found (audit 0.5.0, A-008).** `GET /api/database/backup` wrote a full plaintext snapshot of the corpus into the operating system's temporary directory for ANY GET and removed it after the response. A page of another site can issue a GET with an `<img src>`, so one page view made the machine copy its whole corpus out of the data folder into a shared directory (the route unlinked the owner-only file `mkstemp` made and let the backup API re-create the path, so the copy's mode was not owner-only by construction), as often as the page liked, with nothing to stop a second copy while the first was still being written. (Browsers do not let that page read the response; the harm is the plaintext copy on disk and the disk it fills. A page on a name that an attacker has rebound to 127.0.0.1 is a different case: it is same-origin with itself and CAN read the answer.)

**What the fix does.** The refusal lives in the route (`_refuse_cross_site`), not in a middleware: the `Host` must be a name the app's DNS-rebinding guard serves (the route reads the guard's own two helpers, so the name list has one owner), `Sec-Fetch-Site` must be `same-origin` or `none` when present, and `Origin` (else `Referer`) must name the request's own `Host` when present; all of them must pass. The snapshot goes in a `.oo-backup-*` directory (mode 0700) beside the database, a free-space gate compares the database plus its WAL against the volume (507 with both figures; a volume or a file size that cannot be read is not a refusal and the response says `X-OO-Free-Space-Check: not-read`; a refusal built from a size that could not be read says `at least`, not `up to`), one snapshot is made at a time per process (429 for the second; two servers on one data folder, R176, can each make one), and a `FileResponse` subclass removes the directory and frees the claim in a worker thread, shielded from cancellation, when the response ends or fails.

**Rules.**
1. **A GET that writes, spends CPU or fills a disk is not safe because it is a GET.** If the route does work, it refuses cross-site callers itself; a route that is only safe while a middleware someone else owns stays in place is not safe. And "cross-site" is not the whole attack: a rebound name passes every origin check, so the route checks the Host too, with the test calling the route function directly (no application, no middleware) and a Host the middleware would have stopped.
2. **Refuse before the first effect.** The test spies on `mkdtemp` and `backup_to` and asserts neither was reached for each foreign form (another origin, another port of the same host, `Origin: null`, a foreign `Referer`, `cross-site`, `same-site`, a differently-cased header value, and `same-origin` fetch metadata with a foreign `Origin`).
3. **Say the limit the check cannot close, in every form it takes.** A browser without Fetch Metadata (Firefox before 90, Safari before 16.4, an old webview) sends no `Sec-Fetch-Site`, and a no-cors `<img>` GET with `referrerpolicy="no-referrer"` sends no `Origin` and no `Referer`: the request is indistinguishable from curl and is served. So does a current browser asked for a name that is not a "potentially trustworthy" target: Fetch Metadata is attached only to loopback and HTTPS URLs, so an `OO_ALLOWED_HOSTS` name over plain HTTP gets none. The first version of this lesson said "a page cannot omit it"; an independent read found the first counterexample and a second read the second. A stricter rule for a non-loopback Host (refuse a request with no fetch metadata unless it names itself, for instance with a header an `<img>` cannot send) is a client contract and is left to a ruling. The slot and the space gate bound what it costs; a test pins the case by name.
4. **Put a copy of the corpus where the corpus is.** The data folder is the user's, with the user's permissions and the user's volume; the system temporary directory is neither. And say what a gate could not read instead of treating "unknown" as "fine" or as "refuse" (a size that cannot be read leaves the figure short, so the response says so).
5. **A claim on a shared slot is owned by a token, and released by code that runs when the response does not.** The slot holds the token of the request that claimed it, so a download taken over after the stale age cannot free or overwrite the takeover's claim; the release runs in the response's own `finally` (and by `BaseException` before the response exists). **Cleanup that can take seconds runs off the event loop and is shielded:** deleting a corpus-sized file can stall every request on some file systems, and the task can be cancelled under it (a server shutting down, a cancel scope around the response). Do not write that a disconnected client cancels the task: on a stack whose sends are dropped after a disconnect the response is not cancelled and the file is read to its end first (a probe in the second read), which is a cost to name, not a cleanup to assume. The shield is proved with a level-triggered cancel scope (anyio re-delivers the cancellation at every later await), not only with a single `wait_for` cancellation, which an unshielded `await` survives.
6. **A sweep removes only what it can name, and a leftover is judged by its owner before its age (0.5.1 item 40).** The route's own sweep removes `.oo-backup-*` directories older than the stale age, so several servers on one data folder (R176) never delete another's live snapshot. The boot sweep of `stream_backup` (`sweep_stale_backup_temps`, run at start and by the maintenance pass) and the forensics staging list know the prefix too: before, a snapshot a KILL left stayed until someone asked for the next backup, and the forensics inventory called it "other" bytes beside "orphaned staging: none found". The route now writes an owner marker (pid, process start time, host, machine tag: the one `process_owner` record the streamed backup's `.bak-build-*` directories already carry) into the directory right after it makes it, and the sweep reads it: a dead owner's directory goes at once whatever its age (a recycled pid is told apart by the start time), another live process's stays whatever its age, this very process's own is "unknown" and keeps only the age rule (a live download is never taken from under its client), a marker from another machine is "unknown", and a directory with no marker (the write is best-effort, and a kill can land between the `mkdtemp` and the marker) keeps the 24 h age rule. A `.restore-*` directory is still judged by age alone: widening the owner rule to a prefix whose owner writes no marker would change what the old sweep did, and a test pins that. Measured in a real process: a server killed (SIGKILL) while its snapshot was being written left `.oo-backup-*/snapshot.db` and the marker; with the marker removed the sweep kept the young directory (the control), with it the sweep removed the directory at once. The forensics list also names `snapshot.db` as a plaintext member, so the leftover is reported as a decrypted copy on disk.
7. **Limits of this route, the first corrected twice and the second stated (0.5.1 items 41, 40 and 42).** (41) The first statement of this limit ("a graceful-shutdown cancel leaves the directory") was inferred, not measured, and was wrong in the form stated; the correction that replaced it was wrong too (it called a SIGTERM clean), and an independent read of the second text, running the real app under a real uvicorn with the production `timeout_graceful_shutdown=30`, found the case that matters most. What was MEASURED, case by case: (a) a cancel while a snapshot is being written, whether the one native `task.cancel()` a server applies or an anyio cancel scope, is CLEAN: anyio holds the cancellation until the worker thread has returned, the response is then run, is cancelled at its first await, and its `finally` removes the directory and frees the claim (two whole-app tests; a pin, not a repair). (b) `SIGINT` twice (uvicorn forces on the second `SIGINT` only) closes the loop with no task left, the interpreter waits for the non-daemon worker and exits `rc=0` with `.oo-backup-*/snapshot.db` behind it; `_remove_live_snapshot_dirs`, an `atexit` hook over a table of the directories THIS pid made, removes it (Python joins non-daemon threads before it runs exit hooks, so the file the worker wrote after the loop closed is there to remove; the table is pid-stamped so a forked child never removes its parent's live download). (c) One `SIGTERM` whose graceful window (30 s, set in `_serve()`) runs out while a snapshot is written, or while a client that stopped reading a finished snapshot holds the response open, is NOT clean: uvicorn cancels the request task, puts back the SIGTERM handler it found (the default) and raises the signal again inside `serve()`, and the process dies on the spot (`rc -15`): no thread join, no exit hook, the whole plaintext copy left (measured with an 8 s snapshot against a 2 s window, and with a 54 MB finished snapshot against the 30 s window). This is the in-app power button (`os.kill(self, SIGTERM)` in `src/safety/shutdown.py`), SIGHUP (a terminal closed or a logout; routed onto SIGTERM by `install_signal_handlers`) and a plain `kill` or service stop, so a backup of a real corpus, which takes minutes, is the expected case, not an edge. `install_stop_signal_cleanup()`, called in `_serve()` after `install_signal_handlers()` and before `uvicorn.run`, installs the handler uvicorn then puts back and re-raises into: it removes the directories this pid made, restores `SIG_DFL` and sends the signal to itself, so the exit status is unchanged (`rc -15`, which is also what a launcher already reads) and nothing here turns a SIGTERM into a clean exit. A real-process test per case, with the same script without the handler as the control (it leaves the directory), and the handler's own unit tests (removal fails: the signal is still sent). The R165 exemption test (`tests/test_event_loop_signal_exemption.py`) forbade ANY handler for SIGINT or SIGTERM outside uvicorn, because uvicorn's capture is what exempts the loops that run on the event loop's thread from the loop-shape rule; this handler is installed before `uvicorn.run`, so uvicorn's capture replaces it while serving and puts it back on the way out, and the test now names exactly that function: it must register SIGTERM only, restore `SIG_DFL` and re-signal, and `_serve` must call it before `uvicorn.run` (five red-without cases). It was found by a 59-file run, not by the targeted battery: before adding a signal handler, grep the tests for the ones that scan `src/` for `signal.signal`. (d) A kill (`SIGKILL`, the power) runs nothing at all: that is item 40, rule 6. The copy then stays on disk until the app is next started (nothing runs in between), and is removed by that start's sweep at once when the marker was written, after 24 h otherwise. Where the marker names a LIVE process the sweep never removes the directory, whatever its age, so an abandoned claim of a live server older than a day is removed only by the route's own sweep on its next call. The 24 h line the maintenance sweep applies to this process's own directory is the line the route already relied on (no download of one lasts a day; an 11.7 GB file at 1 MB/s is about 3.3 hours); a download that outlasted it could be taken, and the registry that would prevent it (`active_staging`) is not used here. (42) The response does not watch `receive()` for `http.disconnect` itself (as `RecordedFileResponse` in `src/monitoring/diagnostics_runs.py` does). On Starlette 1.5 to 1.7 (the dependency floor is 1.5.0) nothing watches it under uvicorn, so a client that went away leaves the file to be read to its end and the claim held, 429 for a retry, until then. Measured on a real uvicorn with a 20 GB sparse snapshot and a client that read 262 KB and closed: 1.7.0 had not released after 60 s; 1.8.0 and 1.10.0 released after 0.02 and 0.03 s, because their `FileResponse` stops streaming on `http.disconnect` while the server speaks an ASGI spec older than 2.4 (uvicorn's HTTP implementations speak 2.3). The shield in rule 5 is what makes that early return safe. From 1.8.0 the route needs no code for it; raising the floor to 1.8.0 would close the item, and is a version-coupling change for the coordinator (registry, `pyproject.toml` and the lock in one commit).
8. **A test that hands an ASGI response an immediate `http.disconnect` tests the installed Starlette, not the response.** From 1.8.0 a `FileResponse` races the file stream against `receive()` when `scope["asgi"]["spec_version"]` is older than 2.4 (the default when the key is absent), so a stub `receive` returning `http.disconnect` at once cancels the stream before the first body message: two of this route's tests (a send that fails mid-body, a task cancelled while a send stalls) passed on the 1.7.0 the lane built on and failed on CI's newer Starlette with `DID NOT RAISE`. The stub now stays silent like a connected client, the two tests run on both sides of spec 2.4, and one test pins the contract that holds on every release: whatever the stack does with an immediate disconnect, the directory is removed and the claim freed.
