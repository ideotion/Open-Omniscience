## 2026-10-26 — A heal that changes a stamped field must re-stamp in the same commit, and a limit written from reading the code is measured before it is built on (0.5.1 items 39 and 41)

**What was found.** (39) `upsert_law_corpus_article` healed an article whose text had not changed: it cleared a poll date from `published_at` (and set the language the catalog states) and committed, but never indexed the article again. `index_article` STAMPS both onto the mentions (`observed_on` from `published_at or created_at`, the mention language from the article's), so the heal left every mention carrying the poll day: the article sat in one period by its own clock and in another by every reader of `observed_on`, and the A-003 story read (which chooses articles by the clock) and the older readers (which choose mentions by the stamp) disagreed about it. An independent read then found the SECOND site of the same defect, and the one production reaches first: `register_documents` (`src/law/catalog.py`, every boot and unlock through the law catalogue seed, and `POST /api/law/seed`) sets `Article.language` from the catalogue row and committed with no re-index, and because it runs before any corpus sync it left the corpus heal nothing to heal. (41) The 0.5.1 item said a graceful-shutdown cancel during a snapshot leaves `.oo-backup-*/snapshot.db`. That was inferred from reading the code and was wrong in the form stated; the first correction, also written before the real case was run, was wrong too. The measured cases are in `2026-10-26-backup-get-cross-site.md`, rule 7: a cancel is clean; `SIGINT` twice and one `SIGTERM` past the graceful window both left the full plaintext copy; a kill leaves it for the next start's sweep.

**Rules.**
1. **A heal of a field that is denormalised onto other rows re-stamps those rows through the one hook that stamps them, in the same commit, at every site that heals it.** Committing the column first makes a failed re-index unrepeatable, because the next call finds nothing left to heal; the test makes the hook raise once, rolls back as the batch caller does, and asks the next call to heal. Grep for every writer of the field before calling the fix done (`Article.language` has two). The catalogue heal commits its registration first (it is a boot path and must not fail on one article), then re-indexes each healed article and names a failure in the log; there the document row already states the language, so a failed article keeps the old stamps and nothing re-heals it by itself (stated).
2. **Tell the disposable rollup, once per logical mutation.** `index_article` rewrites changed mention rows in place under their old ids (a heal MOVES them to another day), which the columnar rollup's id-watermark merge cannot see; `bump_corpus_epoch` makes it rebuild. The corpus heal bumps after its own re-index has committed; the catalogue heal re-indexes with `bump=False` and bumps once for the batch. A test per site; a steady-state call bumps nothing. The corpus heal bumps once per healed document, including on a tracker pass, where `bump_corpus_epoch` asks for one per batch: an extra bump only forces a rebuild, and a missed one only lags the rollup, so it is stated and left.
3. **The steady state pays nothing.** The re-index is conditional on the heal having changed something; a test replaces the hook with one that fails if called and asks for the unchanged, already healed article.
4. **Say what the heal does NOT cover.** (a) The content-changed branch of `upsert_law_corpus_article` still commits before it indexes, and its re-index (which rewrites rows in place too) bumps no epoch (not changed here). (b) The re-index is additive for the When-axis date tags (`datestore.store_for_article` keeps human confirm and reject decisions), so tags resolved against the old poll date (a year-less or relative date) survive the heal: measured, `[2020-09-11, 2026-09-11]` before and the same two after. (c) "A failed re-index rolls the heal back and the next pass repeats it" is true of the next CALL of `upsert_law_corpus_article`; `sync_watched_laws` has no caller in `src/` or `scripts/`, and the tracker's unchanged poll ingests only when `latest_text` was missing, so in production a rolled-back heal is redone by the next text change. (d) A store that was healed before this change keeps its stale mention stamps until the article is re-indexed; nothing here sweeps the old ones.
5. **Measure a limit before writing it into a ledger, and when the measurement disagrees correct the earlier text in place, and again when a reader runs the case you did not.** The probe is a real server process, the real app, a patched slow `backup_to`, a socket client and the signals; the unit tests alone could not have shown the leaks, because they need the loop to close or the process to die while a thread is still running. A probe that runs uvicorn without the production `timeout_graceful_shutdown` cannot meet the case that matters (the signal past the window), which is how both false sentences got written.
6. **Python runs exit hooks after it has joined its non-daemon threads, and a death by signal runs no hook.** The order makes an `atexit` removal correct for a file a worker writes AFTER the main thread ended: the test runs a real interpreter whose non-daemon thread writes the file a second after the main thread finishes, and leaves a marker outside the directory after its write, so a hook that ran before the join (the file gone under the thread) fails the test rather than passing it. A `SIGTERM` that uvicorn re-raises after its window kills the process with the default action: only a handler installed BEFORE `uvicorn.run` (which uvicorn restores and re-raises into) can clean, and it must ignore a second copy of the signal first (a nested run found the table emptied and ended the process with the removal unfinished, or blocked on the lock its first run held), then restore the default and send the signal to itself so the exit status is the signal's, not a clean 0. Stamp the table with the pid that made the entry: a forked child inherits the table and the hooks and must not remove its parent's live download. A kill runs nothing; leave that to the sweeps, give the directory an owner marker so the sweep can tell a dead owner's from another live server's (R176), and say that the copy stays until the next start.
