## 2026-10-17 — A CONTEXT MANAGER THAT TAKES SHARED STATE BEFORE ITS `try` LEAKS IT ON AN INTERRUPT, AND A GIVE-BACK THAT CONTAINS A CALL IS STILL A WINDOW

(1) **The rule (R171).** A `@contextmanager` whose body takes shared state (a lock, a counter, a registered hold) before the `try:` that gives it back leaves it taken when a KeyboardInterrupt lands between the take and the `try`. The take goes INSIDE the `try`, with a took-flag set in the same step (or a `finally` that is idempotent), and the give-back is ONE statement with no call in it where that is possible. `tests/test_contextmanager_acquire_before_try.py` scans every `@contextmanager` in `src/` for a take before the `try`: 29 offenders on the first run, 4 converted in that PR (`corpus_lease`, the AI coordinator's hold reasons, `llm.inflight.generating`, `verify._pass_in_flight`), `library_generation.swap_window` converted on its own, 2 owed to the lanes that own the file (`runner.exclusive_window`, `stream_backup.active_staging`, in an `_OWED` table the test checks for staleness) and 23 allowlisted with a written reason (thread-local or ContextVar state, which only the thread that took it can see).

(2) **Why "one statement with no call".** CPython 3.13 checks for a pending signal at calls (after they return), at backward jumps and at the start of a Python frame, NOT between call-free statements. So `_HELD[name] += 1; took = True` is effectively one step, and `n -= 1` / `del d[token]` as a give-back cannot be interrupted half way. The first fix of `corpus_lease` still leaked about 8 % of interrupts because its give-back called `.get()` and `.pop()`: the interrupt arrived after the call returned and before the next line. Rewritten as `_HELD[name] -= 1` (a name at zero stays in the dict and is not listed by `active_leases`) it left 0. **A give-back with a call in it has a window the size of that call's return.**

(3) **What cannot be closed by structure.** A Python call has no protected entry: an interrupt inside a cleanup call's own body, or between the call and its first instruction, is not covered by any `try` in the caller. `swap_window` left state set in 7,013 of 30,872 real interrupts (23 %) before the change; at 46ce6e548 (2026-10-17) 3,836 of 62,053 (6.2 %) still leave the holder (2,015) or the window stamp (1,821) set, never the lock, and every one lands inside a cleanup function's own entry or body (`release_if_held_here`, `_close_window`, `held_here`). Say so in the code and measure it; do not claim zero, and do not quote a figure from an earlier run.

(4) **How to measure without lying.** `scripts/signal_leak_probe.py <gate> <seconds>` raises one KeyboardInterrupt per iteration from SIGALRM every 0.3 ms and reads the damage. READ THE DAMAGE AFTER THE EXCEPTION OBJECT IS GONE: while the traceback still holds a generator-based context manager's frame, the manager looks as if it still holds what it took, which printed false "left held" rows until the read moved outside the `except` block. The probe now prints where each interrupt landed (function and `file:line` per kind of damage), which is how the cleanup-entry landings above were told apart from real leaks.

(5) **Supersession, for whoever reads the history.** The earlier figure in the message of commit 027cc6912 ("about 600 of 30,872") is SUPERSEDED by 3,836 of 62,053 at 46ce6e548 (2026-10-17); the commit message stays in history, this is the number to quote. The state it leaves (holder, window stamp) is in-memory only and is reachable only by a signal that ends the process (library_generation.py:71-74, :139; callers merge.py:5604 and repair.py:1335 run on worker threads in the server; the one main-thread chain, release_run_fresh_restore.py, catches Exception only).
