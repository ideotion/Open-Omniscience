## 2026-11-05 — a thread a test starts must end with the test, and sharding is what shows the ones that do not: fix the leaker, not the victim (C10, PR #1726)

**What was found.** The first full parity run (one unsharded process against the three shards on the same commit) found exactly one order dependence in 1579 modules: `tests/test_scheduler_runs.py` read three run records instead of two when it ran right after `tests/test_scheduler_pause_resume.py`. Two tests of the pause/resume file end on `run_now() is True` and join nothing. `run_now()` starts an `oo-scrape-now` daemon thread whose `_do_run` writes its run report into whatever data directory is current when it finishes, so the report landed in the NEXT test's directory. Unsharded the next file was `test_scheduler_runner.py`, which never looked at the directory; the cost table dealt `test_scheduler_runs.py` next to the leaker. The same dependence was present in both the `test` and the `core-only` shard 3.

**The rule.** Any change to how tests are dealt changes who neighbours whom, so a suite that has only ever run in one order has not proved that no test leans on, or leaks into, another. Fix it where it LEAKS: the leaking file now has an autouse fixture that joins every `oo-scrape-now` thread after each test while its own data directory is still current, and fails the test that left one (`_no_manual_pass_outlives_the_test`). No change to `src/` and none to the conftest, which would have hidden the next leaker; and the table that is shipped must be the one the last parity run proved, because a new table is a new set of neighbours.

**What the guards were shown to do.** The pair `test_scheduler_pause_resume.py test_scheduler_runs.py` passes 3 of 3 with the fixture; with the join replaced by `pass` the pair gives 4 errors. After the fix the next full parity run (the measured table): 1580 modules in the three legs against 1580 in the unsharded run, 29315 passed, 353 skipped, 1 xfailed, 0 differences in any leg.

**Stated limits.** The parity comparison sees outcomes, not what a test did: a test that passes in both orders for different reasons is invisible to it. It proves the dealing it ran on, not every possible dealing; a refreshed table or a different shard count wants the comparison again (`docs/maintenance/CI_SHARDS.md`).
