## 2026-10-27 — An exception that escapes a per-item function after the fetch must leave the same mark a failed request leaves, or the selection feeds on it (R294, the independent read of R293)

**What was found.** `track_document` stamps `last_checked_at` before it fetches and commits only on its own return paths. An exception that escaped it AFTER the fetch (a locked commit, an extractor crash, a malformed page the extractor choked on) reached the batch trackers' `except Exception`, whose `session.rollback()` discarded the uncommitted stamp. The document kept its old time, stayed at the head of `auto_track_due`'s least-recently-checked order, and was fetched again on every pass with no 24 h back-off. MEASURED on main and on the R293 branch alike: 3 requests over 3 passes for one such document, and with a batch of two, two such documents at the head kept a healthy one behind them from ever being fetched in 3 passes (each crash spends the batch, correctly, because a request was made).

**Rules.**
1. **A handler that rolls back must re-apply whatever the rolled-back transaction held that the failure does not undo.** The fetch happened, so the check happened: after the rollback the handler stamps the document the way a failed request is stamped (`last_checked_at` = now, `last_status` = `error: ...` through `record_text`, committed), then counts the error. The same helper serves both trackers.
2. **The back-off is best effort and never aborts the pass.** A database that is itself failing leaves the document where it was; the helper catches, logs and rolls back. A document that cannot be loaded (deleted meanwhile) is skipped.
3. **Only a crash AFTER the fetch returned is a check; mark that moment, and do not infer it from the exception.** A refusal and a deferral are not checks (R293), and an exception can come from anywhere: the walk's own read of the document, or the commit that records a deferral or a kill-switch refusal. The first version of the helper stamped every exception that reached the handler, and a one-off database error on those paths (nothing was asked of any host) came out as a check: `last_checked_at` = now, status `error: ...`, the exact lie R293 removed, found by asking what else raises into this handler rather than by a failing test. `track_document` now records on the session (`session.info`, which survives the rollback and belongs to one thread) the id of the document whose fetch returned a result, clears it at the top of every attempt so an earlier fetch of the same document cannot vouch for a later one, and the helper stamps only when the id matches. Three tests pin the three entry points (a read error, a failed deferral commit, a failed refusal commit) and a fourth the stale marker; each fails against a helper that stamps unconditionally.
4. **A crash spent a request, so it spends its batch slot; the guarantee is that it leaves the head of the queue.** If a crash did NOT spend the batch, one crashing document at the head would cost an unlimited number of requests in a pass (every crash would free the slot for the next document and the walk would go on). So a crash is counted as asked, and what is pinned is the shape that follows: after a crash the document is stamped, it leaves the head, and a healthy document behind it is reached on the NEXT pass (with a batch of two and two crashers ahead of it), or on the same pass when the batch is three.
5. **Not checked, stated.** The back-off is best effort: a crash whose stamp cannot be written (the database failing at that moment, or the row deleted meanwhile) is logged, the pass goes on, and the document is retried on the next pass as before. The 24 h back-off applies to every crash alike; a crash that is transient (a locked commit) waits a day too, the same price a transient request failure pays.
