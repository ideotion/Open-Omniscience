## 2026-10-27 — An exception that escapes a per-item function after the fetch must leave the same mark a failed request leaves, or the selection feeds on it (R294, the independent read of R293)

**What was found.** `track_document` stamps `last_checked_at` before it fetches and commits only on its own return paths. An exception that escaped it AFTER the fetch (a locked commit, an extractor crash, a malformed page the extractor choked on) reached the batch trackers' `except Exception`, whose `session.rollback()` discarded the uncommitted stamp. The document kept its old time, stayed at the head of `auto_track_due`'s least-recently-checked order, and was fetched again on every pass with no 24 h back-off. MEASURED on main (which carries R293): 3 requests over 3 passes for one such document, and with a batch of two, two such documents at the head kept a healthy one behind them from ever being fetched in 3 passes (each crash spends the batch, correctly, because a request was made).

**Rules.**
1. **A handler that rolls back must re-apply whatever the rolled-back transaction held that the failure does not undo.** The fetch happened, so the check happened: after the rollback the handler stamps the document the way a failed request is stamped (`last_checked_at` = now, `last_status` = `error: ...` through `record_text`, committed), then counts the error. The same helper serves both trackers, and it runs AFTER the rollback: before it, the back-off's commit would persist whatever half-finished attributes the crashed attempt had pending (a baseline text with no revision), which a test pins by failing the flush that would write the revision.
2. **The back-off is best effort and never aborts the pass.** A database that is itself failing leaves the document where it was; the helper catches, logs and rolls back. A document that cannot be loaded (deleted meanwhile) is skipped.
3. **Only a crash AFTER the fetch returned is a check; mark that moment, and do not infer it from the exception.** A refusal and a deferral are not checks (R293), and an exception can come from anywhere: the walk's own read of the document, or the commit that records a deferral or a kill-switch refusal. A helper that stamped every exception reaching the handler would turn a one-off database error before any request into a check (`last_checked_at` = now, status `error: ...`), the lie R293 removed. `track_document` therefore records on the session (`session.info`, which survives the rollback and belongs to one thread) `(document id, the attempt's own time)` once the fetch has returned a result, and the helper stamps only when the id matches. The id keeps one document's marker from vouching for the next (document A fetched fine, then B's row cannot be read: B was never asked); the time is what makes a marker left by an attempt that returned normally harmless, because it equals that attempt's own committed stamp (rule 4). A unit test pins the id check on its own and a two-document sequence pins it through `auto_track_due`; tests for the three entry points (a read error, a failed deferral commit, a failed refusal commit) and for an earlier fetch of the same document each fail against a helper that stamps unconditionally.
4. **A crash after the attempt's own commit keeps the outcome it recorded.** The baseline path commits, then indexes the text into the corpus and writes the lane row; either can raise. The document WAS baselined and its stamp is in the database, so overwriting "baseline captured" with `error: ...` would replace a true outcome with a false one (found by the independent read). The helper reloads the document after the rollback and does nothing when its committed `last_checked_at` is already the attempt's own time. The comparison is made on the STORED form of the time (the column is a plain `DateTime`, a read-back value has no zone), and a test pins both the keeping and the zone handling.
5. **Read the id of the item you are about to process without asking the database.** `track_watched` took `doc.id` before its `try`; after any commit every document in the loop is expired, so that read went to the database, and a one-off failure there escaped the loop and failed the whole manual pass (`POST /api/law/track` would answer 500), where before the change it was one counted error. It now takes the identity from the instance state (`sqlalchemy.inspect(doc).identity[0]`, no SQL). `auto_track_due` already read its documents inside the guard on purpose. When a handler needs a name for the item, take it from something that cannot fail.
6. **A crash spent a request, so it spends its batch slot; the guarantee is that it leaves the head of the queue.** If a crash did NOT spend the batch, one crashing document at the head would cost an unlimited number of requests in a pass (every crash would free the slot for the next document and the walk would go on). So a crash is counted as asked, and what is pinned is the shape that follows: after a crash the document is stamped, it leaves the head, and a healthy document behind it is reached on the NEXT pass with a batch of two and two crashers ahead of it, and on the SAME pass with a batch of three (both pinned).
7. **Not checked, stated.** The back-off is best effort: a crash whose stamp cannot be written (the database failing at that moment, or the row deleted meanwhile) is logged, the pass goes on, and the document is retried on the next pass as before. The 24 h back-off applies to every crash alike; a crash that is transient (a locked commit) waits a day too, the same price a transient request failure pays. The "stamp is the attempt's own time" comparison assumes the stored time keeps the attempt's microseconds, which the SQLite and SQLCipher `DateTime` columns do; a store that rounded them would read a committed attempt as uncommitted and stamp over its status.
