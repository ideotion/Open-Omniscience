## 2026-11-05 — a floor is a claim about a release: give it a test that fails on the release below it, and give a range a lane for its other end (R412, the version-coupling bundle, PR #1723)

**What was found.** Three version statements in this repo were true only because someone had once run something by hand. (1) `starlette>=1.5.0` was written for the gzip flush; the reason to move it to 1.8.0 (a closed tab stops the database backup stream, because `FileResponse` races its file against `receive()`) lived in a ledger paragraph and a registry sentence, and no test knew it. (2) `ruff>=0.16.6,<0.18` sat under a count ratchet: the same tree reads 414 on 0.16.9 and 412 on 0.17.3, so the ceiling of 412 was true on the day it was measured and on no other. (3) `duckdb>=1.4` has no ceiling and the `columnar` job installs the newest release, so the 1.x line the floor admits ran in no lane, and a plan-shape assertion that reads a profile 1.x and 2.x write differently could only ever run on one side.

**The rule.** A floor, a pin or a range is a claim about releases; each claim wants the cheapest thing that can contradict it. Here that was: (1) a test that drives the real class and asserts the behaviour the floor buys, run on the wheel below the floor to see it FAIL (the backup response sent 4,194,304 of 4,194,304 bytes on starlette 1.7.0 and one chunk, 65,536 bytes, on 1.8.0), not only on the release it was written against; (2) an exact `==` pin where a count over the tool is ratcheted, so the number is a statement about one release and a new release is its own PR with its own re-measurement; (3) a second lane that installs the OTHER end of an open range, with a check inside the lane that it got what it asked for (`duckdb.__version__.startswith('1.')`) and a test that the two lanes name the same files, so neither can quietly become a copy of the other.

**What each guard was shown to do.** Nine mutants of the real files each failed a named test and were restored: the 1.x job without `"duckdb<2"`, without the version check, with a file dropped, with the `columnar` job pinned to `<2` (two lanes on one line), with another job condition, `ruff` and `mypy` turned back into ranges, a new file that names `http.disconnect`, and the registry entry missing one of the listed sites. The behaviour test itself failed on the 1.7.0 wheel and passed on 1.8.0 and 1.10.0.

**Stated limits.** The exposed-sites list is a grep for the literal `http.disconnect`; a stub built another way is not found. The 1.x lane runs the newest 1.x release pip resolves (1.5.6 today), not the floor (1.4.0). The backup behaviour holds on a server that speaks ASGI spec older than 2.4 (uvicorn: 2.3); on a 2.4 server both releases read the file to the end, and the registry says so. One of the immediate-disconnect tests (`test_the_scratch_archive_is_deleted_once_it_has_been_sent`) is named for something it no longer needs to be true on 1.8: with a disconnect at once the body may not be sent, and it asserts only the deletion; it is the keyword lane's file and the name was left alone.
