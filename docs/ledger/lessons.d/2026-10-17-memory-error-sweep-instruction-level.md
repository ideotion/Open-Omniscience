## 2026-10-17 — Test "the cleanup survives an allocation failure" by failing every instruction that can allocate, not every line (PR #1435)

**What was found.** The question was whether ``swap_window``'s cleanup gives the exclusive library lock back when a MemoryError lands inside it. Read, it looked fine (a ``finally`` that releases); forced, it was not: with a MemoryError raised before each allocating instruction of the cleanup in turn, the lock stayed held at 5 of 10 instructions on main and on the build the 10-16 instances run, and at 2 of 13 on ``#1426`` plus one lost wake-up. A held lock blocks every later ``connecting()`` (every new pooled connection) in ``shared()``, which had no timeout, until the process restarts. The write gate was never at risk: the caller's ``with write_lock():`` unwinds on the error (0 of 34 forced failures left it held).

**The rules.**
1. **A MemoryError comes from an instruction that allocates, not from a statement boundary.** A line-boundary sweep (right for a KeyboardInterrupt) first modelled the wrong event and gave a wrong table. The sweep traces the module's frames with ``sys.settrace`` and ``f_trace_opcodes`` and raises before the Nth instruction whose opcode can allocate (calls, ``BUILD_*``, ``BINARY_OP``, iterators; loads, stores, jumps, pops, comparisons and truth tests cannot). On CPython 3.13 ``f_trace_opcodes`` has to be set at the first ``line`` event of a frame it just entered, not at the ``call`` event. A call into the standard library is ONE instruction ("the call could not start"); a failure half way inside it is not modelled and is said so.
2. **Leave out the enter and exit of ``with <lock>:``, and say that they can fail.** The sweep cannot inject there without deadlocking its own harness, and nothing can protect them. The enter is a ``BEFORE_WITH`` that makes the bound ``__enter__`` and ``__exit__`` (a failure before the acquire is harmless). The normal exit calls ``__exit__(None, None, None)``, which on CPython 3.13 builds a 3-tuple, so it allocates when the tuple free list is empty (after a full collection) and, if that fails, leaves the lock held: measured with ``_testcapi.set_nomemory`` on cold free lists, for a plain ``Lock`` and an ``RLock`` alike. A hang seen when a harness injected at the exit is therefore the interpreter's, not the harness's. The ``with`` form is what the interrupt rules require (R144, R171), so this is a residual to name beside the release call. What can be done is to take no second lock in a cleanup that a failed exit of the first would block: ``swap_window``'s cleanup takes ``_STATE`` three times (the read of ``_DISK_CHANGED``, ``_revive``, ``_close_window``), and removing the first only moves the hang to the next (measured with the allocator: the hang at allocation 24 of the cleanup moves to 25); that is the module's design, not a fix for this change. A small-int count (``self._shared -= 1``) cannot allocate either (CPython returns the cached object below 257); the sweep's list over-counts those, and the report says which sites are real.
3. **``finally: a(); b()`` runs ``b`` only if ``a`` returns.** Nest them (``try: a() finally: b()``) so the release does not depend on the call before it; this was most of the 5 of 10.
4. **No call between "this is ours" and "this is cleared".** The release compared the holder with ``threading.get_ident()`` called inside the lock; that call is a site. Read the identity BEFORE asking for the lock and pass it in: the comparison and the store are then loads and a store. What is left after the holder is clear (``notify_all``) can fail; that costs a wake-up, not the lock.
5. **A wait with no timeout turns a lost wake-up into a hang.** ``shared()`` now waits in steps (``_RECHECK_S``, one second) inside the same ``while True: if not wanted: break`` loop, so the shape the interrupt tests pin is unchanged. The step is the longest a lost wake-up may cost; it is NOT a timeout (an open still waits as long as the window is held, which a test pins). The number is chosen, not measured, and the module says so.
6. **Name the site no code can protect, and let the test allow exactly that one.** The call of ``release_if_held_here`` itself cannot be protected by anything that runs after it (natively the site is the ``BEFORE_WITH`` inside it, which the sweep excludes with the other enters and exits; the model names the call). The test allows that site to leave the lock held and no other, and asserts the site exists in the sweep, so renaming it cannot silently widen the exception.
7. **A sweep that finds nothing proves nothing until it has been seen to find something.** The test rewrites the module's own source three ways (each undoes one fix: the identity call, the cleanup whose second statement is skipped when the first fails, the wait with no step) and requires the sweep to report each; a pattern that no longer matches exactly once fails with its own name. It was also run, unchanged, on ``#1426``'s shape and failed at exactly the two sites the harness had predicted.
8. **The sibling, closed the same way.** ``connecting()``'s cleanup had the same family of site (main: the release call itself, 1 real site of 3; ``#1426``: 3 of 7, two of them the new "did this thread take a level" check placed before the release). A level left raised makes later swaps refuse with ``LibraryBusy`` until restart: a named refusal of a rare operation, not a hang. ``release_shared_since(before)`` replaces the pair of calls: ``before`` is read ahead of the take, the thread's record has a class default so reading it is an attribute load and not a ``getattr`` call (which also makes the take's "no call between the count and the record" comment true), and the comparison and both decrements are loads, stores and small-integer arithmetic. The second sweep leaves ``+= 1`` / ``-= 1`` out because a small-int result is the interpreter's cached object (a test pins that on the running interpreter, so the counters join the sweep if it stops holding). The swap's own wait takes the same one-second step, so a lost ``notify_all`` in the give-back costs the swap one step and not its deadline (the third mutant). Residual, named in the test: the call of ``release_shared_since`` itself.
