## 2026-11-01 — a test that reads the incident record right after `note()` must wait for the record thread, because `note()` waits for it only `RECORD_WAIT_S` (PR #1691)

**What was found.** The Core-only job of #1688 (run 41318585353, job 124883851437; a diff that touches only `BackgroundJob._run`) failed on `tests/test_database_damage.py::test_an_incident_of_another_process_is_its_own_record_even_when_no_session_id_is_known` with `assert 0 == 1` / `where 0 = len([])` (`len(first.state(detail=True)["incidents"]) == 1`), one failed in the whole job. It passes alone, so it read as order-dependent; the mechanism is not the order. `DamageRegistry.note` sets the latch synchronously and writes the incident on a daemon thread (`oo-damage-record`, started by `_single_flight`); it then joins that thread for at most `RECORD_WAIT_S` (2.0 s), on purpose, so that a hung drive cannot hang a collection thread. `state(detail=True)["incidents"]` reads `_incidents` and does not wait for the thread at all. A test that reads the record straight after its notes therefore passes if and only if the record thread finished inside 2 s, and that is a timing coin toss that has been won for months.

**Reproduced, not inferred, at the mechanism.** A pytest plugin outside the repo (`-p stall_plugin`) wraps `DamageRegistry._record_new` in a `time.sleep(0.3)` and sets `damage.RECORD_WAIT_S = 0.01`, the same structure with the numbers scaled down. On the unfixed file, 27 of the 107 tests failed, among them the CI assertion VERBATIM (`assert 0 == 1`, `where 0 = len([])`, at the same line). The plugin is the technique: to prove a bounded wait is not being relied upon, make the thing it waits for slower than the wait and see which tests notice.

**What is NOT known (a negative result).** What stalled the record thread for more than two seconds in the CI job is INFERRED. The thread reads the earlier session's record (`_ensure_loaded`), the session ledger (`_previous_end`) and the file sizes (`_sizes`), and never `fsync`s, so a file-system stall on a loaded runner, a garbage-collection pause or CPU starvation behind a neighbour would each do it. The job's log carries a `sqlalchemy.pool` reset error with a traceback inside the same test, the GC-finalization family of #1681, which is consistent with a collection pass landing there and proves nothing about its length. The Core-only ORDER itself was not reproduced: that is a 70 to 83 minute run for an event that has happened once.

**A second hazard the plugin exposed.** `damage.registry` is ONE process-global object. `_reset_for_tests` clears its state but cannot stop a record thread still writing for the test that just ended, and that thread then puts its incident into the NEXT test's registry: under the stall, `test_the_bundle_member_is_the_record_cut_oldest_first_and_names_the_cut` read 17 incidents where it had noted 12. The `registry` fixture now settles on teardown.

**The rule.** Where code has a BOUNDED wait (a `join(timeout)`, a poll with a deadline), a test of what it produced must wait on the CONDITION (`_settle`: `wait_until` the registry's `_jobs` is empty, with the hang guard as the only deadline), never lean on the bounded wait having been long enough. The latch needs no settling (it is set before `note` returns); the reads that do are those of the incident record, the file, the repeat counters and `write_error`, the four things the record thread (or a `_single_flight` job) writes. A test that exists to pin the bounded wait itself is the exception and was not touched.

**One more test, found by the delta read, and a stronger probe.** The first plugin slows only `_record_new`, so it could not see `test_a_record_that_cannot_be_written_says_the_class_and_the_errno_name_never_the_message_or_the_path` (the test R404 names): it reads `write_error` after two `_single_flight` jobs that nothing waited for, and a late flush of the earlier `note`'s record thread (ENOENT) can overwrite the job's `OSError ENOSPC`. A second plugin (`stall_job_plugin.py`, next to the first) stalls the START of every job (`_job_main`), optionally only the jobs whose key starts with `record` (`STALL_KEY=record`, which makes the late record flush land AFTER the other job and is what proves the `_settle` after the `note` is needed). Under it that one test failed and the other 106 passed; with three more `_settle` lines all 107 pass under both plugins. The delta read (an independent Opus read, given the diff and no conclusion) is what named the test; the probe confirmed it. Take both: a read that cannot be fooled by the probe's blind spot, and a probe that checks the read.

**Where it applies.** The 20 tests that read a record job's outcome now call `_settle` first (25 insertions), plus the fixture teardown; each of six mutants (every `_settle` added to the two named tests, and the teardown, removed one at a time) fails under the plugins and passes without them. The same shape applies to any other registry or job whose `start`/`note` returns before its worker has finished and whose test then reads the worker's output.
