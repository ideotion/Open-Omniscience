## 2026-10-27 — an entity load that reads two columns costs the whole row at the size of the table, and its speed-up must prove which side effects it drops

**Found by the keyword lane's entity-load sweep (R304).** Four sites loaded a whole table as ORM entities to read a few columns: `backfill_baseline_tags` (every keyword: 33.8 s and 2,951 MB of Python allocation on 1,500,000 seeded keywords), `tag_coverage` (86,000 feed states: 1,216-1,312 ms and 152.5 MB) and the due filter (57,333 feed ids: 943-991 ms and 111.3 MB). Read as column queries (`session.query(Model.a, Model.b)`) they came to 3.7 s and 12.5 MB, 548-571 ms and 47.9 MB, and 321-352 ms and 27.2 MB, with the same answers.

**Rules.**
1. A figure for such a change is measured on the SHIPPED statement, on the same seeded store, before and after, and named by size. A chunked read states what the chunk protects in bytes of the widest shape the columns allow (here 20,000 rows of a 10-character language and a 255-character term, about 600 B a row, 11.8-12.0 MB), not "a reasonable number".
2. An entity load fires ORM machinery a column query does not. Before replacing one, list what the load triggered (mapper-level load listeners, relationship loads, lazy attributes, the identity map the rest of the pass reads) and show the projection loses none: for `FeedFetchState` there is no relationship, no mapper-level load listener, and the session-level hooks fire equally for column queries; the identity map only served the pass-level session, which the workers do not share.
3. A cursor over `id > after_id` has a stated limit: a row inserted with an explicit id below the cursor between two chunks is not seen until the next run. Say it where the chunk is defined, and say which writers can do it (an explicit-id merge import; the app's autoincrement inserts cannot).
4. A projection returns `Row`, not the model: helpers that took the entity accept `Model | Row | None` and read attributes by NAME, never by position, and mypy's `arg-type` on `dict(rows)` is the tell for a place that still assumes a tuple.
5. A bound that nothing sets is not tested: a bare `COUNT(*)` in a route with no statement deadline (the rollup benchmark) is a stated limit, not a one-statement fix.
