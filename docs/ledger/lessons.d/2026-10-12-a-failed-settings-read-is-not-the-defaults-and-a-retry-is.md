## 2026-10-12 — A FAILED SETTINGS READ IS NOT THE DEFAULTS, AND A RETRY BELONGS TO THE FAILURE IT WAS BUILT FOR (release candidate diagnostics, core fold 12, `src/config/kv_store.py`, `src/safety/settings.py`, `src/safety/fetcher.py`)

The settings store answered a read that FAILED (locked, keyed to another passphrase, damaged) with `None`, the same word it uses for "nothing stored", and the safety settings turned `None` into the defaults, which are the direct connection. **(1) Absent and unreadable are two answers, and a value that is there and damaged is the second.** `kv_get_json_checked` raises `KvReadError` (the class of the failure and none of the engine's words) for a read that failed, and `None` stays a fact (no file, no table, no row). `load_settings` turns the error into protected mode with no proxy and `read_failed` set, which every builder refuses (`TransportUnavailable`, a session's transport refusal): offline, as the app starts (R117), until the store reads again. A client that already holds a session keeps the one it was built with (`following_session`, `following_fetcher`; the session only for the user agent it was built with), the same for a corrupt legacy `safety_settings.json` and a store that was read and is gone (a first run, with no store yet, keeps the defaults, and the app starts offline); the refusal says the settings could not be read, never "no proxy is configured"; a new passphrase clears the held failure, so a live stream is not moved to a direct connection by a failed read; a failed read is remembered for two seconds so a stream's every event does not open a failing store. **(2) A retry belongs to the failure it was built for.** The read-write retry exists for a read-only open that a read-write one can get past (a hot rollback journal, a directory the `-shm` cannot be written into): "unable to open database file" and "readonly database", matched by class name because the keyed driver has its own `OperationalError`. On a keyed store `connect` turns every failure into `WrongPassphraseError`, so in practice the retry is plaintext-only. It is NOT taken for a wrong key (a read-write close folds and deletes a leftover `-wal`, the evidence of how the last session ended) or a lock (it would stall twice); a real keyed test with a leftover log pins the bytes. **(3) A log line on that path names the class.** A keyed open chains the driver's own error and a traceback prints the chain, so the records say `type(exc).__name__`, and a source-level test fails if `exc_info` comes back. **(4) A save that rewrites what it read reads strictly.** The app, scheduler and custody preferences gained the safety settings' strict read: an unreadable store refuses the save by class, instead of writing the defaults over what the user saved. **(5) A response is not caused by the exception.** `raise HTTPException(...) from exc` inside a route that holds a typed key left the raw engine error as the `__cause__` that a traceback prints; the guard now refuses it (the route layer answers `from None`), and the run journal, the newsletter import and its report are in the guard's table with every handler read.
