## 2026-10-28 — the wheel is built and read at PR time: CI installs the project editable, which reads the source tree and can never show a file the wheel lacks

**What was found (R330, R353, R380).** `release.yml` is the only workflow that builds this project's wheel, and it builds it at tag time with `python -m build` (the sdist first, then the wheel from the sdist, so `MANIFEST.in` decides what the wheel carries). Every CI job installs the project with `pip install -e`, which imports from the checkout, so a data file the code reads and the wheel does not carry cannot show up in CI at all. `pyproject.toml` ships the data by glob (`[tool.setuptools.package-data]`) and `MANIFEST.in` by graft, and a list is something somebody has to remember: a new `src/analytics/table.json` matches none of the `src` globs and would not ship, and the app would boot from the wheel with the feature quietly absent (the lesson of `src/geo/data`, 2026-09-07, which sat uncovered from the day it was added; `src/legal/documents.py` likewise falls back to the French text when a translated one is missing). MEASURED on `8850e61ca`, from a clean `git archive` export: `python -m build` takes 20.1 s (`pip wheel . --no-deps` 14.0 s, `uv build` 10.2 s) and gives an 18,197,068-byte wheel of 1,132 files (1,138 zip entries with the six `*.dist-info` entries; src 826, configs 147, migrations 81, docs 78; 46.5 MB unpacked). Nothing tracked under `src/`, `configs/`, `migrations/`, `docs/legal/` or `docs/i18n/` is missing from it except `src/analytics/duckdb_ext/README.md`. 2,350 tracked files under the ten developer trees of `docs/` are not in it, on purpose (`audit` 1,135, `ledger` 772, `research` 167, `archive` 104, `plans` 77, `design` 66, `product` 22, `maintenance` 4, `process` 2, `testing` 1).

**The rule.** Derive the expectation from the tree instead of remembering it: every tracked file under `src/`, `configs/`, `migrations/`, `docs/legal/` (the 12-language legal gate) and `docs/i18n/` (the translated quick-start) must be in the wheel unless `scripts/check_wheel_layout.py` names it in `NOT_SHIPPED` with a reason, and a stale exemption is itself a problem. A short list of twelve anchors (the code, the UI, the two `src/*/data` kinds, the sources catalogue the sources-import route reads, the migrations, the manual, one translated legal document plus its `ui.json`, the translated quick-start) is checked against the wheel alone, because a rule derived from the tree passes vacuously when the tree loses the file too. The step builds the wheel the way the tag build does, with `python -m build` (an independent Opus read found that the first version, `pip wheel .`, builds from the checkout and so skipped the sdist: a `MANIFEST.in` change that would cost the release wheel two anchors stayed green), and the checker reads the wheel's own file list and prints its `Generator:` line (the setuptools version that built it). `tests/test_ci_wheel_layout_step.py` pins the step the way the installed-versions step is pinned (R364) but strictly: three commands, each alone on its line and matched whole, the checker reading exactly the directory the build wrote, no pipe, `||`, `&`, `!`, `if`, `set +e`, `continue-on-error` (the workflow sets no default shell, so a step runs plain `bash -e` without `pipefail`), and twenty-six mutants, each named by its own sentence.

**What it costs, and what it does not prove.** MEASURED on the runner, from the first CI run of this change (run 40661391305, head `4ce134395`): the step took 15 s (09:06:57 to 09:07:12 UTC: the install of `build`, `python -m build` and the checker), and the `lockfile-install` job took 74 s against 50 s on run 40638055096 (two different runs, so the 24 s is a rough figure: of it 15 s is the step, the "Real install from requirements.lock" step itself took 40 s against 32 s, and the smoke check 8 s against 7 s). The 20.1 s for `python -m build` above is the sandbox figure, from a clean `git archive` export, and is not the runner's. The build resolves setuptools unpinned, as the tag build does (R381), so a setuptools release that breaks the build reddens this step first on every pull request: that is a real release blocker found early, not a flake, and under R349 the lane that sees it diffs package versions first and names the version. **One such release is already announced:** the build log prints `project.license as a TOML table is deprecated ... By 2027-Feb-18, you need to update your project ... or your builds will no longer be supported` (`pyproject.toml` has `license = { text = "GPL-3.0-or-later" }`; the SPDX string form needs setuptools 77 or later). It reads a file list: it does not install the wheel or boot the app from it (that end-to-end run belongs to the release procedure), and it asks for `docs/` only through the two subtrees and the manual. **It does not catch R330 itself**: `sources.yml` is in the wheel, the bug was the path built in the route, so OSM's route test stays the other half of that pair; the check here is a file the code reads being absent from the wheel.
