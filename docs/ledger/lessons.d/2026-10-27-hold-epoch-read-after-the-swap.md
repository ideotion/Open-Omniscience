## 2026-10-27 — a hold that records the corpus's state at the stop cannot be released by the change that caused the stop

**Found by item 1 of the 0.5.1 follow-ons (does an exclusive window wait for a rollup build?).** The window does not: a restore, a repair or an encryption in place swaps the corpus file (`backup.merge.swap_in_corpus`) after waiting only for jobs that hold a `corpus_lease`, and a rollup build is a reader that holds one session for its whole run (15 minutes at 12 million mentions) and takes no lease. The generation guard then refuses the build's next statement (`StaleLibraryError`), the build ends `failed`, and R172's failure hold is kept, with the corpus epoch and mention count read AFTER the exception, which is after the swap: the new corpus's figures. The hold's release rules compare against those figures (a larger limit, offload newly allowed, a materially smaller corpus), so for a restored corpus of the same size none can fire, and the keyword rollup stayed off until the app restarted. Reproduced, then fixed: `keyword-lane/swap-midbuild-repro.py` (swap returned in 0.00 s with the build in flight; next dispatcher call `declined`).

**Rules.**
1. A release rule that compares against a figure taken when the stop was recorded is only as good as the moment the figure was taken. When the cause of the stop is itself a change of that figure, reading it after the cause makes the rule unable to see the very change it exists for. Either read the figure where the cause happened (before it), or keep no hold for that cause.
2. A hold is for a build that failed on the corpus it will read again. A build that died because its file was replaced has not tried the new corpus: classify that death by its cause (`library_generation.StaleLibraryError`, found through the cause chain), say it in `last_decline` and in the boot row, add nothing to the run of failures (an earlier run restored after a restart is left as it was), and let the next request build.
3. A reader that runs for minutes and takes no lease is invisible to every barrier made of leases. The swap's wait is for work that WRITES; a reader is protected from the swap only while it holds one connection: the generation guard refuses a statement or COMMIT on a connection made before the swap (it fails loudly, and whoever classifies that failure has to know it is the swap's and not the build's), but a session that commits between batches hands its connection back to the pool, and the guard's CHECKOUT refusal is a DisconnectionError the pool answers by opening a fresh connection on the NEW file, silently (measured by the Opus read of #1547: select, commit, swap, select on one ORM Session returned the new file's row, no error). So a swap that lands between two batches, or in the DuckDB-only aggregate stage, raises nothing and the build goes on across both corpora; this fix covers only a swap that lands inside a batch's statements. The between-batches case is a separate defect (a build that compares the library generation it started under at each stage boundary would turn it into the same refusal) and is not touched here.
4. The recogniser is tied to the exception a REAL swap raises (a test performs a swap through `swap_window` and `os.replace` on a guarded engine and hands the exception it gets to the recogniser), not to a copy of a class name; mutants: the branch disabled, the recogniser accepting everything, the cause chain not followed: all red.
