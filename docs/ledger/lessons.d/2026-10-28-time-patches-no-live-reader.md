## 2026-10-28 — Process-wide patches of the `time` module have no live reader in the test runner today: a measurement, not a conversion (R376 item 1, after R344/R350)

**The question.** R350 was a process-wide `os.fstat` patch that pytest 9.2.0 met at every phase end. Does the same shape exist for `time`: 53 call sites in 28 test files (`monkeypatch.setattr(time, "monotonic"|"sleep"|"time"|"thread_time", f)` or `<module>.time`, which IS the `time` module; 38 of the 53 spell it `<module>.time`; counts of 18 `monotonic`, 14 `sleep`, 18 `time`, 3 `thread_time`) while the runner reads the clock?

**Answer: no live reader found; no helper added, nothing converted.**
1. **pytest 9.2.0 reads the clock through names it bound at import.** `_pytest/timing.py` is `from time import perf_counter, sleep, time`; a patch of the module attribute does not reach those references. The only place that looks `time.time()` / `time.perf_counter()` up on the module is `_pytest/subtests.py` (pytest's built-in subtests, lines ~219-247), and no test under `tests/` uses `subtests` or `subTest` (grep). Read from the 9.2.0 wheel's source (downloaded and read, not run: the suite here runs pytest 9.1.1).
2. **A probe agrees.** A fixture replaced `time.time`, `time.monotonic`, `time.sleep` and `time.perf_counter` process-wide with pass-through wrappers that count the calling module, then a test wrote a file, logged, started and joined a thread, waited on an `Event` and a `Queue`; run plainly and under `-n 2` (xdist and anyio are installed). The patch is active across the call-phase end, where pytest builds its report. Count of calls from any module: 0, in both runs (threading and queue bind `monotonic` at import; logging uses `time_ns`). Probe at `/tmp/claude-0/probe_time/test_probe.py`, not committed.
3. **So the R350 failure cannot recur through `time` today.** It would need a test that patches `time.time` or `time.perf_counter` process-wide AND uses the `subtests` fixture; 11 files patch those two names, none uses subtests. **A future test that adds the `subtests` fixture (or `subTest`) to a file that patches `time.time` or `time.perf_counter` process-wide must scope that patch to the module under test first** (as `scope_os` does for `os`), or pytest's own subtest timing reads the replacement.

**Rule.** Before sweeping a class on the strength of one incident, find the reader first. A patched module attribute is only dangerous to code that looks the name up on the module at call time; code that did `from time import monotonic` is immune. The sweep of `os` (#1602) was warranted because pytest looks `os.fstat` up on the module; for `time` it does not.

**Not measured, stated.** The app's own background threads (scheduler, briefing) read `time.*` through the module and can run across a test's patch if a test leaves one alive; that is a thread-lifetime class (the quiesce fixture of #1596 covers the briefing threads), not a patch-scope one, and it was not probed. Other plugins CI might add (pytest-timeout is not installed here) were not read. Local figures: pytest 9.1.1, Python 3.13. `shutil.disk_usage` (43 sites) and `tempfile` (8) were not measured; the coordinator parked them.
