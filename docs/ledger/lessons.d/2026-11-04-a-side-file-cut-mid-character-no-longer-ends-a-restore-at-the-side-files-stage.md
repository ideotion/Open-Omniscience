## 2026-11-04 — an `except` around a text read is a decision about what a CUT file is, and a decode fallback on a path into a log is a scrub decision: withhold what cannot be checked, never repair it (R397 follow-on; PR #1703)

**What was found.** `merge_side_files` (`src/backup/merge.py`), the side-files stage of a restore, read each staged text member with `path.read_text("utf-8")` and caught `(OSError, json.JSONDecodeError)` around the two calendar stores and `OSError` around the log members. A calendar store an earlier crash cut in the middle of a multi-byte character is collected into a backup as it is (the backup's hash is of the bytes it was handed, so it verifies), and `read_text` raises `UnicodeDecodeError`, a `ValueError` that is neither. It left the stage, which runs BEFORE the live corpus is touched, so the whole import ended as a failure for one torn file. The same read of a log member and of the live log raised the same way. Reproduced first: the new tests red on main with `UnicodeDecodeError` at the three read sites (8 of 13; 2 more import the new sentence helper; 3 controls green).

**The rule (two parts).** (1) When a `try` wraps a text read plus its parse, list what the READ can raise, not only what the parse can: `OSError`, `UnicodeDecodeError`, then the parser's own error. A file cut mid-character is the common crash shape of a text file and it fails in the decoder. Sweep BOTH sides of a merge: the live store's loader (`events.feeds._load_json`) had caught `UnicodeDecodeError` since R397; the incoming side of the same file had not. (2) A decode FALLBACK on a path that puts text into a log is a passphrase-scrub decision. The first version of this fix read a torn log with `errors="replace"`; the independent read found, and a test then proved (RAN), that bad bytes INSIDE a held passphrase become U+FFFD, the key no longer matches `scrubbed`, and most of it lands in the live log, which the next backup then carries out because the line is valid text by then. The export side (`scrubbed_copy`) already withholds such a line whole, with its size, "never dropped or repaired". The restore now does the same with its own sentence; only the live log's READ for the duplicate check shares the helper, and nothing is written from it.

**What changed.** The calendar member is skipped and reported (`unreadable in artifact`), as an unparseable one already was: a cut JSON document is not a document. In a log, every line that is text is kept; a line that is not text is replaced by `[a line of N bytes is not merged: it is not valid UTF-8, so it cannot be checked for the passphrase]`, and the log's report entry carries `undecodable_lines_withheld: N`, present only when N > 0, so the report is unchanged for a clean log. A log that is all text is read exactly as before. `_log_lines` is the one helper for both logs; its fallback decodes with `surrogateescape` and splits with `str.splitlines()`, so the lines fall where a clean read's do (`bytes.splitlines()` splits on fewer separators, and a log with a U+000B in it would have been two lines on one path and one on the other); a line that does not re-encode as UTF-8 holds a lone surrogate, which is a byte that was not UTF-8. The sentences are written whatever the log already holds and are never deduplicated or counted in `appended`/`duplicate` (the second read found the first design counted them as duplicates and lost all but the first).

**Pinned by** `tests/test_restore_side_files_cut_mid_character.py` (13 tests: the calendar store cut mid-character skipped, for both store names; the stage goes on to the next members; a cut log keeps its readable lines and withholds the torn one by size; a held passphrase inside an undecodable line never reaches the live log; every withheld line leaves its own sentence even when one is already in the log; the fallback splits where a clean read does; a surrogate written as UTF-8 bytes (`ED B2 80`) is withheld; a log that is only a torn line still says what was left out; a clean log's report is unchanged; a cut live log still recognises the lines it holds; a store cut between characters is still skipped; a good store still merges). Each torn fixture is checked to be undecodable before it is used. 18 mutants all killed (the old except, no fallback, the REPAIR, `bytes.splitlines`, the size zero, an undecodable line kept as text, the sentences deduplicated or swallowed by an existing one, no sentence, a torn-only member writing nothing, the count inside `appended`, the report never or always carrying it, either log read strict again, the stage stopping at a torn member, a torn member reported merged, `surrogatepass` for `surrogateescape`).

**Stated limits.** A torn tail already in the live log stays in the file (appends land after it); only the read for the duplicate check is lenient. Restoring the same artifact twice writes the header and the sentences a second time (they are written whatever the log holds), where a clean member's re-run writes nothing. A sentence's byte count is the line WITHOUT its ending; the export's counts the ending, so the same line reads one byte smaller in a restore. A calendar store of the wrong JSON shape, or one holding a lone surrogate, also ended the stage when this change was written (found by the read and reported); it was closed separately, in `src/events/feeds.py`, by #1707. Not seen in the field by this lane: driven by tests that cut the files.
