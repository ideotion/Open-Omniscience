## 2026-10-29 — a guard read inside `try: ... except Exception: pass` is read as "clear": maintenance guards failed open and silent

**What was found (R396; the keyword lane's scan of its owned files, 2026-10-29; PR #1656).** `BackgroundScheduler._run_off_peak_maintenance` read four guards (memory, storage, a damaged corpus file via `damage.registry.corpus_latched()`, the check after an unexpected stop via `damage.registry.verifying()`) inside ONE `try` that ended in `except Exception: pass  # guard read must never block maintenance`. The comment states the intent (an instrument never breaks the thing it guards) and gets the direction wrong for a guard: a guard that raised was read as "clear", so vacuum, cleanup and checkpoints went on against exactly the file or drive the guard exists to protect, with nothing logged (R386), and one guard raising skipped the reads of the three after it (a raising memory guard meant the damage guard was never asked). Found by reading, then confirmed by the new tests: with the fix removed, five of them go red (each guard raising lets the window run; the log carries nothing). Two sibling handlers ended in a bare `pass` as well, `_tail_journal_trim` and the `release_pass_state()` reclaim in the memory pause; both are housekeeping, so they keep going and now log at DEBUG like their neighbours.

**The rule.** A detector that cannot be read REFUSES and NAMES; it is not read as clear. Each guard is read on its own (`_read_maint_guard`); one that raises refuses the window with the skip reason `guard_unreadable` (a counter in `status()['maintenance_skips']`, distinct from the guard's own refusal so "could not tell" is never reported as "found damage") and a record that names the guard (`log_failure`, scrubbed): the FIRST failure of each guard at WARNING, repeats at DEBUG, and a clean read re-arms it (the same shape as `StorageGuard.log_failure_once`). Not WARNING every time: a guard that stays unreadable is asked again every loop and would flood the error ring. Not DEBUG only (the first form, found by the independent read): that traded a silent fail-open for a silent permanent outage. The cost, chosen: while a guard is unreadable no off-peak maintenance runs, and `_last_maint` is not stamped, so every loop iteration asks again and the window resumes by itself the moment the read works. A `best-effort` handler is a different thing from a guard: housekeeping (journal trim, reclaim) goes on, but still says what it dropped.

**Pinned by** `tests/test_maintenance_guard_unreadable.py` (13): each of the four readers raising refuses and is named (parametrised), an unreadable earlier guard wins over a later guard's refusal and the later one is not asked, memory is read before storage, one WARNING then DEBUG then WARNING again after a clean read (and one first warning per guard), readable guards still let the window run, the readers read the live guards, and the two housekeeping handlers log. Mutant-proven: restoring the fail-open return turns five tests red; restoring either `pass` turns one red; always-DEBUG turns two red; always-WARNING, never re-arming and swapping memory/storage each turn one red.
