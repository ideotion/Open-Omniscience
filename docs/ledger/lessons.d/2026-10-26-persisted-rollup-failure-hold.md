## 2026-10-26 — a hold that two code paths need must be written for both, and a "persisted skips it" early return is a missing hold (rollup, 0.5.1 item 28)

**Found by probing the item before building it.** The item said a persistent out-of-memory could make one request start the rollup build twice. The in-memory path did not: with a persistent `OutOfMemoryException` at the aggregate and two `windowed_counts` calls back to back (what `trending` makes: the recent window, then the prior one) with the kick made synchronous so the first build ended inside the request, the probe showed one build, one attempt and a kept `duckdb-limit` hold that declined the second kick. The persisted (D1) path had two early returns, `if _persisted_serve_active(): return` in `_record_failure` and `return None` in `_stopped_build_verdict`, written when the persisted refresh was incremental and cheap; a failure of it kept nothing, so each kick with no rollup built ran another `refresh_keyword_daily`: two attempts for one trending request and one more per poll. The persisted mechanism is read from code; the tests stub `_refresh_persisted_build`.

**Rules.**
1. An early return on "the other store" in a hold's two ends (the record and the verdict) is a missing hold for that store, whatever the original reason; when a path can fail, it needs the hold the sibling path has. The tell is a probe that counts attempts per request, not a read of either path alone.
2. A hold is about the store whose build made it. The record carries `store: persisted`; the verdict ignores a hold of the other store both ways, so an in-memory stop never holds the persisted refresh and a persisted failure never holds an in-memory build (a switch at runtime, when the passphrase arrives, cannot inherit the other path's hold).
3. The persisted store is not touched by a failure hold: the record is this process's only (`_keep_stopped(..., write=False)`), so a restart tries once more, as for the in-memory build (R172). The release conditions are the existing ones.
4. A test for "one request makes one attempt" must run the kick in the calling thread, so the first build has ended before the second call: with a real background thread the second call finds the lock taken and a missing hold hides.

**Limits, stated.** RC2's persistent-OOM run (`rc-diagnostics/r169-remeasure/persisted-oom.md`) exercised the in-memory path for real and the persisted path only as a stub, and the persisted store is dormant in shipped code (blank httpfs pins: an encrypted corpus is served from the in-memory build with no spill), so no field run of this path exists; the fix stands on the code reading and the stubbed tests, and holds a path that is dormant today. The persisted refresh runs under the module lock and so already serialises concurrent kicks: what the hold removes is the repeat after the lock is free.
