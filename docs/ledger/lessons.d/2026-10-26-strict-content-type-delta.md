## 2026-10-26 — a dependency's security default was cited as the whole fix, and the wheels showed it changes one row of five, at a floor no resolver could reach

**Found (audit 0.5.0 item 35, options 1+2).** The proposal said FastAPI's `strict_content_type` (on by default since 0.132.0) is what makes `text/plain`, form-urlencoded and untyped bodies answer 422 on a JSON route, and that `fastapi>=0.110` therefore left older installs without the check. Running the same requests against the unpacked wheels (0.131.0, 0.132.0, 0.133.0, 0.138.0 = the lock, 0.162.0 = newest) showed 0.131.0 already answers 422 to `text/plain`, form-urlencoded and multipart (a body not typed as JSON is not parsed as JSON, so the model fails; the 0.110.0 wheel reads the same), and differs on exactly one row: a body with NO Content-Type is parsed as JSON and reaches the handler. So the floor closes the untyped case, not the ones the proposal listed, and the test that pins it fails below the floor on that row alone. Three more things only the review found: the floor first written, 0.132.0, requires `starlette<1.0.0` while this app floors `starlette>=1.5.0`, so no resolver can install the pair (`pip install --dry-run fastapi==0.132.0 "starlette>=1.5.0"` is ResolutionImpossible; 0.133.0 resolves); the new SECURITY.md paragraph put the layers in the wrong order (the Origin check is the outer middleware and runs before the Host guard: a bad Host with a foreign Origin answers 403, not 421); and it said the layer covers all but six modules, when 148 of the 317 state-changing operations take no body and 11 an optional one (a `text/plain` body reaches those handlers).

**Rule.** (1) When a security property is credited to a dependency's default, run the pinning test against the release just below and the release at the floor, from their unpacked wheels (`pip download --no-deps`, unzip, put it first on `PYTHONPATH`); the delta is what the floor buys, and it is the only honest sentence for the registry entry and the docs. (2) A new dependency floor is tested as a PAIR with the repo's other floors, run through the resolver (`pip install --dry-run`) and by the tests on both floor wheels together, not on whatever companion is installed: a floor the resolver cannot reach is a floor that exists only in the file. (3) A pin test with several rows says which row fails below the floor, and asserts the precondition of that row (here, that the test client sent no Content-Type), or it passes with the protection off. (4) Describe the coverage of a layer from the schema (the OpenAPI operations with and without a body), not from the list of modules the author remembered. (5) Write the floor in the three places the registry coupling test ties (pyproject, the registry, the lock), in one commit.

**Limits.** Only one JSON route was driven; a cross-site request without a Content-Type was not driven from a real browser here; no CI job runs the tests on the floor pair (hand run on the wheels). The counts are a snapshot of 2026-10-26.
