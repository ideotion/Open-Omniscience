## 2026-10-26 — a dependency's security default was cited as the whole fix, and the wheels showed it changes one row of four

**Found (audit 0.5.0 item 35, options 1+2).** The proposal said FastAPI's `strict_content_type` (on by default since 0.132.0) is what makes `text/plain`, form-urlencoded and untyped bodies answer 422 on a JSON route, and that `fastapi>=0.110` therefore left older installs without the check. Running the same four requests against the unpacked wheels (0.131.0, 0.132.0, 0.138.0 = the lock, 0.162.0 = newest) showed 0.131.0 already answers 422 to `text/plain` and form-urlencoded (a body not typed as JSON is not parsed as JSON, so the model fails), and differs on exactly one row: a body with NO Content-Type is parsed as JSON and reaches the handler. So the floor closes the untyped case, not the three the proposal listed, and the test that pins it fails below the floor on that row alone.

**Rule.** (1) When a security property is credited to a dependency's default, run the pinning test against the release just below and the release at the floor, from their unpacked wheels (`pip download --no-deps`, unzip, put it first on `PYTHONPATH`); the delta is what the floor buys, and it is the only honest sentence for the registry entry and the docs. (2) A pin test with several rows says which row fails below the floor in its comment, or a reader assumes all of them do. (3) Write the floor in the three places the registry coupling test ties (pyproject, the registry, the lock), in one commit.

**Limits.** Only one JSON route was exercised; the six API modules that read a raw body, form or upload are outside the layer and rest on the Origin check alone. A cross-site request that sets no Content-Type is a browser-dependent case that was not driven from a real browser here.
