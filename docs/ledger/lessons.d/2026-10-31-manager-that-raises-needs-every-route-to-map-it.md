## 2026-10-31 — a manager that starts raising an error it used to swallow needs every route that calls it to map that error, and to log it

**What was found (R393 class, the WAL lane's 409 bundle; PR #1677).** Making a manager honest about a failed `Thread.start()` (it used to leave a `running` row and return, and now it undoes its state and raises) moves the failure from a row nobody reads to the HTTP caller. Every route that calls the manager and maps only the errors it knew (`ValueError`, or its own refusal class) turns the new `RuntimeError` into an unhandled 500. The two changes before this one each said so as a stated limit, and the sweep of the routes found eight call sites in this lane's files (three in `llm.py`, three branches of `jobs.py`, two routes in `search_omni.py`), none of which mapped it. The independent read of the fix then found two more, in the same two `llm.py` routes: the vLLM download is a `BackgroundJob`, not one of the four managers the sweep started from, and its `start` re-raises the same refusal (and raises `RuntimeError` for a job already in flight). One of them had saved the model as the operator's preference BEFORE the start that then failed. A last pass with the scan below widened found the one that matters most to an operator: the Start button's own route, `POST /api/scheduler/start`.

**The rule.** When a change makes a manager raise where it used to return, grep the callers in `src/api` in the same change or the next one, and read each `except` ladder in order. Five traps. (1) A refusal class that subclasses the broad error (`SearchReindexRefused(RuntimeError)`) must be caught BEFORE the broad clause, or every refusal reads as the new failure, and a test that drives a refusal through each route is the only thing that notices a swapped order. (2) A route family that answers with CODES (the search re-index never puts an exception's text in a response) takes a code for the new failure too, defined next to the others and distinct from them, and a test that the codes are distinct, because a test that compares to the constant passes when two constants share a value. (3) **Sweep by the call shape, not by the classes you already know, and filter nothing by name.** The first sweep listed the managers the earlier changes had named and missed a sibling class with the same behaviour. A scan of every `start`/`resume`/`enqueue` call in `src/api` and `src/api/diagnostics` that asks, for each, which `try` encloses it and what that handler does (`wal-lane/scan-start-callers-2026-10-31.py`) found eighteen unmapped sites at once and, after the fix, seven (three are another lane's, two are start-up threads and two are helper threads joined in the same call; none is a route this lane owns). Its FIRST form skipped any receiver whose name looked like a scheduler or a timer, to keep the output short, and the one route it skipped was the Start button: a filter written to remove noise removes the thing it was not looking for. It also separates a handler that maps (raises) from one that logs and returns and one that does neither, because a handler that names `Exception` is not thereby a handler that says anything; twenty-five call sites in other lanes' files answer a failed start with the job's status or "skipped: already running" and no log line. **The same mistake came back in the scan's own premise:** the first form of the script globbed the top level of `src/api` only, and the claim "there is no subpackage" was checked with a `find -not -path 'src/api/*.py'` that excludes the subpackage it looks for (`*` matches `/` in `find -path`); the independent read found `src/api/diagnostics/` (27 modules, 13 of the silent sites) by running the script recursively. A negative ("there is none") is checked with the tool that would find one, run the way the claim reads, never with a pattern that shares the blind spot of the thing being checked. And a side effect placed BEFORE the call that can fail (a preference saved, a row written) belongs after it. (4) **Mapping the error to a status removes the log line the 500 handler wrote.** The unhandled error logged its traceback; the answered 409 logs nothing unless the clause does, and the managers' own `except` blocks record the failure in the job row, not in the log. The diagnostics panel tells the operator "the log has the details". Each new clause logs at WARNING through `log_failure`, and a test asserts it, AT THE LEVEL, for every clause, because a log line is the first thing a refactor drops without anything going red. A route whose contract must stay a 200 with a status (the vLLM engine install, which the front end reads) logs too, and only when the status it returns is the failure and not the other thing the same exception means (a run already in flight). (5) **A route's exception is not always a status.** The route test uses a client that does not re-raise server errors, so a route that lets the error through is seen as the 500 it answers instead of an exception inside the test; an interrupt (a `BaseException`) is the one thing no such clause may catch, and is driven through every route by calling the handler directly, since a client would not show it; and an error that is not the start's refusal (`TypeError`) is still the unhandled one, so a clause widened to `Exception` is caught too.

**Where it is pinned.** `tests/test_failed_thread_start_routes_answer_409.py` (27 tests, 16 red on the unchanged routes and 11 that pass on both; 65 mutants killed). The routes left to other lanes, the twelve silent callers and the limits are in the shipped-log entry for 2026-10-31. One test-harness lesson from the mutant run: a mutation harness that restores a file in a `finally` does not survive being killed (a worker restart), and the tree it leaves is mutated; the baseline run of the next invocation is what caught it, and a snapshot compared after every run is what makes it certain.
