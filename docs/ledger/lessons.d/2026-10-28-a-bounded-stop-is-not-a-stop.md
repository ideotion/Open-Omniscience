## 2026-10-28 — a bounded stop is not a stop: a caller that joins a thread for N seconds and goes on has not learned that it stopped, so a claim built on "paused" needs a look at the thread, or no claim

**What was found (R360, the WAL lane's read of the restore).** `exclusive_window()` stops the collection loop with `BackgroundScheduler.stop(timeout=10)`, a bounded join, and `hold_exclusive()` blocks the NEXT `run_now`. Neither tells the caller that the work stopped. A pass has no stop check inside it, only between passes, so a pass deep in a write outlives the join (`resume_after_exclusive_operation` records one that took 39 minutes to wind down on a write-bound machine), and a pass started by Run now before the window opened is not touched at all (`oo-scrape-now` thread, `_active` True, loop not running). The restore read the window's return as "collection is paused", copied the corpus, merged into the copy and swapped the copy in. Whatever the lingering pass committed to the live file after the copy was taken was discarded by the swap, and the import dialog told the person collection was paused for the whole import. The pause was a courtesy that nobody had confirmed.

**What it cost.** Not measured as rows lost: no field report names one and no figure puts a size on it. The defect is the unconfirmed claim, not a counted loss.

**The rule.** When a stop is bounded, the code that goes on after it either looks at the thing it asked to stop (and waits, bounded, for it to be gone) or it makes no claim that it stopped. A look reports three answers, not two: confirmed, still there, and could not be read; "could not be read" is never reported as "idle". And a claim shown to the person (a dialog line) follows the look: when the look found the pass still running, the line says it could not confirm a pause instead of saying there was one.

**What shipped (this change).** `src/backup/collector_exit.py`: `wait_for_collector_exit` reads the scheduler (loop thread alive, or the busy flag a pass sets) and waits, bounded at 600 s (the resume side's 19 retries of 30 s rounded up, itself chosen to exceed the 438 s worst single blocked write that project measured), before the working copy is taken, so a pass that finishes inside the wait lands in the copy. A pass still running at the bound is named and not hidden: the restore goes on (the pause is a courtesy and an import is the point), the report and the run log carry `collector_exit` (`confirmed` True / False / None, `waited_s`, `bound_s`, `still`), and the import dialog says it could not confirm a pause. A Stop ends the wait at the next look and the restore's own abort point is re-checked straight after. The exception text of an unreadable scheduler is not stored, only its class. Failing test first: 5 of the 18 tests in `tests/test_restore_collector_exit.py` fail on the previous `merge.py`.

**Stated limits.** It looks only at the collector. The housekeeping lane, the Wikipedia drain, registered background jobs, AI sweeps, boot upkeep and the API write routes are not stopped by the window and are not looked for by this wait; what they commit between the copy and the swap is still discarded (the dialog says so, and the options for closing it are a proposal for the user: `wal-lane/proposal-uncovered-writers-2026-10-28.md` in the project's shared folder). The wait runs once, before the first copy; a pass cannot start afterwards because the window blocks `run_now` and the loop is stopped. Not measured: how long a real pass takes to wind down on a field machine beyond the one 39-minute record.
