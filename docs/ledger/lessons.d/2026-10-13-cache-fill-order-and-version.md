## 2026-10-13 — a cache that is filled by readers and writers needs a per-key version, and the writer's fill belongs inside the lock that orders its commit

**(1) An epoch answers "was the whole cache invalidated since I began", not "did THIS key change".** `kv_store` filled its cache from readers (after a file read) and writers (after a commit). A global epoch moved by `kv_invalidate` closed the restore's swap, but a reader that read the file BEFORE a writer's commit and filled AFTER the writer's own fill stored the older value for the life of the process (the file said 2, the process served 1): no invalidation had happened, so the epoch had not moved. **Every reader notes a per-key write version before it reads and fills only if the version is unchanged; every write bumps it.** The counters are never reset (a reset could meet a number a reader noted).

**(2) Two writers' fills have to follow their commits.** Saves of one key commit in the order they hold the single-writer gate, but the fill sat after the gate was released, so the earlier save could fill last. The fill now sits inside the gate (the leaf lock it takes is never held while anything waits for the gate, so it adds no order). With the gate off (`OO_WRITE_GATE=0`) SQLite orders the commits and nothing orders the fills; that is stated, not fixed. **A deterministic source pin (the fill is inside the gate's `with`) beside a probabilistic stress: the stress alone can pass on the broken code.**

**(3) A guard list that is process-global must name WHAT broke, not only WHERE it was found.** A strict-mode violation is recorded in a list the suite empties per test, so the test that finds an entry is not always the one that made it (a thread another test left running). Each entry now names the calling code (file:line in function, skipping this module and `contextlib`, because the slot is a generator context manager) and the thread.
