## 2026-10-16 — a lock for a native abort nobody can explain: cover the whole call tree, price it before defending it, pin its coverage with a walk, and write the evidence down as inferred

**What was found.** The collector aborted (SIGABRT, no Python traceback) inside `lxml.html.document_fromstring`, called from `trafilatura.load_html` <- `bare_extraction` <- `extract_article`, in a pass with about 50 workers, one boot in seven (2026-10-14). A reading of lxml 5.2 to 6.1.3, libxml2 2.12 to 2.15, trafilatura, htmldate and justext found no changelog or tracker entry for it. The one loose match, trafilatura issue #840 (concurrent extraction, fixed in 2.1.0), is a release OLDER than the one the trace points to: its line numbers (`utils.py:345`, `core.py:382`) are those of trafilatura 2.3.1, while `requirements.lock` pins 2.1.0, so the machine that aborted was not running the lock either.

**The rules.**
1. **When the cause is unknown, make the guarantee structural and make it cover the WHOLE call tree.** `src/ingest/extract.py:_LXML_LOCK` is a process-wide `RLock` around `extract_article` as a whole, not around the parse: the frame that aborts is where an earlier corruption surfaced, and a tree released after the lock is given up frees libxml2 memory concurrently again. On a return the result holds text only, so every tree dies with the call's last local, inside the lock. On a RAISE they do not: an exception carries its traceback and the traceback keeps every frame's locals (`bare_extraction`'s trees) alive until the caller drops it, which was after the lock, in a worker's `except` clause; the independent read found this and `_release_frames` now clears the frames of the traceback and of its chain before the lock is given up (`traceback.clear_frames` keeps the traceback's lines; a `NameError`'s "Did you mean" hint, computed from the cleared frame's locals, is not offered). Frames are not the only holders: since Python 3.10 an `AttributeError` keeps the object whose lookup failed in `obj`, and on an lxml element that is the element and so its document, so `obj` is dropped too (the message stays; Python's "Did you mean" hint, computed from that object, is no longer computed from the real one: not offered for most names, and for a name starting with `_` computed from `None`'s attributes). A test that models the trees as frame locals cannot see this; the test holds a sentinel as the failing object. An exception's `args` or `StopIteration.value` could hold one as well and are not walked. A test releases a sentinel tree on each path and asks whether the lock was held at that moment.
2. **Say that the evidence is inferred, and name the heavier fix and the event that would call for it.** The versions are inferred, not read off the machine (trafilatura's from the trace's line numbers, lxml's and libxml2's from what that release requires and ships); absence of a tracker report is weaker than a report; nobody reproduced the abort, so a lock that "works" is learned only by not seeing it again. The OPEN_QUEUE item records all three, what a recurrence looks like in a build that carries the lock (a trace that reads `... <- bare_extraction <- _extract_locked <- extract_article <- store_fetched`) and the next step then (extraction in a subprocess: the only way to survive a native abort).
3. **Price the lock before defending it, and put the figures in the PR.** Measured on 4 CPUs: extraction alone, 24 pages of 22,000 characters, 1 / 4 / 16 / 50 threads, 213.6 / 57.1 / 52.7 / 46.1 articles per second unlocked against 231.6 / 218.1 / 221.0 / 209.4 locked; the whole pass (96 articles) at 1 / 8 / 50 workers, 1.5 s fetch delay, 0.51 / 2.40 / 3.77 against 0.51 / 2.45 / 3.92. The belief that a lock "serialises the work and so costs throughput" was wrong here: unlocked threads are 3.8 to 4.5 times SLOWER on trafilatura 2.2.0 and 2.7 to 3.3 times on 2.3.1. One thread is the noise floor (3.85 against 4.21 articles per second at one worker with nothing to contend), so a difference under about 10% is not a claim (a small sample of the independent read showed -13% at one thread: read ratios, not percentages, from short runs). The explanation was first written down as a guess (the GIL and the allocator) and isolated the next day: the extra time is CPU, it reproduces with a loop of `os.stat` calls and no lxml, it needs no shared parser or XPath object, and `MALLOC_ARENA_MAX=1` changes nothing, so it is the GIL hand-off of very many very short GIL-releasing calls (method and figures: `docs/ledger/lessons.d/2026-10-17-lock-occupancy-method.md`). The bench gained a `threads` mode (`collect_throughput_bench.py threads`) so the next person measures the same thing.
4. **A lock is only as good as its coverage, and coverage is a property of the tree, so walk the tree.** `tests/test_extract_lock.py` walks `src/` for every way libxml2 can enter the process: an import of lxml, trafilatura, htmldate, justext or readability, a dynamic import of one, `pandas.read_html` (lxml by default), and `BeautifulSoup(...)` without an explicit `html.parser` (bs4 picks the best parser INSTALLED, which is lxml when it is there). Inside `extract.py` only the two locked functions may call trafilatura and only under `with _LXML_LOCK:`; `from trafilatura import bare_extraction` and `import trafilatura as tf` are refused because they hide the calls from the walk. The walk is proved on fixture sources (it must see each way in, and accept what is allowed), and the module was mutated seven ways (no lock, a plain `Lock` that deadlocks a nested call, a lock leaked on a raise, a blank page taken inside the lock, a tree kept past the call, the lock released before the work, the fallback outside the lock): nine in the final form, all killed, and none of them hangs the run: the first form of the file left a daemon thread deadlocked INSIDE a plain `Lock` and the next test on the main thread waited for ever (no pytest-timeout, and the CI job has no limit short of GitHub's), so an autouse fixture now asks for the lock with a one-second timeout and fails the next test by name, and the RLock check runs before the nesting call. A test that reads a thread's state AFTER releasing what it waits for can pass for the wrong reason (the blank-page test did, against its own mutant). Walks also read the NAME, not only the call: `_BARE = trafilatura.bare_extraction`, `getattr(trafilatura, ...)` and `partial(trafilatura.extract)` reach the library without a `trafilatura.x(...)` call, and a `Document()` built anywhere makes lxml trees (the very code of issue #840).
5. **Check that a proposed version bound would have excluded the version in the trace, and record only versions a test run exercised.** `trafilatura>=2.1.0` is justified by #840 but would not have changed the machine that aborted (it ran a newer release), so it is built, with its registry entry, and the PR does not offer it as the fix. The registry says `verified` 2.3.1 (run), and that the floor 2.1.0 was run by hand only: the `lockfile-install` job imports the app and runs no test, and the `test` job resolves whatever release is newest that day.

6. **The cost of a lock is its WORST hold, not its mean, and a benchmark of uniform pages cannot show it.** The figures above (pages of one size, every hold a few milliseconds) say the lock is free; the independent read fed it markup of many small `div`/`span`/`a` blocks and found a 1 MB page holding the lock for 6 s, 5 MB for 35 s and 10 MB (the fetcher's ceiling) for 85 s, while a small page waiting on another thread took 6.18 s against 0.76 s. Before defending a lock with a throughput figure, run its worst realistic input and say what waits behind it; a timeout cannot cancel a thread, so the bound for that case is a process, which is why the subprocess is the recorded next step.

**A lock with no timeout needs its wait and hold on the record, in a place the diagnostics keeps, or its worst case reads as a stalled program.** The coordinator asked for it once the tail was measured: each monitored collect pass now carries the count of holds, the longest and total wait and hold, and the size of the page behind the longest hold, in its `collect_perf.jsonl` summary line AND in its run report (`scheduler.recent_runs`, 30 runs). The second copy exists because the independent read found that the slim ring inside the Diagnostics archive keeps 20 lines (`_DEBUG_BUNDLE_SLIM_PERF_TICKS`, about 30 s of a running pass): a figure written only to the summary line would have been gone from nearly every bundle, and the first draft's text said 200 lines because that is the standalone route's figure. Before promising that a record 'reaches the diagnostics', follow it to the member the bundle actually builds and read its retention. Three choices are worth keeping. The clock is a function the test replaces (`lock_stats.now`), so the numbers are exact and the two-thread wait test needs no sleep (the fake reads the time BEFORE it announces the read, otherwise the test can move the clock between the two). The statistic is taken AFTER the lock is given up and is pinned so (`_is_owned()` in a spy), because a statistic taken inside would lengthen every hold by its own cost. And a figure and the thing it describes are written in ONE step under one lock: the first draft measured the longest hold's page in a second step after releasing the private lock, and a longer hold landing meanwhile, a reset, or a measurement that failed left the new hold paired with an earlier hold's page size (all three reproduced by running code between the two steps); the fix computes the size from the hold's own text before the lock and decides under it which hold is longest. A test for 'paired with the right one' needs the interleaving injected (a hook inside the measurement), not just distinct values: replacing the guard with `if True` passed all sixteen tests that had distinct values.

**What it does NOT cover, said so.** A native abort under the lock still kills the process; `gc.collect()` and `malloc_trim` run from the memory guard during a pass and are not kept out of it (48 extractions left zero unreachable objects, and so did a metadata fault and a body fault, so a collection had no tree to free); one page that takes long stalls every extraction in the process and nothing can time it out (rule 6); a dependency that parses with lxml on its own thread would not go through the lock, and one that reaches libxml2 without lxml is not seen by the import walk: feedparser asks for libxml2's SAX driver first (`PREFERRED_XML_PARSERS`) and uses it wherever the libxml2 Python bindings import (a system or distro Python; a pip venv has none), in every collector worker, outside the lock. Closing that is a choice for the maintainers (set the preferred list to expat only, which changes feed parsing on those installs), recorded in the OPEN_QUEUE entry and not built here.
