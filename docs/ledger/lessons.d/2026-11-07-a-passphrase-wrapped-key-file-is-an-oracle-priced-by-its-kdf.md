## 2026-11-07 — a key file wrapped under a passphrase is an oracle for that passphrase, priced by its key derivation: measure it before choosing the format (evidence key wrap, R442, PR #1749)

**What was found.** The first version of the evidence-key wrap did what the audit and the custody signer showed: `private_bytes(..., BestAvailableEncryption(passphrase))`, a PKCS8 PEM. An independent read of the commit decoded the file it wrote: PBES2 with PBKDF2-HMAC-SHA256 at **2048 rounds**, AES-256-CBC. A wrong-password try on it measured 0.30 ms (re-measured here under cryptography 50.0.2: 0.303 ms, `openssl asn1parse` shows the `0800`). The same passphrase protects the SQLCipher database at about 173 ms a guess (PBKDF2-SHA512, 256,000 rounds, per CLAUDE.md), so the change meant to harden a copied data folder would have made a new file in it the cheapest test of a guess at the database passphrase, about 600 times cheaper than the database. It also refuses a passphrase over 1023 bytes, which would have failed every export and backup for such a passphrase. No test priced the derivation and the audit's proposal ("wrap exactly as signing.py does") named the call, not the cost.

**The rule.** When a file is wrapped under a passphrase that also protects something expensive to attack, the wrap's derivation must cost at least what the other costs, in memory-hardness if not in time, or the wrap becomes the way in. Look at the parameters the library writes, not at its name ("BestAvailableEncryption" is a default of the library, not a cost): decode one file and time a wrong guess. Use the repository's own memory-hard wrap (`src/custody/signing._wrap`: scrypt N = 2^15, then AES-256-GCM, no length limit) for new at-rest key files, and pin its parameter with a test that spies on the derivation (`tests/test_evidence_key_wrap.py::test_the_wrap_is_priced_by_scrypt_not_by_pkcs8s_2048_rounds`) so a later change to a PKCS8 form turns a test red.

**What was and was not established.** Measured: the 2048 rounds and 0.30 ms per wrong guess; the replacement is the custody ML-DSA key's existing wrap; a 3000-byte passphrase wraps and loads; a PKCS8 mutant turns two tests red. A wrong guess on the scrypt wrap measured 88 ms here and 80 ms in the third read, about half of SQLCipher's 173 ms in time (and 32 MiB of memory a guess, which 2048 rounds of PBKDF2 do not need). Not measured: scrypt N = 2^15 against SQLCipher's 173 ms in attacker-hours on a GPU: it is memory-hard where PBKDF2-SHA512 is not, which is why it was taken, and the figure is an argument, not a measurement.

**Stated limits.** The custody Ed25519 key (`src/custody/signing.py`, `_load_or_create_ed25519`) is still written with `BestAvailableEncryption`: on an install with a passphrase held, `keys/custody_ed25519.pem` is today the cheap oracle this lesson describes, 0.3 ms a guess, and it is copied into every backup's `keys/`. Not changed here (another file's owner); the fix is the same wrap, keeping the legacy-plaintext tolerance its loader already has and adding a re-wrap in place. Until then a short database passphrase is exposed through that one file.
