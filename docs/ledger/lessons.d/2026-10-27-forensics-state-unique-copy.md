## 2026-10-27 — A swapped-in file written through ONE fixed copy name is shared by every server on the folder; look for the house helper before writing the repair, and test the second writer in another thread (0.5.1 item 33, audit A-031)

**What was found.** `forensics._write_state` wrote `session_state.json` (the clean-shutdown sentinel the NEXT boot reads to say how this session ended) through `session_state.json.tmp` and `os.replace`. Several servers can share a data folder (R176), and they all wrote that one copy: the second writer truncated the first's open file and the first swap then moved that file, mid-write, into place (the first writer's remaining half landed INSIDE the live sentinel, a mixture of two states), or the second writer's swap found nothing to move (its state was lost, with a warning). Measured on the old writer with two threads standing in for two servers: one writer half-way through its copy, another writing and swapping whole, then the first finishing, left a sentinel that parses and is neither state (the first writer's `pid` with the second writer's last key), and the finishing writer's own swap failed with `FileNotFoundError` and the warning; and a second writer running between the first's write and swap left the first's state lost with the "could not persist" warning. The writer now goes through `src.safety.file_lock.atomic_replace(..., fsync=False)`, the call `expedition.py` and `app_settings.py` already make: the copy is `session_state.json.tmp.<pid>.<thread>`, removed if the swap fails, and a dead process's copies are swept; the last swap wins, as it did.

**Rules.**
1. **A file swapped in with `os.replace` takes a copy name no other writer can share: the process and the thread.** A fixed `.tmp` is safe for one writer and wrong for two, and the second writer need not be another program (a second server on the folder, a watchdog thread beside the main thread). The sentinel is the file whose torn write changes the next boot's verdict, which is why it was worth finding before it fired.
2. **Grep for the house helper before writing the repair.** The first version of this fix hand-rolled the unique copy name, a liveness sweep with a log-once for a missing `psutil`, and a sync before the swap (13 tests, 9 mutants). The independent read then found defects in the hand-rolled parts: a stray file name that made the sweep raise where the old writer never did (F2), a filesystem without `fsync` that would lose every sentinel write (F3), and a sync that could block the data-drive-disconnected shutdown path (F11). `file_lock.atomic_replace` already handles those three (a sweep that never raises, a tolerant sync, `fsync=False`), with its own tests (`tests/test_file_lock.py`) and many callers (27 call sites in `src/`); the fix is now one call and the module's two unlocked write sites are gone from the allowlist in `tests/test_shared_file_writes.py`. The test for the call is the behaviour at the module's edge, not the helper's internals.
3. **Test it with the second writer in ANOTHER THREAD, never a nested call from the first.** The copy's name carries the thread, so a nested call reuses the first writer's name and collides with itself, which no real second writer does: the test passes for the wrong reason or fails for a reason the code does not have. Hold one writer half-way with a gated handle (`Path.open` patched so only that thread's write stops after half its text and waits), run the other whole, release the first: this reads the same on the old code (a mixture, a lost swap) and the new (a whole state, last swap wins), because it patches the OPEN, not the call the writer happens to use. The kill tests run the write in a child process that dies by `os._exit(9)` at the named point; an exception would run the cleanup a real kill never runs.
4. **Pin the choice the helper's default would otherwise make for you.** The sentinel is rewritten at every lifecycle step and a stale one after a power cut reads as an unclean end, so a sync on the shutdown path could block it on a wedged device for no gain the old writer had. `fsync=False` keeps the old behaviour and `test_the_sentinel_is_not_synced` pins it (a mutant passing `fsync=True` dies there).
5. **Not changed, stated.** This is the R175 shape, not the R176 conversion: the read-modify-write of the sentinel (`_read_state` then `_write_state`, in five lifecycle recorders) is still not under `file_lock`, so two servers can lose one of two updates to different fields. A server of an older version on the same folder still swaps the old fixed `session_state.json.tmp`, which nothing here removes. The helper's sweep (`sweep_dead_temps`) judges a copy's owner by `psutil.pid_exists` on a bare pid, and an unlocked caller like this one runs it with no lock held: a server in another pid namespace that shares the folder (containers on one mounted data folder, a folder on a NAS) can look dead and have its in-flight copy removed, which costs that one write (a warning; the sentinel keeps the previous state, or the other server's). The independent read REPRODUCED this with `unshare --pid` on the first version's sweep, which used the same rule; the helper's sweep has the same rule, so the window exists here too (shorter, since nothing is synced), but I did not run it against the helper. The same bare-pid rule leaves one more case: a copy stranded under this process's OWN pid (a container's server that always gets the same pid, killed at the swap) is skipped as its own and never swept, a few hundred bytes of clutter (reproduced by the read on the first version; the helper skips its own pid too, inferred). Both are house-wide for every unlocked `atomic_replace` caller and not changed here: the repair belongs in `file_lock` (a recent-mtime guard, or `process_owner`'s `unknown` verdict for a pid that cannot be judged, R183), or in taking `file_lock` around this write, which is the R176 conversion and a change to the shutdown path.
