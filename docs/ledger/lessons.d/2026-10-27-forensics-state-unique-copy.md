## 2026-10-27 — A swapped-in file written through ONE fixed copy name is shared by every server on the folder, and the test that proves the repair puts the second writer in another thread (0.5.1 item 33, audit A-031)

**What was found.** `forensics._write_state` wrote `session_state.json` (the clean-shutdown sentinel the NEXT boot reads to say how this session ended) through `session_state.json.tmp` and `os.replace`. Several servers can share a data folder (R176), and they all wrote that one copy: the second writer truncated the first's open file and the first swap then moved that file, mid-write, into place (the first writer's remaining half landed INSIDE the live sentinel, a mixture of two states), or the second writer's swap found nothing to move (its state was lost, with a warning). Measured on the old writer with two threads standing in for two servers: one writer half-way through its copy, another writing and swapping whole, then the first finishing, left a sentinel that parses and is neither state (the first writer's `pid` with the second writer's last key), and the finishing writer's own swap failed with `FileNotFoundError` and the warning; and a second writer running between the first's write and swap left the first's state lost with the "could not persist" warning. The copy is now `session_state.json.<pid>.<thread>.part`, synced before the swap and removed if the swap fails (the shape of `collect_perf._trim_jsonl`, R175); the last swap wins, as it did; a copy a killed process left is removed by the next write once that pid is gone.

**Rules.**
1. **A file swapped in with `os.replace` takes a copy name no other writer can share: the process and the thread.** A fixed `.tmp` is safe for one writer and wrong for two, and the second writer need not be another program (a second server on the folder, a watchdog thread beside the main thread). The sentinel is the file whose torn write changes the next boot's verdict, which is why it was worth finding before it fired.
2. **Test it with the second writer in ANOTHER THREAD, never a nested call from the first.** The copy's name carries the thread, so a nested call reuses the first writer's name and collides with itself, which no real second writer does: the test passes for the wrong reason or fails for a reason the code does not have. Hold one writer half-way with a gated handle (`Path.open` patched so only that thread's write stops after half its text and waits), run the other whole, release the first: this reads the same on the old code (a mixture, a lost swap) and the new (a whole state, last swap wins), because it patches the OPEN, not the call the writer happens to use. The kill tests run the write in a child process that dies by `os._exit(9)` at the named point; an exception would run the cleanup a real kill never runs.
3. **Sweep what a killed writer leaves, and do the work only when there is something to judge.** A unique name that a kill strands is an orphan no later write overwrites. The sweep lists the folder, keeps another live process's copy, and imports `psutil` only when a copy of ANOTHER process is there, so a start with nothing left over pays one directory listing; with no way to tell live from dead nothing is removed ("unknown is not dead"), the log says so ONCE per process (the sentinel is written at every lifecycle step) and the write goes on; `psutil` is a core dependency, so only a broken install takes that path.
4. **Not changed, stated.** This is the R175 shape, not the R176 conversion: the read-modify-write of the sentinel (`_read_state` then `_write_state`) is still not under `file_lock`, so two servers can lose one of two updates to different fields, and the allowance in `tests/test_shared_file_writes.py` drops from two sites to one (the swap) and stays with the lane that converts it. A server of an older version on the same folder still swaps the old fixed `session_state.json.tmp`; nothing here removes that name. The copy is synced before the swap, which a write in the shutdown path now pays (one small file); it was not measured on a loaded disk.
