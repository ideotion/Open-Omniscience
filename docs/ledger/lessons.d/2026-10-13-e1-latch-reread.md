## 2026-10-13 — a pause that comes from one failed read is provisional: latch first, claim the re-read in the SAME lock block, release only by the machinery that decides a latch, and let a table that was released and fails again STAY

E1 latched a file on the first `SQLITE_CORRUPT` it saw, from one read on one connection, and only the operator's start released it. A code 11 that a fresh read does not repeat (memory pressure, a copy made while the file changed; NOT measured here) therefore paused an unattended machine until someone came back. The coordinator's ruling (2026-10-13): **pause at once, read the table again on a fresh connection, and end the pause by itself when it reads clean; a table that reads clean and then fails again in the same process latches and stays.** What the build taught, in the order it was found:

**(1) Read-first collapses into latch-after-two-seconds.** `DamageRegistry.note` runs inside the failing statement's own thread and already bounds its own wait (`RECORD_WAIT_S`), and the table a statement failed on can be gigabytes: reading it before the pause either blocks that thread for minutes or lets the writers run into a possibly damaged file while the read is made. So the latch is set first and the read is the provisional pause's way out. A provisional pause is not a damaged verdict (R100): nothing is recorded as damaged until the re-read fails, and a clean release is recorded as one (`reread: clean`, the incident answered).

**(2) The claim belongs in the latch's own lock block, again.** E2's deep delta read (S2) found that `check_tables` stored in a second block let a start land between the two and read a latched file with no set as an E1 latch. The re-read's claim has the same shape: made in `_apply_incident` with the latch, so an operator's start during the window finds a claim and does not release a latch whose answer is being read (`retry` skips a latch that has a claim and no table set yet). The thread is started AFTER the incident's record is written, so the incident exists when a clean answer supersedes it; for the slow drive where the wait times out first, `_record_new` writes the record born answered when the file's `reread` already says `clean`.

**(3) Do not build a second releaser.** The machinery that re-reads tables on fresh connections and decides a latch from the answers already existed for the start-up check (`check_table`, `recheck_finished`: every table clean releases, a failed read that landed meanwhile holds, a stale claim is dropped). The re-read only had to name its tables (`reread_tables`, under the claim) and say it is automatic (`auto`), which changes four things inside `recheck_finished` and nothing else: the result is recorded (`clean`, `clean-held`, `damaged`, `unread`), a clean release remembers its tables (`auto_released`), a table that could not be read drops the table set so the start still releases the latch the E1 way (a set would hold the start for ever on a read that never comes back), and the incidents it answers are the failed read's and the ones after it, not an earlier error an operator's start released unread.

**(4) Names by WORDS, not by a parse.** Which tables a failed statement touched is read as every identifier it writes (bare and quoted forms, lower-cased, values already out), intersected with the tables the file has. A parser for FROM / JOIN / INTO / UPDATE misses a comma join, an alias list and a subquery; a missed table is a table the pause was released without reading. Over-including costs a read. What no reading of the text can find is a table reached through a view or a trigger: that is what the second-failure rule is for, and it is stated in the code and the queue rather than left to be found.

**(5) A new background actor needs an explicit default in every test that is not about it.** The first run of the existing damage suite failed six tests, all of one shape: a test injects a corruption error into a HEALTHY file, asserts the latch it asked for, and a thread now reads the file, finds it healthy and releases it. The fix is not a flag in each test: the re-read is a property of the registry (`rereads`), the process's own registry is built with it ON (a test pins that in a fresh interpreter), a registry a caller builds is OFF unless asked, and the suite's isolation fixture switches the global one off. `_reset_for_tests` leaves the attribute alone, because resetting it undid the fixture (found by the first rerun: two of the six failures came back).

**(6) What it deliberately does not see**, all in `docs/ledger/OPEN_QUEUE.md`: a search index that disagrees with its table reads clean once (the next failure stays), any failed read on another thread during the re-read holds the pause, `auto_released` dies with the process, and a re-read of a big table holds a read snapshot (nothing measured on the users' stores). The rule that follows: **a pause that ends by itself needs a way back for the cases its read cannot see: here, the second failure of the same table latches and stays, and the page says why and what a start does.**

**(7) What the independent read found, which no test of mine had (1 block, 6 medium).** (a) **A claim another actor can also answer must end when that actor's MEASUREMENT arrives.** The re-read of a statement's tables and the start-up check both set `check_tables` on a latch; a check's finding that landed while the re-read ran was overwritten by the re-read's own table list (or popped by its clean answer), so the operator's next start released a latch whose measured table was never read (R100). `_apply_incident` now ends an automatic claim when a check's tables arrive (`reread: not-made, why check-found`), and the late answers find no claim and are dropped. (b) **A baseline compared across a lazy merge must be moved by the merge.** The claim stored the live incident count; the earlier session's record was merged in afterwards, so a clean answer read as "a read failed meanwhile" on every file that had failed before, and the pause never ended by itself. The merge adds the earlier count to the claim's baseline. (c) **One page sentence cannot name one lane's action when the page shows every lane's notes.** "Starting collection again lifts the pause" is false for the Wikipedia file (a start does not release it), and "collection stays paused" is false for the lanes whose note says other sources go on; the two sentences now say "writing to that file" and send the reader to the note above for the action, and while the re-read runs the page shows ONLY the provisional sentence (the damage sentence beside it promised that a start tries again, the repair note that the file is damaged). (d) **A damaged table list is an answer.** A schema that two connections both read as damage was recorded as "no re-read was made"; it is now filed as a damaged `(schema)` the way the start's re-read files it, so a start reads every table. (e) **"Never blocks" means no file system call on the failing statement's thread**: the existence and size test moved onto the re-read's own thread (a stat patched to take five seconds held `note()` for ten). (f) **A restore forgets what the old file taught, latched or not**: `auto_released` of an unlatched file survived `retry(file_replaced=True)`, so the new file's first failed read was refused a re-read and the page said "again" about a file never read. (g) **A test about a LATE answer must join the thread that gives it**: the replaced-file test asserted while the re-read was still inside `check_table` and passed against a mutant whose stale branch wrote a clean answer. (h) The outcome now also stays on the incident it answers (`answered_by`), because the file's `reread` record is not carried by the next process's first write.

`tests/test_damage_reread.py` pins each claim on REAL files (a damaged copy confirms and keeps the latch; a healthy file with a driver-shaped error is paused at once, said as provisional, released by itself and recorded; the same table again stays with no second read; a statement naming nothing the file has, a switch, no file, a running check, an unreadable table list, a stop, a failure and a thread that will not start each keep the latch with their reason; a start during the re-read does not release; a replaced file drops the late answer; a closed connection handed to `note_raw_driver_error` still latches (OPEN_QUEUE (e)); the FTS shadow tables are read; the record carries no engine text) and every guard of the new code was killed by a mutant of it (33 mutants; three SURVIVED the first run and are what the last two tests are for: the late answer of a read that listed its tables after the file was replaced and latched again, which only a token-matched claim stops, and the refusal to make a claim against a running check, which `verify.reread` repeats so that the end state is the same and only the claim's own state tells them apart).
