## 2026-10-26 — a test that reads a clock is one of three different tests, and each has its own fix: name which before changing the number

**What was found.** Four red runs of main in one week (a write-gate breakdown bucket, a stray watchdog wake recorded as the loop's tick, the second pass of a continuous loop that never arrived, a debug bundle that budgeted a healthy member out) looked like four timing problems. A sweep of every test that sleeps, polls, joins or compares an elapsed time showed three problems, which share a symptom (red on a loaded runner, green locally) and nothing else:

1. **Count after a sleep.** The test lets a running thread work for a fixed time and then asserts a POSITIVE count or state (`calls >= 3`, "the second pass ran", "the sampler took more than 20 readings"). A lower count is not a defect, only a slower machine. Fix: wait for the thing asserted, observed, under a guard that costs a passing run nothing (`wait_until`, an Event the code under test sets, a spy that records the arrival); or drive the loop on a clock that moves only when it waits (`SteppedClock`) and read a sum instead of timing a duration.
2. **Elapsed time held to an UPPER bound.** "It came back in under a second." A pause, a stolen slice or a collection of a large process stretches the healthy time as the defect stretches the broken one, so the bound is a guess about the edge of healthy. Fix: assert an ORDER. Make the thing the call must not wait for report that it returned, and assert it had not when the call came back; or run the call on a thread with a long guard (`call_on_thread`, 20 s) and make what it must not wait for outlast the guard, so that waiting is the only way to be late. A scaling test (a ratio of two timings) is timed on the thread's own CPU clock (`CPU_CLOCK`), which a pause does not advance.
3. **A fixed wait for a thread to get somewhere.** `time.sleep(0.4)  # into the statement`, then a positive assumption. Fix: the thread says it is there (an Event, a SQL function that signals and holds, a `/proc` bit that shows the signal handler installed, the checkpoint lock observed through a probe), and the held party is released only when the test says so (its wait is at least three times the caller's guard, and the release sits in a `finally`, so a failing test leaves nothing parked).

**What is safe and was left alone.** An elapsed-time LOWER bound ("it waited the 0.25 s it was given"): a slow machine only makes it longer. A negative assertion after a head start ("still blocked after 0.3 s"): a late thread makes it weaker, never red. A bound that is not time at all (a column count, a byte ceiling, a CPU figure). A wall-clock upper bound at 25 times or more the healthy figure of a path that takes milliseconds. Do not rewrite these; the sweep read 59 more files and left them, each for one of those reasons.

**The two measured facts the scheduler tests needed.** A scheduler pass does not end where its function returns: `_do_run` goes on to a whole-process `gc.collect`, a WAL checkpoint through the write gate (bounded at 30 s), a custody read and, once the cadence says so, the off-peak maintenance (1.5 s on an empty database). Measured, the tail is 0.5 s on a fresh process and 1.6 s with eight million objects alive; the 57-minute full run of a pull request has a heap to match. `stop(timeout)` joins for a bounded time and answers True either way, so `is_running()` can still be True afterwards. A test of WHEN the loop starts a pass or answers a stop is not a test of that tail, so `quiet_pass_tail` takes it out; the tail has its own tests that call it directly.

**How to find the ones that are still there.** Two injectors, run on the tests a sweep touched, found exposures no reading did: (a) a SIGSTOP/SIGCONT of the whole process group at random (mild: about 60 % of the time frozen in 0.1 to 0.4 s stops; harsh: about 4 % duty in 0.02 to 0.1 s runs and 1 to 2 s stops), and (b) a plugin that makes `time.monotonic` jump forward by 8 s at its second to fifth call. The jump found a site no reading had: a call that passed `timeout=3.0` explicitly, so the new 20 s default of its helper never reached it. **The harsh freeze is partly an artifact:** each requested sleep stretches to a whole freeze cycle (a 0.02 s sleep that takes 1.5 s), so a test that is mostly sleeps goes red under it with a CPU use of 0.02 s and passes the mild freeze three times in a row. Judge a harsh red by asking whether the test is sleep-bound; treat a mild red as real. A CPU-burner pass (twelve busy loops and two fsync hammers on four cores) is the third check and is what a loaded runner is.

**A mutant has to restore the defect, not perturb its neighbourhood.** Two scaling tests survived their first mutant: the test text ended in a character the injected quadratic copy never reached (a trailing-closer loop does nothing on text that ends in `x`), and the resync line that was mutated sat in a function the measured shapes never used. They were killed by putting the retired implementation back (the old regex, the plain `re.sub`). A mutant that stays green is information about the mutant until it has been shown to change the code path the test measures.

**Five smaller rules that came out of the reads and the injectors.** (1) A thread that patches module names for a test patches them for every thread: the process's own watchdog woke inside a 50 ms simulation and was recorded as a tick of the loop. A recorder that pins itself to its own thread (`threading.get_ident()`) and answers the stranger with the no-op, plus a test in which a stranger calls on purpose at a fixed point, is the shape. (2) A PASSIVE checkpoint probe takes the checkpoint lock for a moment on every look, so a second checkpointer that is told "busy" at once must ask again until it is the one holding it. (3) A "mutant stays green" with two sites that each cover the other is not a gap in the test: remove both. (4) A claim that a check "has no room to fail" is a claim about a RATE, and the rate is what a loaded runner changes: the WAL starvation soak asserted that a 0.6 s checkpoint attempt always leaves the byte check no room, which holds for a writer at 12.5 MB/s and not for one starved of CPU to 0.4 to 0.7 MB/s, where the allowance no longer reaches what the writer could have written and the check CAN fail. The round now skips with the writer's rate and the attempt's length when the check was able to fail and did not, and a synthetic round pins both sides; a hard failure there would have been a test of the runner, a silent pass would have claimed a property the round could not show. (5) A relation between a gate's own accounting and a test's clock ("the buckets add up to the hold") needs a BRACKET, not a point: the hold began between two reads of the clock before the lock and the sum was taken between two reads around it, so the sum lies between the shortest and the longest span those reads allow, and a pause anywhere only widens the span. A single `held = clock() - t0` taken a few statements before the sum went red when a clock jump landed between the two reads.

**Two more, from the independent read and the burners.** (6) Replacing an upper bound with a hang guard keeps the test able to catch a hang and loses its power over a wait that is bounded but wrong: a checkpoint that waits a configured 10 s for stragglers, a backoff that doubles from 1 s, an open given twice its timeout all come back inside 20 s. Where the old bound was the only thing standing between the code and such a wait, the test must read the number the code ASKED for (the busy timeout in force when the checkpoint ran, the delays a failing write requested, the timeout an open was given, the gaps a loop asked for between passes, every route into `/proc` a thread-clock read took) instead of a duration; a pause moves none of those, and a mutant that is bounded but wrong turns the test red. (7) A threshold lowered for a test makes every other use of the same thing countable: a test that set the write gate's journal threshold to 10 ms to journal one deliberate hold then asserted "exactly one hold was journaled", and the usability probe after it (an acquire and a release) was a second journaled hold whenever a loaded runner kept it for 10 ms, once in 147 runs of the whole burner pass and again at the seventh repeat of that one test (twelve busy loops and two fsync hammers on four cores). Raise the threshold again before the probe, so the only hold that can be journaled is the one the test made on purpose.

**One more, from the delta read of the last commit and the clock-jump pass that confirmed it.** (8) A spy that swaps a module-level synchronisation object (a Condition, a lock) for a recording one takes every OTHER thread's next use of it along: the journal's flusher thread, parked from an earlier test, took its next `wait()` onto the swapped condition, put a `None` in the record, and would have stayed parked on the swap after the undo (every later `notify_all` going to the original), leaving the writer orphaned for the rest of the session. Patch the method of the REAL object instead, and keep only the calls the code under test makes (the caller's frame name, or the test's own lock); a wait that is module-wide (`writer._wait`) is kept to the waits on the test's own gate for the same reason. A clock-jump pass found it because it changes which thread gets to the condition first; a rerun of the test does not.
