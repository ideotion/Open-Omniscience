## 2026-10-13 — A LONG GROUP BY IS READ AS MANY SHORT STATEMENTS, ONE DAY OF ONE KEY RANGE EACH, BECAUSE A KEY RANGE ALONE MAKES THE PLANNER READ THE WHOLE TABLE (WAL / disk thread, read-chunking PR, 2026-10-06)

The guard's 10-06 pin reports named two reads as the longest open readers: `trending()._counts` (a `GROUP BY keyword_id` over a date window, in `fetchmany` of `grouped_counts`, 1,496 s on one machine) and `corpus_keywords` (a `GROUP BY` over an
article set, inside `cursor.execute`, 1,428 s on another). **A pin report proves where the thread WAS when it was taken, not how long one statement lasted**: the checkout is a candidate holder (the findings PR's lesson), and the same lane
runs many statements on one checkout. What is certain is that a RUNNING statement is a reader a checkpoint cannot pass and a finished one is not (pysqlite's legacy mode starts no transaction on a SELECT: measured again on the app's own
engine, `tests/test_windowed_group_counts.py`, the contrast being the old statement with its cursor open, which gives `busy=1`), so the fix is to bound the longest statement, not to guess which of them was long. (1) **Chunk a GROUP BY by the
index's own leading column, not by the group key.** `keyword_id >= a AND keyword_id < b` over a date window makes SQLite choose `ix_mention_covering (keyword_id, ...)` and scan that range across ALL dates (K chunks = one pass over the whole table,
however short the window), which is the "re-read the window once per chunk" cost the old docstring warned of in another form (measured: the plan flips as soon as the range is added). `observed_on = d AND keyword_id` range keeps
`ix_mention_date_keyword (observed_on, keyword_id, count)`: a seek on both predicates, index-only, grouped in index order with no temp b-tree, each index entry read once in total. (2) **The rowid bound keeps it covering**: `id <= max(id) read at the
start` is evaluated from the rowid stored in every index entry (`id` is `INTEGER PRIMARY KEY`), so it adds no table read and keeps a row INSERTED above the start's highest id out of the read (the test inserts into ranges
already read, not yet read and never seen, and fails without the bound). **It is NOT one snapshot, and the text must not say so**: SQLite re-uses the highest rowids after a delete (no AUTOINCREMENT), so an insert made after such a delete can land at or below the bound and CAN be counted (when its key's range has not been read yet and its key lies inside the probes' [min, max]); an article RE-INDEXED while the read runs (a delete, then inserts that get ids above the bound) can be missing from the read altogether, because a later statement finds neither its old rows (deleted) nor its new ones (above the bound); an article that holds the table's TOP ids gets them back (that is the first limit), so its re-inserted rows land under the bound and a keyword that moved from a range already read to one not yet read is counted under BOTH its old and its new keys (the deep delta read's measurement: keyword 119 read 14 against 7 at the start, the total 1,354 against 1,347); a row deleted is seen or missed according to which statement reached it, and a row MOVED to another key (a keyword fold rewrites `keyword_id` in place) is counted TWICE when it moves from a range already read to one not yet read (under both keys: a state that never existed, 338 -> 339 and 180 groups against 179 in the deep read's measurement) and missed when it moves the other way. All of these are pinned by tests that reproduce them, so a "fix" that changes them has to change the text. No reader relies on one snapshot (`trending()` already read its two windows in two statements); no article's rows are half old and half new within one statement. (3) **`keep` runs only between statements** (after the range's days are all read), so it can
never run with a cursor open, and memory is the range (10,000 keywords, widened only when the statement cap needs it on a very wide key span: 65,991 keys for a 90-day window at 14.65 M ids), not the window. **The session's pooled connection goes back after each range** (`release_between_pieces`, which is `release_idle_connection` unless the session is a `read_snapshot_session`, whose one BEGIN is the point): an ORM session autobegins on its first statement and keeps its connection checked out until the caller ends the transaction, so a read of thousands of short statements still showed the pool watch ONE holder for the whole call (MEASURED by the deep read: 52.6 s of 52.6 s on a 1.3 M-mention table, and the storage guard's pin report lists checkouts oldest first as the candidate pinner). A test samples the real pool watch while `keep` runs; without the release the same read shows a holder. (4) **An article set is cut into slices of 100 articles and the sums added**: exact, because `SUM` and the count of DISTINCT articles add across
disjoint article sets, so the ids are de-duplicated first (a repeated id counts once, as `IN` does; mutant caught); ties on (articles, mentions) now break by keyword id, which the single statement left to the sorter. (5) **Measured, so the
cost is not guessed, and a first reading was wrong.** Synthetic, plain SQLite, `ANALYZE`d, 1,750,697 mentions over 30,928 keywords with a dense id space: the recent 7 days = 0.17 s as one statement (longest 0.09 s) against 0.15 s in 213 statements (longest under 5 ms), the 28-day baseline 0.30 s against 0.43 s in 843 statements: "about the same". **That does not hold on a sparse id space**, which is the field's (11 to 14.65 M keyword ids): the deep read's table (1.32 M mentions, ids sparse over 1 to 3 M, 632,644 keyword rows) gave `trending_windows` 2.6 s as the single statements and 17.1 s in 42,708 statements while a new statement was built and run through the ORM each time, and 7.3 s in 42,618 once ONE bound statement is run on the session's connection: about 110 us a statement, of which SQLite is about 70 us (the keyword mentions are read through a view) and the rest Python. The statement count is the key span over 10,000 times the days (capped at 20,000 by widening the range), so it does not depend on the article count: 1 M articles with the field's 11 M span would issue about 76,600 statements for `trending_windows`, 8 to 9 s of overhead inside the 60 s read deadline. What the cost buys is the longest statement (a day of a 10,000-id range: under 5 ms, 61 ms for thirty days in one statement). **Putting several days in one `IN` list was tried and refused**: it removes the overhead (30 days of one range 0.42 s in one statement against 0.21 s in thirty, but 9,000 statements fewer) and then, with the country filter, SQLite chose `ix_mention_country (country=? AND rowid<?)` for EVERY statement, a scan of the country's rows per range; one day with an equality on `observed_on` keeps the seek. Under SQLCipher the per-statement overhead is smaller against the decrypt cost, but that is not measured here. **Those times were taken before the release between ranges existed, and the release costs a checkout and a check-in per range**: the deep delta read measured `trending_windows` at 8.2 to 9.0 s with 1,723 checkouts for the same 42,618 statements (the single statements: 2.9 s on a loaded machine), 8.9 to 10.1 s with 6,054 checkouts at the field's 15 M span against 2.3 s, and 9.6 to 10.4 s on an encrypted file with a warm cache against 2.8 to 3.5 s (no physical reopen, so no key derivation). Under a SATURATED pool every re-acquire queues (synthetic churn on an encrypted file: pool 2+4 with 12 threads, 7.99 to 10.83 s; pool 4+20 with 30 threads, 43.4 to 51.4 s), and the statement deadline does not run while a checkout waits.
(6) **A session whose executes are wrapped keeps every wrapper**: the briefing's WAL guard keeps each result `session.execute` returns (its statement, its parameters, its exhausted cursor result) until the next producer starts. Measured on the test fixture's 1,550 seeks, retained with `tracemalloc` (the figures are the measurement's; the test pins only that at most three wrappers are retained): 15 KB per seek with a statement built each time, 7.4 KB with one `bindparam()` statement, and nothing once the seeks go through `session.connection()` (the guard intercepts only `fetchmany`, so it had nothing to protect in a read finished by `.all()`): about 41 MB for the 5,550 seeks of a 1.5M-id span, 180 MB for the Home poll's three presets, so the bounded read must not pay for its own statement count in memory. (7) The slow-query log sees single statements, so a read of thousands of short ones no longer shows there as one slow query.
What this does NOT fix: `release_idle_connection` itself (the collector's) still reads only the session's own flags, so DML run through `session.execute(text(...))` or on `session.connection()` is rolled back unseen (the deep delta read measured both writes lost; no caller of the read-chunked reads writes that way before reading, and `release_between_pieces` now also asks the driver, whose connection reports a transaction after any write and none after a SELECT); a session that holds a real WRITE transaction open (a lane step that left the session dirty, flushed by autoflush) pins the log for as long as that transaction lives, whatever its reads do; a `read_only_db` / `read_snapshot_session` session, which holds ONE explicit BEGIN across every statement on purpose (one consistent snapshot for the diagnostics bundle, whose trending probes run on it); `emergence.py` still uses
`grouped_counts` (the coordinator limited this PR to the two named reads).
