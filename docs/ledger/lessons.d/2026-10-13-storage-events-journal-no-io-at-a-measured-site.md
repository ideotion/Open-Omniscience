## 2026-10-13 — A JOURNAL AT A MEASURED SITE DOES NO DISK I/O, AN INSTRUMENT NESTED UNDER ANOTHER'S GUARD INHERITS ITS THRESHOLD, AND AN ALLOWANCE BY NAME LETS EVERYTHING WITH THAT NAME THROUGH (the storage-events journal, PR pending)

(1) **The first draft of the journal read its file inside the first `record()`, under the journal's lock, and `record()` is called from the write gate's release, the storage guard's `_account_locked` (under the guard's lock) and the pool's `connect()`.** A drive that hangs, which is exactly when the guard engages, would have stalled the gate's release or the guard's sampler through the instrument that was meant to explain the stall. Reading the history was needed only by two callers: the background writer before its first write (so the file is extended, never replaced by this process's events alone) and the member before it answers. A recording now touches two dicts and a condition variable and nothing else; `test_recording_does_no_disk_io_and_the_file_is_read_by_the_writer_or_the_member` patches the reader and counts calls. Rule: a function called from inside a lock that something else waits on may not perform I/O, even once, even lazily; split "record" from "load" and let the thread that can afford to wait do the load.
(2) **The release line's one-second floor wrapped the journal's 30-second threshold.** `release()` read `if held >= _RELEASE_LINE_FLOOR_S: log(...); if held >= HOLD_RECORD_S: note(...)`, so the journal's threshold only ever applied above the log line's floor. At the defaults (1 s and 30 s) nothing was wrong and nothing could show it; a test that lowered `HOLD_RECORD_S` to 0.05 s for speed got no event at all, which is how it was found. Two thresholds that are independent in intent are two `if`s at one level. The same reading applies to any new instrument added under an existing branch: ask which condition it inherits.
(3) **`handle_error` does not fire for the pool's `TimeoutError` in SQLAlchemy 2.1.1** (tried first, with an event listener; it fires for DBAPI errors). The one place every checkout timeout passes, the pool's own and the collector reservation's explicit raise, is `ReservingQueuePool.connect()`; the hook wraps it, records and re-raises the same exception object, and a test makes the journal fail inside the hook and asserts the pool's error is still the pool's.
(4) **An AST guard that allows "calls named `info` and `get`" allows every `.get()` and `.info()` in the function.** `tests/test_init_steps.py` skipped a statement whose only callees were named `info` or `get` because `init_db` has a `_LOG.info(...)` and a `_stamp.get(...)` that are not steps; `session.get(Model, 1)` would have passed unnamed, and so would a bare import inside an `if`. The allowance is now the pair `(owner, name)` (`("_LOG", "info")`, `("_stamp", "get")`), a call on a dotted owner or an expression has no owner and is a step, and the label is the first import or call in SOURCE order anywhere inside the statement. Five mutants (an import in an `if`, in a `try`, an unnamed `get`, an unnamed `info`, an unnamed call) each fail the guard, and the same `if` with its name before it passes, so the guard cannot be satisfied by refusing everything.
(5) **A journal's own bookkeeping keys must not be settable by the caller.** `open`, `ended`, `ended_at`, `session` and the process token are the journal's; a hook that passed `open: True` would have left an event open for ever and one that passed `ended` would have forged an end. `_OWNED` drops them from every hook's fields, in `record`, `update` and `end`, and a test passes all of them.
(6) **A helper written between a router decorator and its function becomes the route.** `_pool_config()` was added directly above `write_gate_report` in `src/api/diagnostics/system.py`, so `@router.get("/write-gate")` registered the helper (a function returning a dict, called by FastAPI with no arguments) and the real handler had no decorator; the two package-split tests (`test_diagnostics_split_is_route_neutral`, `test_the_package_reexports_every_name_its_submodules_define`) caught it in the first battery, and nothing else would have until a zip was built. The helper now lives in `pool_watch.pool_config()`. Rule: never insert a line between a decorator and its `def`; when a diff adds a function above a decorated one, read the three lines around the insertion.
(7) **A writer thread that waits out a delay outlives the test that started it, and only a reset that wakes it ends the wait.** The coalescing wait (`FLUSH_DELAY_S`) ran to its deadline whatever woke it, so a test that raised the delay to 30 s left a thread that did not write for the next 30 s of every later test (the symptom was two unrelated tests timing out in one run in three). The writer now captures the generation when its wait starts, leaves the wait when it changes, and `reset_for_tests` wakes it; every write and every read it makes is also gated on that generation, so a stale snapshot is never written and a stale read is never applied. The same family: `os.replace` is the process's, so a test that counts or fails it must do so for the journal's file only (`_on_journal_replace`), or another thread's rename is counted and the first call it breaks is not the one under test.
(8) **A writer that dies must be counted, kept by class, and replaced by the next change, and a final write must be a flush that knows what is already written.** The thread's loop catches `Exception` per iteration; a `BaseException` ends it, so the wrapper counts it once (`writer_deaths`), keeps its class (never its text: an uncaught error in a thread prints its message, which can hold a path), and `_mark_dirty_locked` starts a new thread on the next change. `flush()` (the lifespan's clean stop, `atexit`, the tests) writes only when the version recorded is newer than the version written, so a failed write is retried at the stop and a write the thread already made is not made twice. The writer copies the snapshot under the lock and writes outside it, and `record`/`update`/`end` never wait for the write or for the first read of the file (two tests hold each of them stuck on an Event while 1,200 recordings run).
(9) **`pkill -f` and `pgrep -f` with a pattern that appears in the command line that runs them match their own shell.** A wait loop `while pgrep -f "pytest tests/..."` never ended, and `pkill -f "while True: pass"` in the same line that started the busy loops killed the shell (exit 144). Kill by exact PID, or keep the pattern out of the command that carries it.
