## 2026-11-01 — a test whose store is /dev/null passes for a normal user and turns the device into a file for root, and a second SQLite words a plan and an out-of-memory differently from the first (PR #PRNUMBER)

**What was found.** (1) The first full-suite run on a second SQLite: this container's Python 3.13.18 links SQLite 3.53.1 (CI's runner links an older one), venv `[dev,columnar]` only. 28,338 passed, 5 failed, 120 skipped in 5,749 s. Causes: one test needed an extra the venv lacked (VADER, `[analysis]`, which every CI job that has DuckDB installs: environment only); two named SQLite's plan wording; one named SQLite's out-of-memory shape; one was `/dev/null` (2). (2) Three tests (`test_database_damage.py:1273`, `test_database_verify_pages.py:1178` and `:1181`) built a `DamageRegistry` with `path_fn=lambda: Path(os.devnull)` to get a store they never read. The registry persists by writing `<store>.tmp` beside the store and `os.replace`-ing it over the store (`damage.py` `_flush`). A non-root user cannot create a file in `/dev`: `EACCES`, caught by the registry's `except OSError`, recorded in `write_error`, test green. ROOT can: after the run `/dev/null` was `-rw-r--r-- root`, and a test far away (`test_diff_installed_versions`, `stdin=subprocess.DEVNULL`) read `{"files": {"corpus": ...}}` where it expected empty input. Proved with a stand-in path (`os.devnull` patched to a scratch file by a plugin): the two tests left a 979-byte and a 2,006-byte registry record there. CI runs as a non-root user, so it can never see this; a Docker image or a cloud sandbox that runs the suite as root destroys the device for everything after. (3) The ascending page statements of `test_browse_plan.py` sort the ties of the first key only; SQLite up to the 3.4x series words that step `USE TEMP B-TREE FOR RIGHT PART OF ORDER BY` and 3.53.1 words it `USE TEMP B-TREE FOR LAST TERM OF ORDER BY` (`LAST n TERMS` for more). Same plan, other words; the old assertion read the words. (4) An FTS5 `quick_check` under `PRAGMA hard_heap_limit` ANSWERS A ROW ("unable to validate the inverted index ... out of memory", measured on 3.45.1) which `verify.py` parses into "the read ran out of memory", and on 3.53.1 RAISES an empty `MemoryError` (probe on plain `sqlite3`), which `classify_error` reports by class name. Both are `unchecked`, neither is damage; `damage.py` documents that an empty `MemoryError` on a SQLCipher connection can also be a failed page tag, so `verify` cannot call it out of memory from the class alone, and the product code was left as it is.

**The rule.** (1) A test's store path is a `tmp_path` file, never a device and never a path whose write failure the code under test swallows: a write that fails for permission passes for every non-root user and succeeds for root, and a test that needs a write to FAIL must make it fail by structure (a file where a folder must be, `ENOTDIR` for every user). (2) `tests/test_zz_dev_null_is_left_alone.py` pins three things: a static scan (no file under `tests/` or `src/` names `os.devnull`, `from os import devnull` or the whole string `"/dev/null"` as a path unless an allowlist entry says why, and an entry no file needs fails); the premise (a registry replaces whatever node is at its store path, shown with a bound unix socket, which a non-root user can make; a FIFO cannot stand in, because the registry reads its store first and opening a FIFO with no writer blocks forever); and a canary that sorts last and fails when `/dev/null` is no longer a character device. (3) An assertion about what SQLite prints names the MEANING (a sort of every candidate versus a sort of ties) and not the words, accepts every documented wording of the same plan, and is proved on the library that runs the suite (`test_the_running_sqlite_words_its_two_kinds_of_sort_the_way_the_helper_reads_them`). (4) A test of the real driver under a failure accepts each documented SHAPE of the same fact (a row, an exception) and keeps the verdict strict: `unchecked`, never `damaged`.

**Where it applies.** Any test that points an atomic writer at a path it does not read back, or whose pass depends on a permission failure (`chmod 000`, a read-only folder: all of them pass vacuously as root); any assertion on `EXPLAIN QUERY PLAN` text or on an error text a library chooses; a broad test run in a root container, where the first sign of a test destroying a system node is a failure in a test that has nothing to do with it.
