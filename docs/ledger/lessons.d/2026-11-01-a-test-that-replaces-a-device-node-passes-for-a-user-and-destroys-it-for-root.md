## 2026-11-01 — a test whose store is /dev/null passes for a normal user and turns the device into a file for root, and a second SQLite words a plan and an out-of-memory differently from the first (PR #1681)

**What was found.** (1) The first full-suite run on a second SQLite: this container's Python 3.13.18 links SQLite 3.53.1 (the system Python links 3.45.1; CI's runner is a third build), venv `[dev,columnar]` only. 28,338 passed, 5 failed, 120 skipped in 5,749 s. Causes: one test needed an extra the venv lacked (VADER, `[analysis]`, which every CI job that has DuckDB installs: environment only); two named SQLite's plan wording; one named SQLite's out-of-memory shape; one was `/dev/null` (2). (2) Two tests, three registry constructions (`test_database_damage.py::test_a_latch_never_releases_by_itself_however_long_it_stands`, one registry; `test_database_verify_pages.py::test_a_pages_finding_beside_index_only_damage_is_data_scope_not_a_search_index_one`, two) built a `DamageRegistry` with `path_fn=lambda: Path(os.devnull)`. The registry reads its store, then persists by writing `<store>.tmp` beside it and `os.replace`-ing that over the store (`damage.py` `_flush`). A non-root user cannot create a file in `/dev`: `EACCES`, caught by the registry's `except OSError`, recorded in `write_error`, test green. ROOT can: after the run `/dev/null` was `-rw-r--r-- root`, and a test far away (`test_diff_installed_versions`, `stdin=subprocess.DEVNULL`) read `{"files": {"corpus": ...}}` where it expected empty input. Proved with a stand-in path (`os.devnull` patched to a scratch file by a plugin): one registry left a 979-byte record, and 2,006 bytes once the pages test's two registries had both written to the same store (they shared it, and a registry reads its store before it writes, so the second record lands beside the first). CI runs as a non-root user, so it can never see this; a Docker image or a cloud sandbox that runs the suite as root destroys the device for everything after. (3) The ascending page statements of `test_browse_plan.py` sort the ties of the first key only; SQLite 3.45.1 words that step `USE TEMP B-TREE FOR RIGHT PART OF ORDER BY` and 3.50.4 and 3.53.1 word it `USE TEMP B-TREE FOR LAST TERM OF ORDER BY` (`LAST n TERMS` for more); 3.46 to 3.49 were not measured. Same plan (the VDBE opcode sequences are identical), other words; the old assertion read the words. (4) An FTS5 `quick_check` under `PRAGMA hard_heap_limit` ANSWERS A ROW ("unable to validate the inverted index ... out of memory", measured on 3.45.1) which `verify.py` parses into "the read ran out of memory", and on 3.53.1 RAISES an empty `MemoryError` (probe on plain `sqlite3`), which `classify_error` reports by class name. Both are `unchecked`, neither is damage; `damage.py` documents that an empty `MemoryError` on a SQLCipher connection can also be a failed page tag, so `verify` cannot call it out of memory from the class alone, and the product code was left as it is.

**The rule.** (1) A test's store path is a `tmp_path` file, never a device and never a path whose write failure the code under test swallows: a write that fails for permission passes for every non-root user and succeeds for root, and a test that needs a write to FAIL must make it fail by structure (a file where a folder must be, `ENOTDIR` for every user). (2) `tests/test_zz_dev_null_is_left_alone.py` pins three things. A static scan of `tests/`, `src/` and `scripts/`: no file names the null device (`os.devnull` through `os`, `os.path`, `posixpath` or `ntpath` under any import alias, `from os import devnull`, `getattr(os, "devnull")`) or a whole-string `/dev/<name>` constant, str or bytes, as a path unless an allowlist entry says why (three do, each with its reason), and an entry no file needs fails; what it cannot see is stated and pinned (a path built from parts, a variable, a device inside a longer string, `sys.modules["os"].devnull`, a relative store such as the `Path("x")` in `tests/test_damage_reread.py`). The premise: a registry replaces whatever node is at its store path, shown with a unix socket bound by a relative name after `chdir` (a non-root user can make one; a FIFO cannot stand in, because the registry reads its store first and opening a FIFO with no writer blocks forever). And a canary that sorts last in a serial run and fails when `/dev/null`, `/dev/zero`, `/dev/random` or `/dev/urandom` (and `/dev/full`, where the platform has it) is no longer a character device; it names the damage, not the culprit, which is the scan's job, and under `-n` or a random order it can only miss damage. (3) An assertion about what SQLite prints names the MEANING (a sort of every candidate versus a sort of ties) and not the words, accepts every documented wording of the same plan, and is proved on the library that runs the suite (`test_the_running_sqlite_words_its_two_kinds_of_sort_the_way_the_helper_reads_them`). (4) A test of the real driver under a failure accepts each documented SHAPE of the same fact (a row, an exception) and keeps the verdict strict: `unchecked`, never `damaged`; a fake of each shape pins its own mapping on every SQLite, so the real-driver test is the confirmation and not the only proof.

**Where it applies.** Any test that points an atomic writer at a path whose replacement it does not expect, or whose pass depends on a permission failure (`chmod 000`, a read-only folder: all of them pass vacuously as root); any assertion on `EXPLAIN QUERY PLAN` text or on an error text a library chooses; a broad test run in a root container, where the first sign of a test destroying a system node is a failure in a test that has nothing to do with it.
