## 2026-10-17 — HALF OF THE OUTLET JOIN'S COST WAS A STRING BUILT PER ROW, A COLUMN ON THE TABLE YOU SCAN BOUGHT NOTHING OVER ONE ON THE SMALL TABLE, AND ANY PERSISTED OUTLET KEY HAS THREE CONDITIONS (AMENDS ROW J LEFT OPEN (1))

(1) **What was measured (plan-row-j/outlet-key-design-2026-10-17/DESIGN.md; the app's own engine and session, `corpus_gen`'s app schema, 2.34 M mentions in the window, 7,000 sources in 6,500 outlets, plaintext, idle machine, median of 7).** The candidate query of `find_story_propagation`: `count(distinct source_id)` 4.28 s; the shipped outlet join (`LEFT JOIN sources`, `coalesce(domain, 'source-' || cast(id as text))`) 6.47 s, +51 %, the earlier +55 % reproduced. The same join with the string work removed (`coalesce(domain, source_id)`) 5.37 s. An INTEGER `sources.outlet_id` with the join kept 4.51 s (+5 % over the baseline). An integer on `keyword_mentions` with NO join 4.47 s. An integer derived per query by a window `MIN(id) OVER (PARTITION BY outlet)` 7.06 s, slower than shipped.

(2) **So Row J left open (1) was half wrong.** It said a persisted key on `sources` would let readers "group on a column of the table they already scan, with no join". The key on the mention rows buys nothing over the key on `sources` (4.47 s against 4.51 s), and costs a 3.77 s backfill of 2.34 M rows (about 34 s at the field's 20.9 M, extrapolated), +23 MB, a drop and recreate of `keyword_mentions_all` and a second place that must follow every domain change. **Rule: before denormalising a key onto the table a query scans, time the join to the small table with the key as an integer; the cost of a join was the string, not the lookup.**

(3) **What was built: `outlet_expr` is `coalesce(domain, source_id)`** (src/database/outlet.py, tests/test_outlet_expr_types.py). Every count is unchanged (SQLite's `DISTINCT` keeps an integer and a text value apart, so an orphan id `123` and a domain spelt `123` stay two outlets, as `source-123` and `123` did), pinned against the old spelling on a store with each awkward case; the shape (no cast, no concatenation) is pinned red-without. SQLite only, as the app is.

(4) **Conditions for any LATER persisted outlet key (not built; ruled 2026-10-17: leave it unbuilt unless +21 % on this query is judged too much).** (a) **A trigger, not call-site hooks**: the seeder, the CSV/YAML import, `POST /sources`, discovery, the restore merge (a raw `INSERT`) and the collectors all write `sources`, and a path that forgets the second column splits an outlet, which counts one publisher as two voices; a mapper event cannot do it (it does not see the id on insert and the merge bypasses the ORM). (b) **An AFTER DELETE rule**, and an invariant "an outlet id is the id of an existing source of that domain" pinned by test: SQLite re-uses the largest rowid, so with a stale id left behind by deleting an outlet's oldest feed an unrelated source could be given that id and two outlets would merge, which manufactures agreement. (c) **J1's table rebuild must recreate the triggers** (SQLite drops a table's triggers with it) and a test must read them back from `sqlite_master`; the column is derived, so it stays out of the backup format. Write cost, measured: first install of 6,616 sources 0.599 s plain, +0.14 s with an AFTER INSERT trigger, +0.05 s (inside the spread) with one UPDATE after the batch; a steady boot 0.7 ms; one added source 3.2 ms. Not on `keyword_mentions`.

(5) **Not measured:** an encrypted store, a 20.9 M-mention store, the other three gates' own queries (`laundering`, `link_analysis`, `supply_chain_ripple` share `outlet_expr`, so the change applies to them; only story-propagation's shape was timed), concurrent writers, a cold cache.
