## 2026-10-28 — a tool that kept its own copy of a rule disagrees the day the rule moves, and the dangerous direction is silent

**What was found (the follow-on to #1643, the limit that PR's own lesson stated).** #1643 made `lessons.outside_fences` the ledger's one fence rule. `scripts/sweep_pr_number.py` still carried the loop it was written with (toggle on any line that starts with three backticks or tildes), so from that merge on it read a fragment differently from `ledger_fold.py check`. Measured by running the pre-change `sweep_markdown` over the seven shapes where the two rules differ: five (a `~~~` line inside a backtick block, a closer with trailing text, a shorter run inside a longer fence, a backtick run inside a tilde fence, and a line that is only a code span, `` ```a``` ``) made it REFUSE ("an unclosed code fence") a file `check` accepts; one (a backtick fence that a `~~~` line "closes") made it ACCEPT and sweep a file `check` refuses as unclosed; and one, a whole `~~~` block quoted inside a backtick block (the natural way for a lesson about fences to quote its example), made it SILENTLY REWRITE the quoted `PR pending`. Nothing downstream could see that last one: the sweep's survivors check reads the ledger's `_prose`, which hides the same text, so the rewrite looked like a clean file. Separately, `PR #PRNUMBER`, the form the lanes write before the number exists, was a refusal ("would remain") because `_PLACEHOLDER` had learned `#PRNUMBER` and the sweep's `_RULES` had not.

**The rule.** (1) A stated limit ("this tool keeps its own loop") is a hazard with a start date: the day the shared function lands, the copy is wrong in both directions, and a post-check built on the shared rule cannot catch the rewrite the copy made inside text the shared rule calls quoted. When a shared function lands, grep for the readers it did not replace in the same change. (2) The sweep now CALLS `ledger_fold.outside_fences` and `_INLINE_CODE`, names the line an unclosed fence opened at (as `check` does), has a `#PRNUMBER` rule, and judges a csv `refs` cell by `ledger_shipped.REFS_PLACEHOLDER`, the predicate `ledger_shipped.py check` applies (a `pending` word, `#NNNN`, `#PRNUMBER`), so a refs value saying "depending on #1637" no longer makes a sweep refuse what `check` accepts. That swap is a change of strictness, not only of source, and the Opus read caught what it left open: a second gate reads the same cell, `release_notes.refs_carry_placeholder` (the release-notes test), and it flags the SUBSTRING `pending`. On `R9; depending on #1637; PR pending` the old sweep refused, the new one exits 0 with `check` green, and the release-notes test then fails on the swept ledger. Ask which other gates read the same field before calling the shared predicate "the" guard. (3) A drift guard turns the next change red where the sweep would have met it: `test_every_token_the_ledger_refuses_has_a_rule_here` counts the alternatives of `_PLACEHOLDER` against a sample list and sweeps each sample clean. The fence fixtures also assert the LEDGER'S reading of themselves (`QUOTED` absent from `_prose`, `LIVE` present), so a fixture cannot drift from the rule it claims to test.

**What it measured.** 20 of the new or changed tests are red on the pre-change script (12 fence-shape cases, 6 shapes in LF and CRLF; 2 refusal needles; `#PRNUMBER` in prose; the drift guard; 4 refs cells) and all 89 in the file are green on the new one; 61 of 61 mutants of the script are killed (one equivalent kept out). The first mutant run had one survivor: the double-backtick span fixture was still protected under a single-backtick regex, through the span's own inner backticks; a span HOLDING a single backtick separates the two. Stated limits: the two refs predicates disagree about the word `pending` until Plan's follow-on (after this PR) makes `release_notes.refs_carry_placeholder` call `REFS_PLACEHOLDER`; Plan reports that 0 of 1,677 real ledger rows differ between the two (not re-measured here), so the window is latent, and once the two are one predicate the gap is closed with no change to the sweep. And the sweep matches the stretches between code spans one at a time where the ledger deletes the spans first, so a token touching a span (`PR pending`x`s`) is rewritten where `check` would not have flagged it, an extra rewrite and never a missed one.
