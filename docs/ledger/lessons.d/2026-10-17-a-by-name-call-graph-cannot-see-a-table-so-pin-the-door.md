## 2026-10-17 — A BY-NAME CALL GRAPH CANNOT SEE A TABLE OR A COMMON NAME, SO THE DOOR AND THE CALL SITE ARE PINNED INSTEAD

(1) **What the pins are for.** A loop that is exempt from the R161 shape because it runs only on a worker thread (only the main thread receives a KeyboardInterrupt) is exempt on the strength of a report. `tests/test_worker_only_callers_pinned.py` rebuilds from the source, by name, every function that can reach each exempt function and requires: no main-thread entry among them (an `async def`, a module under `scripts/`, a top-level call), and EXACTLY the pinned set, so a new caller fails the test until someone reads it. Private names (`_x`) are followed only inside their own file, public names across the repo.

(2) **Two limits that were measured, not guessed.** (a) A COMMON NAME EXPLODES: following `build` (a function in `bulletin/cards.py`) by name reached ten unrelated scripts that call other things named `build`. For `record`, `start`, `notes` the pin is the call site, not the closure (tests/test_event_loop_rows_pinned.py). (b) A TABLE IS INVISIBLE: `storage_events.diagnostics_member` is called only through a string target in `diagnostics_slots.SLOTS`, and every briefing producer only through the `_DEFAULT_PRODUCERS` tuple run by `registry.run_all_bounded`; the fuller reach tool (`main_thread_reach.py`, receiver types, about a minute, outside the repo) called both rows UNKNOWN. They were read by hand, found worker-only, and then pinned at the DOOR: `tests/test_registry_doors_pinned.py` pins the callers of `run_all_bounded`, `run_all` (called by nothing outside the tests: the one open door) and `diagnostics_slots.members`, fails on a main-thread caller of any of them, and pins `cards.build` to its one importer.

(3) **Where the two tools disagree, read the loop, not the verdict.** The reach tool attributed a generator-expression's jump to the enclosing `for` and reported `ui_clickthrough_run.py:448` as a loop with an uncovered back-edge; after its fix the same loop was still real, because the back-edge of a `for` that ends in an `elif` sits in a gap between exception entries (the `_uncovered_loop_heads` criterion). It had already been converted (`else: pass`, a guard clause). **A tool's false positive on one loop is not evidence about the loop beside it.**
