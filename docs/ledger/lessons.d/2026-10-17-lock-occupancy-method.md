## 2026-10-17 — measuring a lock: read a per-window statistic once per window, check it against a count you already know, and isolate a cause by reproducing it without the suspect

**What was found.** The first matrix of the extraction lock's occupancy at 2 CPUs (collectors 2 / 4 / 8 / 14) reported 180 holds for 720 stored articles. `lock_stats` is reset by the pass monitor at the start of every pass, so the harness's single snapshot at the end covered the last pass of four while wall time and articles covered all four: a reading of one pass dressed as four, with a plausible-looking table around it. It was found because the lock is taken exactly once per stored article in that harness, so holds must equal articles stored, and 180 is not 720. The figures were withdrawn and the matrix rerun with a snapshot per pass, summed; the whole-pass numbers, the isolation runs and the text that quotes them (the lock's queue entry, shipped-log entry and lesson entry) carry the corrected span ("four measured passes, 720 holds"). The cause of the unlocked slowdown, written down as a guess for a day ("GIL and allocator contention"), was then isolated: it is CPU, not waiting, it reproduces with a loop of `os.stat` calls and no lxml, it needs neither a shared parser nor a shared XPath object, and separate processes on the same CPUs do not show it (`/mnt/project-files/keyword-export/lock-occupancy-2026-10-17/RESULTS.md`).

**The rules.**
1. **A statistic with a reset reports one window; read it once per window and sum, and say the span next to every figure.** Whoever reads a counter that something else resets must read it at every reset it sees. The harness (`run_lock.py`) now sums `lock_stats.snapshot()` after every pass; every lock figure in a table says "over the four measured passes".
2. **Give the harness a tell it can check itself: a count it already knows.** Every stored article takes the extraction lock once, so `holds == articles_stored` is written into each result (`check_holds_equal_stored`) and a run that fails it exits 3 with the two numbers. A wrong span now fails loudly instead of producing a table.
3. **Isolate a cause by reproducing it without the suspect, not by naming a suspect and removing it.** The sequence that worked: the slowdown reproduces with extraction alone (no fetcher, no database); thread CPU per call rises (more work, not waiting); separate processes on the same CPUs scale linearly (so it is shared state inside one process, not CPU quota, cache or memory bandwidth); a pure-Python call and a long GIL-releasing call (sha256 over a buffer sized to one parse) do not collapse; parse alone barely does; text by XPath does, with one XPath object per thread as much as with one shared; and 100 `os.stat` calls per task, which share with lxml only that they release the GIL for a microsecond, collapse the same way. Each step removed a suspect (the allocator: `MALLOC_ARENA_MAX=1` changes nothing; the shared parser; the shared XPath) rather than naming one.
4. **Write down which half of a mechanism the runs did not isolate.** The `os.stat` loop shows what makes threads slow; lxml 6.1.3 releasing the GIL twice per XPath evaluation is read from its source, and that `extract_article` is slowed by these calls is inferred. No run removed the XPath calls from `extract_article`, so the share due to XPath evaluation is stated as not isolated.
5. **Two runs of a cell are a noise estimate, not a confirmation.** The same cells run twice differed by up to 12 %, one cell (8 KB, 8 collectors, lock off: 396 against 302 articles per minute) by 24 %. A difference inside that is not a claim, in either direction; "the lock costs nothing beyond run-to-run spread" is what the table supports and no more.
6. **A pass-level measurement and a micro-level one answer different questions.** Extraction in four always-busy threads takes 2 to 4 times the CPU per call; in the whole pass the CPU per article does not move (0.134 on against 0.137 off at 4 collectors), because the collectors spend most of the pass in a 300 ms fetch and the mean number of extractions in flight is 0.1 to 2.2 (the reason is inferred, not isolated). Quote the pass figure for what the product costs and the micro figure for why.
