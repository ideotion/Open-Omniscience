## 2026-11-01 — a sweep for unmapped thread starts goes by what a route CALLS on the object, not by the route's name: `/run-now` sat beside `/start` (R393 / R386; PR #1689)

**What was found.** PR #1677 mapped a refused thread start to a 409 and a log line on the routes that call a manager or job, and the Start button's `POST /api/scheduler/start` was the one a first sweep had skipped because its receiver was named `scheduler`. The next route in the same file, `POST /api/scheduler/run-now`, calls the sibling method `get_scheduler().run_now()` of the SAME object, which makes its own thread (`runner.py`, the `oo-scrape-now` thread), and still mapped nothing. Measured with a probe that makes that module's thread refuse to start: status 500 `internal error: can't start new thread`, the only log line the global handler's `unhandled error on route POST /api/scheduler/run-now`, no run active afterwards (`run_now` raises before it records anything in the scheduler's own state, so there is nothing of the scheduler's to undo), and the kill switch cleared.

**The rule.** When a fix maps a refusal for one method of an object, list EVERY route that calls ANY method of that object which makes a thread (`grep -n "get_scheduler()\." src/api/`), whatever the route is called and whatever the report named. The two clients of this route (`app-sources.js`, `app-backup.js`) read the status, so a 409 with the words shows like the Start button's.

**What changed.** `scheduler_run_now` (`src/api/scheduler.py`) catches `RuntimeError` around `run_now()`, logs a WARNING and answers 409 with the exception's words, as `/start` does; the Wikipedia lane is not resumed as if a run had begun; an interrupt and any other error are not mapped. `runner.py` (the keyword lane's) is untouched: a route-level catch is enough because nothing was recorded.

**Stated limit (R407).** What the route did before the start stays done, as after a refused `/start` since #1677: the kill switch is cleared and the crossing online noted, the memory-guard and storage-guard latches are reset and the database-damage pauses released, and the storage-guard supervisor that `run_now` may have started keeps running (it needs no run). Re-engaging the kill switch on a refusal would also undo an online state the operator chose before the click. With no run and no loop nothing fetches, and the next click retries.

**Pinned by** four new tests in `tests/test_failed_thread_start_routes_answer_409.py` (the real scheduler refused: 409 with the words, no run active, the lane not resumed; a run that works is unchanged; a run already in flight is still a 200 with `started: false`; any other error is still a 500) plus the new entries in the interrupt test and the log test, and 13 mutants of the mapping, all killed.
