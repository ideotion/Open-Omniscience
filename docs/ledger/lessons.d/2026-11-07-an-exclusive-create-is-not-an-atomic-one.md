## 2026-11-07 — an exclusive create is not an atomic one: link a finished private copy into place, and never touch a temporary name you did not make (evidence key wrap, R442, PR #1749)

**What was found.** The evidence key was written by `write_bytes`, so two first callers could each generate a key and the last write won, after the first had already signed a manifest with the other. The first fix was the obvious one: create the file with `os.open(O_CREAT | O_EXCL, 0o600)` and write into it, and treat `FileExistsError` as "load theirs". It passed a test that simulates the loser. An eight-thread test with a barrier then failed on its first run: a caller that did NOT lose the create, but only looked a moment later, found the file there and EMPTY (`MalformedFraming`), because `O_EXCL` makes the create exclusive and does not make the content appear with it. The same window existed before as `write_bytes` truncating and writing, and nothing had ever looked for it. Then the migration of a plaintext key to a wrapped one (written to a sibling, read back, renamed over the original) used ONE temporary name for every caller and removed whatever was there before writing. An independent read of the commit reproduced the loss: caller A has written and checked its wrapped copy and is about to rename it; caller B removes A's file and creates its own (still empty) under the same name; A's rename moves B's empty file over the key, and if B dies there the original plaintext key is gone.

**The rule.** (1) A file that several callers may create and another may read at any moment is created in two steps: write the bytes to a private file (`O_EXCL`, the final mode, flushed), then `os.link(private, path)` and remove the private file. The link is atomic and refused with `FileExistsError` when the file is there, so a reader sees no file or a complete one, and the loser still gets the one answer that means "load theirs". A file system without hard links (a FAT or exFAT external drive) answers `OSError`: fall back to the exclusive create in place, and have readers wait out an EMPTY file a few short looks (an empty key file is never a key). (2) The mode belongs to the creation (`os.open(..., 0o600)`), not to a `chmod` after it, which leaves a window under a permissive umask (POSIX only: Windows ignores the mode). (3) A temporary name belongs to its maker: process id, thread, a random token and purpose in the name (the token is what holds across machines: two containers on one data volume can both be process 1 with the same thread number), removed only by the caller that made it, and never "remove whatever is there first" on a name another caller can also use. (4) Temporary files go in a subdirectory (`keys/.pending/`), not beside the thing they become: the backups list the FILES directly in `keys/` and would carry, or trip over, a temporary file another caller is writing or removing; and the subdirectory is removed again when empty, because the encryption attestation (`doctor`) names every entry of `keys/`. (5) A hard link made for atomicity is a SECOND NAME for the secret: whoever replaces or wraps the canonical name removes the other names too, by file identity (device and inode), never by their text, so that a name another caller has not yet linked is left alone. The identity is read with `os.stat` on the path (a directory entry's own `stat()` answers 0 for the device, the inode and the link count on Windows), and the identity of the file that is replaced is the one taken when it was READ: the rename happens only if the file is still exactly that (device, inode, size, modification time), so a wrap never puts a key it read earlier over a key that another caller or a restore has put there since (found by the delta read of the sweep, which also found the Windows zeros). (6) A test that simulates the loser proves only the loser: a barrier of several threads, repeated, finds the readers, and the interleaving that loses data has to be forced step by step (here through `os.replace`).

**What was and was not established.** Measured: the threaded test failed before the link and passed after it (10 trials of 8 threads, one key every time, nothing left behind); a crash between the link and the removal is simulated through `Path.unlink` and the plaintext alias is gone after the wrap; the forced interleaving leaves the key file at 0 bytes under the shared name and intact under the private names; the umask test asks the `os.open` call for mode 0600 and `O_EXCL`; twenty-five mutants (no wrap, a PKCS8 wrap, mode 0644, no `O_EXCL`, no read-back compare, wrap in place, locked regenerates, review migrates, no link, exception words in the log, held passphrase ignored, the cause text naming the passphrase, a shared temporary name with an unlink first, no random token, a temporary file beside the key, the directory left behind, an empty file not named, no alias sweep, a sweep by directory, a sweep skipped, a PEM only when it comes first, a review that leaves a pending file, a sweep that trusts the entry's own stat, no identity check at the rename, the identity taken when the wrap starts and not when the file was read) each turn a named test red; one mutant survives because it is equivalent (a redundant `passphrase is not None`, kept for the type checker). Not measured: a real FAT/exFAT drive (the fallback is driven by a stand-in `PermissionError` from `os.link`); Windows hard links.

**Stated limits.** The custody keys' creation in `src/custody/signing.py` still writes then `chmod`s and has the same two windows, and the custody Ed25519 key is still a PKCS8 PEM (see the next lesson); it is another file's owner's to fix, and `src/reporting/evidence._create_new` is the model. A process killed mid-way can leave a file in `keys/.pending/` (and so the directory in the attestation's listing): a private copy of a key that never became the install's, or, between the link and the removal, a second name for the install's own key. When that key is the plaintext one (a store with no passphrase at creation), the first wrap under a passphrase removes the name by file identity: the third independent read found that it first left the plaintext key there for good, in a folder nothing sweeps; a second name for a key that was wrapped at creation stays, wrapped under the same passphrase. Nothing else sweeps `keys/.pending/` and the backups do not list it. `src/backup/merge.py` (about lines 6222 to 6230) checks `local.exists()` and later `os.replace`s the restored key over the path, so an export between the two creates a key that the restore then silently replaces, outside the guarantees above; it is not new here, it is another file's owner's, and it is a proposal. A backup restored onto an install with another passphrase brings the key wrapped as the source install wrapped it, and from then on an evidence export and every backup refuse with the cause until the file is moved aside; re-wrapping inside the restore (`src/backup/merge.py`) is a proposal, not built.
