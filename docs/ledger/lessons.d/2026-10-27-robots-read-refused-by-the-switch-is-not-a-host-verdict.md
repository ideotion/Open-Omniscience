## 2026-10-27 — A cache of "the host failed" must not record the operator's own refusal as the host's failure; ask of every catch-and-remember whether the failure could be ours (R297, delta read 2 of R293, L2)

**What was found.** `EthicalFetcher._get_robots` wrapped its robots.txt read in `except (requests.RequestException, FetchError)` and filed everything it caught as "cannot safely determine robots -> fail closed": `cause: unreachable`, a one-hour TTL, a failure counter, and a line in the persisted sidecar. The kill switch's own refusal is a `FetchFailed` (`"network kill switch is active -- collection stopped by operator"`), and a switch engaging while a request is in flight arrives as the socket guard's `AirplaneModeError(OSError)` wrapped in a `requests` error, so both were caught there. A Stop pressed between `fetch()`'s first switch check and the robots read of a host whose verdict was not cached (past the SSRF guard and the per-host lock, where a fetch can wait behind another request to the same host) was therefore recorded as the HOST being unreachable. MEASURED with the real fetcher, the law tracker and one Stop: zero requests, `RobotsUnavailable ... (unreachable)`, the law document stamped as checked, and the next pass (switch clear, a fresh fetcher reading the same sidecar) stamped it again without ever asking the host. The collector (`pipeline.py`) filed the same event as `ROBOTS_UNAVAILABLE`, a statement about the publisher's robots.txt that nobody had read.

**Rules.**
1. **A catch that REMEMBERS a failure (a cache entry, a back-off, a verdict, a persisted line) decides first whether the failure belongs to the thing being judged.** The switch's refusal and a request cut off by the switch belong to the operator. In `_get_robots` the test is the SWITCH (`_KILL.is_set()`), read after the failure, never a substring of the text: a refusal that is already a `FetchError` is re-raised as it is (it names the switch), and a requests error that coincides with the switch becomes that same `FetchFailed`, with no cause chained (`from None`, the module's idiom: the request error's words, a host and a URL, would travel in every traceback, and the sink sweep reads the chain as a finding). Nothing is cached or persisted, so the next fetch asks again. The same rule R293 gave the law tracker, applied to the layer under it; the two now agree on what a refusal is.
2. **Decide by the switch, and accept the cautious direction.** A real failure (a refused connection, a timeout, a redirect loop) that happens to coincide with a Stop is not cached either, so that host is asked once more on the next pass: one request, instead of an hour of a verdict nobody can tell from a real one; and a `FetchError` that is not the refusal is re-raised unchanged under the switch, neither relabelled nor cached (pinned, because a mutant that relabelled every error under the switch survived the first nine tests). A robots answer that WAS received (a 200, or a 403, followed by a Stop) is a real answer and stays cached: a 403 never reaches the catch at all, it is cached as `refused` with its failure counted and its sidecar line written (the independent read measured it; a test pins it); a `FetchFailed` whose WORDS name the switch while the switch is clear is the host's problem (a control pins each).
3. **Both entry points are pinned, because one guard can cover one and miss the other.** (a) the refusal at `_guarded_redirect_get` (Stop pressed before the read), driven through `fetch()` by pressing Stop inside the per-host lock, which is the window of the finding; (b) the switch engaging while the request is in flight, an OSError wrapped by requests. Fourteen mutants of `_get_robots` were run in an exported copy (an independent read wrote them; every one is red on the eleven tests): removing the guard fails 6 tests, handling only the `FetchError` 2, only the wrapped error 4, caching and persisting first and raising after 6 (caching in memory only, 5), a bare `raise` of every error 4, a guard that is always true 2, deciding by the message instead of the switch 4, re-raising a `FetchError` even with the switch clear 1, converting every error under the switch to the sentence 1, reading the switch before the request 3, raising `RobotsUnavailable` under the switch 6, the sentence for every error switch or not 3, and chaining the cause again 1. The consequence is pinned through the real law tracker: the time is given back on the Stop pass and the next pass reads robots.txt again.
4. **Effects to know.** `declared_sitemaps` (which already documents that the switch makes it raise `FetchFailed`) raises under a mid-read Stop instead of returning `[]` and caching; its one caller catches `FetchError`. The collector files a mid-fetch Stop as a fetch failure (offline) instead of `ROBOTS_UNAVAILABLE`. The refusal sentence now appears at five sites in `src/ingest/__init__.py`; a named constant or a `FetchFailed` subclass for the refusal is the sturdier follow-up (it would let `src/law/track.py` and `classify_fetch_failure` test one thing) and is left out here because it touches the four other sites.
5. **Not checked, stated.** The window is narrow (a Stop between two checks) and the entry it wrote lasted an hour, so the reach on a real corpus is small: the catch is real, the reach is not measured. No other `except` in `src/` catches `(requests.RequestException, FetchError)` to remember it (grepped), so this was the only home of THAT tuple. The same catch-and-remember shape lives elsewhere under a plain `except Exception` (the independent read's S1, below), which the grep could not see.
6. **Routed with this PR, stated and not changed (the WAL deadline sweep, R309 S3): `src/law/coverage.py` counts `session.query(LawDocument).count()`, a bare `count(*)` that the statement deadline cannot stop.** It runs inside the all-diagnostics `law-coverage.json` member's deadline, but a statement that is a single SQLite opcode is never asked whether the deadline has passed. It is left as it is because the function runs a FILTERED count over the same table first (`url ILIKE '%.pdf'`, which loops and which the deadline does stop), so the bare count can only overrun after a count that was itself cut off, and it costs a fraction of that one. MEASURED on a synthetic file with the app's `law_documents` schema (plain stdlib SQLite 3.45.1, WARM cache, the progress handler asked every 20,000 opcodes, a real deadline of a millionth of a second): 20,000 rows with two 20,000-byte text columns (783 MiB) the bare count takes 0.3 ms and the handler is asked 0 times, the filtered count takes 3 ms, is asked 6 times and is stopped; 200,000 rows with two 1,000-byte columns (795 MiB) the bare count takes 1.5 ms (asked 0 times) and the filtered one 46 ms (asked 61 times, stopped), while `count(1)` is 4.9 ms and `count(id)` 10 ms and both stop. NOT measured: a cold cache, the SQLCipher engine, or a table above 200,000 rows. A respelled `count(id)` would need a helper of its own to be tested, because the filtered count in the same function raises the timeout first and hides whether the bare one is stoppable; that cost buys nothing while the filtered count precedes it. Revisit if a statement is ever added before the filtered one, or if the filtered count is removed.
7. **Found by the independent read, not changed here (S1, routed): the first-run preflight files the switch's refusal as the host's robots verdict and persists it.** `src/monitoring/preflight.py` (`_check_one`, `preflight_sources`) and `src/monitoring/feed_preflight.py` (`_check_host_robots`, the market sample) catch `Exception`, record `robots: "unreachable"` with the refusal's words, and check only the job's own cancel flag, never the switch. Reproduced twice (by the reader and again by me) with a real fetcher, the switch engaged and two sources whose metadata said `robots_allowed=True`: the sweep returns `complete: True` with both sources unreachable, writes the log that `has_run_before()` reads (so the automatic preflight never runs again), and overwrites both `robots_allowed` values with `None`. The same class as this PR with a longer-lived effect (known verdicts erased); no code was found that cancels the preflight job when Stop is pressed (a grep, not a proof). The fix is to treat the switch like the cancel flag before and after each host so the run ends incomplete, writes no log and rolls back.
