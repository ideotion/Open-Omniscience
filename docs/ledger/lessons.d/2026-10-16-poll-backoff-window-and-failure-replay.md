## 2026-10-16 — a backoff that counts refusals in a window as long as the refusal itself never engages

**(1) The client-wide poll ladder (`_loadFactor`, app-core.js) counts 429/503 inside a 60 s window, and a statement-deadline refusal IS 60 s long.** Every `/api/insights/trending-windows` 503 had left the window before the next one arrived, so the factor stayed 1 and Home's 15 s tick asked the same question 533 times in one session (362 answered 503 at the deadline, 75% of the session's wall clock). A window must be longer than the thing it counts. The fix is a per-call memory in `app-home.js` (`homeTrendsDue` / `homeTrendsNoteResult`): the gap doubles from the tick after each consecutive deadline refusal or partial answer, resets on a full answer, and has a stated ceiling (what it protects: how long the strip may go without even a try). A replayed partial answer counts as partial the same way (the outcome depends on `partial` alone, never on `replayed`). It is driven with a fake clock in `tests/home_trends_backoff_node_test.js`, and the wiring (the call is `{polled: true}`, the tick asks the schedule first, the catch hands over `e.status`) is pinned from the source because that is what a refactor loses first.

**(2) Single-flight shares ONE compute between concurrent identical calls; it does nothing for the call that arrives a moment after a FAILED one.** `_deadlined(degraded_replay=True)` keeps a hard-deadline 503 or a `partial: true` payload for `OO_DEGRADED_REPLAY_S` (30 s, two ticks) in a store of its own and answers the next calls from it (the same 503 with a `Retry-After` of what is left; the partial still `partial: true` with its caveat, plus `replayed: true` and the age of the original; a partial replayed inside the window is the one deliberate difference from "a partial is never cached", because a 20 s partial recomputed on every 15 s tick is still a storm). The invariants that make it safe to add: it is a separate store from `_read_cache` (a partial in the normal cache was served as the answer for the whole 120 s TTL), a full answer in the normal cache always wins, only the two whole-corpus reads that are polled or opened by a click opt in (trending-windows and the map, pinned by an AST scan, so widening it is a decision), and `on_timeout` payloads are not failures to replay.

**(3) A hold that lives only in memory is forgotten by a restart, and a restart is exactly when the same scan is started again.** The stop of a rollup build at DuckDB's limit (1,004 MB, no offload for an encrypted corpus, so the limit is a wall) is kept in `rollup_stopped.json` (`analytics/rollup_hold.py`: a reason code, the stage and numbers, never the engine's text) and read once per process. Its release rule is NOT the epoch: `/api/insights/reindex-all` bumps the epoch on every 300-article call, and a release per bump started the 15-minute scan again. The wall moves with the limit and with the corpus' size, so the hold is released when the limit grew or when the corpus has at least 5% fewer mentions than at the stop (a stated judgement, not a measurement: a build that does not fit says only that it did not fit; a drop of one mention must not start a 15-minute scan; the count is taken only when the epoch moved, not before the rebuild TTL and never more than once a minute), or when offload became allowed for a stop recorded under a passphrase. A prune that keeps the count at or above the stop's is not seen, and the record says so. A boot step that declines now carries the reason in its own row (`detail`, codes and numbers; a raised step carries the exception's class only), because the reason lived in another report's block that a later unrelated check had overwritten.

**(4) A kept stop is evidence about the code that stopped, not about the machine for ever.** The record names the app version and a `BUILD_CODE_VERSION` (bumped by whoever changes the build's memory behaviour) and is released at the next boot if either differs, or if it carries neither: without that, a stop recorded before a fix keeps the rollup off after the upgrade until the limit grows, and "fewer mentions than at the stop" rarely fires because mentions only grow.

**(5) A deadline cannot be nested to give one slow item a sub-budget.** `statement_deadline`'s exit disarms the connection's progress handler, which is also the OUTER block's. The card audit therefore runs a producer known to spend the whole budget (`rising_now`) after the others (`_RUN_LAST`, results and the dedup belt kept in registration order) instead of giving it a nested limit; a slow producer not named there still starves the ones after it, and the summary counts `skipped-budget`.

**(6) A route with no deadline, no cache and no rollup is invisible until someone opens it.** `/api/insights/map` ran two unindexed scans of the window's mentions on every open; it now has the statement deadline, a cache keyed on the corpus epoch and the keyword-filter settings (so a re-index, prune, restore or a newly excluded keyword never serves the old map), and a budget after which the city scan is not started and the payload says `partial` and `skipped: ["cities"]`. A client must not read a list the server did not compute as an empty one (app-map.js shows the caveat, not "No data").

**(7) A partial answer that holds nothing is "not computed", not "nothing here", and an error that never got an answer says nothing about the scan.** `trending_windows(live_budget_s=)` reads the shortest window first (a budget below the longer windows' cost still keeps what it paid for) and leaves an unfinished window out; when none finished, `windows` is `[]` and both panels must print the caveat, not their empty state (`app-home.js`, `app-corpus.js`). The Home back-off counts a 503 or a partial answer only: a `fetch` that rejected (a restart) or a render exception has no HTTP status and doubled the gap for minutes after the server was back. The partial caveat names no cause that can be false (a country-filtered read or a rollup miss is partial with the rollup built): "the rollup is not serving this request".
