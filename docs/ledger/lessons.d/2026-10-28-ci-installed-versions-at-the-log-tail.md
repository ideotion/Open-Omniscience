## 2026-10-28 — the installed versions are printed at the END of a CI job, by a step that runs on red: an install prints them at the head of a log that a tail-limited reader never reaches

**What was found (R349, R364).** Finding the cause of the `test_page_reading` red took a comparison of installed packages between a green and a red job, and the packages are listed by the install step, near the head of a log that runs to several thousand. The one log reader available in the agent sessions (`get_job_logs`) returns the last 5000 lines, and the blob host that serves a whole log answers 403 through the proxy, so the install output of the long `test` job could not be read at all. The comparison was rebuilt from three sibling jobs that were short enough to have a complete log (86 to 104 packages each) plus PyPI's upload time for the one package that differed (pytest 9.2.0, 21:30 UTC on 27 Oct) and a local reproduction under both versions. That worked, but only because those siblings existed; for the next moving part they may not.

**The rule.** A CI job whose red can come from the environment ends with a step that prints the environment, and that step says `if: always()`: without the condition a red pytest step skips it, and the red run is the one that needs it. It goes straight after the pytest step, before any step that installs a scanner of its own (bandit and pip-audit in `test`), so the list is the one the tests ran in. It uses `python -m pip list --format=freeze` (one `name==version` line per package; `pip freeze` prints the editable install as a `-e` line carrying the repository URL and the commit (measured by the reviewer on this repository with pip 24.0), which changes on every run, and leaves pip itself out of the list) and also writes to `$GITHUB_STEP_SUMMARY`, where the list survives the log. The header line carries the Python patch version, the runner image and the kernel, the other things R349 had to diff.

**What it costs, and what it does not prove.** MEASURED on run 40638055096 (head `417f0f11f`, counted from each job's log): the `test` job's step prints 109 packages in 113 lines and 2,002 B, 130 lines and 6,568 B with the echo of the step's own script and the runner's 29-byte timestamp on each line; Core-only prints 87 packages in 91 lines and 1,616 B, 107 lines and about 5.5 KB in all. On a GREEN `test` run the step's first line is the 3,502nd from the end of the log, because 3,389 lines follow it (3,233 of them bandit warnings, 2,823 "Test in comment" and 410 "nosec encountered"): a tail of 1,500 lines misses it and 5,000 reaches it. On a red pytest step the later mypy, bandit and pip-audit steps are skipped, so it sits near the end (only the post steps, about 35 lines, are INFERRED to follow it; no red run has been measured). It lists the packages; it does not say which of them moved. The comparison between two runs is still made by a person or a script, and it covers only the two jobs R364 names, `test` and Core-only. The `portability` job (macOS, an observation lane with `continue-on-error`) runs the whole suite as well and is not covered; the other lanes install less and run a named subset. The header line already earned its place: the two jobs of that one run were on different runner images and Python patch versions (3.13.16 on image 20261023.334.3 against 3.13.17 on 20261026.354.1).

**Pinned by** `tests/test_ci_installed_versions_step.py`: the step exists once in each of the two jobs, says `if: always()`, runs the freeze command, writes the summary and sits straight after the last pytest step; eight mutants per job (condition removed or `failure()`, `pip freeze`, a redirect instead of `tee`, no summary, step missing, step before pytest, a step between) are each named by the checker.
