## 2026-11-01 — an alternate follows the document it was recorded against, and "the same alternate" is the same ROW, not the same identity text (R403 follow-on; PR #1683)

**What was found.** PR #1682 left one limit in its notes: an alternate's recorded spelling is converted to the store's form before anything compares it. In a backup that holds ONE document under two spellings (`gbr` and `gb` in an alpha-2 store, which the restore keeps as two rows), an alternate captured against `gbr` was converted to `gb` and placed on the other document; the restore and the app agreed with each other only because both converted first. Closing that moved three things at once, and each was found by an independent read of the previous attempt rather than by the author: the placement order, the conversion, and the duplicate check.

**The rule.** An identity FOLLOWS ITS DOCUMENT. (1) The conversion toward the store's form (`convert_alternate_countries`) leaves a law identity as recorded when the staged copy still holds that exact spelling at that `document_url`; only the restore asks for this (`keep_with_unconverted_document=True`), the migration keeps converting, and the count is reported as `kept_with_document` only when nonzero. (2) Placement is ONE ordering in the restore (`_alternate_local_match`) and the app (`alternates._local_row_id`): the spelling the identity recorded, then the store's form, then the oldest document; a padded recorded spelling is a candidate, a non-text or empty jurisdiction counts as absent and never raises. (3) "The same alternate" is `(origin, fields_json, local row)`, never the identity text: once an identity can name two documents, a text check either drops an alternate that belongs on a sibling or stores one twice depending on which backup was restored first (tested both orders: BA equals AB).

**Traps this met.** (a) The first duplicate check compared the identity keyed through `law_jurisdiction_key`: order-dependent against the capture, wrong for a padded spelling, and it collapsed siblings. Replaced by the row comparison; the set of held rows is read ONCE per restore (`main.metadata_alternates WHERE table_name = ? AND local_row_id IS NOT NULL`) and extended after each insert, because a per-alternate query was quadratic. (b) The capture (`_capture_alternates`) had the same text-only check, so a carried alternate was captured again by the next restore; it now also compares on the row, through an indexed temp table (`temp.alt_kept`, law scope only, dropped in a `finally`). The first version put an `OR` into the existing NOT EXISTS and was quadratic; with the indexed table 10,000 x 10,000 alternates take 0.61 s against the parent's 0.59 s, and the non-law SQL is byte-identical to the parent. (c) The tests write a carried alternate in the exporter's MINIFIED JSON (`json_object` writes no spaces); a fixture with a space after each separator compared unequal to what a capture writes, so a duplicate test passed against nothing and a mutant survived until the fixture was fixed. (d) New SQL assembled with an f-string carries `# nosec B608 - <reason>` on the FIRST line of the expression, as in #1682 trap (g); bandit cannot be run in this sandbox, so a red `test` job is read from its bandit step first.

**A recipe fact, INFERRED, not measured twice.** The SQLite 3.45.1 run (`PYTHONPATH=<tree>:<venv site-packages> /usr/bin/python3 -m pytest`) fails `tests/test_database_verify.py::test_fts5_running_out_of_memory_on_the_real_driver_is_unchecked_never_damage` with `ModuleNotFoundError`: that test runs a child as `python -I`, which ignores PYTHONPATH, so the child cannot import SQLAlchemy. CI's Python has the dependencies installed and passes it. Inferred from the test's `subprocess.run([sys.executable, "-I", ...])`, accepted by the coordinator as a recipe artifact; a test that spawns an isolated child cannot be judged by that recipe.

**Pinned by** `tests/test_restore_law_jurisdiction_canonical.py` (349 tests; 495 across the seven alternate, country and restore files, run on SQLite 3.45.1 and 3.53.1) and 38 mutants of the conversion, both placement orderings, the row check, the read-once set and the capture's second check, all killed.

**Stated limits.** The same backup restored before AND after the upgrade stores the alternate twice (the legacy copy on `gb`, the new one on `gbr`; it needs a backup holding siblings). A legacy identity with no jurisdiction, or a non-text one, over siblings: the restore picks the oldest revision, the app the newest summary (unchanged). A stale `local_row_id` after a reused rowid could read as a duplicate, but no code path deletes law rows today. A real backup of a real install was not restored.
