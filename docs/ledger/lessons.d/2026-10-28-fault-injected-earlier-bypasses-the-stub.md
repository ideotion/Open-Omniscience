## 2026-10-28 — A fault injected at an earlier step fails the run before the stub under test is reached: the second pass of the vacuous-fault audit (parent sweep R385, follow-through of #1636)

**What the first pass left open, measured.** `2026-10-28-vacuous-fault-reach-audit.md` stated three shapes it did not cover. Each was run the same way (a recorder before every `raise`, one test file at a time, the file restored, the tests that reached none of their stubs listed, each read by hand).
1. `Mock(side_effect=Exc)`: only `tests/test_duckduckgo.py` uses an exception side effect (3 sites). Both failure tests are sound: the stub is the first statement of the code under test, and the mutant "the outer `except Exception` re-raises" turns `test_discover_rss_feeds_failure` red.
2. Multi-line `(_ for _ in ()).throw(...)`: 4 tests (`test_quarantine_job`, `test_stats_fetch`, `test_stats_owid_fetch`, `test_stats_jsonstat_fetch`). All four are `AssertionError("... must not run/reached")` tripwires, so zero raises is the right count.
3. Fakes held as classes, dict values or attributes (any `raise` inside a non-test def that a test references other than as a direct call or a call argument): 1,036 tests reference one; 291 reached none of their non-guard raises. Read by hand: 36 chosen by a failure claim in the title, about 20 more by looking, and about 230 scanned by title only. Nearly all are correct and for the same four reasons as before: the fake has a failure MODE the test does not select (`_FakeOllama(unavailable=...)`, `_Rows(boom=...)`, `_Scripted([BaseException])`), the raise is in a helper another test installs, the stub is a tripwire (`Hostile.__class__` raises only if the code regresses to `a.__class__`), or the test was skipped in this environment (OpenTimestamps). One was real and one is a hardening.

**The real one: `test_a_state_save_that_fails_after_a_download_failure_leaves_nothing_to_chain` (`tests/test_osm_exception_texts.py`).** It wants a download whose TRANSFER fails with an error naming the passphrase, and then a state save that fails too (a full disk). It patched `_save` to raise on every call, but `_download` calls `_save()` once INSIDE its `try` (to record "downloading") before it reads the transfer. The first save failed on the disk, that OSError became the download's failure, and `_Resp.iter_content`, the line that raises the secret-bearing error, was never reached. Measured: `res.error` was `[Errno 28] No space left on device`, with 2 saves. So `HELD not in res.error`, `HELD not in caplog.text` and the rest were true because the passphrase never entered the run. Two source mutants stayed green under the old test and went red under the new one: `entry.error = str(exc)` in place of `record_text(exc)`, and the failure logged with its own text (`_LOG.warning(f"... {failure}")`). The stated mutation target (the save back inside the `except` block) was red under both, which is why the test looked sound. Fixed by letting the first save through and failing only the later ones, and asserting both that exactly two saves happened and that the transfer's own words (`the transfer said`) are in `res.error`.

**Hardening, no distinguishing mutant.** `test_releasing_never_raises_on_a_broken_session` gave `release_idle_connection` a session whose `in_transaction` raises, but the double lacked `info`, which the helper reads before it asks `in_transaction`, so an `AttributeError` took the same `except` and the stub was never asked. The test still goes red when that `except` re-raises, with or without the change; the double now carries the attributes read before the question and asserts it was asked, so it says what it means.

**Rule.** (1) When a test injects two faults, or a fault plus a secret, ORDER matters: a fault patched onto a step that runs earlier than the code path that carries the interesting content ends the run first, and every assertion that the content is absent is true for free. Assert that the later stage was reached (a count, the text only it can produce) next to the "absent" assertions. (2) A mutant that stays green under a test's own stated mutation target is not a reason to trust it: try the neighbouring regressions (the stored text, the logged text), because the stated target is the one the author already had in mind when the test was written. (3) Reading by hand worked at this rate: about one in fifty unreached tests, and none from reading the stub; every real one came from asking what the test claimed to inject and tracing whether that line could run given the other patches.

**Item 3 of the guard's stated limits, measured.** A whole-mention that proves nothing about size (`assert seen is not None`) clears `tests/test_loops_over_callback_lists_assert_non_empty.py`. Treating that as no mention, the guard flags zero tests in `tests/` today, so it stays as stated.

**Not covered.** The 230 title-only tests; stubs that raise inside lambdas passed through helper functions rather than assigned; parametrized tests are still folded to one per function.
