## 2026-10-28 — "diff the package versions first" is one command: two Installed-versions blocks, compared the same way every time, with the environment line read as half the answer

**What was found (R349, R364, R380 item 3; PR #1625).** R349 said to diff the package versions of a green job and a red one before anything else, and R364 made the list readable (it is printed at the END of the `test` and Core-only jobs, on red as well as green). What was still missing was the diff itself: by eye it is two lists of 87 to 109 lines, and a by-eye pass reads "nothing moved" as easily as it finds a pytest minor. `scripts/diff_installed_versions.py OLD NEW` reads the two blocks (each argument a log file or `-` for standard input; the raw log with the runner's timestamps, the step summary, or the JSON that `get_job_logs` returns) and prints what was changed, added and removed, with pip's own name rule (PEP 503: `typing_extensions` is `typing-extensions`, `Jinja2` is `jinja2`). Exit 0 identical, 1 different, 2 not comparable. Standard library only; no network; no cap on the list.

**MEASURED, on two real Core-only job tails** (job 122649746920 of run 40638055096, 06:52 UTC, and job 122725010413 of run 40661391305, 10:21 UTC, both saved from `get_job_logs`): 87 packages each, `0 changed, 0 added, 0 removed, 87 unchanged`, and the environment line differs in all three fields: `python 3.13.17 -> 3.13.16; runner image ubuntu24 20261026.354.1 -> ubuntu24 20261023.334.3; kernel Linux 7.0.0-1017-azure -> Linux 6.17.0-1022-azure`; exit 1. Two things follow. The package list alone would have said "identical" while the Python patch version, the runner image and the kernel had all moved, which is why the header line the step prints is compared first and reported on its own line. And the LATER run was on the OLDER image (20261023 at 10:21, 20261026 at 06:52): the runner pool serves more than one image at a time, so "the red run is on a newer image" is not something to assume from the order of the runs; read it from the line. A copy of the old log with `pytest` set back to 9.1.0, `wrapt` removed and `requests` raised to 2.34.3 came out as `2 changed, 1 added, 0 removed, 84 unchanged` with each named (a hand-made change to a real log, to see the three kinds reported; not a CI result).

**The rule.** The comparison REFUSES TO GUESS, because a wrong comparison reads as an answer: a log with no `### Installed versions` line (the reader returned only the last N lines and started after it, or the job is one that does not print it), a block cut off before its closing fence, a heading with no opening fence, an empty block, a block whose lines are not `name==version`, two blocks in one log and a JSON object without `logs_content` are each an error that names OLD or NEW and what was seen, exit 2, no report. A missing block would otherwise compare as "every package was removed". When both logs are bad, both errors are printed. A line in a good block that is not `name==version` and a name listed twice are listed in the report, not dropped (the first listing is kept and said so). The heading line is matched whole after the runner's timestamp is removed, so the runner's echo of the step's own shell (`echo "### Installed versions"` in ANSI colour, a few lines above the real output) is not taken for it.

**What it does not prove.** It says which pins differ and what moved in the environment; it does not say which of them caused a failure (that stays the reader's call, and R349's own method of installing the suspect under both versions stays the test). It compares what `pip list` reports for the job it was given, not what the code imported and not the packages of the other jobs; the step is printed in the `test` and Core-only jobs only (R364), so the other lanes cannot be compared with it. A reader that returns only the last N lines must reach the heading: `tail_lines=130` reached the Core-only heading on both logs above (the returned text began six lines before it), and in the `test` job the heading is the 3,502nd line from the end of a green log (see the R364 lesson).

**Pinned by** `tests/test_diff_installed_versions.py`: the block read from a timestamped job log with the coloured echo above it, from the plain summary and from the JSON wrapper; every refusal above (each names the log); changed, added, removed and unchanged under the name rule, the environment line field by field, and no cap on 500 changes; the exit statuses and the usage line; and a drift guard that RUNS the `run` text of the real `Installed versions` step of both jobs in `.github/workflows/ci.yml` under bash with a stub `python` and a temporary `GITHUB_STEP_SUMMARY`, then reads its stdout and the summary with the script, so a change to the step that the script cannot read (the heading, the fences, the freeze format, the header line) fails there. Seven mutants of the script and four of the step were each seen to fail a test.
