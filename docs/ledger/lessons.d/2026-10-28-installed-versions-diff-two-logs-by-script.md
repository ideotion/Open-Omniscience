## 2026-10-28 — "diff the package versions first" is one command: two Installed-versions blocks, compared the same way every time, with the environment line read as half the answer

**What was found (R349, R364, R380 item 3; PR #1626).** R349 said to diff the package versions of a green job and a red one before anything else, and R364 made the list readable (the `test` and Core-only jobs print it straight after the test run, on red as well as green: among the last lines of a red job, 3,500 lines from the end of a green `test` job). What was still missing was the diff itself: by eye it is two lists of 87 to 109 lines, and a by-eye pass reads "nothing moved" as easily as it finds a pytest minor. `scripts/diff_installed_versions.py OLD NEW` reads the two blocks (each argument a log file or `-` for standard input; the raw log with the runner's timestamps, the step summary, or the JSON that `get_job_logs` returns) and prints what was changed, added and removed, with pip's own name rule (PEP 503: `typing_extensions` is `typing-extensions`, `Jinja2` is `jinja2`, runs of `-`, `_` and `.` alike). Exit 0 identical, 1 different, 2 not comparable. Standard library only (a test reads the script's imports); no network; no cap on the list.

**MEASURED, on two real Core-only job tails** (job 122649746920 of run 40638055096, 06:52 UTC, and job 122725010413 of run 40661391305, 10:21 UTC, both from `get_job_logs`; the block and the lines around it are committed unedited as `tests/fixtures/ci_logs/core-only-run-40638055096.txt` and `core-only-run-40661391305.txt`, and compared by `tests/test_diff_installed_versions.py`): 87 packages each, `0 changed, 0 added, 0 removed, 87 unchanged`, and the environment line differs in all three fields: `python 3.13.17 -> 3.13.16; runner image ubuntu24 20261026.354.1 -> ubuntu24 20261023.334.3; kernel Linux 7.0.0-1017-azure -> Linux 6.17.0-1022-azure`; exit 1. Two things follow. The package list alone would have said "identical" while the Python patch version, the runner image and the kernel had all moved, which is why the header line the step prints is compared first and reported on its own line. And the LATER run was on the OLDER image (20261023 at 10:21, 20261026 at 06:52), so the order of two runs does not tell which image each got; the R364 lesson already recorded the same thing inside one run (the `test` and Core-only jobs of run 40638055096 overlapped for 49 minutes and sat on different images and Python patch versions), which is the only evidence here that the runner pool serves more than one image at a time. A copy of the old tail with `pytest` set back to 9.1.0, `wrapt` removed and `requests` raised to 2.34.3 (made in the test, not a CI result) comes out as `2 changed, 1 added, 0 removed, 84 unchanged` with each named. `get_job_logs` with `tail_lines=130` reached the Core-only heading on both logs (the returned text began six lines before it); that figure was observed once and is not reproducible from the repository.

**The rule.** The comparison REFUSES TO GUESS, because a wrong comparison reads as an answer: a log with no `### Installed versions` line (the reader returned only the last N lines and started after it, or the job is one that does not print it; when other lines contain the text, as the runner's echo of the step's script does, the error says so and quotes the first), a heading with no opening fence, a block with no closing fence before the log ends **or before the next step starts** (a `##[` line or `Post job cleanup.`: the step runs `bash -e` without `pipefail`, so a `pip list` that dies inside its braces still leaves the step green and the block short, and a later step that prints a bare fence must not be taken for its end), an empty block, a block with no `name==version` line, two blocks in one log, JSON without a string `logs_content`, an unreadable path or a directory and closed standard input are each an error that names OLD or NEW and what was seen, exit 2, no report. A missing block would otherwise compare as "every package was removed". When both logs are bad, both errors are printed, and a crash anywhere (reading or comparing) is exit 2 with the exception named, never exit 1, which is the status for "different". A line in a good block that is not `name==version`, and a name listed twice, are listed in the report and make the answer "different" (`not compared:` lines, exit 1) unless both sides carry the very same unparsed lines: the status 0 means no difference in what could be compared and nothing that could not. Bytes that are not UTF-8 are replaced on both input routes (a log carries arbitrary test output, and strictly decoded standard input used to raise), a byte-order mark before the heading or before the first timestamp is removed, lines are split on `\n` alone so a reported line number is the one `grep -n` shows, and the heading is matched whole after the timestamp is removed.

**What it does not prove.** It says which pins differ and what moved in the environment; it does not say which of them caused a failure (that stays the reader's call, and R349's own method of installing the suspect under both versions stays the test). It compares what `pip list --format=freeze` reports for the job it was given, not what the code imported and not the packages of the other jobs; the step is printed in the `test` and Core-only jobs only (R364), so the other lanes cannot be compared with it. A reader that returns only the last N lines must reach the heading: in the `test` job of a green run it is the 3,502nd line from the end (see the R364 lesson). A log prefixed on every line in some other way (the tab-separated job and step names that `gh run view --log` is said to add; not checked here) is refused with the first such line quoted, not read. A line that is not in `pip list --format=freeze`'s shape (`b @ file:///...`) is never compared as a package.

**Pinned by** `tests/test_diff_installed_versions.py` (100 tests): the block read from a timestamped job log with the coloured echo above it, from the plain summary and from the JSON wrapper, each with a leading mark and with `\r\n`; every refusal above, each checked to start with the log's label; changed, added, removed and unchanged under the name rule, the environment line field by field and as a whole when it is not in the step's shape, and no cap on 500 changes; the exit statuses, both input routes with bytes that are not UTF-8, closed input, and a crash in either stage; and a drift guard that RUNS the `run` text of the real `Installed versions` step of both jobs in `.github/workflows/ci.yml` under bash with a stub `python` and a temporary `GITHUB_STEP_SUMMARY`, then reads its stdout and the summary with the script, so a change to the step that the script cannot read (the heading, the fences, the freeze format, the header line) fails there.
