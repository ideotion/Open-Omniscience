## 2026-10-17 — `clean` says the teardown ran, not that the log was written back: `Engine.dispose()` leaves the whole `-wal` with ONE connection still checked out

**What was found.** The 10-10 session of the field machine ended `clean` (the lifespan's teardown ran to its last line) and the next boot found a 1,409,086,256-byte `-wal`; 90.8 s of the 92.1 s unlock was its write-back. `dispose_engine()` was `engine.dispose()` and nothing else. SQLite writes the log back into the database and removes it only when the LAST connection on the file closes, and `dispose()` closes the connections that are IN the pool. MEASURED (SQLite 3.45.1 and sqlcipher3 3.51.1, the app's own engine, `connect()` and `dispose_engine()`, a reader pinning a 300 MiB log, plain and encrypted): every connection back in the pool, the log gone (3.3 s plain, 2.3 s encrypted); one connection still checked out, idle or inside a read, 100 % of the log left (314,772,152 B plain, 315,919,664 B encrypted), `dispose()` taking 0.00 s. A busy collector is that case: the scheduler's stop gives up after 10 s while a pass is mid-fetch or mid-write.

**The rules.**
1. **`Engine.dispose()` is not "close the database".** It closes the idle connections of the pool; the write-back belongs to whoever closes the last connection on the file, and a checked-out connection is not theirs to close. Anything that must leave the file clean at exit checkpoints it explicitly BEFORE the disposal.
2. **The explicit step never waits for a reader and never takes a time cap.** `PRAGMA busy_timeout = 0` first, then `PRAGMA wal_checkpoint(TRUNCATE)` through `execute` (which releases the GIL, where sqlcipher3's `close()` holds it for the whole checkpoint it runs on the last connection). With a straggler idle it empties the log (2.24 s for 300 MiB, encrypted); with a straggler inside a read it returns `(busy 1, ...)` at once and the log stays. A wait would hold the WAL write lock and a number for it would be invented before any bundle says how often a straggler is inside a read. No cap on the step itself: the next open pays the same time, and a kill in the middle is safe (SQLite recovers from the start; never worse than skipping except for the wait at exit).
3. **Do it from a connection of its own, not a pool checkout.** A checkout waits `pool_timeout` behind the very workers that are the reason for the step, and the pool's creator takes a shared level of the library lock. Open it through the factory, and only for a store this process opened (`locked_state` is `unlocked-*` and the file exists): opening a locked store fails with the key absent, opening a missing one creates it.
4. **A `clean` sentinel is a statement about the teardown, so record the log it left.** The sentinel keeps `clean` meaning "ran to its end" and carries, from the disposal step, `wal_bytes_after_dispose` (0 is a fact, `None` plus a reason is unreadable), `connections_checked_out_at_dispose` (the pool's own count read just before; `None` plus a reason when the pool has none) and `shutdown_checkpoint` (`done`, `busy`, `failed`, `skipped`); the previous-session text says "the -wal was LEFT ... N bytes" whenever it is more than 0 and stays silent for a sentinel from a build that did not record it. `shutdown_began_at` is stamped once, on the first phase, because the last phase and the end were the same second and the teardown's duration was unreadable.
5. **A test that builds its own engine must put the file in WAL mode itself.** The app sets `journal_mode=WAL` in `session.py`'s connect event; an engine built in a test has no such event, and a reader then blocks the writer ("database is locked" after the factory's 30 s), which looked like a hang of the whole file.
