## 2026-10-17 — `clean` says the teardown ran, not that the log was written back: `Engine.dispose()` leaves the whole `-wal` with ONE connection still checked out

**What was found.** The 10-10 session of the field machine ended `clean` (the lifespan's teardown ran to its last line) and the next boot found a 1,409,086,256-byte `-wal`; 90.8 s of the 92.1 s unlock was its write-back. `dispose_engine()` was `engine.dispose()` and nothing else. SQLite writes the log back into the database and removes it only when the LAST connection on the file closes, and `dispose()` closes the connections that are IN the pool. MEASURED (SQLite 3.45.1 plain; sqlcipher3 0.6.2, which carries SQLite 3.51.1 and SQLCipher 4.12.0, encrypted; the app's own engine, `connect()` and `dispose_engine()`, a reader pinning a 300 MiB log): every connection back in the pool, the log gone (3.3 s plain, 2.3 s encrypted); one connection still checked out, idle or inside a read, 100 % of the log left (314,772,152 B plain, 315,919,664 B encrypted), `dispose()` taking 0.00 s. A busy collector is that case: the scheduler's stop gives up after 10 s while a pass is mid-fetch or mid-write.

**The rules.**
1. **`Engine.dispose()` is not "close the database".** It closes the idle connections of the pool; the write-back belongs to whoever closes the last connection on the file, and a checked-out connection is not theirs to close. Anything that must leave the file clean at exit checkpoints it explicitly BEFORE the disposal.
2. **The explicit step never waits for a reader and never takes a time cap.** `PRAGMA busy_timeout = 0` first, then `PRAGMA wal_checkpoint(TRUNCATE)` through `execute` (which releases the GIL, where sqlcipher3's `close()` holds it for the whole checkpoint it runs on the last connection). With a straggler idle it empties the log (2.24 s for 300 MiB, encrypted). With a straggler INSIDE a read the answer is `busy`, in one of two shapes that depend on where the reader's snapshot lies (26 Oct, plain store): a snapshot OLDER than every frame gives `(1, n, 3)` at once with nothing copied (214 MB of log, 0.00 s); a snapshot NEWER than the frames, the common shape of a pass that began its read after the writes, makes TRUNCATE copy every frame first (`(1, n, n)`, 214 MB in 1.1 to 1.4 s) and only then find the reader, so the contents are in the database and the answer is still `busy`, the file keeps its size, and the reader's close as the last connection removes it (107 MB: 0.07 s). `busy` is also what a writer caught mid-write or another checkpoint still on the checkpoint lock gives (the last number is then -1). So `busy` does not say "nothing was written back": the record carries whether every frame was copied (`copied`), and the step does not wait, because a number for the wait would be invented before any bundle says how often a straggler is inside a read. No cap on the step itself: the next open pays the same time, and a kill in the middle is safe (SQLite recovers from the start; not measured: that the recovery copies a left log a second time).
3. **Do it from a connection of its own, not a pool checkout, and hold the swap lock across all of it.** A checkout waits `pool_timeout` behind the very workers that are the reason for the step. Open it through the factory, and only for a store this process opened (`locked_state` is `unlocked-*` and the file exists): opening a locked store fails with the key absent, opening a missing one creates it. The connection is raw, so the pool's stamp never reaches it and nothing refuses it: a restore or repair swap that lands between its open and its close would have this close, as the last connection on the OLD file, remove the `-wal` and `-shm` BY NAME, names that by then belong to the new file. So the whole step (open, checkpoint, close) runs under the library lock's shared level (`library_generation.connecting()`): a swap that arrives mid-step waits for it up to its own bound and then refuses with the file unswitched, and a step that arrives mid-swap waits for the swap. A raw connection to a file that swaps is a connection that takes the same lock the pool's creator takes.
4. **A `clean` sentinel is a statement about the teardown, so record the log it left, as ONE member with codes.** The sentinel keeps `clean` meaning "ran to its end" and carries, from the disposal step, one `dispose` record: `wal` (the log's bytes read after the disposal; 0 is a fact, `unreadable` is a code), `out` (the pool's own count of checked-out connections read just before; `earlier`, `unknown` or `unasked` when it has none) and `step` (`done`, `busy`, `copied`, `failed`, `locked`, `fresh`, `no db`, `not run`), with the words for each code in the reader (the precedent of `died_into_phase`'s reasons); the report adds the teardown's seconds, computed from timestamps it already holds. The reason for codes rather than sentences: every member of the session-forensics report is paid out of a 2,415 B room above the diagnostics floor, a member joins `HEADROOM_MEMBERS` in the commit that adds it with its worst case built by the real code in `tests/test_session_forensics_budget.py`, and the first version of this record (a `why` object, seven members) measured 253 B against 42 B free. The codes are seven characters at most for the same reason, and with the typed `crashing_thread_kind` estimate replaced by its measured worst the room is spent to the byte. A `0` count after a second disposal would be a lie: `dispose_engine` remembers that an earlier disposal replaced the pool (connections checked out then belong to the orphaned old pool and stay open when returned) and says `earlier`, never `0`.
5. **A death inside the longest teardown step has its own phase.** The step can take about 90 s and a service manager's default SIGKILL arrives at about 90 s, so the sentinel is stamped `writing-back` before it and a death there reads `unclean-end-during-write-back`, not the earlier `shutting-down`. The text under a verdict that is not `clean` does not say "'clean' above". `shutdown_began_at` is stamped once, on the first phase, because the last phase and the end were the same second and the teardown's duration was unreadable.
6. **The step and the record read the same file.** Both come from the creator's own path string (`session.DB_FILE`), not from the engine URL (SQLAlchemy decodes `%` escapes and cuts at `?`), and a non-SQLite backend is a named skip.
7. **A test that builds its own engine must put the file in WAL mode itself.** The app sets `journal_mode=WAL` in `session.py`'s connect event; an engine built in a test has no such event, and a reader then blocks the writer ("database is locked" after the factory's 30 s), which looked like a hang of the whole file.
