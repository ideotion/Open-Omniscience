## 2026-11-01 — a writer fix cannot reach what the old writer already wrote, so a match over text that outlives the writer is keyed on BOTH sides (R403 / R399; PR #1682)

**What was found.** Fixing a writer so that it stores the one canonical spelling (PR #1679, `POST /api/law/documents`) stops the divergence growing and, in the same breath, moves the mismatch: from "two installs that typed differently" to "an artifact the old writer already produced against what the new writer stores". A backup is a byte copy of the old spelling. The independent read of that fix measured it through the real merge: of every pair of two- and three-letter spellings of one jurisdiction, 6 (alpha-2 store) and 8 (alpha-3 store, every new install) went from one row to two when an old route's backup was restored over a new route's row, with the UK typed `gb` or `gbr` the case that matters, while 506 and 8 went from two to one. The writer fix was right and shipped with the limit stated; it could not remove it.

**The rule.** When a match is made on the exact text of a column, and the text lives in artifacts that outlive the writer (backups, exports, other installs), canonicalise the COMPARISON, on both sides, through the one function the writers use; do not rely on every writer having been fixed. Two clues that it is needed: the table's merge/dedupe SQL says `a.col = b.col` and the column has a canonicaliser anywhere in the tree, and a staged-copy conversion that exists but is the wrong function for the column (here `to_iso2`/`to_iso3`, which refuse the app's own codes and which a writer never applied to what an operator typed). The key is for comparing only: nothing is rewritten, the INSERT still copies what was staged, so a store keeps whatever spelling it holds and a cleanup stays a separate, deliberate step. A SQL `=` cannot call Python and an index cannot serve a function of the column, so the keys are computed once, in Python, for each side into an indexed temp table and the statements join that (50,000 rows per side: 0.24 s and 0.19 s to key, the match 0.04 s, using the index). Build the working copy's keys AGAIN after the step's own INSERT, or the rows just inserted are invisible to the mapping that follows.

**Seven traps this met.** (a) The key must keep the writer's refusals: a word is never guessed into a code (`france`, `georgia`, `congo`, `england`, and four-letter names such as `mali` and `chad` that a wider "looks like a code" shape would convert), so the key's shape is the writer's, stated once and imported (`LAW_JURISDICTION_CODE`), not copied. (b) Where the working copy can hold two spellings of one key (the unique index is on the text), the mapping must choose, deterministically: the row spelled like the staged one, else the oldest, so an install with no such pair behaves exactly as an exact match did. (c) An old test that used the bug as its demonstration (a document restored as two rows to prove a form-gap measurement was not theatre) turns red when the bug is closed: read the test's purpose before editing it, keep the measurement it was written to protect, and change only the assertion that depended on the defect, saying so in its docstring. (d) Keying turns a one-to-one id map into a many-to-one one wherever the source side can hold two rows of one key (a backup that itself holds a document under two spellings): every child table unique on (parent, something) then meets two parents' rows on one parent and the whole restore fails on a UNIQUE constraint, or lands two summaries on one (revision, model). The first version of this change did exactly that, and its own tests passed because they used an empty target; the independent read found it. Find the source-side groups first (a `sib` flag, computed with the index) and let those rows keep the exact match they always had, so the map stays injective by construction. (e) A choice among several matches that is made in more than one place (the merge's map, the merge's placing of an alternate, the app's later lookup) needs ONE rule written once and a test that runs all the places against the same fixture; the first version had three rules (exact then oldest document, exact then oldest revision, newest row) and two of them picked a different document. (f) The machine that writes the SQL is not the machine that runs it. The map was first written as a scalar subquery `ORDER BY <outer.column> = <inner.column> DESC, id LIMIT 1`, which every local run accepted (SQLite 3.53.1) and which SQLite 3.45.1, the library Ubuntu 24.04 gives CI's Python, refuses at prepare time with `no such column`: every `merge_corpus` call on CI failed, 588 tests, and only the CI job's log said so. Write a choice among rows as an aggregate over the rows (here the exact spelling's lowest id, else the key's lowest id: `COALESCE((SELECT MIN(id) ... AND exact), (SELECT MIN(id) ...))`), which both versions accept and which is the same function (20,000 random staged/working copies, NULLs and empty strings among them, gave the same map on the old and new statements and on both libraries); and before pushing any change to a statement run the touched tests under the OLDEST SQLite the project runs on (`/usr/bin/python3` with `PYTHONPATH=<worktree>:<venv site-packages>` is 3.45.1 here), not only the venv's. (g) A red test step hides every step after it on the same job. The CI `test` job runs the SAST step (`bandit -r src/ -ll`) after the suite, so while 588 tests failed nobody had seen bandit's verdict on this change; once the suite was green, the job went red on two Medium B608 findings (`"SELECT ... WHERE " + _LAW_HELD` and the INSERT that ends the same way): a SQL string concatenated with ANYTHING that is not a literal is flagged, a module constant included, and this file marks each such statement with `# nosec B608 - <why no outside value reaches it>` on the string's first line. Mark a new concatenation when it is written, and read the job's later steps in `.github/workflows/ci.yml` before calling a green suite the whole job.

**Pinned by** `tests/test_restore_law_jurisdiction_canonical.py` (282 tests, run on SQLite 3.45.1 and 3.53.1) and the 42 mutants of the key, the match, the sibling flag, the map and the two alternate lookups, all killed.

**Stated limits.** See the shipped-log entry of the same date: stored rows are not rewritten; a word typed on one install and a code on another stay two rows; the duplicate-key scan diagnostic still lists the app's own codes as unresolved; a real backup of a real install was not restored.
