## 2026-10-26 — an early return is not a build: a function that can decline to run must say so, and the cause in the comment must be read from the callee, not assumed

**Found by an independent read of #1510 (note 3), then corrected by the read of this change.** `_refresh_persisted_build` returned `None` both after a refresh and on an early return, and the dispatcher read "returned without raising" as "built": it released any hold, reset the run of failures and recorded `built`, for a call that refreshed nothing. My first fix named the cause as "the passphrase or the secure backend went away, so `columnar.connect` returned no connection", and that was WRONG: `connect` returns `None` only when DuckDB is missing or `OO_COLUMNAR=0`; given no passphrase or no secure backend it falls through to an IN-MEMORY connection, which the function then recorded as the persisted store. The fix read the callee only after the reviewer did.

**Rules.**
1. A function with an early return on a missing resource returns something its caller can tell apart from a finished job (here `False`; `True` after a refresh), and the caller treats the early return as a decline: no build ran, so no `built`, no release, no reset of a failure run.
2. When existing callers or test stubs return `None` for success, check for the explicit sentinel (`is False`), not for falsiness: `not result` turns every stub that returns nothing into a decline (the mutation that does exactly this fails two existing tests).
3. Before writing "X went away, so Y returns None" in a comment, a row and a lesson, read Y. Here the one-line read of `columnar.connect` would have shown the in-memory fallback, and the real defect (an in-memory connection recorded as the persisted store) was one step from the one being fixed. Decline BEFORE the call that falls back, with the inputs the callee needs read once.
4. The decline names itself (`last_skip` reason `persisted-unavailable`), so a reader of the status sees "declined, and why" and not an absent build.

**Limits, stated.** The persisted store is dormant in shipped code, so this is read from code and exercised through stubs. Not fixed, and queued: when the encryption gate fails or the persisted open raises, `connect` also falls back to an in-memory connection, and the function cannot tell the two apart from the connection it gets; `_build_inmemory_and_swap` returns `None` (read as built) when `connect` gives `None`.
