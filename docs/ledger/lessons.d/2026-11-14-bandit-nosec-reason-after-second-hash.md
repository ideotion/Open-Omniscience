## 2026-11-14 — bandit reads the words after a nosec id as more ids; put the reason after a second # (OPEN_QUEUE 24, PR #1988)

**What was found.** Bandit 1.9.4 parses `# nosec` with `#\s*nosec:?(?P<tests>[^#]+)?#?`: everything after `nosec` up to the next `#` is the test list. The convention this ledger recorded (`# nosec B608 - <reason>`, the merge.py/diagnostics.py form named in an earlier lesson on columnar.py) therefore handed bandit every word of the reason as a test name. The marker still worked, because B608 was in the list, but each word printed a "Test in comment: <word> is not a test name or id, ignoring" warning: about 3,100 of the 3,543 stderr lines of a green static job, burying anything real.

**What it cost.** Nothing broke; a green log that nobody could read. The remaining 435 lines are a second, separate bandit behaviour: a marker on an f-string line warns "nosec encountered (B608), but no failed test" once per string part even when the same marker does suppress the finding on the joined string. Moving markers cannot remove those, and removing one changes which findings bandit reports.

**The rule.** (1) Write `# nosec B608 # <reason>`: the second `#` ends the id list, and the suppressed findings are identical (checked by comparing bandit's full JSON result set, 312 results, before and after). `tests/test_bandit_nosec_form.py` refuses the old form in `src/`. (2) The CI bandit steps hold back only the "nosec encountered (Bnnn), but no failed test" class and print how many there were; every other line and the exit code pass through, so `-ll` blocks on exactly what it blocked on. (3) Before removing a nosec that looks inert, run bandit with and without it over the whole tree and compare the result sets, not the warning count: on a multi-line f-string the marker that warns is often the one doing the suppressing.
