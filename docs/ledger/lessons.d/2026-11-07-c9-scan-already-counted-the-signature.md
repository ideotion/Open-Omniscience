## 2026-11-07 — the keyword scan had already counted the language signature the export then re-read (C9, L1)

**What was found (the C9 measuring half, `c9-measure/report-2026-11-07.md`, 9.9 M mentions).** `/keywords` cold was 19.7 s, of which the ordered scan is 15-16 s and the rest 3.5-3.9 s; the profiler put `fetch_signatures` (a second read of the mention rows of every exported keyword, to count their articles per language) at 4.6 s cumulative. The scan already holds that count while it walks the same rows (`counts` in `scan_keywords`) and drops it at the next keyword.

**The fix, and what it cost to do it honestly.** The ranker keeps the count for the rows it keeps. Three decisions are the lesson: (1) a one-language keyword stores NOTHING (its signature is `{dominant: articles}`), so a corpus of mostly one-language keywords pays no memory; a keyword in several languages stores a flat `(language, n, ...)` tuple, packed only when the heap keeps the row (most rows of a large corpus are discarded, and packing every one would cost more than the read it replaces). (2) The extra memory is priced as ROW UNITS against the same `heap_rows` budget (`_sig_units`), not by moving `ROW_BYTES`: a row that carries a wide signature counts for the rows it takes, so `memory_plan`, `ROW_BYTES`, `HEAP_SHARE` and every test that pins them stay as they were, and the heap spills earlier exactly when its rows are fat. (3) A row that carries nothing (a caller of `Ranker.add` with no counts) falls back to the old read, so the new path is an optimisation with the old one beneath it, not a replacement.

**The equality check that made it safe.** The export prints the signature dict in KEY ORDER, so equality of the dicts is not enough. The order is the order the rows first met each language; both reads are index-ordered by (keyword, article), so it agrees, and a harness over 120 outputs (json, digest, zip x heap/spill x one/many batches x two windows) proved the whole route byte-identical to main. A mutant that sorted the languages was caught by the unit test.

**Measured (cold, fresh process, unperturbed, 3 runs each, alternating trees).** 4096-page store 25.4-25.7 s before, 22.2-23.8 s after; 16384-page store 22.5-25.2 s before, 20.3-21.8 s after. About 2.5-3 s, 11-12 %, below the 3.5-3.9 s the profiler suggested (the profiler inflates per-call cost: its figure was relative).

**The rule.** Before adding a second pass over rows a scan has just walked, ask what the scan already counted and discards at the group boundary; carry it for the rows that SURVIVE, price it in the unit the budget is already counted in, keep the old read as the fallback, and prove equality on the printed form (order included), not on the parsed one.

**Deliberately not done, with the numbers.** A raw driver cursor saves 2.3-2.9 s more but bypasses the three `before_cursor_execute` observers every engine statement passes; the scan loop would be the only long read none can see (comment at the loop in `scan_keywords`). Rewriting the per-row body with `groupby` measured 0.2-0.6 s at 9.9 M rows (3 M synthetic tuples, scaled), under the 1 s bar set beforehand.

**Pinned by** `tests/test_keyword_scan_carries_signatures.py` (10): carried equals re-read with key order in both ranker modes, nothing is read when every row carried one, a row with none is read (orphans never), pack/unpack order, row-unit accounting (one-language row = one row; a replaced row swaps its cost), the wide-row budget trips earlier, the constants bound a measured tuple, and the plan constants are unchanged.
