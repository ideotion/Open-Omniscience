## 2026-10-06 — A CHECK THAT HOLDS COLLECTION MUST ALWAYS END, NEVER CREATE A FILE, AND NEVER CALL "NOT READ" DAMAGE (WAL / disk thread, E2 of the damaged-database plan, 2026-10-06)

E1 notices a damaged file only when something reads the bad page. E2 (`src/database/verify.py`) reads each table of the corpus, Wikipedia and law files once, with `PRAGMA quick_check(<table>)`
on its own read-only connection (through the one `connect()` factory, so SQLCipher and the search index's functions are there), after an unexpected stop, before collection writes to the file
again. What a future change must not undo: (1) **The trigger is the ledger's `clean is False`, and an UNKNOWN end (`None`) is not a reason**: holding collection for a check nobody has a reason
for is a cost, and the ledger writes an end for the previous session before the start-up upkeep runs (`forensics.record_session_start` is the first thing in the lifespan). A check left
`running` by an earlier process is also a reason, whatever the end was, so a kill in the middle of the check is retried; the retry is capped at `damage.MAX_VERIFY_ATTEMPTS` starts in a row, and
what the number protects is a check that itself brings the process down: without it a table that kills the reader is a boot loop that never reaches collection. The mark `state: running` is
written BEFORE the first table is read (a test kills the run with `SystemExit` at the first table and reads the record), and a skipped file is said in the record and starts afresh after the next
unexpected stop (a file HELD on an earlier finding stays held at every clean start in between: the hold's own entry is neither unfinished nor owed, and reading it as "no attempts" ran a crashing check three more times after every hold). (2) **Not reading is not a verdict**: only `SQLITE_CORRUPT` (the driver's code, through `damage.corruption_of`) or a `quick_check` answer other than `ok` is `damaged`; busy,
locked, an I/O error, an interrupt, a missing file, a wrong or missing passphrase (code 26 is both, E1's stated blind spot) and a stop are `unchecked` with the reason in plain words, and a
`file_verdict` of no tables is `unchecked`, never `ok`. A stopped run (shutdown asks it) leaves the file's entry `running` and records no verdict, so the next start reads it again. (3)
**`connect()` CREATES a missing file** (plaintext under `OO_DB_PLAINTEXT=1`, encrypted when a key is held), so a read-only check built on it must test `is_file()` first: the plan skips an absent or
empty file, and `_open` refuses a path that vanished in between (a test pins that no file appears). (4) **ARM as the upkeep's FIRST statement, END in a `finally`**: `main._arm_database_check()` is the first line of `_run_startup_upkeep`, BEFORE its first slow step, the planner statistics (minutes
on a large store); armed after it, an operator who goes online in that time starts a pass first (a test records that the wait is up at the upkeep's first phase). `run_armed` ends the arming however
the run ends (a test makes the run raise), and the upkeep's decorator `_ends_the_check_wait` ends it in a `finally` unless `verify.hand_over()` was called, which the upkeep does the moment the
boot-sequence thread, which runs the check, has started: an exception on the way to that thread must not leave collection waiting for a check no one runs. Arming twice changes nothing, and a
file is read once per process (the upkeep can run twice, an unlock after a locked boot). (5) **The pause is ONE global kind in the guard, so the lanes need no branch of their own**: the housekeeping lane asks `admit()` before every kind, so `"verifying"` already pauses
all of it, and a per-file `writes_paused("law")` branch there was dead code (its test showed the lane stop for the storage reason first and was rewritten); the Wikipedia lane has no `admit()` and
uses `writes_paused(WIKI_FILE)`. `"damage"` is named before `"verifying"`, a storage limit before both, and "Resume anyway" is refused with its own sentence for the check as for damage. (6)
**The progress sentence carries the server's counts** (`table {index} of {total}`), is drawn in a line of its own and never under the damage hover (it is the app reading its files, not a
report of damage: the hover's first sentence would have been false there), and says nothing until the run has counted its tables. The damage hover's old sentence "does not check or repair
anything yet" became false with this slice and was reworded in all twelve locales (a locale key IS the English string, so rewording re-keys it). (7) `quick_check` reads structure (that the pages of each b-tree are well formed and its records readable), **not that an index agrees with its table, and not row content** (SQLite's own words, and a changed
article text still answers `ok`). **`quick_check(<virtual table>)` asks the module to check itself from SQLite 3.44**: FTS5's integrity check of its inverted index, which does NOT compare the index with the
articles (measured on the app's external-content `article_fts`: after an article's text was changed behind the index, the check still answered `ok`; 0.65 s against 0.20 s for `articles` alone on a 100 MB store, so the
index's own pages are the cost, not a read of the content). It reports damage with the words "malformed inverted index for FTS5 table"; a build older than 3.44 reads nothing for it and the shadow tables are all there is.
**FTS5 answers an error that stopped ITS check as a ROW, not an exception** (measured on 3.45.1: "unable to validate the inverted index for FTS5 table main.article_fts: out of memory"), so a non-`ok` answer is read
before it is believed: when every line is that wrapper around an out-of-memory, I/O, full, interrupted, locked or cannot-open text, the table is `unchecked` with the reason, never `damaged` (a corruption text in the
same place stays damage). Damage found only in `article_fts` and its shadow tables is filed as the search
index, anything else, or both together, as data, through the SAME `_apply_incident` a corruption error uses, so the two doors cannot latch differently.
(8) **A DUE CHECK IS WRITTEN DOWN BEFORE IT RUNS (`state: owed`)**: the ledger writes a session that closed before the check began as a CLEAN end, and the next start reads that and forgets the earlier
unexpected stop. So arming records every planned file as `owed` (a boot that stays locked records it too, `owe_at_locked_boot`, because it cannot arm: the key is not there), the next start
reads an `owed` entry as an unfinished check, and `owed` is NOT an attempt: only a check that begins counts toward the cap, so a machine closed from the lock screen many times is not a machine
whose check keeps dying (a test closes it five times and the check is still there with no attempt used).
(9) **A DAMAGED VERDICT MUST SURVIVE A RESTART**: the latch lives in memory and the ledger reads the next start as a clean end, so without a record the finding is forgotten and collection writes on into a file
the check read as damaged (the deep read of E2 reproduced it). The record already holds `state: done, verdict: damaged`; `plan_boot` reads that from an earlier process as a reason to read the file again
(`damage-found-before`), at every start, until it reads clean or the file is replaced (`verification_forget`, called by the restore swap beside the latch release, so a verdict about the file that was live is
not read as one about the new file). **A start of collection must not release a latch the check set unread** (`R117`: going online is the routine click): for an error "the first failed read puts it back" is the safety, and a latch the check found has
no failed read to put it back, so `retry` holds a latch with `check_tables` and `verify.recheck` re-reads exactly those tables on a thread of its own (the latch held, a progress line of its own, one re-read per file at a time, none
while the start-up check still reads); the file is released only when every table reads `ok`, a table that could not be read keeps it, and the answers are merged into the file's record with the rule that **an answer that could not be
read never replaces a finding of damage** (otherwise a busy file, or a stop in the last table, makes the next start forget it). A re-read's answer for a file that was REPLACED in the meantime is dropped (the release ends the claim on
the file), and a restore or salvage swap releases outright (`file_replaced=True`) and forgets the verdict. The sentences that said "starting collection again tries once more, and it stops again at the first failed read" were true only
of a latch a failed read set; for a latch the check set a start re-reads and the pause holds unless the tables read clean, so the three damage sentences (library, search index, the hover) now say both.
(10) **Three small rules the deep read forced**: a quit during the check gives the attempt back (`verification_file_stopped`: the entry stays `running` so the next start reads the file again, but quitting three
times must not skip a check that nothing ever failed); a stop before a file is begun spends no attempt on it; a result for a file that was REPLACED while it was read is dropped (the entry `verification_forget`
removed is not `running`), so a verdict about the old file cannot latch the new one; and **an error `connect()` chains must be the one from the candidate that got past page 1** (any code but 26, the HMAC check every wrong size and wrong passphrase fails on; else the first), because the
last candidate is the undeclared default size and fails with code 26 whatever the file's state, and the first is the right size only when it is cached for the path: a schema page damaged under the right key read as
"the passphrase did not open the file". A record whose
`attempts` is not a number counts as none instead of aborting the whole plan.
(11) **A RECORD THAT STANDS IN FOR AN EARLIER ONE MUST BE READ AS THAT ONE**: a boot that starts locked writes its `owed` entry over the earlier process's (carrying its attempts and trigger), and the unlock, in the SAME
process, plans again; `previous_verification` returned nothing for any entry of this process, so the plan could not see the state the owed entry was copied from, and a damaged verdict, an unfinished check and the
attempt cap were all erased on the default (encrypted) install, which boots locked every time (the deep delta read found it by combining a locked boot, an unlock AND a clean previous end; the tests had combined two of the
three). `previous_verification` now returns this process's own `owed` entry, and four tests run the combinations. **A re-read's claim needs an identity and a count**: it carries a token (every method that settles it presents
its own, because the first read's ending waits on the record before it gives its claim back and must not give back a second claim) and the incident count it was made at (a clean answer about the tables a check
reported says nothing about a read that FAILED after the claim began, so the latch holds and stops being the check's). **And a "(schema)" the check could not read is not an answer about the tables**: it means no table was
read, so when the list reads later every table of it is read, and the schema answers clean only beside them.
(12) **A CAP THAT STOPS A CHECK MUST NEVER CLEAR WHAT THE CHECK FOUND, AND A READ THAT COULD NOT HAPPEN IS NOT A CLEAN READ (the deep delta read and the coordinator's check, R120/R121)**: the three-starts cap stops RE-RUNNING the check; it is not a way to forget a finding. A file an
earlier check reported as damaged stays latched from the record when the cap skips its check (`verification_file_held`, the note `FRAME_CHECK_STOPPED` says "stopped after N starts" and is in memory only), and the latch ends the way a check's latch always does: a re-read of the reported tables
that comes back clean, or the file replaced. **The finding is CARRIED through every entry that replaces it** (`owed`, `started`, `skipped`, `done` copy `earlier_damaged` from `damage.carried_damage`, which reads the tables a finished check read as damaged, `(schema)` when the record
names none, and what a later entry carried): a verdict of `unchecked` that replaces `damaged` with the table still unread would otherwise let the next process plan nothing. A table clears only by reading `ok`; one that is no longer in the file has nothing in it to be damaged; a `(schema)`
in the set means no table was read, so when the list reads every table that does not answer `ok` is left (damaged or merely unread: counting only the damaged ones released a latch on a table that answered "busy"); when the LIST could not be read nothing is cleared (`listed: False`).
**An I/O error from `stat` or `is_file` is "could not examine", never "nothing to read"**: the second releases a latch (a switched-off check, a file that is gone), the first keeps it. **A locked boot's own `owed` entry is due, not unfinished** (its trigger and attempts are the
earlier ones'; an "unfinished check" label on a file that was damaged before was untrue). **A call that names no claim settles no claim** (`_claim_is` with `token=None` matched whatever claim was there). **And a check that only reads opens `mode=ro`** (`connect(read_only=True)`):
`query_only` does not stop the last connection to close from folding a leftover `-wal` into the file and deleting it, a test compares the file and the log byte for byte. Four of the twenty-seven mutants of this fold survived the first test list (the carry on a partial
re-read, a note outliving its latch, a replaced file keeping its note, a clean read keeping it): a note or a carry is only tested by what a LATER latch or a LATER process sees, not by what the same call returns.
(13) **UNDER SQLCIPHER A TABLE CHECK THAT RAISES THE GENERIC ERROR HAS NOT ANSWERED, AND ONE PRAGMA ANSWERS FOR IT (E2b, 2026-10-06; every figure measured)**: on a 500-article store of 367 pages of 16 KiB, 40 single pages overwritten
with random bytes, `quick_check(<table>)` filed 10 files `damaged` (it answered rows: "unable to get the page", "btreeInitPage() returns error code 11") and 30 `unchecked` (it RAISED `SQLITE_ERROR`, code 1, "SQL logic error", which the record kept as just "OperationalError"); a table's data pages are the usual raisers (on a two-table store pages 2-56 all raised it, the index's pages 57-70 answered rows), and after the first corrupt read every later read on that connection raises `MemoryError`, so each probe needs a connection of its own. `PRAGMA cipher_integrity_check` named "HMAC verification failed for page N" for 9 of 9 pages tried, every unchecked one among them. E2b asks it ONCE, only after that generic error (code 1 AND the text "SQL logic error": `no such module` shares the code) on a file whose header is ciphertext, and files the answer as one more entry, `(pages)`, a name no table has (like `(schema)`). What must not move: (a) **an unknown pragma answers NO rows, exactly as a healthy file does**, so a build without the pragma would read as clean: `cipher_check_present()` asks a keyed in-memory database (the pragma answers it with a row, "database file is undefined", an unknown one with none), and a build without it leaves the file `unchecked` with that reason; (b) **a clean pass never makes a file clean**: the tables that did not answer stay `unchecked` beside a `(pages)` that reads `ok`; (c) **`(pages)` is not a table of the list, so "a table no longer in the file counts as read" must not apply to it**: `_recheck_main`'s `gone` and `DamageRegistry._carry_after` each needed an exception, and a re-read that answered it by its absence released a latch whose pages still failed (a test latches `notes` and `(pages)` with the damage in a page of `articles`); (d) the page numbers kept are the lowest `MAX_PAGES_LISTED` = 32 (a bounded heap) and the count is always kept, because a set of every failing page was 65 MB at a million of them (that is the code's own side: SQLCipher computes the whole check while the statement is prepared and holds one result row per failing page inside SQLite before the first is read, +25 MB at 247,877 failing pages, about 100 MB at a million, +0 at 2,035); (e) MEASURED COST, a 234 MB store of 60,000 articles in the full schema, 4 vCPU, cache dropped: the pragma 1.0 s on a healthy file and 1.0 s with 356 of 14,266 pages overwritten (all named), about 230 MB/s (4.3 s per GB), peak RSS 47 MB before and 48 MB after on a healthy file, against 12.6 s for the 61 per-table checks of the same file (a keyed connection each, 0.17 s of key derivation apiece). It is one C loop that answers no progress handler (19 s on a 4 GB copy): a stop is looked for before it starts, and a quit does not let a pass that began end (its thread is a daemon and shutdown does not wait), so `stop()` hands the file's attempt back AT THE STOP, once, because nothing after the C call would ever run, and the progress line names `(pages)` before the call; three quits that landed in a pass had spent the three attempts and skipped the check with no finding recorded. (f) **A disk error on a page is ANSWERED by the pass as a row, it does not raise**: "error reading 16384 bytes from file page 40 at offset 638976" (measured with an `LD_PRELOAD` `pread` that returned EIO; **SQLCipher prints the offset through a 32-bit `%d`, so a page at 2 GiB or later prints a NEGATIVE one: "error reading 16384 bytes from file page 140000 at offset -2001223680", measured on a 3 GiB store, and the first pattern wanted digits only, so that row was filed as one nobody knows, which is damage: the coordinator's check of E2**), and the first version filed every row it did not know as `damaged`, so an I/O error read as a verdict on the file; the four rows that say the pass could not read or could not run are `unchecked` (`_COULD_NOT_READ`, counted apart as `pages_unread`, kept in the detail beside a page that did fail), and a row nobody knows stays damage in its own words. A test that stands in a RAISE where the real driver answers a row pins nothing: the stand-in text is now the driver's own row. SQLite 3.43 and later report a failed READ as `SQLITE_IOERR_CORRUPTFS`, which reaches the application as `SQLITE_CORRUPT`, so the PER-TABLE check files such a read `damaged` (a plaintext store; 5 of 8 EIO pages of a SQLCipher store): that is SQLite's own position, unruled here, and in the open queue. Of twenty-four mutants of the change two survived the first test list, both because a test passed for the wrong reason: a stand-in connection whose statement had no `fetchall` made the probe FAIL instead of ANSWER, and a test that replaced `inspect_file` whole never ran the code that carries the driver's code. A test that needs a page the driver answers a certain way must ASK the driver (`_find_page` tries pages and reads the verdict), not assume a page number: the layout is the driver's.
(g) **`PRAGMA cipher_integrity_check` CANNOT CHECK A FILE PAST 4 GiB, AND FILTERING ITS ROWS AFTERWARDS DOES NOT HELP (the coordinator's check of E2b, 2026-10-06; every figure measured)**: on a HEALTHY 4.52 GB store of 16 KiB pages `quick_check` answered `ok` and every byte read fine through the codec, yet the pass answered 13,934 "HMAC verification failed" rows, one for every page from 262,145 on (the first page that starts at 2^32); a `pread` shim saw no read at or past 4 GiB, so the pass's offsets wrap and it checks the wrong bytes. The engine builds every row before it returns the first (+28 MB at 260,000 rows, about 113 bytes a false row, about 250 MB on a 40 GB corpus), so dropping the false rows afterwards still reads the whole file and holds them. The only correct move is not to ask: a main file longer than `verify.PAGE_PASS_LIMIT_BYTES` (2^32) is `unchecked` with the reason and the table that sent it there stays `unchecked` (a page starts at 2^32 or later exactly when the file is longer than 2^32 bytes; a file of exactly 2^32 is still checked; the length is read again AFTER the pass, because an outside writer can take the file past 2^32 while it runs, and the rows are then dropped; the sentence the record keeps says the pages were NOT checked and stays under the detail cut, which had cut it to "...a failure for every page fro"). A correct page check past 4 GiB is a follow-up in the open queue. Two smaller rules from the same check: **a cap may shrink what is PRINTED, never what is COUNTED** (the maintainer's ruling of 2026-09-11): the unknown rows beside a failing page were cut by `lines[:DETAIL_LINES]` with no count, so the record now carries `strange_rows` beside `pages_unread`, and the branch that files a file `unchecked` because its table list could not be read keeps `pages_unread` as a number and not only as words inside `reason`; and **a cap inside a loop that only repeats the final slice protects nothing unless it says what it protects and a test pins it** (`verify._Kept`: the first lines of a kind and the count of all of them).
(14) **A LOG RECORD'S TRACEBACK PRINTS THE ERROR THE ERROR WAS RAISED FROM, SO A SCRUBBED WRAPPER DOES NOT MAKE `exc_info` SAFE (the passphrase audit of the stack, 2026-10-06; found by reading, not by a trigger).** A site that wraps a driver's error in a message of its own and logs it with `exc_info=True` writes the wrapper's text, the original driver error (`raise ... from`) and every frame, and `errorlog` carries the record to `data/app_errors.jsonl`, which rides the debug bundle; a keyed connection's errors can hold a `PRAGMA key` statement. Of the 34 `exc_info=True` records the stack adds, seven sit in a `try` that can see an engine, a pool checkout or a keyed driver connection (the start-up check and its re-read, the index build and its statistics, the repair and its two writes after the switch); those keep the exception's TYPE and nothing else, and the other twenty-seven sit in a `try` that only reads a file, a registry or a clock (each PR's body tables its own). A test that wants this pinned must raise an error whose `__cause__` holds the secret, because a test that puts it only in the outer message passes with `exc_info` removed from the wrong record.
