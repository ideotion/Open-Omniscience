## 2026-10-13 — hold the narrowest thing the racing writers all pass through, never the single-writer gate across a file swap; and an invalidation needs an epoch

**(1) The carry alone left a silent loss.** `_carry_live_settings` read the live settings rows just before the replace, and a `kv_set_json` that committed between that read and the replace was lost: it returned success, the in-process cache served it, and it reverted at the next start. Settings writers hold neither the corpus lease nor a swap-window guard.

**(2) The obvious close, holding `write_lock()` across the swap, was measured to be wrong.** `swap_in_corpus`'s file steps wait (up to `_SWAP_HANDLE_WAIT_S`, 300 s) for every handle on the live file to close, and some threads check a connection out FIRST and only then wait for the gate (an ORM session that reads before it writes, `hold_write_window`, `checkpoint_wal`). Before, such a thread got the free gate, was refused as stale, closed its handle and the swap went through (0.6 s in the probe). With the gate held it kept the handle while it waited for the restore: the swap failed with the sharing violation after the budget (3.6 s with a 3 s budget), every writer in the app stood still, and the earlier connections stayed refused although the file never moved. **A hold across a swap must not take a lock that a thread holding a handle needs in order to let go. Ask, for every wait inside the hold, what the waiter holds while it waits.** No test could see it: the real-swap test had patched the engine disposal away and opened no engine connections, which is why the independent read at the final head is not optional for new locking.

**(3) The fix is a hold on the writers that race, not on the gate.** `kv_store.hold_writes` counts settings saves in flight and makes a new one wait at the door (bounded, `OO_KV_WRITE_WAIT_S`) or be refused with fixed words and nothing written; the restore waits for the count to reach zero (bounded, refusing if a save is stuck behind a long writer), carries, swaps, empties the cache, releases. No lock is held while a save waits for the gate, so there is no lock order to get wrong, and it works with `OO_WRITE_GATE=0`. A caller that already holds the gate (against the documented constraint) is refused at once during a hold, and the suite sets `OO_KV_STRICT_GATE_ORDER=1` so the suite itself finds such callers. **A test that pins the gate FREE inside the hold (a thread takes it to let go) is the one that fails when someone "simplifies" this back to `write_lock()`.**

**(4) Emptying a cache is not enough while a reader that began before can still fill it.** A reader that missed the cache and read the old file just before the replace stored its value AFTER `kv_invalidate()` (probed: the file said the copy's value, the process served the live one, for good). The cache carries an epoch that every invalidation moves; a reader or writer fills the cache only if it has not moved since it began. The repair, which swaps the same way, gained the same invalidation.

**(5) An epoch that skips a cache fill must also drop what the fill would have replaced, and a strict guard that raises is not a guard where callers swallow.** The epoch is global, so a per-key invalidation moves it too: a save queued behind the gate that overlapped one skipped its fill and left the OLDER value cached for good (the file said 2, the process served 1; the existing test used a full invalidate, which hid it). And the audit mode that raised `AssertionError` was blind to thirteen `except Exception` wrappers; it now also records, and a fixture fails the test that left a record. It found a real, older bug (`revert_overlay` saved a setting while its own session held the gate: a 30 s stall and a preference never saved). **A hold that sets state before its `try` leaks it on a `BaseException`; the hold's set and its wait now sit inside the `try`, and the `finally` clears the hold only if it is the caller's (`_hold_by == me`) because the flag is set one statement before the hold.** The cache is not made fully coherent by the epoch: a per-key version is the open follow-up.

**(6) Moving a call into a helper moves the anchors of every source-scanning guard.** Three older tests located the commit point by the literal `swap_in_corpus(` in `run_restore`; they were re-anchored onto the helper's call with dated comments. **Run every structural source-scan test when a call changes place, not only the suites that touch the behaviour.**
