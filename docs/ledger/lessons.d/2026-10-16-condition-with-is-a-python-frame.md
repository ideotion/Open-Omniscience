## 2026-10-16 — `with condition:` is two Python frames, and a signal can land between them: take the plain lock under the Condition (R144)

**(1) The hazard, measured.** `threading.Condition.__enter__` and `__exit__` are Python code (`return self._lock.__enter__()`, `return self._lock.__exit__(*args)`), and CPython delivers a signal at the start of a Python frame and after a call returns. A KeyboardInterrupt landing after the inner lock is taken but before `__enter__` returns, or at the start of `__exit__` before it releases, leaves the lock taken for ever. Real SIGALRM interrupts at 0.3 ms on CPython 3.13 (the only version measured to be fixed by this; see (5)): `with condition:` left it held in 15,174 of 43,142 interrupts (35 %, empty body); `with raw_rlock:` 0 of 40,151; `with raw_rlock: cond.notify_all()` 0 of 46,483; `with raw_rlock: cond.wait(...)` 0 left held in 65,632 (174 of them, 0.27 %, surfaced as `RuntimeError: cannot release un-acquired lock` in place of the KeyboardInterrupt, and the interrupted waits left stale waiter entries in the Condition: a stale entry takes the wake-up of one `notify()`, so a real waiter can sleep to its deadline, or for ever on a wait with no timeout, until the next release; `kv_store` uses only `notify_all` and is not affected, and this needs an interrupt on the waiting thread itself). The production settings write slot, driven the same way: 3,156 of 29,506 interrupts left `_hold` taken on the parent commit, 0 of 28,911 after. A C lock's `__enter__` / `__exit__` run inside one bytecode, so there is no instant between "taken" and "will be released" at which Python handles a signal; and a blocked C `acquire` that is interrupted raises WITHOUT having taken the lock.

**(2) The rule.** `self._lock = threading.RLock()`, `self._cond = threading.Condition(self._lock)`, `with self._lock:` everywhere, `wait` / `notify` on the Condition (it needs the lock owned, and it is). An RLock because `Condition()` defaults to one and a section can be re-entered. This does not stop the interrupt (signal masking is a pair of calls with the same window); it stops the lock being left taken. Converted: the settings write hold (`kv_store._hold_lock`), `pool_reserve._Slots`, `library_generation._Lock`, `bandwidth` permits. `database/writer.py` (9 sites) and `monitoring/storage_events.py` (2) still use the form and are pinned by count in `tests/test_condition_with_form.py`, which reads all of `src` and fails on any other `with <Condition>`, with a planted case per spelling (attribute, module name, `from threading import Condition`, alias, local, annotated, multiple items, `async with`).

**(3) Why not a detector.** A design with registered sections and a `sys._current_frames()` probe (no timeout) was written down and parked by ruling: after the swap the measured leak is gone, and a detector adds moving parts near the release. The ruling for any later detector: it REFUSES and NAMES what it found (operation, thread kind, UTC time; never a thread name, which can be request-chosen) and NEVER self-heals by replacing the lock, because a replaced lock lets a stuck section and a live one share a critical section under two locks, the race the lock exists to stop. The signal-loop scripts are kept out of CI in the Q thread's folder (`probes/`): timing-dependent, they measure; the unit tests pin the FORM.

**(4) How the settings tests changed.** The three tests that wrap the lock in a proxy now wrap `_hold_lock` (`_InterruptedEnter` raises before the lock is taken, as an interrupted acquire does; `_AfterFirstExit` starts a hold in the gap after the check); `wait` is still patched on `_hold`. Mutations checked: reverting one `with` per module fails the form pin (each of the four), building a Condition without an explicit lock fails the non-vacuity test, each reader clause removed fails a planted case, and the kv release moved back inside the lock fails the release pin (and seven more through the token it leaves in `_inflight`, because the `store` fixture does not reset it).

**(5) THE GUARANTEE IS CPYTHON 3.13'S, found by an independent read of the final head.** On 3.13 `with x:` compiles to `BEFORE_WITH` and the protected range starts right after it, which is why a raw lock left 0. On 3.14 (measured on 3.14.0rc2) it compiles to `LOAD_SPECIAL __enter__; CALL` and the signal check at the end of the call runs before the protected range: the same probe left a raw RLock held in about 80 % of interrupts (6,516 of 8,157) and `with condition:` in about 30 % (2,410 of 8,123); the production slot leaked on 3.14 under both forms. The project supports 3.13 only (the classifier, CI and `release.yml`), but `requires-python` is `>=3.13`, so a source install on 3.14 is allowed. `tests/test_condition_with_form.py::test_the_with_statement_still_compiles_to_before_with` fails on a Python that does not use `BEFORE_WITH`, with the instruction to re-run `probes/sigprobe4.py` first. **A guarantee measured on one interpreter is a claim about that interpreter: say so in the comment, and pin the assumption the measurement rests on, not only the form that exploits it.** (The "before" figure for the production slot is measured against the commit this change branched from; the probe's `old` mode now takes a git ref.)
