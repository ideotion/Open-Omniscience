## 2026-10-06 — THE COPY THAT DROPS NEWSLETTERS MUST NOT VACUUM, AND A DELETED WORD OUTLIVES ITS ROW (merge thread follow-up to #1328, 2026-10-06, `src/backup/newsletter_export.py`)

`stream_backup._drop_newsletters_in_file` deleted the newsletter articles from the encrypted snapshot and ran `VACUUM`. Under SQLCipher the temp store is memory (a file there is written in the clear, below the codec; see the entry above), and VACUUM builds its whole new copy in it, ungated: measured on a 406 MB encrypted store of 60,000 articles, peak RSS **366 MB** for the filter against **87 MB** for the replacement, in the same time (28 s against 25 s). The replacement deletes with `secure_delete` ON, merges the search index, and rewrites the survivors with `sqlcipher_export` into a fresh keyed file read back through the production open path before it replaces the copy; any failure STOPS the newsletter-free backup with a keyed notice (it never falls back to a filtered copy as it is, and never to a full backup), because secure_delete cannot reach stale bytes already in a page's free space.
**Two facts that were not what they looked like.** (1) `article_fts` is an external-content FTS5 table: a delete writes a marker and leaves the postings and the term dictionary in the segments, and NEITHER `VACUUM` NOR `sqlcipher_export` removes them (the newsletters' unique words were still in the decrypted copy after both, on the PLAINTEXT path as well, for as long as the filter has existed). `INSERT INTO article_fts(article_fts) VALUES('optimize')` merges the segments and drops them; a test reads the DECRYPTED copy for a marker word, because the encrypted bytes cannot show it. The merge now sits in `_drop_newsletter_rows` for both paths, and a merge that fails stops the backup rather than keeping the words. (2) `ATTACH DATABASE ? AS x KEY ?` accepts the key as a BOUND parameter on the raw driver connection (the older helpers interpolate it with `''`-doubling because `PRAGMA key` takes no parameter; ATTACH does), so the new code never puts the passphrase in SQL text; the failure path records the exception's CLASS, and its text only through `scrub_text`. An attached alias takes SQLCipher's compiled-in page size, not the source's, so every cipher setting is read from the source (`cipher_page_size`, `auto_vacuum`, `kdf_iter`, the HMAC and KDF algorithms; a plaintext header, which needs the source's salt, refuses the export) and compared on the result.
**The space the new path needs was claimed, not measured, until the review**: the preflight bound (copy plus a volume set of at least the copy's size, about 2.12 x the copy) covers the copy and the rewrite, which is renamed over it before the volumes exist, and `test_the_space_check_asks_for_the_copy_and_its_rewrite_at_the_least` pins that. It does NOT cover the deletes and the index merge, which run in ONE transaction with secure_delete on: the rollback journal then holds every page the transaction frees (the deleted articles' pages as well as the old index segments) before it is zeroed, while the merged segment is written beside them. Measured in delete-journal mode (the copy is exported, never file-copied, and `connect()` sets no journal mode; a WAL copy would reach about 3 x the index): 25% of 60,000 articles deleted peaked at 2.06 x the copy, 90% of 30,000 at 2.0 x with the index 39% of it, where the extra above the copy was 2.6 x the index, so a figure taken from the index alone undershoots (the review's probe: over 2 x the index in 5 of 6 runs). The copy now asks, before anything is deleted, for its own size plus its index (the journal cannot hold more than the file, and the merged segment is no larger than the index), and skips the rewrite, saying so in the note, when the drive lacks the copy's size free. The index size is the sum of the segment blobs' lengths, which undercounts by about 13% at 4096-byte pages (each block spills onto an overflow page); the file size in the bound absorbs it.
**A merge costs nothing in memory**: `optimize` at 60,000 and at 180,000 articles left the process's peak RSS where it started (66 and 65 MB) and took 8.2 s and 18 s (about 150 to 200 s projected to 1.5 million), so it needs no memory gate; the full path peaked at 87 MB at both 60,000 and 180,000 (83 s at 180,000, 911 MB result).
**What an older backup carries**: `article_fts` is `fts5` with the default `detail=full`, so each posting holds the document id, the column and the POSITIONS of the term (measured on a minimal case: the leftover segment read `zorp` at positions 0 and 2 of document 7 after a delete and VACUUM). A newsletters-excluded backup made before this fix therefore holds the lower-cased, diacritic-stripped words of each excluded newsletter AND their order, once the file is decrypted; the casing, the punctuation and the text itself are not there. The shipped fragment says so and that a new backup drops it; there is no in-app prompt.
**Free pages cannot be read from the encrypted build** (`sqlite_dbpage` and `dbstat` are not compiled in, and a decrypting export copies live rows only), so what secure_delete leaves is tested on a plaintext twin whose raw bytes are read (control: without the pragma the words are in the file), and the module's own use of the pragma by the order of its statements. **The twin must be BUILT with the pragma on, and the test failed on macOS CI until it was:** a page that splits while `secure_delete` is off keeps a stale copy of the cells it moved in its free space (the root of `articles`, once it becomes an interior page, kept the first rows it held), the pragma cannot reach those bytes afterwards, and whether a given build splits that way differs from one SQLite build to the next, so the same twin was clean on one engine and not on another. The same fact is why a failed rewrite stops the backup (question 37, option a) instead of keeping the secure-delete result: a real corpus was written with the pragma off for its whole life, so only the rewrite (or VACUUM) guarantees no deleted text.

THE READ-ONLY URI WAS BUILT BY HAND IN FOUR PLACES (merge thread follow-up to #1328, 2026-10-06, `src/database/read_only_uri.py`)

`sqlite3.connect(f"file:{path}?mode=ro", uri=True)` reads the file NAME as syntax: a `?` ends the path, a `#` starts a fragment (taking `mode=ro` with it), `%41` becomes `A`. The open lands on a different path, read-WRITE, and creates an empty file there; it is not an error. The staging tree sits under the operator's data directory, so any of those characters can be in it. Four openers (`sqlite_backup.validate_sqlite_file`, `migrate.file_revision`, `merge.merge_custody`, `artifact._corpus_stats`) now go through `open_plain_read_only`, which percent-encodes the absolute path (`os.path.abspath`, not `resolve`: a mapped drive resolves to a UNC spelling) and writes the Windows forms SQLite reads (`file:///C:/dir/x`, `file:////server/share/x`; `Path.as_uri` writes `file://server/share`, which SQLite refuses). A source-scan test fails on any `f"file:{` spelling in `src/`. `connect.py` has its own encoded builder and is left to its owner.

A FAILED RUN'S TEXT IS A SINK IN FIVE PLACES, AND THE RECHECK MUST READ WHAT THE SCRUB READS (merge thread follow-up to #1328, 2026-10-06, `src/backup/runlog.py::failure_fields`)

The volume backup, restore and verify runners, the newsletter import job and `runlog.run` each wrote `str(exc)[:2000]` and the formatted traceback to the run journal, logged with `_LOG.exception` (into `app_errors.jsonl`, which rides the debug bundle) and served `str(exc)` as the job's error, with a passphrase in scope; the import queue then saved the same text into its queue file. One helper now serves all six (`runlog.failure_fields` / `scrub_secrets`): both passphrases in every form, scrubbed BEFORE the cut (a secret straddling the cut survives as a half no scrub can match), the log lines written through `_LOG.warning` with the CLASS ONLY (a traceback ends with the message and every chained one, and `exc_info` hands it to the handler raw; the scrubbed text lives in the journal and the served error -- first written as logging the scrubbed text, which CodeQL's clear-text-logging query flagged on all eleven lines because it does not know the scrub is one), and one test per writer. Two traps found by the reads: a REFUSED restore RETURNS, so its `refused` text and whole report reach the queue file without ever passing an `except` (the handler was the only place scrubbed); and the final "no form survived" check, first written over `json.dumps(report)`, read keys and numbers that `scrub_value` deliberately leaves alone, so a short passphrase equal to a count blanked a GOOD report and silently dropped a held backup's history entry. The recheck now walks the string values, the same walk the scrub makes. The persisted import report is scrubbed where it is written (`import_reports._scrubbed`), the legacy restore endpoint and the restore's refusal branches use the same helper. Not done and recorded in OPEN_QUEUE (R114): a static walk over `volume_job.py` and a central scrub in `errorlog.py`.
