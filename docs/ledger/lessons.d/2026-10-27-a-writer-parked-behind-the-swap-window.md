## 2026-10-27 — a thread that holds SQLite's write lock and asks the guarded engine for a second connection while the swap window is held costs the repair's data-version read its whole busy timeout; the gate rules out every gated writer, the shipped app has no ungated one that does it, and the pin is an ORDER test

**The question (coordinator item 2 of 20:42Z).** Inside the swap window the repair runs `check` = `written_to_since` → `_Probe.moved()` (`repair.py`): `BEGIN IMMEDIATE` on a connection opened with a 30 s busy timeout (`repair._probe_open`), to read `PRAGMA data_version`. Every new connection waits behind the window in `connecting()` → `shared()` with no timeout. Can a writer hold SQLite's write lock while it is parked there? Then the probe waits for the lock, the writer waits for the window, and the window ends when the probe gives up.

**Forced (the lane's `swap-window-parked-writer-data/force.py`, the app's own engine, plaintext store, SQLite 3.45.1, a 4-core virtual disk).** A writer thread INSERTs on its first session (`in_transaction` True: the write lock is held), the window opens through `swap_in_corpus(check=probe.moved)`, and the writer asks for a SECOND session. Result: the statement that waited is the probe's `BEGIN IMMEDIATE` (busy timeout 30 s): **30.065 s** (30.085 s in an earlier run), then `database is locked`; the window was held 30.066 s; the writer's second open waited **29.767 s** (29.787 s), in `connecting()`. `_swap` turns any failure of the probe into `Declined("writer-busy")`: the copy and its sidecar stay, nothing is switched, the window gives the earlier connections their validity back and the writer's second connection then opens on the live file. Control (the writer touches its FIRST connection again after 0.3 s of its own): refused as stale at once, the connection rolls back, the lock is free, `BEGIN IMMEDIATE` 0.33 s. n = 1 each (two for the forced case). So the wait is bounded by the probe's own timeout, loses no data, and costs a repair that is made again at the next start.

**Why the shipped app should not do it (mechanism, then evidence).**

1. **A gated writer cannot be in that state when the repair's window opens.** `repair.run` holds the single-writer gate (`write_lock()`) for the whole repair, window included (with `OO_WRITE_GATE=0` it declines, `write-gate-off`); a gated writer (every ORM flush, ORM-issued DML, textual write, the explicit `write_lock()` sites) holds the gate from its first write to its commit or rollback, so a holder `write_lock()` had to wait for has already ended its transaction; and a gated writer takes its pooled connection BEFORE the gate (`writer.connection_first`, "one order everywhere"), so one that is queued for the gate holds a connection and no SQLite lock.
2. **The writers the gate does not see** (Core or raw-driver write transactions; the repair's docstring and `writer.py` say so) are, in `src/`: the settings saves (`kv_store`: one raw `connect()`, outside the guard, so it never parks in `connecting()`, and nothing opens a second connection under its transaction) and the `init_db` DDL steps (`maintenance.ensure_*`, `source_identity`, `country_form`: run at launch and at unlock, before the boot steps of which the repair is one; that no other thread runs one during a repair is read from the call sites, not proved). `scheduler/hygiene.py` and `release.py` open a raw connection for a checkpoint (under the gate) and for `shrink_memory`: no row write. The restore has no such read: its window waits for no SQLite lock (`dispose_engine`'s closes, `disk_changing`, two unlinks, one replace; the close-time checkpoint of a last connection tries SQLite's lock once and does not wait, from SQLite's documentation and the code, not measured here); its file steps wait for HANDLES (below).
3. **Sweep of the test suite** (the lane's `nested_plugin2.py`: a `Pool` checkout listener; for every checkout by a thread that already holds another it records whether that other connection is inside a transaction AND has changed rows since it was checked out, and whether an ORM Session checked it out). Four shards over all 1,506 `tests/test_*.py` on the Core-only profile of this box: 136,587 checkouts, 103,477 of them by a thread that already held another, 2,166 with the held one inside a transaction, **668 with it inside a transaction that had changed rows** (1,240 held-connection observations over 1,047 distinct call chains): **all 668 held by an ORM session, none by Core or raw code.** The repair, swap, restore and damage test files again alone (the shared run had 48 of `test_repair.py` refuse for disk room, 4.1 GB free while four shards ran; the file passes alone, 115 passed): 669 passed; 2,729 checkouts, 1,521 nested, 244 in a transaction, none with rows changed.

**What the evidence does not cover.** Tests, not the field. Four modules not collectable here (`test_awareness`, `test_commodity`, `test_confidence_intervals`, `test_statistical_tests`: numpy, scipy and `vaderSentiment` are not in this profile) and 15 failures in files that do not touch the swap (`test_analysis_api` 9, `test_launcher_stop_row` 2, `test_commodity_csv` 2, `test_workflow_integration` 1, `test_csv_feeds` 1), not examined. Raw `connect()` opens are not pool checkouts, so the recorder does not see them, and they do not pass `connecting()` either. A held connection that leaked from an earlier test stays "held" for its thread until it is returned, so the nested counts are an upper bound. A thread that holds a connection and asks for a second is common in the app (`pool_reserve` counts it as `collector_nested`); the claim is only about one that holds the WRITE LOCK without holding the gate.

**Windows, the same shape without the lock (not exercised).** The restore's file steps wait up to `_SWAP_HANDLE_WAIT_S` (300 s) for every handle on the live file to close (`_retry_while_locked`, a sharing violation only), and a thread parked in `connecting()` with a connection checked out holds its handle whether or not it wrote. The restore does not take the gate on purpose (`_carry_and_swap`: the first build did, and the wait was measured), and relies on a thread's next statement being refused as stale so that it lets go: a thread parked in `connecting()` never gets to its next statement. The rollup build's boundary check is written around exactly this (`rollup_serve._require_library_unchanged` never waits for the window: "a build parked behind the window with its handle open would make the restore fail"). Nothing enforces the rule for other callers.

**Ruled R338 (22:06): a stated limit, no defect PR (R189).** Two design changes are named so they are not re-asked; both are proposals for the user, neither is built.

**Proposal 1, recommended: `connecting()` refuses at once, with `StaleLibraryError`, a thread that already holds a connection of the library engine while the window is held.** Every connection that thread holds was made before the window and will be refused at its next statement anyway, so waiting buys it nothing; failing lets its transaction roll back and its handle and its write lock go. It closes both shapes above at once (the repair's probe could not wait on a parked writer, and the restore's Windows file steps could not wait on a parked handle) and makes structural the rule the rollup build keeps by hand (`rollup_serve._require_library_unchanged`). It needs a per-thread count of checked-out connections of the library engine (`pool_reserve.holds()` covers collector threads only), and it changes the behaviour of every nested open during a swap: a request that opens a second session in the middle of a restore fails with the stale-library error instead of waiting, which is the answer its first connection would give it one statement later.

**Proposal 2, not recommended until a real parked writer exists: a shorter busy timeout for the probe inside the window.** The probe's 30 s is the wait for a commit that is under way (the design says so: it takes SQLite's write lock first, which waits for a commit that is under way), so a shorter figure would be a chosen number and not a measured one, and it would cut that wait for every honest committer to cure a case no shipped writer produces.

**The pin (`tests/test_repair_probe_parked_writer.py`, two tests, ~1.3 s).** The forced case with the probe's busy timeout at 0.5 s and the control, on an engine built as the app's is (`guarded_creator` + `attach`). The forced test asserts an ORDER, not a duration: when the probe has failed (inside the window) the creator has run once, for the first connection; after the window it has run a second time, on the live file, and the lock holder's uncommitted row is not in it; nothing was switched. Mutation-proved: with `connecting` replaced by a no-op the forced test fails ("DID NOT RAISE": the writer opens its second connection at once and gives the lock back); with `valid` always true the control fails (`ran` for `StaleLibraryError`).

**The rules.**

1. **Ask of every wait inside a window: who can hold what it waits for while parked behind this window?** The repair's `BEGIN IMMEDIATE` is safe today because of two facts three files apart (the repair holds the gate; a gated writer's lock lives inside the gate), neither written next to the probe. This lesson is where they are written together.
2. **A thread must not park in `connecting()` while it holds a connection.** The rollup build keeps the rule by hand; the engine does not enforce it, and the restore's Windows file steps and the repair's probe are the two places that would pay for a caller that breaks it. Option (c) is the structural form, if a report ever shows a case.
3. **A pin for an interleaving is an order test with a mutation.** Event order, not a stopwatch (`tests/wallclock_helpers.py`); the figure (30 s) is in the lesson and the probe's timeout in the test is only a parameter. It can be vacuous (a writer that has not reached `connecting()` when the probe fails) but never red for a slow runner.
4. **A sweep for a precondition states what it could not see.** Raw opens, non-test threads, a leaked held connection, the profile; "none found" is the sentence, "cannot happen" is the mechanism in point 1 and 2.
