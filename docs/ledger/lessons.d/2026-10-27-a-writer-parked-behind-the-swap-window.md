## 2026-10-27 — a thread that holds SQLite's write lock and waits behind the swap window (a second connection, or the gate the repair holds) costs the repair's data-version read its whole busy timeout; the gate rules out every gated writer, the shipped app has no ungated one that does it, and the pins are order tests

**The question (coordinator item 2 of 20:42Z).** Inside the swap window the repair runs `check` = `written_to_since` → `_Probe.moved()` (`repair.py`): `BEGIN IMMEDIATE` on a connection opened with a 30 s busy timeout (`repair._probe_open`), to read `PRAGMA data_version`. Every new connection waits behind the window in `connecting()` → `shared()` with no timeout. Can a writer hold SQLite's write lock while it is parked there? Then the probe waits for the lock, the writer waits for the window, and the window ends when the probe gives up.

**Forced (the lane's `swap-window-parked-writer-data/force.py`, the app's own engine, plaintext store, SQLite 3.45.1, a 4-core virtual disk).** A writer thread INSERTs on its first session (`in_transaction` True: the write lock is held), the window opens through `swap_in_corpus(check=probe.moved)`, and the writer asks for a SECOND session. Result: the statement that waited is the probe's `BEGIN IMMEDIATE` (busy timeout 30 s): **30.065 s** (30.085 s in an earlier run), then `database is locked`; the window was held 30.066 s; the writer's second open waited **29.767 s** (29.787 s), in `connecting()`. `_swap` turns any failure of the probe into `Declined("writer-busy")`: the copy and its sidecar stay, nothing is switched, the window gives the earlier connections their validity back (`_close_window`: the swap did not happen and `disk_changing` was not called) and the writer's second connection then opens on the live file. Control (the writer touches its FIRST connection again after 0.3 s of its own): refused as stale at once, the refusal invalidates the connection (the driver connection is closed), the lock is free, `BEGIN IMMEDIATE` 0.33 s. n = 1 each (two for the forced case). So the wait is bounded by the probe's own timeout, loses no data, and costs a repair that is made again at the next start.

**A second shape, found by the read of this PR and forced in the pin (not in the harness above).** `repair.run` holds the single-writer gate across the window (`with write_lock():`), so a thread that wrote through a path the gate does not see and then enters ANY gated operation waits on the GATE while it holds SQLite's lock: the same 30 s wait, with no second connection and no `connecting()`. A pool-checkout sweep cannot see it. It needs the same precondition (an ungated write transaction) as the first.

**Why the shipped app should not do either (mechanism, then evidence).**

1. **A gated writer cannot be in that state when the repair's window opens.** `repair.run` holds the single-writer gate (`write_lock()`) for the whole repair, window included (with `OO_WRITE_GATE=0` it declines, `write-gate-off`); a gated writer (every ORM flush, ORM-issued DML, textual write, the explicit `write_lock()` sites, and the settings saves: `kv_store.kv_set_json` and `kv_delete` take `write_lock()` and then a raw `connect()`, `kv_store.py` module docstring) holds the gate from its first write to its commit or rollback, so a holder `write_lock()` had to wait for has already ended its transaction; and a gated writer's pooled connection is taken BEFORE the gate (`writer.connection_first`, "one order everywhere"), so one that is queued for the gate holds a connection and no SQLite lock. (The settings saves take the gate first and use a raw connection, which never passes `connecting()`.)
2. **The writers the gate does not see** (Core or raw-driver write transactions) are, in `src/`, the DDL steps of `init_db` (`maintenance.ensure_*`, `migrate`, `fts.ensure_fts`; `source_identity` opens `BEGIN IMMEDIATE` on a Core connection). `library_generation.py`'s module docstring (lines 33-35) also lists `spell_index` and the `fts` rebuilds as writers the gate does not see; the review of this PR read them as gated (`spell_index.build` is a task-manager job whose DROP/CREATE/INSERT/ALTER statements are `text()` calls in a `session_scope`; the `fts` rebuilds run under `write_lock()`), so that list is stale and is the next change to that docstring. They run at launch and at unlock, before the boot steps of which the repair is one, and again as `init_db()` after a restore's swap (`merge.py`) and after a repair's own swap (`repair.py`, after the window has ended). That no such step runs on another thread during a repair, and that none opens a second pooled connection or enters the gate while it holds the lock, is read from the call sites, not proved. A read of `src/` for both shapes (the review of this PR, by grep) found none. `scheduler/hygiene.py` runs a PASSIVE checkpoint outside the gate (a checkpoint takes no write lock) and `release.py` opens a raw connection for `shrink_memory`: no row write. The restore has no such read: its window waits for no SQLite lock (`dispose_engine`'s closes, `disk_changing`, two unlinks, one replace; the close-time checkpoint of a last connection tries SQLite's lock once and does not wait, from SQLite's documentation and the code, not measured here); its file steps wait for HANDLES (below).
3. **Sweep of the test suite, shape (a) only** (the lane's `nested_plugin2.py`: a `Pool` checkout listener; for every checkout by a thread that already holds another it records whether that other connection is inside a transaction AND has changed rows since it was checked out, and whether an ORM Session checked it out). Four shards over all 1,506 `tests/test_*.py` files of the tree it ran on (the base now has 1,508) on the Core-only profile of this box: 136,587 checkouts, 103,477 of them by a thread that already held another, 2,166 with the held one inside a transaction, **668 with it inside a transaction that had changed rows** (1,240 held-connection observations over 1,047 distinct call chains): **all 668 held by an ORM session, none by Core or raw code.** The repair, swap, restore and damage test files again alone (the shared run had 48 of `test_repair.py` refuse for disk room, 4.1 GB free while four shards ran; the file passes alone, 115 passed): 669 passed; 2,729 checkouts, 1,521 nested, 244 in a transaction, none with rows changed.

**What the evidence does not cover.** Tests, not the field. Four modules not collectable here (`test_awareness`, `test_commodity`, `test_confidence_intervals`, `test_statistical_tests`: numpy, scipy and `vaderSentiment` are not in this profile) and 15 failures in files that do not touch the swap (`test_analysis_api` 9, `test_launcher_stop_row` 2, `test_commodity_csv` 2, `test_workflow_integration` 1, `test_csv_feeds` 1), not examined. Raw `connect()` opens are not pool checkouts, so the recorder does not see them, and they do not pass `connecting()` either. A held connection that leaked from an earlier test stays "held" for its thread until it is returned, so the nested counts are an upper bound. The sweep does not look for shape (b) at all. A thread that holds a connection and asks for a second is common in the app (`pool_reserve` counts it as `collector_nested`); the claim is only about one that holds the WRITE LOCK without holding the gate. A transaction can also hold the lock without a write (`BEGIN IMMEDIATE`, as `source_identity` opens); the sweep keyed on rows changed would not have counted one.

**Windows, the same shape without the lock (not exercised).** The file steps of `swap_in_corpus` wait up to `_SWAP_HANDLE_WAIT_S` (300 s) for every handle on the live file to close (`_retry_while_locked`, a sharing or lock violation: winerror 32 and 33), and a thread parked in `connecting()` with a connection checked out holds its handle whether or not it wrote. So does a thread queued on the gate with a connection checked out, and the repair runs `swap_in_corpus` under the gate. The restore does not take the gate on purpose (`_carry_and_swap`: the first build did, and the wait was measured), and relies on a thread's next statement being refused as stale so that it lets go: a thread parked in `connecting()` never gets to its next statement. The rollup build's boundary check is written around exactly this (`rollup_serve._require_library_unchanged` never waits for the window: "a build parked behind the window with its handle open would make the restore fail"). Nothing enforces the rule for other callers.

**Ruled R338 (22:06): a stated limit, no defect PR (R189).** Two design changes are named so they are not re-asked; both are proposals for the user, neither is built.

**Proposal 1, restated R340 (22:27): `connecting()` refuses at once, with `StaleLibraryError`, a thread that already holds a connection of a guarded engine while the window is held. NOT recommended as stated; the stated limit stands. If the user wants a refusal, the shape to offer is one only on the swap path that exempts the window ending without a swap (`_close_window`).** As stated it would close shape (a) and the Windows handle shape for a thread parked in `connecting()`, and make structural the rule the rollup build keeps by hand (`rollup_serve._require_library_unchanged`). **Why it is not recommended as stated, which the first draft of this lesson got wrong:** a connection made before the window is NOT always refused at its next statement. When the window ends without a swap (a declined repair; a restore that refused before `disk_changing`) `_close_window` gives the earlier connections their validity back, and the forced case here relies on it (the writer's `c1.rollback()` after the window). So the refusal would turn a declined swap into a `StaleLibraryError` for every thread that holds a connection and opens another during it, which in the app is a request that opens a nested session in the middle of a repair or restore. It needs a per-thread count of checked-out connections for EACH guarded engine (the app's and `read_snapshot`'s: `pool_reserve.holds()` covers collector threads only), and it does not touch shape (b), the wait on the gate, which needs a different rule (an ungated write must not be followed by a gated call on the same thread). **What R340's form does and does not reach (the delta read of the fold):** a refusal inside `connecting()` cannot know whether the window will end with a swap, and the only point where "the earlier connections will not be given back" is certain is `disk_changing()`, which comes AFTER the `check` (`merge.py` `swap_in_corpus`). So a refusal that exempts a swapless window can only start at `disk_changing`: it closes the Windows handle shape, not shape (a), because the probe runs before `disk_changing`. Nothing in the R340 form shortens the probe's wait; only Proposal 2 does, at the cost it names. The call is the user's.

**Proposal 2, not recommended until a real parked writer exists: a shorter busy timeout for the probe inside the window.** The probe's 30 s is the wait for a commit that is under way (the design says so: it takes SQLite's write lock first, which waits for a commit that is under way), so a shorter figure would be a chosen number and not a measured one, and it would cut that wait for every honest committer to cure a case no shipped writer produces.

**The pins (`tests/test_repair_probe_parked_writer.py`, three tests, ~1.7 s).** The two forced cases with the probe's busy timeout at 0.5 s, and the control, on an engine built as the app's is (`guarded_creator` + `attach`). The first forced test starts the probe only after the writer is inside the wait for the window (`gen._wait`, called from `connecting()`, is wrapped to say so), and asserts an ORDER, not a duration: when the probe has failed (inside the window) the creator has run once, for the first connection; after the window it has run a second time, on the live file, and the lock holder's uncommitted row is not in it; nothing was switched. The second holds the gate around `swap_in_corpus` as `repair.run` does, has the writer enter `write_lock()` after its ungated write, starts the probe only once the writer is queued on the gate (`write_gate_waiters() >= 1`) and clears `OO_WRITE_GATE` for its length. The control's writer does NOT roll back until the probe has answered, so only the refusal's `invalidate()` can have freed the lock; its probe waits `HANG_GUARD_S`, which only a mutant pays. Mutation-proved, each by the test it should kill and no other: `connecting` a no-op fails the first forced test ("the writer must be parked behind the window"); `valid` always true fails the control; the refusal without `invalidate()` fails the control (`database is locked` after its probe gave up); the gate not held fails the second forced test ("the writer must be queued on the gate"). The first draft's tests left five file descriptors open on the live file after teardown (the first connection returned to the pool the swap had disposed), so every writer ends with `invalidate()` now (0 open, gc disabled).

**The rules.**

1. **Ask of every wait inside a window: who can hold what it waits for while parked behind this window, or behind the gate the window sits under?** The repair's `BEGIN IMMEDIATE` is safe today because of two facts three files apart (the repair holds the gate; a gated writer's lock lives inside the gate), neither written next to the probe. This lesson is where they are written together.
2. **A thread must not park in `connecting()` or on the gate while it holds a connection.** The rollup build keeps the rule by hand; the engine does not enforce it, and the restore's and the repair's Windows file steps and the repair's probe are the places that would pay for a caller that breaks it. Proposal 1 (restated R340: only on the swap path, exempting a window that ends without a swap) is the structural form for `connecting()`, if a report ever shows a case and the user wants it.
3. **A pin for an interleaving is an order test with a mutation, and it starts the observer only once the other side is in the state under test.** Event order, not a stopwatch (`tests/wallclock_helpers.py`); the figure (30 s) is in the lesson and the probe's timeout in the test is only a parameter. The first draft could pass without the writer having reached `connecting()` (a stall longer than the probe's timeout); it now waits for the writer to be inside the wait.
4. **A sweep for a precondition states what it could not see.** Raw opens, non-test threads, a leaked held connection, the profile, a lock taken without a write, and every shape the recorder is not keyed on; "none found" is the sentence, "cannot happen" is the mechanism in points 1 and 2.
5. **Name the facts a mechanism rests on from the code, not from memory.** The first draft called the settings saves ungated; they run under `write_lock()` (`kv_store.py`), and the conclusion stood only because point 1 already covered them.
