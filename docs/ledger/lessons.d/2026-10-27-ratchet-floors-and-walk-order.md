## 2026-10-27 — a ratchet that counts routes is measured on two installs, and a walk that blames the route in front of it is measured behind other tests

**Found (audit 0.5.0 item 35: #1521, #1533).** Both ratchets walk the app's own OpenAPI schema (`tests/test_origin_guard_every_route.py`, 317 state-changing operations; `tests/test_get_routes_side_effects.py`, 467 GETs). Three things the first drafts got wrong, each seen only after the push:

1. **The floor was one number.** The Core-only lane (no `[analysis]` extra) mounts 11 fewer state-changing operations and 3 fewer GETs, because the commodity, statistical-analysis and article-similarity routers are disabled without numpy/pandas/scipy/sklearn/statsmodels and say so at boot. `test_the_schema_walk_still_sees_the_routes` failed there with 306 < 317. Reproduced locally by making the five packages unimportable: 306 state-changing, 464 GET. The counts were confirmed on a full install only, which is the install a developer has.
2. **The GET walk passed alone and failed behind other tests.** The first request of the process that appends to the error log creates `app_errors.jsonl.lock`, and the first diagnostics call creates the crash black box `native_inflight.bin`; which request that is depends on the test files that ran before. Run alone they land at app start; run after any database-seeding file they land inside whichever route is walked at that moment, and the test then names an innocent route. CI order (499 files first) reproduces it; the fix is one warm-up request outside any monitor plus an ambient row for each file.
3. **A temp file was matched by the wrong name.** The app's atomic writers call `src.safety.file_lock.temp_name`, which makes `<name>.tmp.<pid>.<thread>`; the matcher knew only `<name>.tmp`. A 20 Hz writer through `atomic_replace` during the walk produced three false accusations. The sampler writes about every 5 s, so a few percent per run. The unit test had pinned two forms the helper never produces.

A fourth, smaller: the Core-only CI run caught what no local run could, because the local user is root: `GET /api/llm/install/status` starts `sudo -n true`, which exists only on a non-root host with sudo. And `tests/test_utf8_file_io.py` (a repo-wide guard) flagged two `write_text` calls in the new test file; it was never run on it.

**Rule.** (1) A floor on a count taken from the running app states BOTH install profiles, full and Core-only, with the reason in the comment, and the file is run once with the five analysis packages blocked before the push (a pytest plugin that raises `ModuleNotFoundError` for them in `sys.meta_path` and makes `importlib.util.find_spec` answer None is enough). (2) A walk that attributes effects by time window is run behind OTHER test files in one process, not only alone; a first-write file is warmed up outside the monitor or listed ambient with its reason. (3) A name matcher for a file the app writes is tested against the helper that produces the name, not against names typed into the test. (4) A new test file gets the repo-wide guards run on it (`test_utf8_file_io.py`, `test_repo_invariants.py`, `test_ledger_fragments.py`, `test_planned_index.py`), not only itself. (5) A monitor for a class of side effect is tested by mutants of every call it patches; the reads of #1533 found `connect_ex`, `sendto`, `gethostbyname`, removed files, comment-prefixed and `WITH ... DELETE` writes, `PRAGMA x(v)`, and subprocesses all unseen.

**Limits.** The sweep of other route-count assertions (item 1 of the 2026-10-27 plan) found only these two profile-dependent floors; `tests/test_destructive_surfaces.py` reads the source, not the app, and counts 91 on both installs. No mechanism forces a floor to name both profiles (a proposal, R189). The 20 Hz figure is from the reader's experiment, the 5 s sampler period is from the code, and the "few percent" is an estimate, not a measured rate.
