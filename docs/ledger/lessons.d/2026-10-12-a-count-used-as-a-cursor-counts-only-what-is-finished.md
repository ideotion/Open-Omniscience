## 2026-10-12 — A COUNT USED AS A CURSOR MUST COUNT ONLY WHAT IS FINISHED, A HELPER TWO PAYLOADS SHARE IS GATED FOR BOTH, AND A POLLED READ IS RE-ASKED FROM THE SIDE THAT HAS FEWER ROWS (E3 fold 11, the coordinator's check of fold 10)

(1) **A resume watermark derived from a count is exact only while the count holds finished things alone.** `merge.reindex_imported_articles` saves `ids[done - 1]` as the last article that completed, where `done` is the pass's count of articles finalised. An id that names no article (an imported article deleted before its batch drained: `merged_rows` has no cascade) is not finalised, so after one the count lags the list and the watermark names an EARLIER id than the last finished: the safe direction, because the resume redoes the articles between and the re-index is idempotent. The tempting repair (count the absent id as it is found, at the top of its window) puts the watermark AHEAD of an unfinished article: a crash resumes past it and it is never indexed. Test the direction, not the arithmetic: crash the pass on the article after the first one of a batch whose last id is absent (an exception that derives from `BaseException`, so nothing in the pass catches it), read the watermark from disk, and resume. The same pass must still let the batch END: the absent ids are counted once, at the end, and the final report is made full there, because a bar that ends one short reads as a stuck job.

(2) **A helper that two outputs share is gated at the helper, and the sweep of a payload asks every NUMBER on it, not the ones the diff touched.** Fold 10 gated each arm of `concept_arms` and left the centre printed beside them, computed by `_distinct_articles`, which `trend` also calls and which has two branches (one query; chunks assembled in Python). One return then counted two populations: arm N, centre N + 1, under a caveat that explained the difference by overlapping languages only. The helper carries the condition in BOTH branches, the single-keyword branch of `trend` goes through it instead of repeating the count inline, and the tests ask the centre in the concept payload and the helper with the chunk size patched to 1 (a branch is not tested by a test that never leaves the first one).

(3) **A polled read that gained a question is measured on the same fixture, in the same run, against the version without it, on a quiet machine, and the question is asked from the side with fewer rows.** `_BACKLOG_SQL` is read every 5 s. Fold 10 added `m.row_id IN (<the stand-in hash range>)` evaluated for every pending row: at 1,000,000 pending articles it cost 333 ms with NO stand-in at all and 665 ms with 1,000, against 220 ms for the read without it. The stand-ins are few and the hash index names them without a row page, so the question is asked from them (`articles` by range, then `merged_rows` by `(table_name, row_id)`, a second statement the caller merges by batch id): 215 ms with none or 1,000 and 333 ms with 100,000. The two forms were compared row for row by the probe before the old one was dropped. **And the plan that makes it cheap is measured on a store WITHOUT statistics as well as after ANALYZE**: the statement joined `articles` to `merged_rows` and SQLite chose `articles` as the outer table only once it had statistics (`sqlite_stat1`); on a fresh salvage copy, or a merged file before the next boot's optimize, it chose `merged_rows` first and fetched an article row for every pending row to test a hash (the whole read took 481 and 507 ms against 216 and 214 ms for the read without the question, at a million pending articles, and on a real store each fetch reads the article's page). The probe's fixture had been analysed, so the figure was true of the case the fixture happened to be in. **And a never-analysed case is a fresh file on a fresh connection**: a probe that reused one file and ran `DELETE FROM sqlite_stat1` on a connection that had already loaded the schema measured the previous case's statistics, not none (SQLite keeps them in memory per connection), so its later "no statistics" cells read fast (212 to 342 ms); a connection opened after the rows were deleted chooses the slow order again, and only the first case of a run on a freshly built file was genuinely unanalysed. `CROSS JOIN` fixes the order whatever the planner knows, and the test asserts the plan on a file with no `sqlite_stat1` and on one after ANALYZE (a mutant back to `JOIN` fails the first). Figures from another session's machine (the docstring's 102 ms) are in other units: compare inside one run. Timing on a loaded machine moved by 30 to 40 % between two runs of the same statement; the numbers in the docstring come from a run with nothing else going.

(4) **A battery that starts failing in the middle, a block at a time, with the free space falling, is a full disk, not the diff.** A 1 GB probe fixture written to the temporary directory beside a test run left the drive with 3.5 GB free; the repair's own space check (`no-room`, reserve 5.4 GB) then refused in 46 tests of one file, all of which pass with room (113 passed). The tell was in the log's warnings (`the drive has 3,567,202,304 bytes free and the repair needs about 5,415,057,080`): read the first failure's text before reading the failure list, check `df` before a probe that writes, delete its file when it ends, and remove old suite directories of one's own (a finished run's base directory held 5.5 GB).

(5) **A mutant that dies of an error is not killed.** A new test that raises for its own reason (a UNIQUE violation the filtered runs never reached) made every later mutant look killed in fold 10; the identical pass count and the same error text on every line were the tell. Run the whole file clean first, and read one failure's text per mutant class.

(6) **A guard around a callback the caller owns logs the class, not the traceback.** The final progress report of a drain is wrapped so that a failing report can never undo the stamp; the first version logged the failure with `exc_info=True`. The callback is the caller's job-state writer, so what it raises is not the guard's to know, and a traceback prints the exception and the error it was raised from, which for a database error ends in the engine's own words (a record's `exc_info` rides the diagnostics bundle). The guard logs `type(exc).__name__`, and its test is the one that was missing, a callback that raises on the last report: the stamp still stands, the class is in the log, the marker the callback raised with is not, and the record has no `exc_info` (a mutant that deletes the `try` fails it; so does one that puts `exc_info` back).
