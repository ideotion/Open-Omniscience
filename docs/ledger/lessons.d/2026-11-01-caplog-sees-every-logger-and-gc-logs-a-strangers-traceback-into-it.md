## 2026-11-01 — `caplog` sees every logger, and the garbage collector logs another test's abandoned connection, with a traceback, into whichever test is running (PR #1681)

**What was found.** The Core-only job of #1680 (a docs-only PR; run 41265710087, job 124727977314) ended `1 failed, 28016 passed, 419 skipped, 1 xfailed` after 79 minutes. The failure was `tests/test_database_damage.py::test_a_record_that_cannot_be_written_says_the_class_and_the_errno_name_never_the_message_or_the_path` on `assert all(r.exc_info is None for r in caplog.records)`; run alone it passes. The test's captured log held its own three records (one ERROR and two WARNINGs from `src.database.damage`, none with a traceback) and TWELVE more from `sqlalchemy.pool.impl.SingletonThreadPool`, all with a traceback: six "Exception during reset or similar" (`base.py:1042`) and six "Exception terminating connection" (`base.py:374`), each ending `sqlite3.ProgrammingError: SQLite objects created in a thread can only be used in that same thread`. All six connections were created in ONE thread and finalized in ANOTHER, the test's own. Mechanism: SQLAlchemy's `_finalize_fairy` runs when the garbage collector collects a checked-out connection nobody returned; it tries to roll the connection back from the collecting thread, SQLite refuses (it is bound to the thread that opened it), the pool logs the failure with `exc_info`, and the record travels to the root logger and so into the `caplog` handler of whichever test the collection happened to interrupt. The log names no test for the abandoned connections (a pool record carries none), and which test abandoned them is a separate question from this one. The same shape sits in other files (`all(r.exc_info is None for r in caplog.records)` or `not any(r.exc_info ...)` in `test_article_indexes.py`, `test_engine_text.py`, `test_failure_scrub.py`, `test_import_checkpoint.py`, `test_newsletter_export.py`; `caplog.text == ""` or `caplog.records == []` in `test_failed_thread_start_routes_answer_409.py` and `test_bulletin_sink_sites_rest.py`); they have not failed because the collection happened to land elsewhere, which is luck and not a property of the tests. The same file's `test_with_the_pause_off_the_log_does_not_say_the_writers_are_paused` unpacked `[line] = [... if r.levelno == logging.ERROR]` and fails with "too many values to unpack" the same way, and `tests/test_database_verify.py` had the same `all(...)` twice.

**The rule.** A test that judges the log judges THE RECORDS OF THE CODE IT TESTS: filter `caplog.records` by `r.name` (the module's own logger) before asserting about `exc_info`, a level or a count, and assert the filtered list is NOT EMPTY, because an `all()` over nothing passes and a filter that matches nothing would turn the test into a decoration. `caplog.at_level(level, logger=name)` narrows what is recorded at the source, not what the handler receives from other loggers, so the filter belongs in the assertion. Proved on three tests with a stranger injected into the call phase (a `sqlalchemy.pool` ERROR with a traceback): the old assertions fail, the new pass; and a mutant that makes the code under test log a traceback is still killed (the write-failure warning in `damage.py`, the start-up warning in `verify.py`), so the filter did not blind them.

**Where it applies.** Every `caplog` assertion that is about the ABSENCE of something (no traceback, no record, no passphrase, an exact count): the other files named above, owned by other lanes, are left as a finding. A test that creates an in-memory SQLAlchemy engine (the default pool is `SingletonThreadPool`) and uses it from a worker thread, a `TestClient` handler or a daemon thread without disposing the engine leaves exactly this garbage behind.
