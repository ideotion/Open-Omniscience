## 2026-10-27 — a guard that answers a stale connection by reconnecting protects a statement, not a task that spans commits

**Found by the Opus read of #1547 (the rollup build and the corpus swap).** The generation guard (`library_generation`) refuses a statement or COMMIT on a connection made before a swap, and a CHECKOUT of such a connection raises `DisconnectionError`, which the pool answers by opening a fresh connection on the NEW file, silently. A rollup build commits after every batch, which returns its connection to the pool, so a swap that landed between two batches (or during the DuckDB-only aggregate stage, which holds no SQLite connection at all) raised nothing: select, commit, swap, select on one ORM session returned the new file's row. The build went on reading the new corpus's keywords against mentions it had staged from the old one, and swapped the mixed rollup in. #1547 fixed only the case where the build's connection was open across the swap.

**Rules.**
1. A guard made of refusals on a connection protects whatever holds ONE connection. A task that returns its connection between steps (a commit per batch, a stage that uses another engine) needs its own comparison: take the guard's generation (`library_generation.current()`) before the first read and compare it at every boundary with the guard's own `valid()` (not a copy of its rule: an aborted swap that changed nothing gives the old generation back, and the task must go on).
2. The boundary is the unit, not a timer: after each batch, when each stage begins and ends, and once more before the result is swapped in (the compact and the serve check between the last batch and the swap-in run for a while). A comparison that raises the guard's own `StaleLibraryError` joins the existing classification (no hold, say why, the next request builds) with no second path.
3. Test it with a REAL swap on a guarded engine (`swap_window` + `os.replace`), through the real `build_keyword_daily`, and remove the comparison once to see every case go red; a mutant that drops only the last check must fail only its own case, and a mutant that compares with `!=` instead of `valid()` must fail the aborted-swap control.
4. Not covered, said where it is read: the persisted refresh (`refresh_keyword_daily`) takes no hook and is not compared.
