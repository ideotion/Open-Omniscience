## 2026-10-26 — a name says what the author meant; the request says what the function does, and a DELETE route with no confirm erased a source's articles

**Found (the sweep after the verb-finder of #1499).** Finding destructive handlers by the verbs in their names was already better than by their first letters, and it still missed five things, all found the next day by reading the REQUEST instead: `toggleAiCoordinator`, `mbRun` and `runAiCheck` (one button each; pressed while a job runs it cancels the job; no verb in any name, and `runAiCheck`'s only confirm sat behind `deep &&`, false on the cancel half, so a finder that counted a confirm anywhere in the body vouched for it), `familySplit` (writes a curation override; "split" was not on the list), and `deleteCustomPrompt` (the name had the verb, but no allowlisted binding reaches it: a plain `onclick` calls it, so the allowlist ratchet never looked). On the server the same blindness was bigger: `DELETE /api/sources/{id}` erased the source AND every article it had collected (an ORM `delete-orphan` cascade), and `DELETE /api/wiki/pages/{id}` every captured revision, and `POST /api/quarantine/start?write=true` bulk-hides every detected article with no route that reverses it, each with no confirmation of its own, in an app whose safety routes all take `confirm`. The UI asked first, so nothing had ever gone wrong, which is exactly how a missing server guard stays missing.

**Rule.** (1) Find a destructive function by the request it makes (a DELETE, or a POST/PUT to a route with a destructive verb in its path), as well as by its name; a ratchet that reads only names finds the author's intent, not the effect. (2) Find a destructive ROUTE from the source of the router files (method plus verb in path or handler name), not from the live app object: the routes then cannot vary with what a test registered, and the finder cannot quietly return nothing when a framework changes how it stores included routers. (3) A route that deletes a row whose ORM relationship cascades is destructive in proportion to the cascade, whatever its verb: list the cascade parents, say which route reaches each, and make a new parent fail until it is accounted for. (4) Every finder is pinned against going blind: a floor equal to what it sees today (91 routes, 65 functions, 10 cascade parents here; a loose floor lets a third of the matches vanish unseen), and a test that each table entry still names a real match, is not also guarded, and has not gained a confirm. A confirm that counts is one that runs on EVERY path to the request, and a guard parameter counts only when its default refuses. (5) When a route gains `confirm`, the tests that call it prove the REFUSAL once, then send the flag; a test about something else (`test_stand_in_rows` expects the route's own 404 for a stand-in id) just sends the flag, because without it the 400 would fail it and with it the test stays on the lookup it exists for. (6) The precedent for a server-side confirm is bulk, whole-class, cascade or sole-copy destruction; a single record or a list the UI already asks about is listed as a proposal, with its names, not folded in. (7) An exemption table is worth only what its reasons are: every reason was re-read against the handler by the review of this change, and five were false (a bulk delete filed as one record, a mere un-watch filed as a delete, a person's dismissals filed as derived, a bulk hide filed as additive, a job-status list filed as a record). Write the reason from the handler's body, not from its name or its docstring's first line.

**Limits.** A cascade made by the DATABASE (`ondelete="CASCADE"` foreign keys, 23 of them, live because `foreign_keys` is on) is not seen, only ORM relationships. The request finder reads named function declarations: seven requests sit in anonymous callbacks inside delegated click listeners (pinned by count), and a request made through a helper with a variable URL under a name with no verb is not seen. A trusted click is still not intent.
