## 2026-10-12 — a CI gate the sandbox cannot run is red on the first push

Fourteen folds of the damaged-database work were checked line by line, mutated and run against thousands of tests, and the first push of the carrier (#1346) still came back red from a gate none of that touched: bandit (`bandit -r src/ -ll`, blocking, the last-but-one step of the `test` job) reported B608 on 14 f-strings of `src/database/salvage.py`. The work had been held unpushed for days, so CI had never seen the file, and the sandbox has no bandit. The suite, ruff, mypy and the i18n gates were green because they were the ones that could be run.

**The rule:** before the FIRST push of a branch that has lived unpushed, read `.github/workflows/ci.yml` and list every step by whether the sandbox can run it. Each step that cannot is a place where the branch's code has never been judged, and the lines a repo gate would flag are found by READING THEM for that gate's class: for SAST, every string-built SQL statement, every `subprocess` call and every `yaml.load`; the repo's own marker (`# nosec B608 - reason`, 85 of them in `src/backup/merge.py` alone) shows the form a reviewed exception takes. A `nosec` is a claim about the line and is written only after checking that it is true: here the claim "every interpolated name is quoted" was false for exactly one name (the row-id column's, `_Table.rid`, taken raw from the schema of the file being copied), and it was fixed in the code (quoted where it is set, with a test whose tables have a space, a quote character and a reserved word in the column name; the repair aborted on each before) rather than excused in a comment.

**Also measured:** the gate comes after the whole `pytest` step, so a red `test` job that stops at SAST means everything before it was green.
