## 2026-10-29 — a claimed slot is given back when the launch fails: a slot, a queue entry or a state that is claimed before `Thread.start()` must be undone next to that call

**What was found (R393 class, the WAL lane's candidate 3).** The first lesson of the class ([a start that fails must leave no job that says it is running](2026-10-29-a-start-that-fails-leaves-no-job-that-says-it-is-running.md)) covered a job's own state. The same order of operations hides in three other shapes, found by the sweep that followed it. (1) A SLOT: the Wikipedia dump and OSM region managers count downloads by status, not by thread liveness, so that two concurrent pumps cannot launch past `max_concurrent`; the status is therefore set to `downloading` under the lock BEFORE the launch, and a launch that raises leaves a slot that no worker will ever end, which is a permanent reduction of the machine's download capacity (3 dumps, 2 OSM regions) plus a retry that queues behind it. (2) A QUEUE ENTRY: the model pull queue appends the model, then starts the pump that drains it; a pump that never starts leaves a model that "is already queued", so the retry returns early and nothing ever pulls it. (3) A LOOP OF LAUNCHES: `_pump` claims several entries under the lock and launches them in a row outside it, so the first launch that raises strands the rest of what it claimed, and it runs on the thread of a download that has just finished, so the exception also ends that thread.

**The rule.** Whatever was claimed before `start()` is given back next to it: `except Exception:` put back the claim (the slot's status becomes `error` with the exception's class, the registered thread and stop-event are dropped, the entry leaves the queue and the history says why), save it where the state is saved, and re-raise. A loop that launches several claimed things catches the `Exception` of each launch, logs it and goes on, because one entry that cannot start is not a reason to strand the others, and never catches `BaseException`. A lock around the put-back is not needed when the put-back is one status write (`_save` has its own); do not add one where the file's other status writes take none. And a test of the pump calls it directly with the first launch refusing and asserts that the entries claimed after it still ran: the case a test of `start()` alone never reaches.

**Where it is pinned.** `tests/test_failed_thread_start_leaves_no_leaked_slot.py` (17 tests, 10 red on main, 7 interrupt pins that pass on both). The unread remainder of the class and the limits are in the shipped-log entry for 2026-10-29.
