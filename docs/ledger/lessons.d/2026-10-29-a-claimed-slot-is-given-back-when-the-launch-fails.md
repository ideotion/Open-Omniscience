## 2026-10-29 — a claimed slot is given back when the launch fails: a slot, a queue entry or a state that is claimed before `Thread.start()` must be undone next to that call, and only what that launch registered

**What was found (R393 class, the WAL lane's candidate 3).** The first lesson of the class ([a start that fails must leave no job that says it is running](2026-10-29-a-start-that-fails-leaves-no-job-that-says-it-is-running.md)) covered a job's own state. The same order of operations hides in three other shapes, found by the sweep that followed it. (1) A SLOT: the Wikipedia dump and OSM region managers count downloads by status, not by thread liveness, so that two concurrent pumps cannot launch past `max_concurrent`; the status is therefore set to `downloading` under the lock BEFORE the launch, and a launch that raises leaves a slot that no worker will ever end, which reduces the machine's download capacity (3 dumps by the Optimized profile's default, 2 OSM regions) until that entry is retried or deleted or the process restarts, with the other entries queued behind it and a retry at capacity that is itself queued with nothing to launch it. (2) A QUEUE ENTRY: the model pull queue appends the model, then starts the pump that drains it; a pump that never starts leaves a model that "is already queued", so the same model's retry returns early and starts no pump (another model's enqueue would start one, which drains both, and `cancel()` removes it). (3) A LOOP OF LAUNCHES: `_pump` claims several entries under the lock and launches them in a row outside it, so the first launch that raises strands the rest of what it claimed.

**The rule.** Whatever was claimed before `start()` is given back next to it: `except Exception:` put back the claim (the slot's status becomes `error` with the exception's class, the stop event this launch registered is dropped, the entry leaves the queue and the history says why), save it where the state is saved, and re-raise. A loop that launches several claimed things catches the `Exception` of each launch, logs it and goes on, because one entry that cannot start is not a reason to strand the others, and never catches `BaseException`.

**Put back only what this launch registered, and register under the lock the put-back takes.** The first version of this fix dropped `_threads[key]` and `_stops[key]` by key, outside the lock, and called the entry `error`; the first independent read showed that a second `start()` of the same key, arriving between the machine's refusal and that put-back (it finds a thread that is not alive and a status of `downloading`, so it launches), has its stop event dropped and its entry called `error` beside a live worker that `pause()` cannot reach, and that a pop of `_threads[key]` between `start()`'s two reads of it (`get(k) and [k].is_alive()`) raises `KeyError`. The second version took the manager's lock and compared the stop event, and the delta read showed that a lock on ONE side excludes nothing: the registration (`_stops[key] = stop`, `_threads[key] = t`) was made without it, so it could land between the put-back's read and its `del`. A guard that compares a registration needs the writer of that registration under the same lock, and the things it compares must be written in one step. So: register the stop event and the thread together under the manager's lock, put back under that lock, compare against the object this launch made, touch nothing if it is no longer ours, change the status only if it is still the one this launch claimed (a second start may have queued or paused the entry and answered its caller), and leave the thread that never started where it is, because it reads `is_alive()` False, which is all the other readers ask. The earlier wording of this lesson called the put-back "one status write" that needs no lock; it is two removals, a status, a text and a save, and that was the mistake. What stays open: a second start that has CLAIMED the entry but not yet registered looks, to the put-back, like no second start at all.

**Test it the way it fails.** A test of the pump calls it directly with the first launch refusing and asserts that the entries claimed after it still ran: the case a test of `start()` alone never reaches. A test of the takeover makes the refusing `start()` itself call `mgr.start(code)` before it raises, with the second worker held on a gate, and asserts that the entry is still `downloading`, its stop event is still registered and its worker is alive; a variant at capacity asserts that the entry stays `queued`. A test of the save asserts that a save that fails inside the put-back neither replaces the start's own error nor swallows it. The lock itself CAN be pinned, which this lesson first said it could not: hold a second start between its claim and its registration (a hook in the `Thread` the shim builds, so nothing in the code under test changes), and release it from a `dict` subclass's `__delitem__` at the moment the put-back drops its stop event; if both take the lock the second start can only register after the put-back, and if either does not it registers first and its stop event is dropped. The test waits for the second start with a timeout, because the right code always makes it wait. And a mutant that survives is either equivalent (say why) or a missing test: two survived here, the put-back keyed on the thread instead of the stop event, which is the same check once both are registered in one step.
