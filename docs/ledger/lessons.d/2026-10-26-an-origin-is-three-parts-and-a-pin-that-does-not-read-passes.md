## 2026-10-26 — an origin is three parts, and a pin that does not read passes

Three findings of the 0.5.0 audit (A-001, A-005, A-030) had one root: a check that looked at the easy part of the thing it guarded.

**1. An origin is scheme, host AND port; the hostname is the smallest part.** The CSRF guard (R191 had just made it refuse a hostless `Origin`) still compared only `urlparse(origin).hostname` with the loopback names, so `Origin: http://localhost:9999`, the page of ANY other local web app (a dev server, a notebook, a local UI), passed as "loopback". Browsers tell two pages apart by the whole origin, and the `Host` header already carries the host and port of the server the request reached, so the rule needs no new configuration: the `Origin` (or the `Referer`, only when no `Origin` is sent) must name the same hostname and the same EFFECTIVE port (the scheme's 80 or 443 when none is written) as `Host`, and the hostname must be one the Host guard serves (`OO_ALLOWED_HOSTS` too, which the CSRF check had ignored: a self-hoster under another name could not post from their own UI). A value that names no http(s) server, or a port that is not a number in range, is refused, not defaulted. The scheme is not compared (the `Host` header has none). Behind a TLS-terminating proxy the route is `OO_ALLOWED_HOSTS` for the public name plus a proxy that forwards `Host` and `X-Forwarded-Proto` (uvicorn applies the scheme from 127.0.0.1 and ::1); a proxy that hides the scheme gives different effective ports and the request is refused. The hostname is compared for EQUALITY with the Host header's, not for membership in the loopback names, so `Origin: http://127.0.0.1:8000` against `Host: localhost:8000` is refused too (a browser's Origin and Host come from the same URL, so use is unaffected). Not browser-verified: the tests send the headers by hand. The red-without tests are the point: of the 13 that fail on the old guard, 11 are a 200 to a foreign port or a foreign name (the other two fail on an import and on an allowed name's 403). Three more cases found by an independent read are in the tests: the Host guard serves the test client's own name, which an Origin must NOT be allowed to carry; a run of 4,300 or more digits as a Host port made `int()` raise inside the middleware (a 500, now a refusal); an IPv6 literal in `OO_ALLOWED_HOSTS` is written with its brackets, the Host guard reading `[fe80::1]` whole while `urlparse` hands the Origin's name back without them, so the check takes either spelling.

**2. A pin that lists what it does NOT read is a promise nobody re-checks.** `tests/test_condition_with_form.py` said "NOT READ (none occurs in src today): ... reached as `with other._cond:` through another object". `src/safety/file_lock.py`, written AFTER R144, was exactly that: a dataclass built with `_Local(cond=threading.Condition(threading.RLock()), ...)` and entered as `with loc.cond:` at two sites, and the scan returned `names=set() sites=[]` for it. Measured with real SIGALRM interrupts (one per call, CPython 3.13.14, 20 s): the `with <Condition>` form left the in-process lock owned in 18 of 66,290 interrupts with the file free and 5 of 65,998 with another thread holding it (7 more became a `RuntimeError`, the bare-`cond.wait` gap `src/utils/interrupts.py` documents); the plain lock under the Condition, `with loc.lock:` and the wait through `src.utils.interrupts.wait`, left 0 of 65,901 and 0 of 66,074. The reader now follows a Condition handed to a class of the same module, by keyword or by position, and flags an entry through that attribute; a non-vacuity pin names `file_lock.py`; `scripts/signal_leak_probe.py gate_file_lock` and `gate_file_lock_contended` measure the claim. RULE: when a scan has a NOT-READ list, the sentence "none occurs today" is a claim about the tree on one day; either read the shape or make the list fail on it. The docstring on `file_lock` ("an interrupt at any line leaves nothing held") was false for the same reason: a stated guarantee about interrupts is a measurement or it is not stated.

**3. A rename is a change to the folder.** `atomic_replace` flushed the file before `os.replace` and never the folder, so a power cut right after a replace could bring the OLD file back (it stayed whole, as promised, but the new one was not durable). The folder is flushed after the move, POSIX only, and only for a replace that asked for a flush (`fsync=False` is for state rebuilt after a power cut anyway). Where the platform or the filesystem cannot (Windows, `EINVAL`/`ENOTSUP`/`ENOSYS`/`EOPNOTSUPP`, a folder that cannot be opened) the replace stands and the skip is COUNTED by reason and said ONCE per reason on stderr; any other failure (`EIO`) is raised with the new file in place, as the file's own flush does. The folder's descriptor is closed in a `finally`. An interrupt that lands after the open returns and before the descriptor is stored still leaks it, and no pure-Python shape closes that window (measured with real SIGALRM at 0.3 ms, CPython 3.13.14, 10 s each: 1,602 of 32,288 interrupts left a descriptor open, against 1,509 of 32,291 for the shape that opens first and enters the `try` after); Python's handlers run on the main thread only, so the residual is a Ctrl-C on the command line and not a request thread. The skip is counted (`directory_flush_skips()`, read by the tests; no diagnostics member carries it, its bytes are spent).

**Also.** A table of owed conversions kept an entry after the conversion had landed (`tests/test_event_loop_rows_pinned.py`, `storage_events.record`); a parametrised test over an EMPTY table is reported as skipped, which reads as a check that did not run, so the test is a loop that passes on an empty table.
