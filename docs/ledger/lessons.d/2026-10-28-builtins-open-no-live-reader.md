## 2026-10-28 — A process-wide replacement of `builtins.open` (and `io.open`) has no live reader in the test runner today: a measurement, not a conversion (R385 item 3, after R376's `time` measurement)

**The question.** R350 was a process-wide `os.fstat` patch that pytest met at every phase end. Does the same shape exist for `open`? Sites: `tests/test_native_inflight.py:206`, `tests/test_core_guard.py:554` (also `io.open`), `tests/test_session_hwm_light.py:315` (also `io.open`), `tests/test_member_error_scrub.py:568`, and `tests/test_reindex_throughput.py:473` (the string form `"builtins.open"`); `tests/test_memguard_release.py:546` sets it inside a CHILD process's source string and never runs in pytest. Three of the five filter on a path and pass everything else through; `test_core_guard.py` refuses EVERY open; `test_session_hwm_light.py` passes through and records.

**Answer: no live reader found; no helper added, nothing converted.**
1. **Where a patch of `builtins.open` is read.** Only by code that calls the bare name `open(...)` in a module with no global `open` (the lookup falls through to `builtins` at call time). Code that calls `Path.open`/`read_text`/`write_text` goes through `io.open` (`pathlib._local`), a separate attribute. `tokenize.open`, `linecache` (source lines in a failure report) and `logging.FileHandler` bind the builtin at import or class creation.
2. **pytest 9.1.1 (installed) and 9.2.0 (wheel read, not run) call the bare name in the same eight places**, none at a call-phase end: `config/__init__.py` (only with `PYTEST_DEBUG`), `assertion/rewrite.py` (the first import of a module pytest rewrites, and `get_data`), `junitxml.py` and `helpconfig.py` (session end / `--debug`), `capture.py` (creating a capture at start), `_py/path.py` (`pyimport` with a custom module name).
3. **A probe agrees.** An autouse fixture replaced `builtins.open` and `io.open` process-wide with pass-through spies that record the calling module, under the repo's own conftest and `addopts`, plain and with `-n 2 --junitxml -rA`, with `--log-file`, `--capture=sys` and `-p no:cacheprovider`. Tests: a pass, a failed `assert` and a raised exception (both make pytest read source for the report), a parametrized test and a `capsys` test. Calls from any module other than the test itself during the patch: 0 for `builtins.open`; 0 for `io.open` except `tempfile.TemporaryFile` (below). CONTROL: a bare `open` and a `Path.write_text` in the test body were recorded, so the zeros are not a spy that sees nothing. Probe at `/tmp/claude-0/probe_open/test_probe.py`, not committed.
4. **The one reader that exists is the `capfd`/`capfdbinary` fixtures.** Creating them calls `tempfile.TemporaryFile`, which calls `io.open` at call time (6 calls per test). `capsys` does not. A `refuse`-all `io.open` replacement that is alive when `capfd` is set up (a fixture that patches, requested before `capfd`) would be handed to pytest. No test under `tests/` uses `capfd` or `capfdbinary` (grep: 0 files), and the two `io.open` patches sit in test bodies, so this cannot fire today.

**Rule.** (1) A test that replaces `io.open` or `builtins.open` for every caller must do it in the test body, not in a fixture that can be set up before `capfd`; if the repo ever adopts `capfd`, scope the patch to the module under test first (as `scope_os` does for `os`). (2) Before sweeping a class, find the reader (the `time` and `open` measurements were both zero; the `os` sweep was warranted only because pytest looks `os.fstat` up on the module).

**Not measured, stated.** pytest 9.2.0 was read, not run (the suite here runs 9.1.1); the plugins CI may add (xdist was run, others were not); the app's own background threads that call `open` through the module and can outlive a test are the thread-lifetime class (the quiesce fixture of #1596 covers the briefing ones), not probed here. `shutil.disk_usage` (44 sites) and `tempfile` (3) stay parked.
