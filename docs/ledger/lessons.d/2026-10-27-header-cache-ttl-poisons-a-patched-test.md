## 2026-10-27 — A test that patches `connect.is_encrypted_file` is also patching the lock gate's header read, and the gate's 5 s cache decides whether the test passes (PR #1588)

**What was found.** `tests/test_backup_download_route.py::test_an_encrypted_store_is_refused_and_leaves_nothing` patched `src.database.connect.is_encrypted_file` to return True so the route would refuse an encrypted store. The lock gate (`_lock_gate` in `src/api/main.py`) reads the same header through `main_header_state`, which caches the answer for `_HEADER_TTL_S = 5.0` seconds. While the cached plaintext entry was fresh the patch reached only the route and the test passed (every local run). When the entry had gone stale before the first request (the lifespan reads the state, then the deferred startup runs; on a loaded runner that took longer than 5 s), the gate re-read through the patch, saw an encrypted store with no passphrase, answered 503 `{"locked": true}` before the route ran, and cached "encrypted" for the next 5 s. Every test of the file that ran in that window failed with a 503 as well (10 of 69 on #1588's full run, all at the same second, 503 against 400, 507, 200 and 429, and "the snapshot never started"); the app's own log said `started LOCKED (locked)` for each. The file passed alone, so it looked like pollution from another test; it was one test poisoning its neighbours through the cache. REPRODUCED by forcing `_HEADER_TTL_S = 0.0`: the unfixed file fails on exactly that test, and the fixed file passes 69 with the TTL at 0 and at 5.

**Rules.**
1. **Patch the read the code under test makes, not the function two readers share.** The test now also patches `main_header_state` to the plaintext answer, so only the route sees the file as encrypted. Patching the leaf (`is_encrypted_file`) changes every caller of the cache's refill path, and whether a test sees that depends on a timer.
2. **A cache with a TTL is an input to every test that goes through it.** Run a suspect test with the TTL forced to 0 (and, for the opposite failure, very large) before calling a red "pollution" or "flake"; the timing-dependent ones fail on the first test that patches under the cache.
3. **A run of failures that all land in the same second, with a lock or auth state in their own logs, is one cause upstream of them, not ten.**

**Not checked, stated.** Other tests that patch `is_encrypted_file`, `main_db_path` or `DATABASE_URL` and then go through the app's middleware were not swept; this PR fixes the one that failed. How long the boot took on the failing runner was not measured.
