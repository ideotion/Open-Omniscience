## 2026-10-13 — an unpinned driver moved under the suite: read the red as a behaviour change of the engine before touching a test

**(1) What happened.** `pyproject.toml` said `sqlcipher3>=0.6.2`. The release of 0.6.4 (SQLCipher 4.19.0 on SQLite 3.53.4; 0.6.2 and 0.6.3 are 4.12.0 on 3.51.1) reached the CI runners at 18:20 UTC, and the `test` and `Core-only install` jobs went red on every PR and on main in 8 tests of `tests/test_poisoned_connection.py` and 21 setup errors of `tests/test_database_verify_pages.py`, while the same heads had passed the same files an hour earlier. The first two reds on one PR looked like unrelated flakes (a timing test, then the page-damage files), and the second head passed them locally on five runs. **A failure that passes locally and fails in CI on an unchanged head is a difference in the environment until shown otherwise; reproduce it with the fresh install the job does, on a clean checkout of main, before standing down.** A fresh venv, `pip install -e ".[dev]"`, found it in minutes; the job's own log hides the versions.

**(2) The red is information, not noise.** The canary test says "if SQLCipher stops doing this, the fix is moot": on 4.19 a read after a damaged page raises "database disk image is malformed" where 4.12 left a poisoned connection answering an empty `MemoryError`, and no page of the `articles` table makes its table check answer "unchecked". The lane that classifies damage (`damage.py`, the page pass) is built on the engine's reports, so a newer engine may need the APP changed, not only the test. **Cap the dependency (`<0.6.4`, with the measured reason), record it in the registry, and qualify the new engine as its own piece of work; never loosen the test to get the lane green.** Bisect the version by installing each release into the same venv (`0.6.2`, `0.6.3`: 110 passed; `0.6.4`: 8 failed, 21 errors).

**(3) The lock hid it from the users who install from the lock, not from the others.** `requirements.lock` and the wheel smoke job pin 0.6.2, so those lanes stayed green while a user who installs from `pyproject.toml` got the unqualified engine. Wherever a core dependency is a native engine bundled in a wheel, give `pyproject.toml` a ceiling at the first unqualified release.
