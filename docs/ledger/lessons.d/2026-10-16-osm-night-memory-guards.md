## 2026-10-16 — a memory rule chosen by a FILE's size needs a check on what the file turns out to hold, and every C++ id filter costs by span (PR #NNNN)

**What was found.** Three things the 16x composite, run at the 3.5 GiB / 2-core envelope on the history phase and on the pure-Python reader, and two small probes, showed. (1) `osmium.filter.IdFilter` is backed by the same `IdSet` that cost the kept-id sets 1.4 GB: 4 MiB per 2**25-id window an id falls in, whatever the count, so the history phase's node pass held a flat 1,205 to 1,250 MB for its whole length whether the file was 3 M or 12 M versions, and a border's thousand node ids would cost the same 1,434 MiB while the border is assembled. It is a price of the id RANGE, freed with the filter, so it was documented and put into the runner's plan, not changed. (2) libosmium's `sparse_mem_array` is 16.0 bytes a location settled and 1.7 times that while its vector grows, and the lane chooses it by the extract FILE's size (512 MiB), not its node count: a city-dense file under the threshold would take 3.5 GB settled and 5.9 GB at the growth peak, and the kernel would kill the process with nothing in the run record. (3) The pure-Python reader, assumed one to two orders of magnitude slower "from memory", cut the 16x composite 1.4 times slower (902 s against 642 s) with identical counts, and its dict held about 217 bytes a node of resident memory against the 190 its budget divides by.

**The rules.**
1. **A choice made on one proxy (the file's bytes) needs a check on the quantity that actually hurts (the node count), made while the work runs.** `_OsmiumLocations` stops with `LocationIndexTooLarge` when `1.7 x settled + 600 MB` would pass the room read once at the start, and the error (numbers, source, way out) is written to the row by the handler that was already there. The 1.7 is the measured growth peak, the 600 MB is the rest of the cut on the largest run (823 MB peak less 296 MB of locations, rounded up); a number in a guard must say what it protects and where it was measured.
2. **A memory limit that cannot be read is not a limit that is not there.** `cgroup_reading()` names an absent file, an unreadable one and "no limit set" as three facts in `notes`, `memory_room()` takes the tighter of the cgroup's headroom and `MemAvailable`, and with nothing readable the cautious file index is taken. A VM with no cgroup file is the common case, so "absent" cannot be allowed to read as "unlimited".
3. **An opaque C++ container is measured by id SPAN and count separately, with ids spread over the real range.** `idfilter_probe.py` and `idset_probe.py` differ from a naive test only in the spread: a thousand ids over 1.2e10 and four million ids over 8e6 are the two ends. A fixture whose ids are dense and small cannot show either.
4. **Say which number is a peak and which is settled.** `location_index.memory_bytes_settled` is arithmetic from the entry size and is not a bound; an index that grows holds more while it does.
5. **A runner's plan should show a phase's memory floor beside its disk need**, from the probes' numbers cited in the code, and say "unchecked, because X" when the limit could not be read; it warns and starts, since the floor leaves out a term (8 bytes per tracked id) only the cut can count.
6. **Container restarts kill background runs silently.** A 40-minute measurement lost to one was re-run; hold local work in a commit and a bundle outside the working tree while a long run goes.
