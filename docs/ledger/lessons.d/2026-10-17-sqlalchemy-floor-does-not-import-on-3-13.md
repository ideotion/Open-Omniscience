## 2026-10-17 — A dependency floor nobody has run on the interpreter the project requires is a claim, not a floor (PR #1429)

**What was found.** Reading the SQLAlchemy names the write-gate phase table relies on against four releases, the floor `pyproject.toml` names (`sqlalchemy>=2.0.30`) did not import at all on the required interpreter: on Python 3.13, `import sqlalchemy` from the 2.0.30 wheel raises `TypeError: Can't replace canonical symbol for '__firstlineno__'` in `sqlalchemy/util/langhelpers.py` (a class body gains `__firstlineno__` on 3.13, which the release's symbol machinery refuses). 2.0.31 imports and passes `tests/test_write_gate_phase.py` (10 tests), as do 2.0.51 (the `requirements.lock` pin), 2.1.1 and 2.1.5. `requires-python` is `>=3.13`, so no install can reach 2.0.30 by pip in practice, but the number in the file says something untrue, and nothing in CI would ever have shown it: the test job resolves the newest release the range admits, and the lock pins 2.0.51.

**The rules.**
1. **A floor is the lowest release a test has passed on, on the interpreter the project requires.** Where a floor is stated (a `pyproject.toml` range, a registry `floor`), the evidence is a run, not the date a requirement was first written. For SQLAlchemy the registry and `pyproject.toml` now both say 2.0.31, in one commit (registry, pyproject and lock move together); the lock pins 2.0.51 and needed no change, because the lock-file install job reads neither the specifier nor a metadata hash of `pyproject.toml`. A test pins registry floor = pyproject floor <= the lock pin.
2. **Qualify a release that is not installed by putting its unpacked wheel first on `PYTHONPATH`.** `pip download PACKAGE==X --no-deps --only-binary=:all:`, unpack with the standard library's `zipfile` (nothing from the wheel is run to unpack it), and run the one test file under `env -i PYTHONPATH=<wheel>:<repo>`. The first line of the run prints the version and the path actually imported, so a run that quietly used the installed copy is visible.
3. **Do not point a GitHub release watch at a project whose tags are not its versions.** SQLAlchemy tags `rel_2_1_5`; `scripts/check_upstream_updates.py` strips only a leading `v`, so an `upstream_check` there would read as different from `2.1.5` on every weekly run and open a freshness issue that is never true. The registry entry says why it has none; Dependabot and the CI test job are the trigger.
