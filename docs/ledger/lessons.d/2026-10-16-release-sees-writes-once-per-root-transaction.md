## 2026-10-16 — a guard that must see "was anything written?" counts rows on the driver once per ROOT transaction and flags what is not a plain read; a plain `in_transaction` flag cannot tell a read pin from a write (PR #1418)

**What was found.** `release_idle_connection` (`src/database/session.py`) ends a read transaction so a pooled connection goes back, and it declined only on what the ORM and its own flags recorded; a write sent round the ORM (`session.connection().execute(...)`, a Core statement) sets none of them and the rollback that freed the connection discarded it without a sound. `query.py` had a private guard for its own path (the driver's `in_transaction`); the collector and the all-diagnostics build called the bare helper. A schema change (`CREATE`, `DROP`, `ALTER`) or a header `PRAGMA user_version = n` under an explicit BEGIN moves no row count and was discarded the same way.

**The rules.**
1. **`in_transaction` cannot tell a read pin from a write, so it cannot live in the primitive.** SQLite reports it for an explicit `BEGIN` (the `read_snapshot` recipe) exactly as for a write; putting it in `release_idle_connection` reddens `tests/test_all_diag_read_release.py::test_a_pinned_snapshot_is_released_at_the_boundary_so_the_log_can_be_checkpointed`, which is the only reason that test exists. What a read pin does not do is change a row: compare the DBAPI connection's `total_changes` (it exists on `sqlite3` and `sqlcipher3.dbapi2`) with a value taken when the transaction began, and decline on any difference, on a count that cannot be read, on a transaction with no recorded start, and on a session bound to two connections.
2. **SQLAlchemy's `after_begin` fires for a SAVEPOINT as well as for the root transaction: a "state at the start" guard is taken once per ROOT transaction.** The first build retook the baseline when a savepoint began, with an unseen write already in the count, so the release saw "nothing changed" and the rollback discarded the row (reproduced: the row was gone). Guard the listener by "this connection already has a baseline" and clear it in `after_transaction_end` when `transaction.parent is None`; test a write BEFORE a savepoint and one INSIDE it.
3. **A row count is blind to everything that changes no row; for that, ask the statement, with an allowlist where an unknown statement is NOT a read.** An `Engine` `before_cursor_execute` listener flags the connection when `statement_kind.is_plain_read` says no (SELECT, WITH, VALUES, EXPLAIN, BEGIN, SAVEPOINT, RELEASE and the read-only PRAGMA forms; `PRAGMA name = value` and `PRAGMA name(value)` are writes for the header names, and a pragma that acts, such as `wal_checkpoint` or `key`, is on neither list). A deny-list of write verbs would read the next statement SQLite grows as a read. The flag costs about 0.36 microseconds per statement (measured), and its price is stated: an UPDATE that matched no row declines the release too, which loses nothing (the connection stays until the caller's own commit).
4. **A sentence in a docstring that says what a guard does not see is a test target.** The DBAPI cursor, used directly, bypasses SQLAlchemy's statement events and moves no row count for a schema change; the limit is written in `release_idle_connection`'s docstring and in the queue entry, and no caller does it. The day one does, route the statement through `session.connection()`.
5. **A count-only drain is a gate hold nobody wrote a policy for.** `reindex_all_batch`, the corpus re-index job and the re-index that ends a restore ended a batch by its width alone, so a save from the UI waited behind up to 200 articles (36 s at the field's rate, 60 to 175 s on the machine that crashed). Hand every drain the one policy (`merge.reindex_flush_policy`, `OO_REINDEX_HOLD_TARGET_S`, 0 = the count-only rule) and publish `batch_commits`, `early_batch_commits` and `longest_batch_s` from each, so a drain that forgets the policy is a test failure and not an operator's wait.
6. **A mutant harness that parses test logs reads `FAILED ` lines from `-rf`, never the word "failed".** A log WARNING containing "failed" read as a kill and hid a surviving mutant for one round; a battery killed mid-run was run on stale code, so the worktree stays untouched while a battery or a mutant run uses it.
