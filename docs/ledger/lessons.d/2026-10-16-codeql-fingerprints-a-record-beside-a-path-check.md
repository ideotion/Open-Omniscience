## 2026-10-16 — a record written beside a path check turns the finding that was already on main into a new finding of the pull request: the check and the lines after it stay exactly where main has them, and the record is written by a net round the function header (PR #1421)

**What was found.** The first push of the run records (`42246e6e1`) made the pull request's CodeQL check go red with six HIGH `py/path-injection` alerts: the three volume starts' `is_dir()`, the legacy restore's `is_file()` and `read_bytes()`, the folder restore and verify start's `is_dir()`. None was a new flow. Main already had the same six statements with the same request-supplied paths reaching them; what the push changed was the text on and after them. A record had been written inside the branch (`run_refused(...)` between `if not destp.is_dir():` and its `raise`), the check had been split into `is_folder = destp.is_dir()` plus a later `if not is_folder:`, and a `run_ended(...)` had been put inside the `except OSError` that follows `data = p.read_bytes()`.

**The first cure was not enough.** `62e1eca87` put the original text back and wrapped each check in a context manager (`with run_refused_if_raised(...):` round the unchanged `if`), so the statement and the 100 characters after it hashed as on main (a script that reimplements the fingerprint said `OK` for all six). The check stayed red with the same six alerts on `125c1c0bc`. What a wrapper does that a fingerprint does not see: it moves the statement one level IN, so every sink line is a CHANGED line of the diff (`git diff -U0 origin/main` lists it as `+`), and code scanning reports a finding on a pull request for a line the pull request changes. (Reconstructed from the outcomes, not from GitHub's source; the proof is the next paragraph.)

**The verdict.** On `4b3c1390b` the six statements are context lines of the diff, at their original columns, with the same text after them, and the `CodeQL` check reads "No new alerts in code changed by this pull request" (green) while `Analyze (python)` ran the same analysis on the same code. What the cure was, in one line: not the fingerprint alone (`62e1eca87` matched it and stayed red) but the fingerprint AND the line not being part of the diff.

**How the fingerprint reads (reconstructed).** `primaryLocationLineHash` is the hash of 100 characters starting at the first non-blank character of the alert's line and running forward, spaces and tabs skipped; a repeat of a hash in one file gets a `:2`, `:3`. So what moves a fingerprint is the sink line itself and the next ~100 non-blank characters after it. Equal fingerprints are necessary and were not sufficient.

**The rules.**
1. **A path-check statement keeps its text, its column and the ~100 non-blank characters after it, and is not a `+` line of the diff.** No record, log line or metric goes on it, in its branch, in the handler of the read that follows it, or in a `with` round it. The record is written from OUTSIDE the function body: `storage_events.run_refusals_net(kind, via=, refused_as=)` is a context manager on the existing `with self._lock,` header of each start (and a decorator on `restore_legacy_path`); a run is opened and closed by `storage_events.run_open(...)` on the `with` that already converts the legacy restore's errors. A pre-push check says it in three facts per sink line: not an added line, same indentation as on main, same following text (`git diff -U0 origin/main`).
2. **The net reads the CLASS of what leaves, never its words.** The records guard (`tests/test_sink_sweep_records.py`) lets a caught exception reach only `type()`, `isinstance()` and the scrubbing calls, so a net that told `"... is not a folder."` from another sentence by its ending failed it. `refused_as` is a tuple of (class, key of `RUN_REFUSALS`) pairs; an `OSError` is `path-unreadable`; any other error is not named. A class stands for a place, so the tests read every `raise` of the guarded functions: the only un-recorded `raise` of a named class under a net may be the end of a path check (`if not x.is_dir():` / `is_file()`), and any other must be recorded where it is raised (`test_the_net_stands_for_a_raise_only_where_it_is_the_path_checks_own`).
3. **One start, one record.** A `ContextVar` scope marks that a refusal or a run was already written, so the net writes nothing for a start that recorded its own, a nested net marks the ones round it, and the scope ends with the start.
4. **A new finding on a pull request is not always a new flow.** Before reading it as a defect in the change, check whether the same statement is on the base branch (`git show origin/main:<file>`): if it is, the change moved something about it, and the cure is the text and its place, not a dismissal.
5. **Python 3.13's `Path.is_dir`, `exists` and `is_file` re-raise every `OSError` but a missing path**, so the net's `path-unreadable` refusal is a real branch there, not dead code.
6. **What the net cannot do.** An HTTP error built from another in a handler reaches `run_open` as an `HTTPException`: the record's failure class is the response's, not the engine's (`ArtifactError`, `PermissionError`), because reading the chain is a read of the exception that the records guard refuses. The inline `refused` and `stopped-by-operator` outcomes written in the handlers stay.
