## 2026-10-16 — a record written beside a path check turns the finding that was already on main into a new one: GitHub's CodeQL fingerprints a finding by the statement and the text that follows it, so the record wraps the check from outside and the check keeps main's text (PR #1421)

**What was found.** The first push of the run records (`42246e6e1`) made the pull request's CodeQL check go red with six HIGH `py/path-injection` alerts: the three volume starts' `is_dir()`, the legacy restore's `is_file()` and `read_bytes()`, the folder restore and verify start's `is_dir()`. None was a new flow. Main already had the same six statements with the same request-supplied paths reaching them; what the push changed was the text on and after them. A record had been written inside the branch (`run_refused(...)` between `if not destp.is_dir():` and its `raise`), the check had been split into `is_folder = destp.is_dir()` plus a later `if not is_folder:`, and a `run_ended(...)` had been put inside the `except OSError` that follows `data = p.read_bytes()`. GitHub's PR check compares the alerts of the head with the alerts of the base by `partialFingerprints`, so an alert whose fingerprint is not on the base is reported as new, whatever its line number.

**How the fingerprint reads (reconstructed, not copied from the action; the proof is the check on the next head).** `primaryLocationLineHash` is the hash of 100 characters starting at the first non-blank character of the alert's line and running forward, spaces and tabs skipped, line ends counted; a repeat of a hash in one file gets a `:2`, `:3`. So what moves a fingerprint is the sink line itself and the next ~100 non-blank characters after it, and NOT the lines before it, NOT the indentation and NOT the line number. A script that computes it for the sink lines of a file on `origin/main` and on the head, and says whether each hash is still there, tells before a push whether a change has moved a finding (it said `DIFF` for all six on `42246e6e1` and `OK` for all six after the fix).

**The rules.**
1. **Do not edit a path-check statement, or the lines that follow it, to add a record, a log line or a metric.** Wrap it from the outside: `with storage_events.run_refused_if_raised(kind, key, ValueError, via=...):` around the unchanged `if not destp.is_dir(): raise ValueError(...)`, and `with storage_events.run_ended_if_raised(note, "error", OSError):` around the unchanged `data = p.read_bytes()`. The wrapper catches the one exception the statement raises, records, and re-raises it unchanged, so the caller sees what it saw before the record existed. Indentation does not count, which is what makes a wrapper free.
2. **A new finding on a pull request is not always a new flow.** Before reading it as a defect in the change, check whether the same statement is on the base branch (`git show origin/main:<file>`): if it is, the change moved a fingerprint, and the cure is the text, not a dismissal.
3. **A structural test that reads the AST for "a record precedes the raise" has to learn the wrapper form**, and a second test pins that nothing under a wrapper is a `storage_events` call (`test_the_path_checks_stay_as_written_and_the_record_wraps_them_never_sits_inside_them`), or the next edit puts the record back inside and the alert comes back with it.
4. **Python 3.13's `Path.is_dir`, `exists` and `is_file` re-raise every `OSError` but a missing path**, so `run_path_checked`'s `path-unreadable` refusal is a real branch there, not dead code, and it stays outermost of the two wrappers.
