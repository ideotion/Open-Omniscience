## 2026-11-08 — what moves the write gate's hold for one flush on an encrypted store: the pool's checkout order a little, the page-cache size and the auto-checkpoint threshold not at all, memory security possibly a lot (R470; PR #@@PR@@)

**What was found.** The 07 Nov Windows run held the write gate for 36 to 68 s per long hold with 83 to 97 percent of those seconds in thread CPU, and nothing explained the cost. Measured on a Linux VM (SQLCipher 4.19.0, SQLite 3.53.4, 16 KiB pages, a 4.4 GB encrypted store, a throwaway key, scratch only): one flush of 8 articles (640 mention rows) touches about 3,060 pages and dirties 2,539 WAL frames (41.7 MB); its hold is 0.55 s wall and 0.43 s CPU at the default 64 MiB cache. (1) `cache_size` 64 MiB to 1 GiB changes the hold by 0.09 s only; with 72 pooled connections 256 MiB each would be 18 GiB, so the setting stays. (2) The pool handed out connections first-in-first-out, so every checkout rotated to a connection with a cold cache: 3,076 pages read before COMMIT and 0 of 84 flushes warm; last-in-first-out read 2,151 to 2,322 pages with 50 to 54 of 84 flushes warm, worth up to about 0.05 s of CPU per flush (an upper bound: another connection's commit drops the cache). (3) `wal_autocheckpoint` 1000, 10000 and 0 gave a mean hold of 0.532, 0.524 and 0.415 s; 10000 moves the checkpoint into 7 of 30 commits (a worse tail), and 0 saves 0.12 s but the WAL reached 1.46 GB in 35 flushes (the storage guard's `wal_high`). (4) `cipher_memory_security` ON raised the hold CPU by 64 percent here (this build reads it as 0) and a SAVEPOINT from 0.008 to 0.129 s: it is the one lever with a plausible 100-times cost on Windows (locked pages), and it has not been measured there.

**The rule.** Before turning a knob for a long gate hold, measure the whole flush with the production page size and pool shape; a setting that looks like the cause (a bigger cache, a different checkpoint threshold) may be worth less than the connection order, and the one lever that could matter is a build property nobody had read. So: the pool is last-in-first-out (`pool_use_lifo=True`, the same ceilings and slot accounting); no pragma changes; the machine record now carries the SQLCipher build (provider, provider version, memory security) so the next Windows bundle names the lever's state, and the gate's `total_hold_cpu_s` says whether a hold was work or waiting. A checkpoint outside the gate would be a design item that needs its own ruling and a Windows measurement. Turning `cipher_memory_security` off is a security-posture decision for the maintainer, not a tuning step.

**What changed.** `src/database/session.py` (`pool_use_lifo=True` on the SQLite engine), `src/database/writer.py` (`total_hold_cpu_s`), `src/monitoring/machine_record.py` (`versions.sqlcipher_build`, read through a throwaway in-memory database with a random raw key kept nowhere, failing closed).

**Pinned by** `tests/test_pool_lifo.py` (the real engine's pool is LIFO and still a `ReservingQueuePool`; a returned connection is the next one handed out; the collector ceiling and slot counts are unchanged, one thread per slot, because same-thread collector checkouts are nested and take no slot), `tests/test_write_gate_hold_cpu.py`, `tests/test_machine_record_sqlcipher_build.py` (the key text is in neither the record nor the log).

**Stated limits.** One Linux VM, one store, 84 and 30 flush samples; the Windows cost of each lever is not measured, and the pool-order saving is an upper bound. The numbers describe a flush of 8 articles, not an import of thousands.
