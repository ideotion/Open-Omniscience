## 2026-10-16 — a memory budget is a model you fit and test, not a number you guess (rollup build, PR #1422)

**Found.** The in-memory keyword rollup build stopped at DuckDB's 1,004 MB limit on every boot of a 12 M-mention corpus. The first guess (the stage rows are small, 76 MB in a file) was wrong by a factor of nine: an in-memory DuckDB table is NOT compressed (the same rows were 659 MB resident with the original column types, 438 MB with INTEGER ids, 389 MB with all INTEGER), and one `GROUP BY` with `COUNT(DISTINCT)` over the whole stage then needs a hash table about the size of the stage again. Measured peak of the single pass: 1,986 MiB, and it needed a 2,400 MB limit to finish.

**Fix and how it was proved.** Cut the stage by `keyword_id % shards` (a rollup row is one keyword on one day, so the cuts are independent whole groups), aggregate one shard at a time and DROP its stage as soon as it is aggregated. Peak at 1,004 MB: 602 MiB DuckDB (polled by a concurrent cursor, an upper reading; the build's own synchronous boundary reads gave 403 MiB, see the 2026-10-17 lesson item 5) / 896 MB RSS, content and meta digests identical to the single pass, build time 1% to 6% slower. The shard count is DERIVED: `peak(k) = base + aggregate / k + overhead * k` with 40 and 92 bytes a mention and about 2 MiB a table, fitted to the measured peaks at 1, 2, 4, 8, 16 and 32 shards, and a test (`tests/test_rollup_sharded_build.py`) reproduces three of those peaks within 5%, so a DuckDB bump that changes the memory behaviour fails a test instead of a customer.

**Rules this gives.**
1. Measure the resident size of the structure you are budgeting, in the engine and the configuration the user runs (offload off, encrypted); a file size or a different configuration proves nothing (a first baseline "succeeded" only because DuckDB spilled to `.tmp`).
2. Derive a size from the limit and write what the margin protects next to the constant; a fixed shard size is the same guess with a smaller number.
3. When the engine's own limit is hit, split the unit of work and try again a bounded number of times, then decline with the same named vocabulary as every other stop; never retry a non-memory error, and never leave a partial rollup served (the swap is a rename inside a transaction).
4. Extrapolations beyond what was streamed are labelled inferred: 24 M mentions was measured on a replicated stage file, not a streamed run.
