## 2026-11-08 — a test that ends while its background build still runs starves the next test's build (PR #1843)

**What was found.** `test_figures_are_served_stale_rather_than_recomputed_inline` missed its 10 s wait on #1828's shard 3, on a PR that src/ never imports. The test before it in the file (`test_stats_and_library_overview_share_one_cache_mechanism`) calls `library_figures` cold, which kicks a background count holding the `db:figures` build lock, and the autouse teardown's `invalidate()` then bumps the generation, so that count stores nothing when it ends. If it is still running when the next test calls cold, `_kick_background_refresh` finds the lock taken and starts nothing, and the next test waits for a refresh that never comes. On an idle machine the count ends first. On a loaded 4-CPU runner it does not. Reproduced deterministically by making the first count sleep 12 s.

**What it cost.** A red required check on an unrelated PR and a steward's diagnosis. The 10 s deadline was a timing bet that a loaded runner can lose.

**The rule.** A test that kicks background work must not hand the next test a lock or a thread it left running. The cache tests' autouse fixture now waits for every in-flight build to release its lock before it invalidates, and `_wait_for_refresh` waits on the build lock (a build stores before it releases) instead of polling against a deadline. The only timeout left is a 120 s hang guard. Load can make the test slower but never red, and the assertions are unchanged. When a wait in a test has a deadline, ask what event the deadline stands in for, and wait for that event.
