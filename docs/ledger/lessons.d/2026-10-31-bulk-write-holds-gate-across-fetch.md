## 2026-10-31 — a bulk statement takes the write gate at once and nothing releases it until a commit: the housekeeping lane carried it across the next outlet's network work

**What was found (P-A; field diagnostics 9931cffe, build a38defa27, 2026-10-28 20:43; the WAL lane's check of the zip).** `gate_hold`: `oo-housekeeping-lane` held the write gate for 2,933 s, 2,666 s of it BETWEEN statements, phase samples python 142 / execute 50 / commit 1, stack at the end `safety.fetcher:send <- _send <- ingest.airplane:_guarded_getaddrinfo`. The record carried no lane kind, so the step was unknown. Read on main: `_lane_step_crawl` ends each outlet with `session.query(Source).filter(...).update(...)` (the sibling feeds' `last_crawled_at`). A bulk statement does not fire `before_flush`; the gate's `do_orm_execute` hook takes the gate AT ONCE and sets the session's gate flag (`_oo_write_gate_held`), which is cleared only at the outermost transaction end. Nothing committed after it, so the NEXT outlet's `discover_sitemap_urls` and its page walk ran with the gate held, until the first batch flush of that walk, and so on down the rotation. The fetcher the lane hands its steps (`wrap_fetcher`) hands a session's connection back before a fetch only when the session has not written, so it declined, by design: `run_housekeeping_lane`'s own comment names the limit ("a kind that leaves the session DIRTY across its own fetch loop ... is correctly DECLINED"). That comment named the limit and the kind it was about was never fixed. REPRODUCED before the fix with a real gated session and recorders in place of the network: outlets two and three fetched with the flag set (`('discover', 'b', True)`, `('crawl', 'b', True)`, ...), outlet one with it clear. The same shape held on the failure path (an outlet that raised after writing was swallowed with its write open).

**The fix.** `_lane_step_crawl` commits after each outlet's stamp and after a recorded sitemap (the walk fetches page after page), and rolls back an outlet that failed; `run_housekeeping_lane` commits after each kind, so no kind hands the next a session that holds the gate (and a later kind's failure rollback no longer discards an earlier kind's uncommitted writes). Each step runs under the fixed pool-watch label `lane:<kind>` (`pool_watch.set_endpoint`, the kinds are a fixed set, never a path), and the `gate_hold` closing record reads `pool_watch.work_label()` when no request template exists: a label set without a method or scope names work the app started itself, a request always carries both. The watchdog's samples already read the label of the holder's checkout, so they name the lane as well.

**The rule.** A bulk `Query.update()/delete()` or `session.execute(insert/update/delete)` is a gate holder from the statement, not from the flush. A loop that writes bookkeeping and then fetches must commit between the write and the fetch; "dirty across the fetch is declined by the release" is a description of the cost, not a safe state. Other steps of the lane (markets, calendar, law, hazards, qualification, backfill) were read for the same shape; their library calls commit on their own paths or write after their fetches, and the per-kind commit now covers any that do not.
