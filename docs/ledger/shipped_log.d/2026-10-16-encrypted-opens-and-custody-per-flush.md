## 2026-10-16 — encrypted opens are counted per pass, and the custody log is opened once per flush instead of once per stored article

The export lane's investigation of "one collector thread spends 41 CPU-seconds a minute on encrypted-connection key derivation" (coordinator's ruling of 2026-10-16: build the counter A and the per-flush custody log B as one local bundle on the extraction-lock bundle; C, a per-thread cached connection, waits for A's field numbers and needs its own ruling because it keeps a keyed connection and the signing key for a thread's life).

**A, the counter** (`src/database/open_stats.py`, wired in `connect._connect` around each keyed attempt on an existing encrypted file; a failed attempt and each page size tried count, since each pays the derivation; plaintext opens and the creation of a new file do not). The collection monitor opens the window when a pass starts and writes `encrypted_opens` into the pass's summary line in `collect_perf.jsonl` and, through the scheduler, into the run report in `scheduler_runs.jsonl` (the `scheduler.recent_runs` member of the debug bundle, last 30 runs), the same two places as `extraction_lock`. Numbers and two closed vocabularies only: `file` is one of the app's own database file names else `(other)`, `thread` is the family of the opening thread's name else `(other)`; never a path, a full thread name, the key or an exception's words. Per (file, thread) row: opens, failed, `cpu_s` (the opening thread's own CPU), `wall_s`, `wall_max_s`, and `cpu_unmeasured` where the CPU clock could not be read (`cpu_s` is absent when none could). Rows are capped at 32 kept and 11 printed, the rest in an `(others)` row; the totals are exact. A full block measured 2.1 KB. `safe_snapshot` returns `{"unavailable": <class>}` on a failure. A statistic never fails an open: `begin`/`end` swallow their own faults.

**B, the custody log per flush** (`_CustodyBatch` in `src/ingest/pipeline.py`, used by `ArticleBatch._flush_batched`): one `CustodyLog` for the whole final loop of a flush, opened when the first entry is written and closed when the `with` block ends, dropped after a failed write so the next article opens a fresh one, as every article did before. The entry's fields are read before the log is touched, so an article read that fails (an exhausted pool, CUST-1) neither costs the batch a healthy log nor opens one for nothing; the failed entry is still queued as owed (`pending.note_failed`). The unbatched paths (`store_fetched`, the per-article redo after a failed batched commit) call `_maybe_record_custody(article)` unchanged. Measured on the probe (real pipeline and pool, an encrypted store, two CPUs, 96 articles, flush size 8): opens 118 to 32, process CPU 51.7 s to 34.3 s, wall 45.9 s to 30.3 s; with two articles per flush 22 custody opens became 7.

**Not claimed.** The field bundles put custody at about 2 CPU-seconds a minute for the whole process (12.5 articles a minute), not 41 for one thread: the counter exists to say what the 41 is. The benchmark stores every fetched page as new, which the field does not.

`tests/test_open_stats.py` (83 tests) and `tests/test_custody_batch.py` (13): 46 mutants across `open_stats.py`, `connect.py`, `collect_perf.py`, `runner.py`, `pipeline.py` and `batch.py`, 45 killed; the one that survives (the run report reading the block from the monitor after the pass instead of from the summary line) reads the same window and is equivalent.
