## 2026-10-16 — encrypted opens are counted per pass, and the custody log is opened once per flush instead of once per stored article

The export lane's investigation of "one collector thread spends 41 CPU-seconds a minute on encrypted-connection key derivation" (coordinator's ruling of 2026-10-16: build the counter A and the per-flush custody log B as one local bundle on the extraction-lock bundle; C, a per-thread cached connection, waits for A's field numbers and needs its own ruling because it keeps a keyed connection and the signing key for a thread's life).

**A, the counter** (`src/database/open_stats.py`, wired in `connect._connect` around each keyed attempt on an existing encrypted file; a failed attempt and each page size tried count, since each pays the derivation; plaintext opens and the creation of a new file do not). The collection monitor opens the window when a pass starts and writes `encrypted_opens` into the pass's summary line in `collect_perf.jsonl` and, through the scheduler, into the run report in `scheduler_runs.jsonl` (the `scheduler.recent_runs` member of the debug bundle, last 30 runs), the same two places as `extraction_lock`. A pass without a monitor (the sequential path) writes no block, and the step that repays owed custody entries runs after the window is read. Numbers and two closed vocabularies only: `file` is one of the app's own database file names else `(other)`, `thread` is the family of the opening thread's name else `(other)` (`oo-<word>` of at most 16 letters, or a fixed name from a list including the real `AnyIO worker thread`); never a path, a full thread name, the key or an exception's words. An AST scan of the `Thread`/`ThreadPoolExecutor` calls in `src` fails an `oo-` name that does not start with a literal word. Per (file, thread) row: opens, failed, `cpu_s` (the opening thread's own CPU), `wall_s`, `wall_max_s`, and `cpu_unmeasured` where the CPU clock could not be read (`cpu_s` is absent when none could). The window keeps the first 32 pairs it sees and prints the 11 with the most CPU, the rest summed in an `(others)` row; the totals are exact. A block is 2 KB typically and at most 3.2 KB, 30 reports at most 97 KB (computed in a test from the real `snapshot()` over the longest strings and largest numbers). `safe_snapshot` returns `{"unavailable": <class>}` on a failure. A statistic never fails an open: `begin`/`end` swallow their own faults. `connect.py` imports `open_stats` unguarded (it imports only `re`, `threading` and `time`), so a fault in that module is a code fault that stops every open.

**B, the custody log per flush** (`_CustodyBatch` in `src/ingest/pipeline.py`, used by `ArticleBatch._flush_batched`): one `CustodyLog` for the whole final loop of a flush, opened when the first entry is written and closed when the `with` block ends, dropped after a failed write so the next article opens a fresh one, as every article did before. A log fixes its anchoring mode, its PQC flag and the key when it is opened, so each entry compares the custody settings it was just read with, and whether the process still has a passphrase, with what the log was opened under, and a log opened under others is dropped first: OpenTimestamps consent withdrawn mid-flush (invariant #14f) and a crypto-erase mid-flush take effect at the next entry, as they did when every entry opened its own (found by the independent read; tested with a stamp counter and with a real encrypted store). The entry's fields are read before the log is touched, so an article read that fails (an exhausted pool, CUST-1) neither costs the batch a healthy log nor opens one for nothing; the failed entry is still queued as owed (`pending.note_failed`). A failed INSERT leaves a transaction and a write lock open until the connection is closed; the test fails a real INSERT (a duplicate entry hash) and takes the write lock from a second connection straight away. The unbatched paths (`store_fetched`, the per-article redo after a failed batched commit) call `_maybe_record_custody(article)` unchanged. Measured on the probe (`keyword-export/reopen-2026-10-16/probe.py` in the project files, not in the repo: real pipeline and pool, an encrypted store, two CPUs, 96 articles, flush size 8): opens 118 to 32, process CPU 51.7 s to 34.3 s, wall 45.9 s to 30.3 s.

**Not claimed.** The field bundles put custody at about 2 CPU-seconds a minute for the whole process (12.5 articles a minute), not 41 for one thread: the counter exists to say what the 41 is. The benchmark stores every fetched page as new, which the field does not. The cost of one derivation is 163 ms of thread CPU (median of 20, range 158-208 ms, one pinned core), measured on the development machine, not on the user's VM.

`tests/test_open_stats.py` and `tests/test_custody_batch.py` (111 tests together): 58 mutants across `open_stats.py`, `connect.py`, `collect_perf.py`, `runner.py`, `pipeline.py` and `batch.py`, all killed but one (57 of 58) that differs from the original only by opens landing between the summary line and a second read of the same window (the run report reading the block from the monitor after the pass instead of from the summary line).
