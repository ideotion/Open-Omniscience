## 2026-10-27 — `fts.fts_status` now reports the full-text index's own population and names an index that is empty, or whose tail is missing, as unhealthy; the integrity report's `delta` is the first one that can be non-zero (0.5.1 item 29 follow-on, PR #1534)

**The defect (a clear one).** `article_fts` is an external-content FTS5 table (`content='articles'`), so `fts_status`'s health probe (`SELECT rowid FROM article_fts LIMIT 1`) and its count (`SELECT count(*) FROM article_fts`) are answered from the `articles` table, not from the index. Measured on a 300-article store after `INSERT INTO article_fts(article_fts) VALUES ('delete-all')`: `article_fts_docsize` 0, `fts_status` present, healthy True, `rows` 300, `count_status` "ok". The function's docstring said it reports "a damaged/incomplete index"; for this table it could not. The same defect sat one level up: `monitoring/integrity.py` computed `delta = articles - fts_rows` with `fts_rows` the content count, so the delta was always 0 (or None), beside a note saying "a large delta means the index is stale". `backup/merge.py` had named the gotcha and probes `article_fts_docsize` for its own restore; `fts_status` had not been taught it. Found by an independent read of the item 29 tests, which ended on `fts_status` rows equal to the articles and could not fail. The Export lane's separate settle-it measurement (14 real SIGKILLs and 3 clean runs on a 40,000-article store; 400,000 for probe costs) found the same blind spot from the other side: a PREFIX index (some rows, not all; constructed, no app writer makes one, a torn file copy or a hand-made restore could) read as settled everywhere: boot said `skipped`, `fts_status` said healthy with `rows` equal to all the articles, and search returned about half.

**What changed (`src/database/fts.py`, `src/monitoring/integrity.py`).** `fts_status` gains step 4, one bounded block (the count deadline, 15 s): the shadow table's presence from `sqlite_master`, then ONE statement that returns `max(id)` of `articles`, `COUNT(*)` of `article_fts_docsize` and `max(id)` of `article_fts_docsize`. New keys: `indexed_documents` (the index's own count), `indexed_status` (ok | timed_out | error | skipped | `unprobeable`, the last for a `columnsize=0` build with no shadow table, which is never rebuilt on that account), and `index_state`, what the index's ENDS say: `"empty"` (no document while `articles` has a row), `"partial (inferred)"` (its highest document id is below the highest article id: a tail of the articles is not indexed; INFERRED from two ends, how many are missing is unknown) or `"ends-agree"` (neither seen; the words say what was compared, and it is neither agreement nor a proof of completeness), `None` when unknown. Empty and partial both set `healthy` False with a fixed `error` label (`EmptyIndex`, `PartialIndex`): the empty state is the one `ensure_fts` heals at the next start, a re-index heals either now. The label never replaces an error the content count already named (`count_status` says it failed, the class stays, `index_state` carries the verdict). NOTHING is repaired and no article is counted: the boot's refusal of `count(*) FROM articles` (74 s cold on a 2.7 GB encrypted corpus) stands, and the boot still skips a prefix index. A timeout or an error anywhere in step 4 clears all three keys (the verdict is applied only after the statement has come back), and an error step 4 meets never replaces one an earlier step already named. `rows` is unchanged and its docstring now says what it reads. The integrity report counts `articles` BEFORE it reads the index, so a concurrent ingest can only push `delta` below zero; its `fts` block gains `indexed_documents`, `indexed_status`, `index_state`, keeps `fts_rows` (the content table's count, for readers of earlier reports), and `delta` is now `articles - indexed_documents`, which is also what sees a hole the ends cannot. The one new `failure_text(exc)` sink is registered in `tests/test_sink_sweep_records.py` (3 to 4).

**Why ONE statement (the first version was wrong, and an independent read proved it).** The first version read the articles' top id first (it only grows, so an ingest between the reads could only leave the index ahead) and asked it once more when the ends disagreed (a delete of the top articles takes their index rows in the same transaction). The delta read reproduced a fully indexed store, ids [1, 2] in both tables, reading `partial (inferred)`: the top id is read (2), the top article is deleted (a deleted source cascades to its articles), the index's count and top id are read (1, 1), a new article is ingested and, with no `AUTOINCREMENT`, takes the free id 2 and is indexed by its trigger, and the second look reads 2 above 1. The same shape reads an index of an emptied store as empty. Ids are reused, so no order of separate reads is safe, and the second look was itself a read after the thing it guarded against. Measured (`item29s/one_statement_snapshot.py`, 20,000 articles, a Python function in the middle of the statement that makes another connection delete the top article): in WAL mode the writer commits and the statement still returns (20000, 20000, 20000), all three numbers from the snapshot it started in; in rollback-journal mode the writer is refused (`database is locked`) until the statement is done. One statement also removed a branch, a re-read and two tests' worth of machinery.

**Tests (`tests/test_fts_status.py`, 17 new functions, one parametrized twice, and 2 extended; `tests/test_repair_search_index.py`, 4 added).** Whole index: 1 document, `ends-agree`. Emptied under its articles: healthy False, `empty`, `rows` still 1 (the reason the key exists), `error` "EmptyIndex". Empty index over no articles: healthy, not called empty. A tail missing (a second article no trigger indexed): `partial (inferred)`, healthy False, "PartialIndex", `rows` 2 (cannot show it), the integrity `delta` 1 where it used to be 0. A prefix of 10 of 20 articles through the app's own `index_articles`: named, and no statement taken at the cursor is a count of the articles however it is spelled. A HOLE IN THE MIDDLE, built the way a missing tail turns into one (article 2 never indexed, the trigger back, article 3 indexed): `partial (inferred)` before the ingest, `ends-agree` and healthy after it, and the integrity `delta` 1: the stated limit, pinned so it cannot be forgotten. An index AHEAD of its articles (a document whose article is gone, the delete trigger dropped): `ends-agree`, delta -1. An id freed by a delete and taken again by an ingest: whole. The three numbers come from one statement (a spy; a statement that carries fewer is red). A slow count; the population inside a deadline of its own; a failed read keeps the class only; an earlier error is not replaced by the population's failure, and a corruption error on the content count beside an empty or a partial index stays the one named while `index_state` and `healthy` carry the verdict; a `columnsize=0` index: unprobeable; no index and no backend: unasked; the failing-probe parameter set gains the population read. THE EXPORT LANE'S TESTS (its draft, `export-lane/fts-settle/test_fts_interrupted_rebuild.py`, joined `tests/test_repair_search_index.py` under its name): a full "always" rebuild that dies after two batches leaves the whole old index and a boot says `skipped`; an emptied index whose heal dies after two batches stays empty and the next boot rebuilds it; a strict xfail that a boot repairs a prefix index (it does not, by design, and flips only when one does); and one more test that `fts_status` names that same prefix while the boot still skips it. **Stated limits.** (1) A HOLE IN THE MIDDLE or a missing HEAD is not seen by the ends: `ends-agree` says what was compared, not that the index is whole; only a count comparison or a walk key by key sees those, and the count of `articles` is the scan the boot refuses. The integrity `delta` is the count comparison, inside its own 15 s. (1b) A MISSING TAIL becomes a hole in the middle at the next ingest (the new article is indexed by its trigger, the ends agree again), so `partial (inferred)` is a window that closes with the next collected article, and only the integrity `delta` still shows it; an index that holds documents beyond the highest article id reads `ends-agree` too. (2) `partial (inferred)` does not say how many documents are missing. (3) An index read while `ensure_fts` is still building it on a store that already has articles (boot, `init_db`) reads empty or partial until the first build is done: a false alarm in that window, which the docstring says. (4) The integrity report's `drift` verdict (`_verdict`) does not read the `fts` block, before or after; a bad index shows in `fts.healthy`, `fts.index_state` and `fts.delta`, not in `drift`. (5) The `unprobeable` build is rare and unseen in the field (every index the app creates has the shadow table); its test builds one by hand. (6) The statement costs two id lookups and the shadow table's own count: Export measured the ids at 0.1 to 0.25 ms warm and plaintext at 400,000 articles and the count at 2.5 ms; the cold encrypted figure is not measured (it is a b-tree end lookup, expected not to scale with the corpus), and the count was not timed on a 1 M-article store here. (7) The prefix index is constructed: no app writer makes one, so this is a diagnostic for a torn copy or a hand-made restore, not a repair. (8) The "interrupted" mapping in `salvage._raise_for_target` that the item 29 shipped log names as a dead line is unchanged and still has no source today.

**Later note (2026-10-27, PR #1543).** (1) The 74 s cold figure for a count of articles quoted above was not reproduced on the current schema (a count over a covering index took 0.24 to 0.33 s cold at 1,000,000 articles); the boot's refusal to compare counts is a decision that stands, not a measured necessity. (2) "One bounded block" is true of the block, not of every statement in it: SQLite runs the shadow-table `count(*)` as one opcode that the deadline's progress handler is never consulted during, so that count is bounded only by the table's size (one short row per article; 61 to 82 ms cold at 1,000,000 articles). The cold cost of the ends and of the 1 M-article count, listed above as not measured, was measured afterwards (`wal-lane/cold-encrypted-1m-measurement-2026-10-27.md`).
