## 2026-10-28 — a restore waits for the collector to leave the corpus before it copies it, and the import dialog says what its pause is and is not (R360)

**What was found.** The exclusive window (`runner.exclusive_window`, `pause_for_exclusive_operation`) stops the `oo-scheduler` loop with a bounded join (10 s) and blocks the next `run_now`. A pass deep in a write can outlive that join (one recorded at 39 minutes), and a pass started by Run now before the window opened is untouched. `run_restore` read the window's return as "collection is paused", took the working copy, merged into it and swapped it in, so anything such a pass committed after the copy was discarded by the swap. The import dialog said "Background collection is paused for this whole import and resumes when it finishes." and the restore's own docstring said "nothing else is expected to write the live corpus"; the writers the window never reaches (the housekeeping lane with its crawl and backfill, the Wikipedia drain, most registered background jobs, AI sweeps, boot upkeep, 317 API write routes) were named nowhere a person reads.

**What changed.**
- Defect: `src/backup/collector_exit.py` (new), called from `run_restore` (`src/backup/merge.py`) before the snapshot, only for an owner restore that takes a fresh working copy. `wait_for_collector_exit` waits at most 600 s (`COLLECTOR_EXIT_WAIT_S`) for the loop thread and the scheduler's busy flag, polling every second and honouring Stop; the answer (`confirmed` True / False / None with `waited_s`, `bound_s`, `still`, `reason`) goes into `report["collector_exit"]` and a `collector_exit` run-log milestone. The wait is also a timed sub-stage (`snapshot_working_copy:wait_for_collector`, journalled at its begin, never pinged as a phase) and publishes itself in the module, so `ImportQueueManager.status()` carries `collection_exit_wait` while it waits and `collection_exit_unconfirmed` from the moment the wait gives up (the running item is read from the published answer, a finished item from its summary when the restore's own report says its copy reaches the corpus (swapped, staged, or done and not refused): a refused or discarded restore touched nothing live; the verdict is read from the restore's own report, not from the item's label, because a Stop pressed after the swap labels the item stopped). The dialog (`src/static/app-backup.js`) then says the pause could not be confirmed instead of claiming one, shows a waiting line with the time spent, says so when the exclusive window itself could not open (`collection_window_failed`), and keeps the unconfirmed line after the run. Failing test first: 11 of the 50 tests in `tests/test_restore_collector_exit.py` fail on the previous `merge.py`; `tests/import_tail_phase_node_test.js` pins the dialog; `tests/torture_helper.py` gained the additive `--exclusive` and `--collector-busy` flags so the report is produced by the real `run_restore` against a real corpus.
- Wording: the visible line now adds "Other background work is not paused: what it, or you, saves to your corpus while the import runs can be lost." and its hover (the translated `title`, so the long form is layered and the caveat stays visible) names what is paused (the collection loop and the Collect now button), what is not (the background tasks, Wikipedia updates, AI sweeps, start-up upkeep, anything the person changes), that that other background jobs are not paused either (a few workers wait at their next batch and carry on after the import, so a batch already running can still save), that starting collection again (the Collection switch, the Start button, switching the network back on) is not blocked, that the swap discards what is saved between the copy and the swap except settings, agenda and interface choices, and that the import waits up to 10 minutes before each copy. Five new keys against the base in all twelve locales (non-English AI-drafted, flagged for native review); `collection_note` in the queue status says the same; the `exclusive` docstring in `merge.py` and the pause comment in `volume_job.py` no longer say "nothing else writes". A test pins the hover's "10 minutes" to `COLLECTOR_EXIT_WAIT_S`.

**Not changed, on purpose.** No writer other than the collector is stopped, locked or refused: that is a decision for the user (`wal-lane/proposal-uncovered-writers-2026-10-28.md`, options A to D, recommendation C now plus B reduced to one list). `runner.py` is not touched (the keyword lane's file); the wait lives in the restore, so `exclusive_window` itself still returns after its 10 s join. The Opus read of this PR found two defects there (a Run-now pass on a stopped loop is never signalled to stop; `start()` ignores the hold) and the coordinator ruled them into the keyword lane's runner PR; the hover states the second as a limit meanwhile.

**Stated limits.** The wait runs before every working copy (at a checkpoint interval of 1, each item waits for itself); the published wait state is process-wide, so a restore started through the API directly while a queue run is in flight would be shown as the queue item's. The wait is a courtesy with a bound, not a lock: a pass still running at 600 s is named and the restore goes on. Not measured: rows lost to any writer class during a span (R341's 0 to 1,174 frames, 21 restores, plaintext SQLite 3.45.1, one synthetic writer, is the only figure and is not for these classes).
