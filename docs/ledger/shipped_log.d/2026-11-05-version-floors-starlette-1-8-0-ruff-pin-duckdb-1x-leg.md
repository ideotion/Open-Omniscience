## 2026-11-05 — three version statements get something that can contradict them: the Starlette floor is 1.8.0, ruff is pinned to 0.17.3, and a CI job runs the columnar tests on DuckDB 1.x (R412, the version-coupling bundle; closes OPEN_QUEUE items 16, 28 and 29)

R412 adopted Plan's recommendations on three user-decision items, each a version coupling that has to move in one commit: the registry, `pyproject.toml` and, where one exists, the lock. The lane built them as one local bundle from `cff93665b` (the SPDX licence string, the fourth R412 item, waits on the user and is not in it).

**Starlette 1.8.0 (item 16, R325, gate item 42).** `GET /api/database/backup` returns `_SnapshotResponse`, a `FileResponse` over a snapshot of the whole store. From 1.8.0 on, `FileResponse` races its file against `receive()` and stops at an `http.disconnect` when the server speaks an ASGI spec older than 2.4 (uvicorn's HTTP protocols speak 2.3, read in the installed 0.54.0); 1.5.0 to 1.7.0 never watch, so a closed tab left the response reading the snapshot to its end, holding the one backup slot and the snapshot's disk space. Read by diffing the two `FileResponse` classes; measured with the app's own class over a 40 MiB file, a send of 10 ms per chunk and a client that leaves after 0.2 s: 1.7.0 ran 7.1 s and sent 40 MiB, 1.8.0 ran 0.3 s and sent 1.1 MiB; on a 2.4 server both read to the end (the race is not armed), which the registry says. The pyproject floor moves 1.5.0 to 1.8.0, the registry entry `starlette-gzip-flush` moves with it (floor, description, couplings, `verified` and `upstream_check.current` to 1.10.0, the newest, because the route set was run on it), and the stale `1.5.0` in the fastapi comment, entry and docstring is corrected after the floor pair fastapi 0.133.0 with starlette 1.8.0 passed all seven `json_route` rows. The lock already pinned 1.8.0. The route set (the API, security and compression files plus the three that drive a response by hand) passed 567 tests with 2 skips on the 1.8.0 wheel first on `PYTHONPATH` and the same 567 on 1.10.0. The grep of `tests/` for immediate disconnects found five files that name `http.disconnect`: one source file, and in `tests/` one file with two stubs that disconnect AT ONCE (`test_keyword_export_bounded.py`, asserting only that the scratch archive is deleted, so it passes either way), one that does so and asserts only cleanup (`test_backup_download_route.py`, on both spec versions), and two whose stub waits for an event or for the response to end. None failed on the floor. They are now pinned, with what each does, by `tests/test_version_floor_legs.py`, so a sixth fails by name.

**What is new that can fail.** `tests/test_version_floor_legs.py` drives the real backup response with a client that leaves after the first chunk and asserts the rest of the file was not sent: it FAILED on the 1.7.0 wheel (4,194,304 of 4,194,304 bytes) and passes on 1.8.0 (65,536) and 1.10.0. It also pins the exposed-sites list, the DuckDB 1.x job and the exact tool pins. Nine mutants of the real files each failed a named test (see the lesson of this date).

**ruff 0.17.3 (item 28, R391).** `ruff>=0.16.6,<0.18` becomes `ruff==0.17.3`, like `mypy==2.4.0`: the same tree reads 414 on 0.16.9 and 412 on 0.17.3, so the ceiling of 412 is now true by construction and a new release is its own Dependabot PR whose run re-measures it. The ceiling stays 412 (read here under 0.17.3 on the base, and with the new test file and these edits). `docs/maintenance/RUFF_STYLE_LANE.md`, `EXTERNAL_DEPENDENCIES.md`, the ratchet script's docstring and the `ci.yml` note say so; 0.17.3 is also the newest release on PyPI today.

**A DuckDB 1.x job (item 29, R392).** `ci.yml` gains `columnar-duckdb1`, a separate blocking job (a matrix leg would have renamed the `columnar` check) that installs `duckdb<2`, checks it got a 1.x release, and runs the same 29 files as `columnar`; the `duckdb>=1.4` floor and the registry floor are unchanged and still equal. Run locally under duckdb 1.5.6 (the 1.x release pip resolves today): all 29 files, 472 passed and 2 skipped (the two skips are the offline secure-crypto test and the CI-only httpfs lane, each says so). The first run had one failure, `test_mean_tone_is_honest_never_a_fabricated_zero`, which is a venv without `vaderSentiment` and fails the same way on 2.0.0 here; CI installs it.

**Not changed, and what is not known.** The 1.x job runs the newest 1.x release, not 1.4.0, the floor; a defect only 1.4 has is unseen and the registry says so. The persisted-encrypted round trip stays in `columnar` (it needs the network). The test name `test_the_scratch_archive_is_deleted_once_it_has_been_sent` (keyword lane) says more than it needs to on 1.8; left alone. `docs/ledger/OPEN_QUEUE.md` items 16, 28 and 29 and the RULINGS_INDEX rows are Plan's files and are not edited here; this fragment names which items it closes.

Release-notes line for this change: the database backup now stops when the browser tab that asked for it is closed, instead of reading the snapshot to its end (the install now asks for Starlette 1.8.0 or later); for contributors, ruff is pinned to 0.17.3 so the style ceiling is exact, and CI runs the columnar tests on DuckDB 1.x as well as the newest release.
