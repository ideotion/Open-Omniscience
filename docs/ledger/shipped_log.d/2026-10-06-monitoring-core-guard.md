A core dump is a copy of the passphrase that the kernel chooses how to keep, a log line is the passphrase in words, and a child process holds a passphrase it was never going to use. `src/monitoring/core_guard.py`
sets `RLIMIT_CORE` to exactly 1, soft and hard, inside the process and before the passphrase is read (the server's `_serve()` and its lifespan, the restore child, the encrypt command, `connect.set_passphrase`, each place `connect` gives a key to the engine (the store's `PRAGMA key`, the encrypt tool's `ATTACH ... KEY`: a key typed into a request reaches the engine before anything holds it), through `secret_scrub.guard_process()`, and the module's own import when
`OO_DB_PASSPHRASE` is set; the OSM reference run asks strictly and is refused where the limit cannot be set), with `PR_SET_DUMPABLE 0` as the fallback where the hard limit is already 0, and with no option and no
launcher line, because MEASURED (kernel 6.18.44, a bare Python child killed by SIGSEGV) a core piped to a handler ignores the limit at 0, 2, 4096, 1 MiB and unlimited (the handler received the whole 6.5 MB) and is
aborted only at exactly 1, a file pattern treats the limit as a size cap (4096 left a 3,929-byte file), `ulimit -c 1` is 1,024 bytes in bash and 512 in dash, and after `ulimit -c 0` an in-process
`setrlimit(RLIMIT_CORE, (1, 1))` is refused, so a launcher line and the in-process call exclude each other. A process held to 1 never runs the piped handler, so the handler's own journal line is gone and `kernel_log`
matches the kernel's line instead (`RLIMIT_CORE is set to 1, aborting core`; older kernels `has RLIMIT_CORE set to 1`); the boot record names the mechanism; `python -m src.monitoring.core_guard` lists what a machine
already holds (names, sizes and dates under a label, never a path, nothing opened), which is how a crashed machine's owner learns whether it kept a dump from before this version. The log: `secret_scrub.SecretFilter`
stands in front of every handler the app builds (`setup_logging`'s audit files and console, the server's two through `uvicorn_log_config()`, the console `migrations/env.py`'s `fileConfig` builds, and every handler
that exists when a process first holds a passphrase or hands one to the engine, the last-resort handler (which writes to `stderr` before the journal installs) included, through `guard_process()`) and hands each one a scrubbed COPY of the record (Python 3.12 added the replacement record; the project's floor, its installers and its
workflows are pinned to 3.12 by a test, and below 3.12 the filter writes the words into the record it was given and a record it cannot check is withheld in itself), because the record is shared by every handler it
reaches and the error journal counts `database is locked` and an interrupted statement off the words as logged; a handler built AFTER the install is caught by a hook on `logging.Handler.__init__`
(`protect_new_handlers`, put in by `protect_handlers`), and the test that boots the way the app really starts (the server configures logging, then the lifespan runs the deferred start) adds a handler late, makes

the filter's check. It fails closed (what the process holds unreadable, or a record that cannot be checked: a fixed line with no exception; a record that cannot even be copied is not written). The journal
