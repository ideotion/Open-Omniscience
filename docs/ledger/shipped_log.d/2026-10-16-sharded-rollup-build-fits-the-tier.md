## 2026-10-16 — the keyword rollup build fits DuckDB's 1,004 MB tier (PR #1422)

`columnar.build_keyword_daily` stages mentions into `shards` tables by `keyword_id % shards`, aggregates them one at a time into `keyword_daily_building` and drops each stage once aggregated; the swap into `keyword_daily` stays one transaction, and a failed shard leaves the previous rollup and no stage or building tables. `plan_build_shards(rows, limit_mb)` derives the count from the limit (the smallest count whose predicted peak is under 70% of it, never past the count where another table costs more than it saves). A shard that raises `OutOfMemoryException` (matched by class name) is halved on `(keyword_id // shards) % parts` up to 16 parts, then `BuildDeclined("duckdb-limit")` carrying shards, shard and split into the kept stop; any other error is never retried. `BUILD_CODE_VERSION` is 2, so stops kept by the single pass are released; `status()["last_build"]` reports shards, splits, the predicted and observed peaks and the build time.

Measured on a seeded corpus of 12,000,000 mentions / 1,500,000 keywords / 10,386,404 rollup rows at a 1,004 MB limit (957.5 MiB), 2 and 4 threads: DuckDB peak 604, 584 and 600 MiB, RSS 923, 911 and 906 MB, build 87.1, 84.6 and 88.5 s in the final-code runs (84.3 to 84.8 s earlier), against 1,986 MiB / 2,467 MB / 83.6 s for the single pass, which stopped at a 2,000 MB limit (peak 1,898 MiB) and built at 2,400 MB. Content digest (10386404, 24000000, 12000000, 17997137587126, 95801022961174191706596220) and meta digest (1500000, 13832410933449212566372076) are identical between the single pass and the sharded build at 2 and 4 threads; against the live SQLite count, mentions are exact and distinct is the disclosed upper bound. At 500 and 420 MB the build declines cleanly as `duckdb-limit`. The user's 856 s benchmark cannot be reproduced here: the ratio (about 1.01 to 1.06) is measured, a build of about 865 to 890 s on the user's machine is inferred. 24 M mentions was measured on a replicated stage file, not a streamed run. Constants measured on DuckDB 1.5.6.

Folded from the independent read of the commit: the halving filter is made non-negative (DuckDB's `//` truncates toward zero and `%` keeps the sign, so a negative keyword id matched no residue and its group vanished when its shard was halved); the id columns take BIGINT when an id is below -2**31 as well as above 2**31 - 1; the stage columns are NOT NULL, because the lenient JSON path turns an overflowing id or a malformed date into NULL where the single pass raised (an id rewritten by the keyword fold after the sizing now fails the build loudly instead of becoming a NULL id); the swap's ROLLBACK no longer replaces the error of a COMMIT the engine already rolled back; every `keyword_daily_stage_%` table is dropped at the start and end of a build (a build killed in a persisted store left stages a smaller later plan never named). Each has a test that fails without it. Stated, not fixed: the model's constants were measured with INTEGER stage columns and do not add the 8 bytes a row a BIGINT stage costs.

R147 (the coordinator session's ruling, same night; its RULINGS_INDEX row rides Plan's J PR): a build reads the budget ONCE (`columnar.budget_snapshot()`: DuckDB limit, threads, the machine total they came from, `read_at`), connects with it, cuts its shards from it, and names it in its stop record and `status()["last_build"]`; nothing in the build asks the budget again. A test whose budget answers one reading and then a different machine fails without it (a stop that names the later limit, a connection or plan from another). `X-OO-Paused: wal` is added to the stub's scan-pause 503 beside `Retry-After: 10`, matching what the WAL follow-on sends.

**Correction, 2026-10-17 (R164):** the DuckDB peaks above (604, 584 and 600 MiB) were read by a second cursor polling `duckdb_memory()` while the build ran; poller-free, the build's own synchronous boundary reads were 403 MiB at 12 M (a lower bound), so the peak is a band, not these numbers. See the OPEN_QUEUE R164 passage.
