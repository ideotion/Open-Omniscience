## 2026-11-05 — the `test` and Core-only CI jobs run in three cost-balanced shards (C10, decision 27, R412; PR #1726)

Each of the two full-suite jobs ran the suite in one process, 70 to 80 minutes (79:36 as the unsharded job of the proving run), and a PR waited for the slower. Each is now a matrix of three legs that run a third of the test files. `scripts/ci_shard.py` deals the files from `configs/ci_shard_costs.json` (longest first to the least-loaded shard; shard 1 starts with the static steps; a file the table does not name goes to `crc32(path) % N + 1`, so a new test file needs no edit). A leg ignores the files of the other shards (`--ignore` lines in an argument file read by `pytest @file`) and lets pytest collect `tests`, because a path named on the command line escapes `collect_ignore` (see the lesson of the same date). The required checks keep their names through two aggregators, `test-all` (named `test`) and `core-only-all` (named `Core-only install (no [analysis] extra)`), `if: always()`, green only if every leg of the matrix succeeded; a cancelled or skipped leg is red. No change to branch protection.

**Proof, once.** Temporary jobs on the proving head ran the whole suite in one process and compared each shard with it, module by module and outcome by outcome (run 42014873848, head `0d8047c91`, the PR merged onto main `c0c66ffd8`): unsharded 1580 modules, 29315 passed, 353 skipped, 1 xfailed; shard 1 533 modules, 11142 passed, 151 skipped; shard 2 523 modules, 8545 passed, 157 skipped; shard 3 524 modules, 9628 passed, 45 skipped, 1 xfailed; 0 differences in any leg, and the legs sum to the unsharded run. The earlier run, on the first table, had found one order dependence (`test_scheduler_runs.py` after `test_scheduler_pause_resume.py`, an unjoined `oo-scrape-now` thread), fixed at the leaker. Core-only has no unsharded twin; its legs use the same planner and table and were green, and the real core install collects 29440 tests in 1555 modules both as one suite and as the three plans (528 + 514 + 513 modules), 0 differences. The temporary jobs are removed from the final head (their text is `git show 0d8047c91:.github/workflows/ci.yml`).

**Measured, against the goal of about 25 minutes (not reached).** Job time, start to end, including the install: `Test (shard N of 3)` 28:12 / 25:34 / 26:59; `Core-only install, shard N of 3` 17:46 / 28:22 / 25:54. The required `test` check was green 29:51 after the run was created. Balanced perfectly, `test`'s legs would take 26:55 each. Known imbalances left alone (moving the dealing means proving the new neighbours again): the static steps of `test` leg 1 cost more than the 80 s the table models, and Core-only deals from a table measured with the analysis tests running. Next steps if the time matters: a Core-only table of its own, a measured overhead, or four shards. `docs/maintenance/CI_SHARDS.md` says how to run one shard by hand, refresh the table and change the count.

**Folded from the independent delta read of `ci_shard.py` (three findings, each reproduced):** `parity` now refuses a comparison in which neither side holds a named module; `costs --table X` rewrites X, not the shipped table; `check` counts each problem once.

**Not covered / unchanged.** `release.yml` still runs the suite in one process at a tag. The macOS/Windows `portability` observation lane is unchanged (the macOS leg was cancelled again at 45 minutes on the proving run, never red by design). Order dependence beyond what ran is not proved; a refreshed table or another shard count wants the comparison again.
