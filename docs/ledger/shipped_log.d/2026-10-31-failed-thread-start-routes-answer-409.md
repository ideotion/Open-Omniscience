## 2026-10-31 — the routes of the managers and jobs that now raise a failed thread start answer 409 and log it, not an unhandled 500 (R393 class, the WAL lane's 409 bundle, behind candidate 3 and PR #1661; PR #1677)

**What was found.** The two changes before this one (`tests/test_failed_thread_start_leaves_no_phantom_job.py`, `tests/test_failed_thread_start_leaves_no_leaked_slot.py`) make a manager whose `Thread.start()` refuses ("can't start new thread": the process or the machine is out of threads) put its job right and go on raising the `RuntimeError`, so the caller learns the start failed. Both stated the same limit: a route that maps only `ValueError`, or only the manager's own refusal class, lets that `RuntimeError` through as an unhandled 500. `BackgroundJob.start` (`src/jobs/background.py`) does the same (it marks the job `error` and re-raises), and also raises `RuntimeError` for a job already in flight, which its docstring says the caller maps to 409. `BackgroundScheduler.start` (`src/scheduler/runner.py`) undoes its state and re-raises too. `src/api/backup_v2.py`, the folder-backup, newsletter-import, re-index and quarantine branches of `/api/jobs/{id}/resume` and `src/api/ingestion.py` already answered 409 (`http_detail(exc)`). Read from the code, with the unchanged routes driven by the new tests (the client does not re-raise, so the 500 is the status the route answers with), the ones that did not:

| Route | Maps | A failed start answered |
|---|---|---|
| `POST /api/llm/pull/queue` | `ValueError` only | 500 |
| `POST /api/llm/default-model/install`, the Ollama path | `ValueError` only | 500 |
| `POST /api/llm/default-model/install`, the vLLM path (a `BackgroundJob`) | nothing | 500, **after** the model had been saved as the operator's preference |
| `_queue_downloads`, the Ollama batch (the model-catalogue buttons) | `ValueError` per model | the `RuntimeError` aborted the batch at that model; the models before it were queued, the ones after it were not tried |
| `_queue_downloads`, the vLLM batch (one `BackgroundJob` for every model) | nothing | 500 |
| `POST /api/jobs/dump:{key}/resume`, `osm:{key}/resume` | nothing | 500 |
| `POST /api/jobs/search-reindex/resume` | `SearchReindexRefused` only | 500 |
| `POST /api/search/index-job`, `POST /api/search/index-job/resume` | `SearchReindexRefused` only | 500 |
| `POST /api/scheduler/start`, the Start button | nothing | 500 |

The vLLM rows were found by the Opus read of this change, not by the sweep: the sweep that produced the other rows started from the four managers the earlier changes had named, and the vLLM download is a different class with the same behaviour. The collection-start row was found by widening the scan that had found them (below): its first form skipped any receiver with `scheduler` in its name, and `POST /api/scheduler/start` was the one route it skipped. `src/api/scheduler.py` is in no ownership table and no open PR touches it (R307).

**The scan, and what it does and does not read.** `wal-lane/scan-start-callers-2026-10-31.py` walks every `.start(` / `.resume(` / `.enqueue(` call in `src/api` and its subpackage `src/api/diagnostics/` (72 call sites in 99 modules, whatever the receiver; no route is defined outside `src/api`) and reports, for each, the nearest enclosing `try` that names `RuntimeError`, `Exception`, `BaseException` or is bare: none, one that raises (maps), one that logs and returns, or one that does neither. It reads handlers by SHAPE: it does not know whether a receiver can raise (a `Timer` or a `Thread` is not a route), and a call inside a helper is judged by its own `try`, not its caller's. Its output on `ee0ecf3` and on this bundle is in `wal-lane/scan-start-callers-2026-10-31-output.txt`. Before: eighteen sites with no handler, twenty-three that map, five that log and twenty-six that neither raise nor log. After: seven with no handler, thirty-three that map, seven that log and twenty-five that neither. The seven left are the keyword fold's three (`insights.py` start and `resume`, `jobs.py` fold resume: that lane's, not touched), two start-up threads that are not routes (`boot_sequence.py`'s `Timer`, `main.py`'s boot thread: Q's) and two helper threads started and joined inside one call of the diagnostics bundle (`diagnostics/bundle.py` at 355 and 1602: not job managers, not read further). The twenty-five "neither raises nor logs" sites are listed under the stated limits. **A first form of this paragraph said "57 call sites in 72 modules" and "`src/api` has no subpackage", which was false:** the script globbed the top level only, and the check that no subpackage existed was a `find ... -not -path 'src/api/*.py'`, whose pattern also matches paths below a subdirectory (`*` matches `/` in `find -path`), so it excluded the subpackage it was looking for. The independent read of this PR found `src/api/diagnostics/` (27 modules) by running the script recursively.

**What changed.** Each answers 409. Where the neighbouring routes carry the exception's words the new clause does too, through `http_detail(exc)`: the pull queue, the default-model install (both paths), the vLLM batch, the dump and OSM resumes and the collection start. The pull queue and the install keep `ValueError` -> 400 and add a separate 409 clause; only the dump and OSM resumes map `(RuntimeError, ValueError)` together, the shape of the folder-backup branch beside them. The default-model install does not save the model as the operator's preference when the download could not start: the Ollama clause sits before `save_settings`, and the vLLM path now starts the job first and saves the preference after (it saved first, then started). The Ollama batch refuses ONE model like a malformed tag, with the reason, and goes on: the failure is in the pull history and the next model gets its own try; a batch in which every model was refused answers `nothing_to_do` with the refusals, like the empty batch and the pre-flight refusal beside it, so the panel does not draw "Downloading:" beside an empty list. The vLLM batch has one job for every model, so a failed start refuses all of them with a 409. The search re-index never puts an exception's text in a response (its routes answer with a CODE), so its three routes answer `{"code": "worker-not-started"}` (`fts_reindex.REFUSED_WORKER_NOT_STARTED`), and the clause comes AFTER the refusal's: `SearchReindexRefused` is a `RuntimeError`, so with the order swapped every refusal would read as a failed start. The collection start answers 409 and does not go on to resume the Wikipedia lane.

**Every new clause logs.** Before this change the unhandled 500 logged the error with its traceback, and the diagnostics panel tells the operator after a failed re-index "the log has the details". With the status answered nothing else logged it: the managers' own `except` blocks record the failure in the job row, not in the log. Each clause now logs the refused start at WARNING through `log_failure` (scrubbed, the exception's own line first), with a message that is the code's own words; the Ollama batch logs a refused start and not a malformed tag, which it never logged. The dump and OSM resume clauses also map a `ValueError` (an entry whose stored wiki, kind or code no longer validates), so their log line says the download "could not be resumed", which is true of both, and the exception's own line says which. The vLLM ENGINE install route (`POST /api/llm/vllm/install`) keeps its contract, 200 with the job's status and `started: false` (the front end reads it), and now logs when the status it returns is `error`, which is a failed start, and not when it is a run already in flight (one narrow case is stated below).

**Pinned by** `tests/test_failed_thread_start_routes_answer_409.py`: 27 tests. The failure is injected in the module under test (its `threading` replaced by one whose `Thread` refuses, or a stub job that raises), never on the process-wide class; the collection start is driven with the REAL `BackgroundScheduler`. Against the unchanged routes (the new code constant present) 16 fail: the pull route, the Ollama install with the preference not saved, the Ollama batch, the all-refused batch, the dump and the OSM resume, the re-index start, the re-index resume on both its routes, the vLLM install (both errors, and the happy path: the preference is saved after the start, not before), the vLLM batch, the collection start, a `ValueError` from the dump and from the OSM resume (500 before, 409 now), and the log. Eleven pass on both and are kept for what they pin: an invalid name still answers 400 on the queue route and on the install, an unknown dump or region key still 404, a refusal still answers its own code on every re-index route, the four re-index codes are distinct, a vLLM batch that starts queues every model, a vLLM engine install that lost a race is a status and is not logged as a failed start, an error that is not a `RuntimeError` is still the unhandled 500 (the vLLM install and the collection start), a collection start that works is unchanged, and an interrupt (`KeyboardInterrupt`) is not mapped by any of the eleven routes it is driven through. 65 mutants of the new code were run against the file and `tests/test_search_reindex_ui.py`, each with a baseline run first, and 65 are killed (per route: no clause, the wrong status, the exception's text in the body, the words not carried; the Ollama install saving the preference anyway and the vLLM install saving it before the start or never; the batches aborting, counting the model as queued, answering the old shape when all were refused, or answering `nothing_to_do` when some were queued or without the refusals; the dump and OSM 404 turned into 200 and their `ValueError` unmapped; a malformed tag answering 409; each clause widened to `BaseException`, and the collection start widened to `Exception`; the clause order swapped at each of the three re-index sites; the new code equal to an existing one; the collection start resuming the Wikipedia lane after a failed start; each of the twelve log lines removed, the engine install logging a run already in flight, and the level of four of them lowered to INFO). The harness writes no bytecode, restores each file byte for byte with its mtime and refuses a verdict unless the unmutated tree passes first; one run of it was killed mid-mutant by a worker restart and left a mutated file in the tree, which the next baseline run caught (a test failed on code that had not been touched), so the four-file snapshot is now compared after every run. Two forms of the file let mutants through and were fixed by the tests above: the distinct-codes test exists because a first form compared a route's answer to the constant, and the interrupt test first covered eight routes and let the vLLM install's widened clause survive until the two installs were added to it.

One line in `BackgroundJob.start` itself, where the failed start is caught, would put all twenty-five of them in the log without a per-route clause (and make the engine-install route's own log redundant); that is a change to a file this lane has not been given and is proposed in `wal-lane/proposal-failed-start-silent-callers-2026-10-31.md`.
- `wiki.py` (`dumps_start` at 591 and the dump index build at 748) and `geo.py` (the OSM region start at 87 and its resume at 131), RC2's #1671, map a failed start to 409 and write no log line: the lost-500-log defect this PR fixes on its own routes. Not touched (their lane's files); reported to the coordinator.
- The vLLM engine-install route logs when the status it returns is `error`. A run that has just failed and is still writing its own failure reads `error` too, so a second start in that window is logged as a failed start with an "already running" exception; the response is unchanged. Moving the line into `BackgroundJob.start` (the follow-on) removes it. The same window gives the default-model install and the vLLM batch a 409 reading "a ... job is already running" when a run began between their pre-check, which answers 200 (`downloading` or `busy`), and their start: better than the 500 it replaces, and pinned as intended.
- The vLLM batch's 409 does not echo the entries refused before it (the one job refuses every model, and the caller asks again); the Ollama batch does keep them. Stated in `_queue_downloads`'s docstring.
- The collection start clears the kill switch (and notes the operator crossing online) BEFORE it starts the loop, as it always did; a refused start leaves the switch cleared with no loop running. Nothing fetches without the loop, and the 409 tells the operator, who presses Start again; re-engaging the switch on a refused start is a behaviour change this does not make.
- The dump, OSM, pull-queue, install, vLLM and collection-start routes carry the exception's words (`can't start new thread`), the shape of the routes beside them. The re-index routes carry a code, the shape of theirs. A code the front end does not translate is shown as the status it came with: `src/static/app-diagnostics.js` swallows a 409 from `POST /api/search/index-job` ("one is already running") and polls the status, which reads `error`, so the operator sees the failure there; no front-end string was added.
- An interrupt (`KeyboardInterrupt`) is not mapped: it propagates, as it does everywhere in this class (R393). Pinned.
- Not observed in the field: driven by the tests, with the failure injected.
