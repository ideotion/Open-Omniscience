## 2026-10-13 — init_db is timed step by step (PR #NNNN)

- **2026-10-13 · wal-disk-pool/init-db-steps (WAL / disk thread; STORE-02, audit 16 finding 9).**
The unlock record kept ONE number for `init_db` (4.2 s and 4.1 s on two field machines after an unclean end, 0.7 s on a third) and nothing in any zip could say which of its 37 steps was the time. New `src/database/init_steps.py` (standard library only): `init_db` carries `@recorded` and names each thing it does with `_init_step("name")` on the line before it (37 calls and 7 imports; an import is a step of its own, `import:<module>`), so a step runs from its name to the next one. One record per call: `steps` (name, ms; `raised` = the exception CLASS when a step raised), `total_ms`, `process_call` (how many calls the process had made, this one included), `earlier_complete_calls` (0 = no earlier call got through: this is the cold call that opened the store; the launcher's `init_db` against a still-locked encrypted store raises at `create_all` and is call 1, so the unlock's is call 2 with 0), `complete`, `machine_uptime_s` (psutil boot time, read before the clock starts; absent with `machine_uptime_unavailable: <class>` when unreadable; not a page-cache reading) and `at`, timed with `perf_counter`. The call lines stay literal, so the source-reading tests and the scale-bench drift guard are untouched; an AST test fails for ANY top-level import or call in `init_db` (a logger line and a dict read apart) that is not preceded by its own name, and for a name used twice. Nothing `init_db` does was changed: same statements, order and connections, no lock, no decision. Step names are code constants and a raising step is kept by class alone, pinned by a test that plants a marker in a raising step's message and finds it in no record and no file under the data dir. Readers: `api/unlock.py` puts the unlock thread's record in `last_unlock.init_db_steps` (so it rides `session-forensics.json` and the P0.4 measurements), `p0_validation._unlock_verdict` names the slowest step when `init_db` is the slowest phase (and prints the method beside it), and `main._note_boot_init_db()` writes the process's first call to COMPLETE to the sentinel as `last_init_db` (the latest record when none has completed, also when the lifespan's `init_db` raised), carried forward like `last_unlock`, because a default (plaintext) start has no unlock record. Size: a full record is about 2.4 KB and is carried three times in `session-forensics.json`; a real quick Diagnostics zip built here was 242 KB of the 4,000,000-byte budget (55 members) and a test pins a record at 4,000 bytes.
Measured (synthetic store, 1,200 articles, plain and SQLCipher, warm page cache, no unclean end; this machine cannot reproduce the field's cold cache after a crash; the probe imported the modules before it started the clock and was not the shipped recorder, which counts them as steps: `import:models` was 182 ms in one cold run): a cold process on an already stamped store (4 runs) took 503 to 1,241 ms, with no `ensure_*` step above 8.5 ms; the first run on a never-stamped copy (4 runs) took 579 to 1,602 ms; the same call again in the same process took 44 to 114 ms (all eight); the steps account for the call's total to within 0.4 ms. The audit's reading ("about 30 self-heal probes") is therefore not what the time is here, and it is not refuted for the field either. The cold time sat in alembic's first use (`align_stamp_to_head` 149 to 771 ms on a stamped store; `stamp_if_unstamped` 308 to 927 ms on a first run, the stamp itself), `create_all` (33 to 282 ms on a stamped store, up to 550 ms on a first run; the process's first connection, with the key derivation on the encrypted store) and `heal_bulk_build` (97 to 255 ms, which carries SQLAlchemy's one-time mapper configuration of about 95 to 250 ms, taken as its first call minus its second, because it is the first ORM use); the largest `ensure_*` steps were one-time backfills on a first run (196.5 ms once, and 50 and 65 ms for `ensure_hot_indexes` on the encrypted store). Not done, on purpose: no step is skipped, cached or moved off the synchronous path until a field record names it; the first candidate is a constant fast path for alembic's head resolution (`_head_revision()` parses all 76 revision files at every boot, 180 to 230 ms cold here), pinned by a test against the scripts. The probe harness and raw outputs: `/mnt/project-files/wal-disk-pool/init-db-2026-10-13/`.
The same PR carries five small fixes found by the read of the write-gate-holds PR (#1367): `longest_batch_s` is None when the session is not under the write gate (the hold is taken only when `hold_write_window` returned True); a test of the real `hold_write_window` on a gated session; `OO_REINDEX_HOLD_TARGET_S="-0"` publishes `0.0`, not `-0.0`; a comment at `_flush` saying the hold note is skipped when the rollback raises and when the commit raises a non-Exception, which is acceptable because the call aborts and the gate is given back at the transaction's end; and the clock wording of lesson 5 of the write-gate-holds lessons.
