## 2026-10-28 — a custody entry owed for a reused article id is written, not settled by the entry of the article that held the id before (R365)

**What was found.** The custody log keys an article's entry by `article:<articles.id>` and is append-only, in its own file (`custody_log.db`) that a restore's swap never touches. `articles.id` is a plain `INTEGER PRIMARY KEY` with no AUTOINCREMENT: SQLite hands the highest ids out again after those rows are deleted, and a restore's swap discards every article committed to the live file after its working copy was taken, so the next articles take the ids those had. The log then holds `INGEST article:6` with the hash of an article that no longer exists, and the corpus holds a different article at id 6. `pending.drain` (the queue that re-tries a custody write that failed at ingest, `note_failed`) settled an owed entry as "already present" when ANY INGEST entry existed for the id, so a new article at a reused id whose own custody write had failed was never given its entry, and nothing said so. The same shape arises without a restore: deleting the highest-id articles and ingesting more.

**What changed.** `drain` (`src/custody/pending.py`) settles an owed entry as already present only when an INGEST entry at that id carries the article's own content hash: the hash on the queued record, else the stored row's. An entry at the id for other content leaves the owed entry to be written, marked `earlier_ingest_other_hash` so a reader can tell it from an ordinary late write. When the hash cannot be learned yet (no hash on the record and the rows could not be read) an entry already at the id cannot be judged, so the owed one stays queued for the next drain instead of being dropped. A gone article is counted `article_gone` whichever entries sit at its id (it was counted `already_present` when any INGEST was there). Failing test first: 7 of the 10 tests in `tests/test_custody_drain_reused_id.py` fail on the previous `pending.py`; they drive the real `drain` against a real `CustodyLog`. Of 12 mutants of the new branch logic, 11 are killed by that file; the survivor (a case-insensitive hash compare) is equivalent in practice, because every writer stores the same lowercase-hex string.

**Not changed, on purpose.** `gap_scan` still builds its "logged" set from ids and so still reports no gap for a reused id whose entry is the earlier article's: comparing hashes there would report false gaps, because `Article.hash` is rewritten in place by the law, hazards, series and wiki lanes after ingest. The restore still writes no DELETE entry for the articles its swap discards (it does not compute that set today): that is a design question, not part of this defect. No production caller puts a hash on a queued record (`src/ingest/pipeline.py` calls `note_failed(article_id, error=...)`), so the hash compared is the stored row's current one; the record-first ordering is exercised by the tests only. If a drain writes an entry but cannot remove it from the queue and the hash is rewritten in place before the next drain, a second entry is written (marked). The (id, hash) pair narrows the question without closing it: the same text collected again at a reused id matches the discarded article's entry. None of this is observed in the field: the mechanism is read from the code and driven by the tests, not measured on a real corpus.
