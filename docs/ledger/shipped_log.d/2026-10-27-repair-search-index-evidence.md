## 2026-10-27 — what a repair that is cut short leaves the full-text search index as: five test cases over real stores and a real SIGKILL, so the state is named and never assumed (0.5.1 item 29, test-only, PR #1529)

**The question (RELEASE_0.5_GATE.md row 29; plan row 29: "a test interrupts a repair and asserts the index state is named, never assumed").** A repair copies the damaged library into a new file and rebuilds the article search index in that copy (`salvage._rebuild_search_index` → `fts.rebuild_index`, 500 documents a batch, one transaction) before the copy is checked, given a sidecar and swapped in. If the repair is cut short at the worst place, inside that rebuild, what state is the index in, and does anything assume it? `src/` and `scripts/` are unchanged: the answer is in the behaviour, and the tests pin it. New file `tests/test_repair_search_index.py` (4 test functions, 5 cases, about 10 to 15 s; the fixture is the real app schema with 1,300 articles and two damaged leaf pages).

**The tests and how each interruption is real.** The index's size is read from its own shadow table, `article_fts_docsize`, never from `fts.fts_status`, which cannot see it (measured, below).

1. `test_a_stop_inside_the_rebuild_...` (two parametrisations). A stop is asked on the second of three batches by the repair's own `repair.stop()`. (a) With the copy's own progress handler: the rebuild finishes and the stop is honoured when the copy comes back (`check_copy` raises). (b) With a finer handler of the SAME shape set on the same connection (it returns 1 once the stop is asked, at every 100th step instead of every 100,000): SQLite interrupts the statement inside the rebuild, the third batch never runs, and `_raise_for_target` ends it `SalvageStopped`. Both end the same way: outcome `stopped`; the live file byte for byte what it was; `its index still holding all 1,300 documents (docsize) and the app's own probe, `fts.fts_status`, reading the same before and after; no scratch left (the half-built index went with the copy); the engine never touched; the registry record `state: stopped` carrying no `search_index`, no `kept_rows`, no `kept_file`: a stopped repair states no figure for an index it threw away.
1b. `test_the_copys_connection_hears_the_stop_it_was_given`. The copy's own connection carries a progress handler on the stop it was handed: a recursive query of 300,000 steps in one statement runs to its end while the stop is clear, and one of 20,000,000 is interrupted by SQLite ("interrupted") once it is set. The stop tests also assert that the copy was handed the repair's own stop (`copy.cancel is repair._CANCEL`) and the finer handler reads the copy's stop, not the repair's.
2. `test_a_process_killed_inside_the_rebuild_...` (POSIX). A child process runs the repair end to end and kills itself with SIGKILL on the second batch of the rebuild (no handler, no `finally`, no atexit; the shape `test_db_reliability_torture.py` uses). What the kill left: the live file untouched; exactly one `.partial` copy; no sidecar, no final-named copy, no kept file. The copy has every article and an index of 0 documents. The next start (a fresh registry, the check run again in that process, as R100 requires) plans a plain `repair` (a killed start is never mistaken for a copy to resume), counts the unfinished start (`unfinished_starts` 1), removes the old scratch, makes a fresh copy and swaps it in: the damaged file is kept byte for byte, and the repaired file's index holds exactly as many documents as the file has articles and as the report's `search_index.documents` counted.
3. `test_a_cut_before_the_swap_carries_the_index_figure_...`. The replace is cut after the copy is whole: the sidecar's `search_index.documents` equals the finished copy's article count AND the documents its index holds (a figure is asserted equal to what the file holds, not only present); the resume's report and the registry record carry the same figure; the file swapped in has an index of exactly that many documents.

**Measured facts the tests rest on (run on the final test file, python 3.13.14, SQLite 3.45.1).**

- The killed copy reads CLEAN: `PRAGMA quick_check` ok, and `salvage.check_copy` returns `(True, [])` for it, with 1,296 of its articles copied and 0 documents in `article_fts_docsize`. Nothing in the copy's check compares the index with the articles. The guards are the ORDER (the rebuild, then the check, then the sidecar, then the final name) and the name (`.partial` with no sidecar is scratch, removed by `_remove_scratch` at the next repair).
- The boot path heals only a FULLY empty index: `ensure_fts` (rebuild "auto") rebuilds when `docsize == 0` while articles exist and by its own docstring does not look for a PARTIAL index (a count of articles costs a corpus scan, 74 s cold on 2.7 GB). So a copy swapped in with a partial index would stay partial. That is why the kill and cut tests assert the index's own document count against the articles, and why the early-stop rebuild mutant below is red.
- `fts.fts_status` CANNOT SEE THE INDEX'S SIZE OR AN EMPTY INDEX. The article index is an external-content FTS5 table (`content='articles'`), so the probe (`SELECT rowid ... LIMIT 1`) and the count are answered from the `articles` table. Measured after `INSERT INTO article_fts(article_fts) VALUES ('delete-all')` on a 300-article store: `article_fts_docsize` 0, `fts_status` present, healthy True, `rows` 300, `count_status` "ok". On the damaged live file of the fixture it reads present and healthy too (and the count can error, `rows` None, when it walks the damaged pages). Its own docstring says it reports "a damaged/incomplete index"; for this table it cannot. The tests therefore read `article_fts_docsize`, and `fts_status` is compared before and after a stop only as the app's own probe.
- The copy's stop poll is the SQLite progress handler set to fire every 100,000 virtual-machine steps of one prepared statement, and the step count of a prepared statement accumulates across its runs. Measured with a stop asked at the entry of the rebuild: a 4,000-article store ran the whole rebuild (8 of 8 batches, 4,000 documents, 0.5 s) and the stop was honoured at the copy's check; stores of 8,000, 12,000 and 16,000 articles were interrupted INSIDE the rebuild after 15 batches (7,500 documents) every time (16,000: 15 of 32 batches, 1.8 s). So a stop is noticed within about 7,500 documents of being asked, not after the whole rebuild; the figure is a measurement on this SQLite, not a pinned constant.
- Field storage-events.json (the two copies in the project folder under diagnostics-2026-10-16/scrubbed, since 2026-10-16T07:47:58Z): six kinds only (`gate_hold`, `guard`, `checkpoint`, `checkpoint_notable`, `open`, `pool_timeout`), no repair or index kind; the open event's `init_db` takes 1,127.5 ms (`align_stamp_to_head` 692.4, `create_all` 260.3, `heal_bulk_build` 122.3), and no index step is among its top three. The state of the index after an interrupted repair is therefore in the repair report and its registry record only, never in the event journal, and the field data neither shows nor contradicts a case: the evidence for this row is the tests.

**Not claimed / limits.** (1) The "inside the rebuild" parametrisation sets a finer handler than the production one (every 100 steps, same return rule) because the production one cannot fire in a store small enough for a test; the production handler's firing is the measurement above, not a test. (2) The kill test kills at a named point (the second batch), not at a random time; a kill during the copy's rows, indexes, final checkpoint or swap is the other tests of `test_repair.py` and `test_db_reliability_torture.py`. (3) A killed copy's on-disk index is empty here because its inserts are one uncommitted transaction under a cache that holds them; a copy of a corpus whose dirty pages outgrow the cache would spill part of the index to the file, and (`journal_mode = MEMORY`) a kill then leaves a partial or damaged scratch file. That copy is still scratch, never swapped in, and removed at the next repair; the test asserts only that the index is not the finished one. (4) Encrypted stores are not walked here (the index code is the same; the encrypted repair is covered by `test_repair.py`'s own encrypted test).

**Proposals, not made (R189: design changes are proposals).** (c) `fts.fts_status` should report the index's own document count (`article_fts_docsize`) beside `rows`, and `healthy` should not read True over an index that holds fewer documents than the articles (at least over an index of 0 while articles exist, the case the boot heals): until then its docstring overstates; recommendation: yes, and accepted as a clear defect: it is this lane's next change, in `src/database/fts.py`, pushed once this one has merged. (a) Poll the cancel flag between rebuild batches, so a stop is noticed within 500 documents instead of about 7,500; recommendation: no, the bound is already small against the repair. (b) Before the sidecar is written, compare `search_index.documents` with `COUNT(*) FROM articles` of the finished copy; recommendation: no for now, it is a corpus scan in a path that already holds the whole copy, and `rebuild_index` counts its own rows, so it would guard only a future defect in the rebuild, which these tests already catch.
