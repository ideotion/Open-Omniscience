## 2026-10-29 — a start that cannot make its worker thread no longer leaves a running job with no worker, and no longer refuses every later start (R393 class, the WAL lane's candidate 2, PR #1661)

**What was found.** The WAL lane's [G] sweep of the job managers that set their state to `running` and then call `Thread.start()` with nothing around it. `Thread.start()` raises `RuntimeError("can't start new thread")` when the process or the machine is out of threads, and then no worker runs. Probed on main fcba4b4f0 with the first `start()` refusing (`wal-lane/measure-start-failure-g-sites-2026-10-29.md`, probes `probe-job-start-raises-2026-10-28.py` and `probe-start-failure-g-sites-2026-10-29.py`):

| Manager | After the failed start | Next start |
|---|---|---|
| `VolumeBackupManager` (export, import, verify: `start_backup`, `start_restore`, `start_verify`) | `running`, a thread that was never started | refused for the life of the process: `_reap_or_reject` joins it and raises `RuntimeError("cannot join thread before it is started")` |
| `ImportQueueManager.start` | `running`, the new items queued, `_save()` already wrote `running` | refused the same way (the join at the top of `start`); a restart would read the file back as `interrupted` for a run that never began |
| `FolderBackupManager.start` | `running` with `status()["running"]` false | accepted (the guard is `_alive()`); `/api/jobs` lists "Backing up to ..." as running, with a Pause and a Cancel that act on nothing, until the next start |
| `SearchReindexJobManager.start` | `running` in memory and in the saved file, no worker | accepted; `resume()` refused as "nothing paused" in the meantime |

**What changed.** Each takes an `Exception` from `start()` and goes on raising it. The volume manager and the folder backup (each with a `_start_worker` helper; the volume manager's serves its three starts) say `error` with the exception's CLASS (`RuntimeError: could not start the worker thread`) and nothing it said, because a start's arguments carry a passphrase; `/api/jobs` then lists the folder job as `failed` with Resume and Cancel, and `resume()` starts it again from the recorded destination and mode. The import queue puts back the run it had before the start (its nine fields, saved again) and drops the passphrase the way a run's end does, because a half-built queue of items that never began would have to be called something, and `skipped` is counted in `items_committed`. The search re-index saves `error` with the code its worker uses (`failed`), which `start()` and `resume()` both continue from.

**Pinned by** `tests/test_failed_thread_start_leaves_no_phantom_job.py`: 14 tests. The failure is injected in the module under test (its `threading` is swapped for one whose `Thread` refuses to start), never on the process-wide class. Against main's `src/`, 10 fail (the three volume starts, the refused second start, the three import-queue cases, the folder backup including its `/api/jobs` row, the re-index start and the re-index resume of a paused run) and 4 pass: the interrupt pins, one per manager, which assert that a `KeyboardInterrupt` raised from `start()` leaves the job `running` (the shim raises before the real start, so they pin the class of the catch, not the shape with a thread that really started, which `tests/test_thread_start_interrupt.py` covers for the managers it names). 30 mutants of the new code were run against the file and 30 are killed (the review added one: a failed re-index start that also wiped the cursor, the ceiling and the tally of a paused run survived the first 13 tests, and the resume case kills it): for the volume manager `BaseException`, the unstarted thread kept, the exception text in the error, the state not set, the error swallowed, the error text not set; for the queue `BaseException`, the thread kept, the passphrase kept, no save, and each of the nine fields not put back (six of those survived the first version of the tests: four are killed by comparing the whole status and the run id before and after, and the cursor and the window flag each needed a case: a run a restart read back as interrupted, and a run whose window failed); for the folder backup the state, `BaseException`, the text, the error, the error swallowed; for the re-index the state, the save, the thread, `BaseException`, the error. Three source-text pins elsewhere read the starts and were brought up to date in the same change: `tests/test_import_queue.py` (the sub-manager must publish `running` before it spawns its worker: the spawn is now the `_start_worker` call or `self._thread.start()`, whichever comes first), `tests/test_storage_events_folder_runs.py` (every `raise` of `FolderBackupManager.start` follows a journal record: the re-raise lives in the helper, so it needed no edit once the helper took it) and `tests/test_p0_validation.py` (a function that holds the passphrase and raises what it caught again as it was is listed with why: `ImportQueueManager.start`, whose only caller wraps the call in `scrub_and_reraise`). Ruff 0.17.3 advisory count 412 (ceiling 412), mypy clean, ruff F/B clean.

**Stated limits.**
- Only an `Exception` is taken (R393). An interrupt delivered while `start()` waits for the new thread leaves the OS thread created and about to run the worker; calling that job `error`, or putting the old run back, would let a second start run a second worker beside it. So the job stays `running` and the interrupt propagates. An interrupt that lands before the OS thread exists leaves `running` with no worker; for the volume manager and the queue the next start's join then raises, as before. Nothing here makes that case worse.
- The backup routes (`src/api/backup_v2.py`, `src/api/jobs.py`) map a `RuntimeError` out of the volume, folder and queue starts to 409 with the exception's text, so an out-of-threads failure reaches the caller there as a conflict status reading "can't start new thread". The search re-index routes (`src/api/search_omni.py` and the Task Manager's resume in `src/api/jobs.py`) catch only `SearchReindexRefused`, so there it reaches the global handler as a 500. Not changed: the status mapping is the API's.
- A `Thread.start()` also waits on an event AFTER the OS thread exists (`self._started.wait()`); an `Exception` raised there (a `MemoryError` allocating the wait's lock is the one the review injected) is indistinguishable here from a creation failure. With that fault the volume manager said `error` while its worker ran and a second start ran a second worker beside it (peak 2), and the import queue put the earlier run back while its worker ran, which re-drove the restored run's items with an empty passphrase. Narrow (a small allocation has to fail right after the thread is created) and not pinned by a test. The exact discriminator, the thread's `_handle.ident`, is private and R393 declined it; the premise is R393's, so it stays and is recorded here.
- The failed start leaves no storage-events journal record: `RUN_REFUSALS` has no key for it and the refusals net records only an `OSError` or a declared class.
- The volume manager does not put back the earlier result: `start_*` has already cleared the summary, mode and destination. The job says `error`, the earlier completed backups stay in `_done_backups`.
- The folder backup's `_thread` keeps pointing at the thread that never started (harmless: `_alive()` reads false and the next start replaces it).
- Not examined: the other managers that start a thread after setting a state (`src/wiki/dumps.py`, `src/wiki/runner.py`, `src/geo/osm_downloads.py`, `src/llm/pull_queue.py`, `src/safety/data_volume.py`, the newsletter import job and the rest of the `.start()` sites a grep lists). Other lanes' R393 sweep named some as not defects (`storage_guard`, `runner._start_detached`, the `*_serve` and `served_cache` sites); the ones listed here are unread by this change [I].
- Not observed in the field: measured with a probe and driven by the tests.
