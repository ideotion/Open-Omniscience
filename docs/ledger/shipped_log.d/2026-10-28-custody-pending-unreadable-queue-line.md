## 2026-10-28 — a custody retry-queue line that cannot be read is kept, reported and never glued to the next record (R386 class)

**What was found.** The WAL lane's read-only scan of `src/database`, `src/custody`, `src/backup` and `src/api` for "an exception dropped unlogged" (R386) found `read_pending` in `src/custody/pending.py`: a queue line that is not JSON is skipped with no log record. `custody_pending.jsonl` is the file a custody write that failed at ingest waits in (`note_failed`), and what makes such a write fail (a full disk, a power cut) is also what cuts a queue write short. Measured with a probe on main 7b25d059a: records 1 and 2 queued, a third line cut short with no trailing newline; `read_pending` returned `[1, 2]` and logged nothing; `note_failed(4)` returned `True`, yet `read_pending` still returned `[1, 2]` because `_append` had written record 4 onto the cut-short line, so both were unreadable; and after `drain`'s `_rewrite` the cut-short text was gone from the file (the rewrite wrote back only the records it had read; with none left it unlinked the file). A line whose bytes were not text was worse: `read_text(encoding="utf-8")` raised `UnicodeDecodeError`, which is not an `OSError`, so `read_pending` raised out of the drain.

**What changed.** `_append` writes a newline first when the file ends mid-line (`_ends_mid_line`: a seek to the last byte, `OSError` for a missing or empty file reads as "nothing to close off"); both appends go through one `_append_bytes`. `read_pending` reads bytes (`_read_all`), splits on `\n`, and treats a line as a record only when it is a JSON object whose `article_id` is an integer (not a boolean, which Python counts as an integer); anything else that is not blank is unreadable, including a line that is not text and one nested too deep to parse (`RecursionError`). The read takes the file lock, so an append in progress is never read half written. Each unreadable line is reported once per process (`_report_unreadable`) by line number and byte length, never its text (a queue line can hold a url), keyed `(line number, byte length, crc32)` and pruned to the lines the file holds now. `_rewrite` takes the unreadable lines and appends them byte for byte to `data/custody_pending.unreadable` (`_set_aside`, which also closes a cut-short tail of that file) before replacing the queue; if that write fails they go back into the queue file, so no line is erased unseen. A file that cannot be read is no longer an empty queue: `read_pending` logs and returns no records, and `drain`'s final re-read leaves the file exactly as it is and reports `queue_read_error` (before this, that re-read returned no records and the rewrite deleted every record still owed). 32 test cases (27 functions) in `tests/test_custody_pending_unreadable_lines.py` drive the real `note_failed`/`read_pending`/`drain` against real files.

**Evidence.** Against base 7b25d059a's `pending.py` (with the two new names stubbed in), 11 of the first 13 tests failed (the other 2 are controls: a newline-terminated file gets no blank line, an empty file no leading one). After the independent read added 19 cases, 10 of those 19 fail on the first pushed version of `pending.py` (head 13b3ff9c4: a text, boolean or float `article_id`, nesting too deep to parse, a read that does not wait for an append, a cut-short tail in the side file, an unreadable file read as empty at the final re-read and in `read_pending`, a directory at the queue path, a text id stopping the drain); the other 9 pass there and pin behaviour it already had (bytes that are not text, a record without an id, a line cut short during a drain, whitespace-only lines, a drain limit that keeps the rest, an entry queued during a drain, the arguments of every log record). 36 mutants of the new logic were run against that file plus `test_custody_drain_reused_id.py` and `test_custody_log.py`: 36 killed (no newline guard, guard always, guard inverted, missing/empty file read as mid-line, line numbers from zero, a non-object read as a record, a boolean read as a record, any id read as a record, blank lines read as unreadable, whitespace-only lines read as unreadable, no dedup, report every time, no prune, report never called, side file overwritten, no newline in the side file, side-file tail not closed, set-aside claiming success, never keeping, never setting aside, a set-aside with nothing to set aside, a set-aside twice per drain, unlink although lines are kept, kept lines not written, drain dropping the unreadable lines, the final re-read dropped or taken from the first read, a rewrite after a failed re-read, the queue error not named, `read_pending` raising, any `OSError` read as an empty queue, the text in the set-aside log, a text prefix at DEBUG, only JSON errors caught, `RecursionError` not caught, the read without the lock). A mutant that survived one version of the tests is not counted as killed: the whitespace and the final-re-read-from-the-first-read mutants survived the first version of the folded tests and each now has a test. The read-time report function receives the raw `(number, bytes)` list and passes on only a line number, a byte length and a crc32; that is a property of its log call, not of its signature, so a test asserts that every argument of every record the queue writes is a number, a digit list or the side file's name (an independent read showed that a prefix of the text logged at DEBUG passed the first version of the test, which looked for the marker only).

**Limits.** A queue holding only unreadable lines is never rewritten (`drain_owed` returns on no records, `drain` on no todo), so the line stays in the queue file, is reported once per process, and is set aside the next time a record is drained; the read-time warning says "a drain that rewrites the queue keeps it". The side file is plaintext like the queue (R387: production queue lines carry no hash and no url, so it adds no new class of content), is read by no code path, and is not pruned. The set-aside runs before the queue file is replaced, so while the replace keeps failing (a nearly full disk takes the larger temporary file and not the small append) every drain appends one more copy of the same lines to the side file, until the disk is completely full; nothing is lost, and the fallback that keeps a line in the queue file moves it behind the records, so its line number changes and it is reported again. The record test is stricter than the old one: a line whose `article_id` is text, a boolean or a float is now unreadable (before, `"7"` was drained as article 7, a non-numeric text id stopped every drain at its `int()`, and `true` was drained as article 1), and a hand-edited file changes in three more ways, all probed: records separated by a lone `\r` are one unreadable line (they were read before), a record followed by a form feed is unreadable (it was read before), and a UTF-8 byte-order mark or a UTF-16 line is now read (`json.loads` on bytes detects the encoding); CRLF endings and whitespace-only lines still read as before. A file only this module writes (ASCII JSON, `\n` endings) reads identically. `pending_count()` and so the Chain of custody tab still leave out unreadable lines, so an operator sees "0 pending" for a queue that holds only a cut-short line and learns of it from one log line (a count beside "pending" is a separate change that adds a string in 12 locales). The scan covered the four directories only; the same `except ValueError: continue` shape was not searched for elsewhere in `src`. Not observed in the field.
