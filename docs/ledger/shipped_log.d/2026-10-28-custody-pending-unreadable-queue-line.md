## 2026-10-28 — a custody retry-queue line that cannot be read is kept, reported and never glued to the next record (R386 class)

**What was found.** The WAL lane's read-only scan of `src/database`, `src/custody`, `src/backup` and `src/api` for "an exception dropped unlogged" (R386) found `read_pending` in `src/custody/pending.py`: a queue line that is not JSON is skipped with no log record. `custody_pending.jsonl` is the file a custody write that failed at ingest waits in (`note_failed`), and what makes such a write fail (a full disk, a power cut) is also what cuts a queue write short. Measured with a probe on main 7b25d059a: records 1 and 2 queued, a third line cut short with no trailing newline; `read_pending` returned `[1, 2]` and logged nothing; `note_failed(4)` returned `True`, yet `read_pending` still returned `[1, 2]` because `_append` had written record 4 onto the cut-short line, so both were unreadable; and after `drain`'s `_rewrite` the cut-short text was gone from the file (the rewrite wrote back only the records it had read; with none left it unlinked the file). A line whose bytes were not text was worse: `read_text(encoding="utf-8")` raised `UnicodeDecodeError`, which is not an `OSError`, so `read_pending` raised out of the drain.

**What changed.** `_append` writes a newline first when the file ends mid-line (`_ends_mid_line`: a seek to the last byte, `OSError` for a missing or empty file reads as "nothing to close off"). `read_pending` reads bytes (`_read_all`), splits on `\n`, and treats a line that is not a JSON object with an `article_id` as unreadable; each such line is reported once per process (`_report_unreadable`) by line number and byte length, never its text (a queue line can hold a url), keyed `(line number, byte length, crc32)` and pruned to the lines the file holds now. `_rewrite` takes the unreadable lines and appends them byte for byte to `data/custody_pending.unreadable` (`_set_aside`) before replacing the queue; if that write fails they go back into the queue file, so no line is erased unseen. 13 tests in `tests/test_custody_pending_unreadable_lines.py`.

**Evidence.** 11 of the 13 tests fail on the previous `pending.py` (with only the two new names stubbed in); the other 2 are controls (a newline-terminated file gets no blank line, an empty file no leading one). 19 mutants of the new logic were run against that file plus `test_custody_drain_reused_id.py` and `test_custody_log.py`: 19 killed (no newline guard, guard always, guard inverted, missing/empty file read as mid-line, line numbers from zero, a non-object read as a record, blank lines read as unreadable, no dedup, no prune, report never called, side file overwritten, no newline in the side file, set-aside claiming success, never keeping, never setting aside, unlink although lines are kept, kept lines not written, drain dropping the unreadable lines, the text in the set-aside log). A 20th, the explicit empty-file test before the seek, was equivalent (the seek on an empty file already raises `OSError`) and was removed instead of kept. The read-time report is handed only `(number, size, crc32)`, so it cannot carry the text by construction; no mutant of that exists.

**Limits.** A queue holding only unreadable lines is never rewritten (`drain_owed` returns on no records, `drain` on no todo), so the line stays in the queue file, is reported once per process, and is set aside the next time a record is drained. The side file is plaintext like the queue (R387: production queue lines carry no hash and no url, so it adds no new class of content), is read by no code path, and is not pruned. A rewrite that set a line aside and then failed to replace the queue sets it aside again at the next one (a duplicate in the side file). The scan covered the four directories only; the same `except ValueError: continue` shape was not searched for elsewhere in `src`. Not observed in the field.
