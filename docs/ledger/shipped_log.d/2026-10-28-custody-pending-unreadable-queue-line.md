## 2026-10-28 — a custody retry-queue line that cannot be read is kept, reported and never glued to the next record (R386 class)

**What was found.** The WAL lane's read-only scan of `src/database`, `src/custody`, `src/backup` and `src/api` for "an exception dropped unlogged" (R386) found `read_pending` in `src/custody/pending.py`: a queue line that is not JSON is skipped with no log record. `custody_pending.jsonl` is the file a custody write that failed at ingest waits in (`note_failed`), and what makes such a write fail (a full disk, a power cut) is also what cuts a queue write short. Measured with a probe on main 7b25d059a: records 1 and 2 queued, a third line cut short with no trailing newline; `read_pending` returned `[1, 2]` and logged nothing; `note_failed(4)` returned `True`, yet `read_pending` still returned `[1, 2]` because `_append` had written record 4 onto the cut-short line, so both were unreadable; and after `drain`'s `_rewrite` the cut-short text was gone from the file (the rewrite wrote back only the records it had read; with none left it unlinked the file). A line whose bytes were not text was worse: `read_text(encoding="utf-8")` raised `UnicodeDecodeError`, which is not an `OSError`, so `read_pending` raised out of the drain.

**What changed.** `_append` writes a newline first when the file ends mid-line (`_ends_mid_line`: a seek to the last byte, `OSError` for a missing or empty file reads as "nothing to close off"); both appends go through one `_append_bytes`. The queue is read as bytes (`_read_bytes`, under the file lock, so an append in progress is never read half written) and parsed after the lock is released (`_parse`, so a large queue never makes an ingest thread's `note_failed` wait for the parse: the reader measured 211 ms against 47 ms with 60,000 records when the parse held the lock). A line is a record only when it is a JSON object whose `article_id` is a positive integer no larger than SQLite's (not a boolean, which Python counts as an integer; an id past SQLite's made every drain's column read raise `OverflowError`); anything else that is not blank is unreadable, including a line that is not text and one nested too deep to parse (`RecursionError`). Each unreadable line is reported once per process (`_report_unreadable`) by line number and byte length, never its text (a queue line can hold a url), keyed `(line number, byte length, crc32)` and pruned to the lines the file holds now. `_rewrite` takes the unreadable lines and appends them byte for byte to `data/custody_pending.unreadable` (`_set_aside`, which also closes a cut-short tail of that file) before replacing the queue; if that write fails they go back into the queue file, so no line is erased unseen. A file that cannot be read is no longer an empty queue: `read_pending` logs and returns no records; `drain`'s first read logs and returns at once with `queue_read_error`; and `drain`'s final re-read leaves the file exactly as it is and reports `queue_read_error` (before this, that re-read returned no records and the rewrite deleted every record still owed). 43 test cases (34 functions) in `tests/test_custody_pending_unreadable_lines.py` drive the real `note_failed`/`read_pending`/`drain` against real files.

**Evidence.** Against base 7b25d059a's `pending.py` (with the two new names stubbed in), 11 of the first 13 tests failed (the other 2 are controls: a newline-terminated file gets no blank line, an empty file no leading one). The independent read of the first push added 19 cases; 10 of them fail on that push (head 13b3ff9c4: a text, boolean or float `article_id`, nesting too deep to parse, a read that does not wait for an append, a cut-short tail in the side file, an unreadable file read as empty at the final re-read and in `read_pending`, a directory at the queue path, a text id stopping the drain) and 9 pass there and pin behaviour it already had (bytes that are not text, a record without an id, a line cut short during a drain, whitespace-only lines, a drain limit that keeps the rest, an entry queued during a drain, the arguments of every record a read logs, a clean drain that sets nothing aside). The delta read of the second push added 9 cases and the read of the third 2 (43 in all); against it, with the renamed internals stubbed in, 6 fail on behaviour (an id of 0, a negative one and one past SQLite's integer are records; the parse runs under the lock; a drain whose first read fails returns a clean zero; `still_pending` after a failed re-read) and the others pin what it already did (a permission error is not an empty queue, a digit text id is not a record, no 12-byte window of an unreadable line is in any log record of a read or a drain). 50 mutants of the new logic were run against that file plus `test_custody_drain_reused_id.py` and `test_custody_log.py`: 50 killed (no newline guard, guard always, guard inverted, missing/empty file read as mid-line, line numbers from zero, a non-object read as a record, a boolean read as a record, a digit-text id read as a record, any id read as a record, no id bound, the upper bound only, the lower bound only, blank lines read as unreadable, whitespace-only lines read as unreadable, no dedup, report every time, no prune, report never called, the drain's first read unreported, side file overwritten, no newline in the side file, side-file tail not closed, set-aside claiming success, never keeping, never setting aside, a set-aside with nothing to set aside, a set-aside twice per drain, unlink although lines are kept, kept lines not written, drain dropping the unreadable lines, the final re-read dropped or taken from the first read, a rewrite after a failed re-read, `still_pending` 0 or all of what was read after a failed re-read, the queue error not named at either read, the first read an empty queue on error, `read_pending` raising, a permission error read as an empty queue, the text in the set-aside log, a text prefix at DEBUG, in the failed-set-aside message or in a DEBUG set-aside record, only JSON errors caught, `RecursionError` not caught, the read without the lock, the first read of a drain without the lock, the parse under the lock, the largest SQLite id refused). A mutant that survived one version of the tests is not counted as killed: the whitespace, the final-re-read-from-the-first-read, the prefix-in-a-message and the first-read-unreported, drain-first-read-unlocked and largest-id-refused mutants each survived a version and now have a test. The log claim is narrower than the first version of this entry made it: a test asserts that no 12-byte window of an unreadable line appears in any message, argument or traceback that a read, a drain that sets lines aside, a drain whose set-aside fails and a drain whose final re-read fails log, and that the set-aside record carries only numbers and the file name (the first version looked for one marker past the first bytes of the line, which a logged prefix passed; the report function receives the raw lines and only its log call is narrow).

**Limits.** A queue holding only unreadable lines is never rewritten (`drain_owed` returns on no records, `drain` on no todo), so the line stays in the queue file, is reported once per process, and is set aside the next time a record is drained; the read-time warning says "a drain that rewrites the queue keeps it". The side file is plaintext like the queue (R387: production queue lines carry no hash and no url, so it adds no new class of content), is read by no code path, and is not pruned. The set-aside runs before the queue file is replaced, so while the replace keeps failing (a nearly full disk takes the larger temporary file and not the small append) every drain appends one more copy of the same lines to the side file, until the disk is completely full; nothing is lost, and the fallback that keeps a line in the queue file moves it behind the records, so its line number changes and it is reported again. A queue file that cannot be read is logged at WARNING with a traceback on every call (no once-per-change suppression), `drain` says so in its result, but `pending_count()` still reads it as 0: the end-of-pass `drain_owed` asks that count first and returns "nothing owed", and the Chain of custody tab hides its line; showing it needs a `pending: null` with a reason and a string in 12 locales (in the proposal for the unreadable count, `wal-lane/proposal-custody-unreadable-count-2026-10-29.md`). The drain's tail holds the file lock while it re-reads and replaces the queue (479 ms for 60,000 records, measured by the reader), so a `note_failed` or the settings route waits for it. The record test is stricter than the old one: a line whose `article_id` is text, a boolean, a float, 0, negative or past SQLite's integer is now unreadable (before, `"7"` was drained as article 7, a non-numeric text id stopped every drain at its `int()`, `true` was drained as article 1, and an id past SQLite's stopped every entry without a hash from being written), and a hand-edited file changes in three more ways, all probed: records separated by a lone `\r` are one unreadable line (they were read before), a record followed by a form feed is unreadable (it was read before), and a UTF-8 byte-order mark or a UTF-16 line is now read (`json.loads` on bytes detects the encoding); CRLF endings and whitespace-only lines still read as before. A file only this module writes (ASCII JSON, `\n` endings) reads identically (a 2,300-record file reads to the same SHA-256 on base and head, and the two write identical bytes once the timestamps are masked). `pending_count()` and so the tab also leave out unreadable lines, so an operator sees "0 pending" for a queue that holds only a cut-short line and learns of it from one log line (the same proposal). `_LOCK` is not re-entrant and `read_pending`/`pending_count`/`_read_locked` take it: calling any of them while holding it hangs (a mutant that calls `_read_locked` inside the drain's tail hangs the suite, which has no timeout) (the comment at `_LOCK` says so; the suite has no timeout, so a regression would hang CI rather than fail it). The scan covered the four directories only; the same `except ValueError: continue` shape was not searched for elsewhere in `src`. Not observed in the field.
