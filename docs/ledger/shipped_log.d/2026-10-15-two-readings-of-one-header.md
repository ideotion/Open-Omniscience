## 2026-10-15 — the boot page check: pages in the file against the header's, at every open, as a fact (PR #NNNN)

- **2026-10-15 · wal-disk-pool/page-reading (WAL / disk thread; diagnostics-members plan, PR B of A then B).**
The Asus machine's file held 14,981 pages more than its header counted, and nothing in the bundle could say when that began: the only place that read both was `database/verify.py`, after damage had been found. `src/monitoring/page_reading.py` now takes the reading at every open and keeps it on the journal's `open` event as `pages` (`source`, `state`, `pages_in_file`, `pages_in_header`, `difference`, `page_size`, `header_valid`, `trailing_bytes`, `file_bytes`, `wal_bytes`; 235 bytes of each of the ten events). At boot `forensics.record_session_start` (or `take_boot_wal_reading` ahead of it, for `serve`) reads the file's first 100 bytes and its length with no engine, before any connection can unlink the `-wal`; at an unlock `_unlock_locked` reads `PRAGMA page_size` and `page_count` off the verify connection before it is checkpointed and closed. A plaintext header whose change counter equals its version-valid-for number gives a `difference` (file minus header); an invalid one gives none, because SQLite would not use it; an encrypted file read by bytes is `encrypted-or-foreign` with its length alone. One WARNING line, counts only, is written when the file holds MORE pages than the header counts (`boot: ...` / `unlock: ...`).
What it cannot say (all in OPEN_QUEUE.md): a store opened at boot by `OO_DB_PASSPHRASE` is encrypted and has no unlock, so it keeps only the length; the engine source cannot show an invalid header; a negative difference is normal while a `-wal` holds frames not yet folded in; the reading checks no page.
Rode with it: the journal's reset removes the paths it used and never resolves `data_dir()` (the coordinator's lows 4 and 5); `_CLASS_ONLY_HELPERS` reads the bodies of the two helpers the log guard excuses by name (low 3); the write gate's release line and watchdog line scrub the holder's thread name; the tombstone bound's reasoning is written beside `ENDED_KEYS_MAX`; the pool-reader marker test has its positive control; the strict `>` and the restored `writer._JOURNALED_HOLD`.
