## 2026-10-13 — read chunking: the two reads the pin reports named (PR #1360)

- **2026-10-06 · wal-disk-pool/read-chunking (WAL / disk thread, the two reads the 10-06 pin reports named).**
`trending()._counts` now reads its date window as one short statement per day per 10,000-keyword-id range (`windowed_group_counts` in `database/query.py`) and `corpus_keywords` reads its article set 100 articles at a time (`_corpus_keyword_rows`), adding the
sums, instead of one `GROUP BY` open for the whole read. Same answer and the same ascending key order as the single statement (property tests over range widths, windows, the country filter and slice sizes); `rowid <= max at the start` in every statement,
so rows inserted above it while it runs are not counted (a test writes between statements and fails without the bound; it is NOT one snapshot: a re-used rowid is counted and an article re-indexed during the read can be missing, both pinned by tests); `keep` runs only between statements; a real WAL file and the app's own engine show a checkpoint passing between statements and not while the old
cursor is open. Measured, and a first reading was wrong: on a dense synthetic 1.75M-row table the total is about the same and the longest statement falls from 0.09-0.15 s to under 5 ms, but on a sparse id space (1.32M mentions over 3M keyword ids) `trending_windows` takes 7.3 s in 42,618 statements against 2.6 s for the single statements (about 110 us a statement; 8.2 to 9.0 s once the pool slot goes back after each key range, 1,723 check-outs), so the cost is real and follows the key span times the days; several days in one `IN` list was refused (with the country filter the planner then scans the country's rows for every statement). Each key range's connection goes back to the pool before the next, except on a snapshot session, and a `datetime` bound is left to the single statement (it is not a whole-days window); a row moved to another key by a fold during the read can be counted twice. A pin report proves where a thread was, not how long a statement lasted, and a session holding a real write transaction
is out of its reach, as is a `read_only_db` session (one BEGIN on purpose). The seeks go through the session's connection so the briefing's WAL guard keeps nothing per seek (measured 7.4 KB each otherwise). Lesson: `LESSONS.md`, the entry "A LONG GROUP BY IS READ AS MANY SHORT STATEMENTS".
