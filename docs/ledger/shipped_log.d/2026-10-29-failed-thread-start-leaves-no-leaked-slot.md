## 2026-10-29 — a start that cannot make its worker thread no longer leaks a download slot, a running import or a queued model (R393 class, the WAL lane's candidate 3, PR #1666, behind PR #1661)

**What was found.** The read-only sweep that followed candidate 2 (`wal-lane/measure-start-failure-sweep-2026-10-29.md`, probe `probe-start-failure-sweep-2026-10-29.py`, run against main 6a81aa7ff with the first `Thread.start()` refusing, the way `RuntimeError("can't start new thread")` does when the process or the machine is out of threads):

| Manager | After the failed start | Next start |
|---|---|---|
| `DumpDownloadManager.start` / `_pump` (Wikipedia dumps) | the slot was CLAIMED (status `downloading`, saved) before `_launch`; no worker, so the row stays `downloading` and counts against `max_concurrent` (3 by the Optimized profile's default, `OO_DUMP_CONCURRENCY` overrides it) | the other entries queue behind it; a retry of the same key with spare capacity relaunches it, a retry at capacity is itself queued with nothing to launch it; the claim ends when that entry is retried or deleted, or the process restarts |
| `OsmDownloadManager.start` / `_pump` (OSM regions) | the same, with its own capacity (default 2) | the same |
| `_pump` of either | it launches every entry it has claimed, in a row: the first launch that raises also leaves the entries claimed after it `downloading` with no thread, and the exception escapes the thread that ran the pump (an uncaught-exception report; that thread was about to end either way, so the harm is the stranded entries) | the stranded entries never move |
| `NewsletterImportManager.start` | `running` in memory and in the saved file (`_save()` ran before the thread), `status()["running"]` false | accepted (the guard is `_alive()`); a restart reads the saved `running` as an interrupted run |
| `DumpIndexManager.start` | build `running`, no worker | accepted; the new start replaces the state |
| `ModelPullManager.enqueue` | the model was appended to the queue before the pump was started, and stays there | the same model again returns at "already queued" and starts no pump; another model's enqueue starts a pump that drains both, and `cancel()` removes it |

On main every one of these starts already let the `RuntimeError` out of `start()` / `enqueue()` (there was no `try` around `t.start()`), so this change alters no API response: the difference is the state behind the exception.

**What changed.** Each takes an `Exception` from the `start()` call and goes on raising it, so the caller learns the start failed. The two downloaders (`_launch`) say `error` with `RuntimeError: could not start the worker thread` (the exception's CLASS, nothing it said, the shape the neighbouring starts use), drop the stop-event they had registered, and save, so the slot is free, a restart does not read it as an interrupted download, and the retry takes the slot. A launch registers its stop event and its thread TOGETHER, under `self._lock`, and the put-back runs under the same lock, only when the entry's stop event is still the one this launch registered, and only changes the status when it is still `downloading`: a second `start()` of the same key that finds the unstarted thread and a status of `downloading` registers its own stop event and thread, and its worker is then the entry's; one that queued the entry (at capacity) or paused it (airplane mode) has answered its caller, and that status stays. `_threads[key]` is left in place: a thread that never started reads `is_alive()` False, which is all `start()` asks of it. Their `_pump` takes an `Exception` from each launch and logs it, so one entry that cannot start does not strand the entries claimed after it. The newsletter import says `error` and saves it (a state `resume()` accepts, from the cursor the start set). The index build says `error`. The pull queue takes the model out of the queue and records the failure in its history (`status: error`), the place a failed pull is already recorded.

**What the independent reads changed.** The first version of this change (commit 6c5c6c551) dropped `_threads[key]` and `_stops[key]` by key, outside the lock. The first read showed two ways that went wrong, both needing a second `start()` of the same key while a launch was failing (a case main already handles badly: it gets two workers): the failure path could drop the second start's stop event and call the entry `error` beside a live worker that `pause()` could not reach (reproduced deterministically), and a pop of `_threads[key]` between `start()`'s two reads of it (`self._threads.get(k) and self._threads[k].is_alive()`) raises `KeyError`. The fix of that (82a3b889c) compared the stop event under the lock, and the second read (a delta read, reproduced) showed that the lock did not help: `_launch` registered the stop event and the thread WITHOUT the lock, so a second start's registration could land between the put-back's read of `_stops[key]` and its `del`, which then removed the second start's stop event (one live worker, status `error`, `pause()` False, `_downloading_now()` 0). The registration now takes the same lock. The same read found that a second start at capacity had set the entry `queued` (and put it in the queue) and the put-back overwrote that with `error`; the put-back now changes the status only when it is still `downloading`. And it found that the resume test read the stored count from the tally, which `resume()` overwrites after `start()` returns (a worker that finished first lost its count; a half-second of starvation was enough); the test now counts the stored rows. The first read also found wording in this entry, the lesson, the comments and the PR body that overstated the defect ("for the life of the process", "nothing ever pulls it", "ended the thread of the download that had just finished", "used to be a 200") and a lock precedent that was backwards (`start()` and `pause()` write the status under `self._lock`; only the worker's own writes in `_download` do not). All are corrected here.

**Pinned by** `tests/test_failed_thread_start_leaves_no_leaked_slot.py`: 26 tests. The failure is injected in the module under test (its `threading` is swapped for one whose `Thread` refuses to start), never on the process-wide class. Against main's `src/`, 17 fail (the slot given back and the retry running, the pump that goes on past one failed launch and the pump whose every launch fails, a save that fails during the put-back, a second start that queued the entry, and a second start between its claim and its registration, each per downloader; the fresh import; the resume that keeps its place, now pinned by the rows it stores (2 of 3, not 3); the index build; the pull; a pull that leaves another queued model alone) and 9 pass: the 7 interrupt pins (a `KeyboardInterrupt` from `start()` leaves the job claimed or running and the pump does not swallow one) and the 2 takeover tests (main leaves a second start's worker alone too, which the put-back must not make worse). 52 mutants of the new code were run and 50 are killed; the 2 that survive are equivalent (per downloader 17: the put-back keyed on the thread's identity instead of the stop event's, which is the same test now that the two are registered in one step). Per downloader the 16 others are: `BaseException`, `_threads[key]` dropped, the stop event kept, the status not set, the text carrying the exception's message, the text not set, the error swallowed, no save, the pump not catching, the pump catching an interrupt, no identity check, the save's own error raised through, the save's error swallowing the start's, no status check, the put-back without the lock, the registration without the lock; for the import: `BaseException`, the state, the text, the message in the text, no save, the error swallowed, the cursor reset; for the index: the same without the save; for the pull queue: `BaseException`, the model left queued, no history record, the message in the text, the error swallowed, the whole queue cleared. The lock is pinned by `test_a_second_start_between_its_claim_and_its_registration_keeps_its_stop_event`: a second start, held in the construction of its thread by a hook in the shim, is released from a `dict` subclass's `__delitem__` at the moment the put-back drops its stop event; it can register only after the put-back when both take the lock (the test waits one second for it, always, when the code is right), and a put-back or a registration without the lock lets it register first and have its stop event dropped. One source-text pin elsewhere reads these starts: `tests/test_storage_events_import_via.py` requires every `raise` of `NewsletterImportManager.start` to follow a journal record (`run_refused`). The first version put the undo inline and the pin failed on the new bare `raise`; the undo now lives in a `_start_worker` helper (as in the folder backup of the candidate before this one), the pin needed no edit, and the failed start leaves no journal record, as the limits below say.

**Stated limits.**
- Only an `Exception` is taken (R393). An interrupt delivered while `start()` waits for the new thread leaves the OS thread created and about to run the worker; freeing the slot, calling the job `error` or taking the model out of the queue would let a second start run a second worker beside it. So the job stays claimed or `running` and the interrupt propagates, and `_pump` lets it through (the entries after it stay claimed, unlaunched). An interrupt that lands before the OS thread exists leaves the claim with no worker, as before. Nothing here makes that case worse. The interrupt pins raise before the real `start()`, so they pin that limit, not the "OS thread created" case.
- A second `start()` of the same key that has claimed the entry (its status stays `downloading`, its error is cleared) but has not yet registered its stop event when the put-back runs cannot be told from a start that never came: the put-back calls the entry `error`, the second start's worker then registers and runs, and the entry reads `error` beside it until the worker writes `downloading` after its first fetch (on the dormant segmented path, until `done`). `pause()` reaches that worker, but `_downloading_now()` reads low in the meantime, so a concurrent start or pump could launch past `max_concurrent`. It needs two starts of the same key inside the refusal window, which main already mishandles (it gets two workers); not changed.
- A failure BEFORE `start()` in the downloaders' `_launch` (the `Event` or the `Thread` could not be built) leaves the claim as it was; `_pump` logs it, and that log line is then the only trace.
- The API is unchanged by this change. The dump and OSM start routes (`src/api/wiki.py`, `src/api/geo.py`) and the model pull routes (`src/api/llm.py`) map only `ValueError` from these starts, so the `RuntimeError` reaches the caller as an unhandled 500, as it did on main; the dump-index route (`src/api/wiki.py`) and the newsletter import routes (`src/api/ingestion.py`, `src/api/jobs.py`) already answer 409 for it. The 409 mapping for this lane's routes is its own change; `src/api/wiki.py` and `src/api/geo.py` are the RC2 lane's.
- The saved file of the newsletter import says `error`, and a restart does not restore an `error` import (the worker's own failure path has the same property), so a start that failed after a resume loses the place the saved `running` would have given back as `paused`. The in-memory state keeps the cursor, and `resume()` continues from it for as long as the process lives.
- After an out-of-threads failure a queued download that the failed pump did not claim stays `queued` with nothing running; it is picked up the next time a download finishes or a start is accepted. Honest ("queued" is what it is), not changed.
- The newsletter import's, the index build's and the pull queue's `_thread` keep pointing at the thread that never started (harmless: `is_alive()` is false and the next start replaces it); the downloaders' `_threads[key]` does too, on purpose.
- The failed start leaves no storage-events journal record: the thread start of `NewsletterImportManager.start` sits outside the journal's wrapper (`run_path_checked` covers only the folder check) and `RUN_REFUSALS` has no key for it. The coordinator ruled to leave it so for this class; the ruling's index row is Plan's.
- Not observed in the field: measured with a probe and driven by the tests. The remaining `.start()` sites a grep lists are unread by this change, except those the sweep named as not defects (`WikiLaneRunner.start`, the drain thread in `src/wiki/service.py`); `src/safety/data_volume.py` is Q's and was passed to it.
