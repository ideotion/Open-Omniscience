## 2026-10-29 — a start that cannot make its worker thread no longer leaks a download slot, a running import or a queued model (R393 class, the WAL lane's candidate 3, behind PR #1661)

**What was found.** The read-only sweep that followed candidate 2 (`wal-lane/measure-start-failure-sweep-2026-10-29.md`, probe `probe-start-failure-sweep-2026-10-29.py`, run against main 6a81aa7ff with the first `Thread.start()` refusing, the way `RuntimeError("can't start new thread")` does when the process or the machine is out of threads):

| Manager | After the failed start | Next start |
|---|---|---|
| `DumpDownloadManager.start` / `_pump` (Wikipedia dumps) | the slot was CLAIMED (status `downloading`, saved) before `_launch`; no worker, so the row stays `downloading` and counts against `max_concurrent` (default 3) for the life of the process | `start` at capacity queues behind the leaked slot; nothing ever ends it |
| `OsmDownloadManager.start` / `_pump` (OSM regions) | the same, with its own capacity (default 2) | the same |
| `_pump` of either | it launches every entry it has claimed, in a row: the first launch that raises also leaves the entries claimed after it `downloading` with no thread, and ends the thread of the download that had just finished | the stranded entries never move |
| `NewsletterImportManager.start` | `running` in memory and in the saved file (`_save()` ran before the thread), `status()["running"]` false | accepted (the guard is `_alive()`); a restart reads the saved `running` as an interrupted run |
| `DumpIndexManager.start` | build `running`, no worker | accepted |
| `ModelPullManager.enqueue` | the model was appended to the queue before the pump was started, and stays there | the same model again returns at "already queued" and no pump ever runs |

**What changed.** Each takes an `Exception` from the `start()` call and goes on raising it, so the caller learns the start failed. The two downloaders (`_launch`) say `error` with `RuntimeError: could not start the worker thread` (the exception's CLASS, nothing it said, the shape the neighbouring starts use), drop the thread and stop-event they had registered, and save, so the slot is free, a restart does not read it as an interrupted download, and the retry takes the slot; their `_pump` takes an `Exception` from each launch and logs it, so one entry that cannot start neither strands the entries claimed after it nor ends the thread that ran the pump. The newsletter import says `error` and saves it (a state `resume()` accepts, from the cursor the start set). The index build says `error`. The pull queue takes the model out of the queue and records the failure in its history (`status: error`), the place a failed pull is already recorded.

**Pinned by** `tests/test_failed_thread_start_leaves_no_leaked_slot.py`: 17 tests. The failure is injected in the module under test (its `threading` is swapped for one whose `Thread` refuses to start), never on the process-wide class. Against main's `src/`, 10 fail (the slot given back and the retry running, per downloader; the pump that goes on past one failed launch and the pump whose every launch fails, per downloader; the fresh import; the resume that keeps its place; the index build; the pull) and 7 pass: the interrupt pins, which assert that a `KeyboardInterrupt` from `start()` leaves the job claimed or running, and that the pump does not swallow one. 36 mutants of the new code were run against the file and 36 are killed (per downloader: `BaseException`, the thread kept, the stop-event kept, the status not set, the text carrying the exception's message, the text not set, the error swallowed, no save, the pump not catching, the pump catching an interrupt; for the import: `BaseException`, the state, the text, the message in the text, no save, the error swallowed; for the index: the same without the save; for the pull queue: `BaseException`, the model left queued, no history record, the message in the text, the error swallowed). One source-text pin elsewhere reads these starts: `tests/test_storage_events_import_via.py` requires every `raise` of `NewsletterImportManager.start` to follow a journal record (`run_refused`). The first version put the undo inline and the pin failed on the new bare `raise`; the undo now lives in a `_start_worker` helper (as in the folder backup of the candidate before this one), the pin needed no edit, and the failed start leaves no journal record, as the limits below say. An eleventh downloader mutant (the state change made without the lock) survived and was not kept: the lock was not load-bearing there (a status string is read atomically and `_save` takes its own lock), and it would have been the only place in the file that took `self._lock` around a plain status write, so the code does not take it.

**Stated limits.**
- Only an `Exception` is taken (R393). An interrupt delivered while `start()` waits for the new thread leaves the OS thread created and about to run the worker; freeing the slot, calling the job `error` or taking the model out of the queue would let a second start run a second worker beside it. So the job stays claimed or `running` and the interrupt propagates, and `_pump` lets it through (the entries after it stay claimed, unlaunched). An interrupt that lands before the OS thread exists leaves the claim with no worker, as before. Nothing here makes that case worse. The interrupt pins raise before the real `start()`, so they pin that limit, not the "OS thread created" case.
- The API maps only `ValueError` from these starts (`src/api/wiki.py`, `src/api/geo.py`, `src/api/llm.py`), so a `RuntimeError` out of them reaches the caller as an unhandled 500 where it used to be a 200 with a row that never moved. Not changed: the status mapping is the API's, in files this change does not touch (`src/api/backup_v2.py` maps the same error to 409). The batch route in `src/api/llm.py` that enqueues several models aborts at the model whose pump could not start; the ones before it are queued, and the failure is in the history.
- The saved file of the newsletter import says `error`, and a restart does not restore an `error` import (the worker's own failure path has the same property), so a start that failed after a resume loses the place the saved `running` would have given back as `paused`. The in-memory state keeps the cursor, and `resume()` continues from it for as long as the process lives.
- After an out-of-threads failure a queued download that the failed pump did not claim stays `queued` with nothing running; it is picked up the next time a download finishes or a start is accepted. Honest ("queued" is what it is), not changed.
- The newsletter import's, the index build's and the pull queue's `_thread` keep pointing at the thread that never started (harmless: `is_alive()` is false and the next start replaces it).
- The failed start leaves no storage-events journal record: the refusals net records only an `OSError` or a declared class.
- Not observed in the field: measured with a probe and driven by the tests. The remaining `.start()` sites a grep lists are unread by this change, except those the sweep named as not defects (`WikiLaneRunner.start`, the drain thread in `src/wiki/service.py`); `src/safety/data_volume.py` is Q's and was passed to it.
