## 2026-10-27 — a writer parked behind the swap window: forced, bounded, ruled out for the shipped app, pinned by order tests (coordinator item 2 of 20:42Z; ruled R338; follows PR #1580; test and ledger only) (PR #1594)

**The question.** The repair's data-version read runs INSIDE the swap window (`_Probe.moved()`: `BEGIN IMMEDIATE` on a connection with a 30 s busy timeout) while every new connection waits behind the window in `connecting()` with no timeout, and the repair holds the single-writer gate across it. Can a writer hold SQLite's write lock while parked behind either?

**Forced.** A writer that holds the lock on a connection made before the window and then asks the guarded engine for a second one: the probe's `BEGIN IMMEDIATE` waited 30.065 s (30.085 s in an earlier run) and failed `database is locked`; the window was held 30.066 s; the writer's second open waited 29.767 s (29.787 s) in `connecting()`. The repair turns any failure of the probe into `Declined("writer-busy")`: nothing is switched, the copy and its sidecar stay, the writer's second connection then opens on the live file. A second shape needs no second connection: an ungated write followed by any gated call (the repair holds the gate) holds the lock the same way; it is forced in the pin and is invisible to a pool-checkout sweep. Control (the writer touches its first connection again): refused as stale and invalidated, the probe goes through in 0.33 s (0.3 s of it the writer's own delay). Bounded by the probe's own timeout, no data lost.

**Why the shipped app should not.** `repair.run` holds the gate for the whole repair, a gated writer (ORM flush, ORM-issued DML and textual writes, the explicit `write_lock()` sites, the settings saves `kv_set_json` and `kv_delete`) holds the gate for exactly the life of its write transaction (a pooled connection is taken BEFORE the gate; the settings saves take the gate and then a raw connection that never passes `connecting()`), so no gated writer holds the write lock when the window opens. The writers the gate does not see are the DDL steps of `init_db` (`maintenance.ensure_*`, `migrate`, `fts.ensure_fts`, `source_identity`; run at launch and unlock, and again after a swap; `library_generation.py`'s docstring also lists `spell_index` and the `fts` rebuilds, which are gated, so that list is stale); none was found opening a second pooled connection or entering the gate while holding the lock (read from the call sites, not proved). A sweep of the 1,506 test files it ran on with a pool-checkout recorder (136,587 checkouts, 103,477 by a thread already holding another, 668 with the held one in a transaction that had changed rows): all 668 held by ORM sessions, none by Core or raw code; the repair, swap, restore and damage files alone, 669 passed, none. The restore's window waits for no SQLite lock; on Windows the file steps of the restore and of the repair wait up to 300 s for the handle of a thread parked in `connecting()` or on the gate (the shape the rollup build's boundary check avoids by hand), not exercised.

**Delivered.** `tests/test_repair_probe_parked_writer.py` (three order tests: the two forced shapes at a 0.5 s busy timeout, and the control; the first starts the probe only once the writer is inside the wait for the window; four mutants, each killed by the intended test) and the lesson `lessons.d/2026-10-27-a-writer-parked-behind-the-swap-window.md`, which names two proposals for the user and builds neither: `connecting()` refusing at once a thread that already holds a connection (restated R340: not recommended as stated, because a declined swap gives earlier connections their validity back and the refusal would be spurious there; the shape to offer, if the user wants one, is a refusal only on the swap path that exempts a window ending without a swap, which can only start at `disk_changing` and so closes the Windows handle shape but not the probe's wait) and a shorter probe timeout (not recommended).
