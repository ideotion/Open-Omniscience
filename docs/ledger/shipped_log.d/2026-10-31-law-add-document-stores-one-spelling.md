## 2026-10-31 — a law document pasted by URL is stored under the one spelling the catalogue's rows use, so a restore of a backup written from here on finds one row (R399 / R189, the WAL lane's measurement of 2026-10-29; PR #NNNN)

**What was found.** The question was whether a law document typed `fr` duplicates on a restore of a backup that holds `FRA` for the same URL. Measured on the real path, one scenario per process (a store created by `init_db`, `POST /api/law/documents` with the kill switch engaged so the row is stored and not fetched, `write_backup_v2`, `restore_legacy_path`): the reported case does not reproduce (a boot-time migration never rewrites rows, the backup is a byte copy of the store, and the merge converts the staged copy toward the working copy's form), but two neighbouring cases do. **H**, a store that predates the country marker: an operator who types `FRA` gets `fra` stored ("an alpha-2 store is written exactly as it always was"), and restoring a backup that holds `fr` for the URL adds a second row. **J**, every store, so every new install: `uk` (the app's own code for the UK, which no ISO conversion can place) and `GBR` are one jurisdiction to the app and two strings to the merge, and the duplicate scan lists `uk` as unresolved instead of counting the pair. Cause: the catalogue's loader writes the jurisdiction through `law_jurisdiction()` (`FRA`/`fra`/`FR` -> `fr`, `GBR`/`gb`/`uk` -> `uk`, `EUU` -> `eu`) and the document's `country` through `config_country()`, while the paste route lowercased the jurisdiction as typed and stored it (and stored `country` exactly as typed), so one table held two spellings of one jurisdiction. The restore's match is the exact string (`m.jurisdiction = i.jurisdiction AND m.url = i.url`).

**What changed.** `add_law_document` (`src/api/law.py`) puts a typed CODE (two or three ASCII letters) through `law_jurisdiction` and the document's `country` through `config_country`, the same calls the loader makes; the column's bind then writes the store's own form. A WORD (`france`, `georgia`, `congo`) is stored as typed, as it always was: the country-name index guesses between a country and a US state and between the two Congos, the first form of this change converted words too and broke the duplicate check for rows stored as `france` (found by the independent read; see the lesson of 2026-10-31), and the wire layer deliberately never converts a name. The duplicate check beside it is unchanged: it widens a code to its spellings and still finds rows an earlier version stored as typed. The merge needed no change for backups written after this change (see the stated limits for those written before).

**Pinned by** `tests/test_law_add_document_one_spelling.py` (53 tests): the stored string for every spelling of a code and for words, in an alpha-2 and an alpha-3 store; the `country` column; a re-add in another spelling is still a duplicate, including against rows stored before the fix (codes and words) and against an unwatched row (reactivated, not duplicated); another URL under the same jurisdiction is a new document; and the restore end to end through `merge_corpus`, every combination of source and target store form over five spelling pairs, leaving the target's row untouched (`new == 0, duplicate == 1`). 14 mutants of the route were run on the hardened harness, each with a baseline first, and 14 are killed. Verified against the real path before the change (the WAL lane's throwaway worktree, with the call added for every input): H leaves `fr` only and J leaves `uk` only; `FRA`, `uk` and `gbr` are all code-shaped, so the shipped rule gives the same result.

**Stated limits.** **A backup written before this change can add a second row.** The route now stores `uk` for a jurisdiction typed `gb` or `gbr` (the UK is the case that matters: the interface shows `GBR`), and `eu`, `an`, `ae`, `cd` for `euu`, `ant`, `uae`, `drc`. A backup made by the earlier route holds the spelling it stored (`gb`, `GBR`), and the merge converts the incoming value toward the store's form but compares exact text, so restoring it over a store whose document was pasted after this change, with the same alias typed on both sides, adds a second row where it used to find one. Measured through the real `merge_corpus` (`wal-lane/probe-law-cross-version-restore-merge-2026-11-01.py`) and over every pair of two- and three-letter spellings of one jurisdiction (`probe-law-cross-version-restore-2026-11-01.py`): with the earlier route's backup restored into a store written by this route, 6 pairs (alpha-2 store) and 8 pairs (alpha-3 store, so every new install) go from one row to two, and 506 and 8 pairs go from two rows to one. It is transitional (it needs a backup made before the upgrade and the same document pasted in both places), and it is the price of changing the string stored for these aliases. Making the merge compare canonical forms on both sides would remove it, H and J for every writer; that is a restore-path change and is proposed separately (`wal-lane/proposal-restore-compares-canonical-jurisdiction-2026-11-01.md`). Rows already stored in another spelling stay as they are until the country migration or a scan-guided cleanup (J's rows stay invisible to the duplicate scan until then). A jurisdiction typed as a word on one install and as a code on another is still two rows to a restore, as before. The same free-text entry on other country-bearing columns (`sources.country` and the routes that write it) was not measured and is not changed. A click-through of the law tab's add form was not run (the UI is unchanged and never sends `country`).
