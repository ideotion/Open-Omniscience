## 2026-10-16 — an installer or prepare failure after a followed redirect says only a status or a class (R142), and no host list reaches further than its consent-popup lane (R143) (PR #1414)

R142 (the coordinator session, amending R141's «other failures unchanged»). The installer's two fetches, the `api.github.com` release lookup and the download of the script the release names, answered every failure that was not a host-list refusal with the failure's own text. For a followed redirect that text quotes the address being fetched, and the download's address is a signed storage URL with its signature in the query, so an HTTP 404 or 5xx from the storage hop, a dropped connection, a timeout, a redirect loop, a `Location` `requests` could not read or a body that was not JSON carried the signature into the 500 and the log. `src/llm/installer.py` now raises `InstallerFetchFailed` (a subclass of `InstallerVerificationError`, so `/api/llm/install/prepare` answers 502 through `http_detail`) from `_get_within`: a fixed sentence per stage (`LOOKUP`, `DOWNLOAD`, each ending at https://ollama.com/download) plus `why`, which is `HTTP <status>` or the exception's class name and nothing else (`src/safety/fetcher.py:failure_words`; `FETCH_FAILURES = (requests.exceptions.RequestException, ValueError)` lives there because the installer may not import `requests`). It is raised after the `except` block, so it has no cause and no context, and it is logged with the same two words and no `exc_info`. `raise_for_status()` moved inside the `try`; `TransportUnavailable` and `NetworkBlocked` pass through (each is its own fixed text with no address); a refusal stays `InstallerRedirectRefused`, caught first. `_default_get_json` turns a body that is not JSON into the same failure by class name. A malformed `Location` on a hop is a plain `ValueError` from inside `requests`, so it is caught by `FETCH_FAILURES` and is now an ordinary fetch failure, which closes the read's item L2 on #1409.

R143 (the coordinator session, option A of three, after item 3 of the follow-up found three lists wider than the popup that discloses them). `tests/test_session_host_list.py::test_no_host_list_reaches_further_than_the_consent_popup_tells_the_person` maps each of the 11 lists the code hands `GuardedSession` to the `src/static/net-hosts.js` lane that names it (an exact entry is a host; a leading-dot entry is `*.x`) and fails on any host the lane does not name; a list may be narrower than its lane. It failed on exactly three lists, which are now exact: `WIKI_SESSION_HOSTS = (".wikipedia.org", "wikimedia.org", "stream.wikimedia.org")` (the `.wikimedia.org` suffix is gone), `ORES_HOSTS = ("ores.wikimedia.org",)` and the DuckDuckGo `ALLOWED_HOSTS = ("html.duckduckgo.com",)`. Each has an exact-list test that only it can fail; the Wikipedia lane also names `dumps.wikimedia.org`, which the wiki session does not fetch, and adding it to the list is killed by the exact-list test alone. A redirect that stays inside the domain but leaves the exact host now fails closed with the existing named refusal.

Not done, and said so: the lists were narrowed because the code promised the person less than it allowed, not because a live redirect was seen going elsewhere, so whether any real service answers with a redirect off the exact host is an operator look recorded STILL OPEN in `docs/ledger/OPEN_QUEUE.md` (for ORES it is the same look as Q717 (a), the move to Lift Wing); urllib3's own DEBUG logging of a request line is not covered by R142, and a success's `source_url` is the `browser_download_url` the release names, not the signed storage address.

Tests: `tests/test_session_host_list.py` (the sink test per stage and per kind of failure, 404, 503, connection, timeout, truncated body and bad `Location`, each with a planted signature that must appear nowhere in the response, the log or the exception chain; the non-JSON lookup; `failure_words` alone; the pin test; the three exact-list tests).
